# ADR-017: Draft Page Lifecycle

**Status:** Accepted (design frozen; implementation may proceed against this contract, following [ADR-018](./018-document-editing-identity-decoupling.md))

## Context

Today, `PageOperations.create()` is the only way a page comes into existence, and it is eager: call it, and a real file is written through the Persistence Gate and a real `Page` is added to `Vault` before the user has typed a single character. Clicking "New Note" twice, or opening one and abandoning it immediately, permanently litters the vault with `Untitled.md`/`Untitled 2.md`. There is no concept of a page that exists only in memory until it has real content.

`PageStatus` is `'active' | 'archived'` only. `docs/adr/012-phase2-application-layer-consolidation.md` already considered a `'draft'` status once, found nothing in the codebase referencing it, and recorded a **permanent omission unless a future product decision introduces a draft concept**. This ADR is that decision being evaluated — not a gap being closed, a genuinely new capability being considered for the first time.

This document evaluates whether Clutter should adopt a unified draft lifecycle for all page types (not just Daily Notes), without weakening Architecture v1.0 (ADR-001 through ADR-016, all accepted).

## Governing Principle

**Navigation must never create durable knowledge.**

Opening a page, following a reference, selecting a calendar date, choosing "Today," or any other navigation action may create an editing session, but must not write to `Vault`. Durable knowledge is created only by explicit user content that reaches the Persistence Gate. Concretely: any action whose purpose is _getting somewhere_ either finds an existing `Vault` page (read-only) or opens an unpersisted `DocumentSession` for one that doesn't exist yet — it never calls the Gate. The Gate is reached only by an action whose purpose is _recording something the user actually wrote_ — `save()`, and only `save()`.

This principle governs the whole evaluation below, including reversing this ADR's own earlier draft conclusion about Daily Notes (Section 5). It is scoped to this ADR only, deliberately not promoted to `ARCHITECTURE_RULES.md` yet — it should be validated by implementing the draft lifecycle first, and promoted to a permanent, numbered rule afterward only if it still holds up in practice.

## Evaluation

### 1. Is a Draft a Page?

No, and it shouldn't become one. `Page` (spec §3) is built exclusively by `PageBuilder`/`PageRebuilder` from resolved, on-disk content — every `Page` in `Vault` corresponds to a file that was either scanned at startup or written by the Gate's `create` operation. There is no path in the current object model for a `Page` that lacks a real path and real persisted content; `Vault.addPage` is only ever called from the Gate/Sync, both of which act _after_ a disk write succeeds.

A Draft should be a separate, purely in-memory concept that exists **before** a Page exists, and it should stay completely outside `Vault`. This isn't a workaround — it's the same principle Rule 3 already states (`Vault` is the sole authoritative model of _what is known to exist_), applied to something that, by definition, doesn't exist yet.

The direct payoff: **Search, `VaultQuery`, Backlinks/References, Sync, and Persistence require zero new code to ignore drafts.** They already only ever see `Vault` content. This is a structural guarantee, not a filter someone has to remember to add — and forgetting a filter is exactly the kind of regression a "just add `'draft'` to the enum" design would invite forever.

### 2. Should `PageStatus` change?

No. Challenging the obvious solution, concretely:

- Every current and future consumer that iterates `vault.pages()` or filters by status (search indexing, the knowledge graph, backlinks, `VaultQuery`'s collection getters, a future plugin API) would need to remember to exclude `'draft'`, forever, as a defensive habit rather than a guarantee the type system or the data source enforces. One missed filter is a draft leaking into search results or a backlink.
- `Vault.addPage`'s own invariants (no duplicate ids, `pagesByPath`/`pagesById` always consistent) assume a resolved path. A page with `status: 'draft'` either needs a fake/placeholder path (violates the invariant's spirit) or `Vault` needs to special-case path-less entries (a `Vault`-level branch for something that was supposed to be excluded from `Vault` entirely — worse than not solving the problem).
- Keeping `active | archived` is cleaner and costs nothing: it's still a complete, exhaustive description of every state a **persisted** page can be in. Draft is not a page state; it's a pre-page state, and conflating the two is the actual "obvious solution" trap.

**Verdict: `PageStatus` is unchanged.**

### 3. Ownership

Rule 6 ("How to decide whether a new subsystem is justified") requires a genuinely new category of responsibility not covered by any of the twelve subsystems. A draft doesn't clear that bar:

- **`DocumentEditing`** (`DocumentRegistry`/`DocumentSession`) already owns "the live edit buffer... for pages currently open in an editor" (spec §9) — and, at the level of what it _should_ own, it doesn't need to care whether the id it's tracking resolves in `Vault`. The shipped code as it stands today does not yet honor that: `DocumentRegistry.open()` currently requires a full `Page`, not an id, a real coupling this ADR depends on being removed. That removal is decided separately, on its own architectural merit, in [ADR-018](./018-document-editing-identity-decoupling.md) — this ADR's `openDraft()` is not implementable until ADR-018 lands.
- **`PageOperations`** already owns "the entire lifecycle of a page as a single capability surface" (spec §6). A draft is the earliest phase of that lifecycle, not a different lifecycle.

No new subsystem, no new facade, no new file beyond a small internal collaborator (see Decision, below) is justified. A dedicated "Drafts" subsystem was considered and rejected — see Alternatives.

### 4. Lifecycle

The proposed flow (Open → existing? → yes: open / no: create draft → open draft → first meaningful edit → persist through Gate → promote into Vault) collapses, once mapped onto the existing contracts, into something much smaller than it first looks:

```
"Create draft"        = generate an id (IdGenerator, same generator PageCreator
                         already uses), open a DocumentSession for that id with
                         seed content. No Gate call. No Vault call.
"Open draft"           = Workspace.openPage(id) — same call as opening a real page.
"First meaningful edit" = the *first* PageOperations.save(id, content) call for an
                         id that vault.getPage(id) returns undefined for. Not a new
                         trigger — the existing onBlur → save() UI wiring already
                         fires this. shouldPromoteDraft, named but unused per
                         ADR-012, becomes exactly this check: `!vault.getPage(id)`.
"Persist through Gate" = the existing `{ kind: 'create', path, content }` operation
                         — no new PersistenceOperation kind.
"Promote into Vault"   = the existing Vault.addPage call inside the Gate's create
                         handler — no new Vault method.
```

In other words: **the entire lifecycle is "defer `PageOperations.create()`'s Gate call from open-time (or navigation-time) to first-save-time."** It requires zero new Persistence Gate operation kinds, zero new `Vault` mutation methods, and zero `PageStatus` values. The blast radius is `PageOperations` + `DocumentEditing`, exactly as Section 3 concluded.

The one hard constraint this collapse creates: `PageOperations.create()`'s existing eager path and `save()`'s new first-save-branch **must** share one private helper that performs the actual `PagePathResolver` + `Gate.enqueue(create)` call. Two independent call sites doing "resolve collision-free path, enqueue create" would be exactly the duplicated-business-rule pattern Rule 4 forbids, and would reopen a second write path in substance even though both still nominally go through the Gate (Rule 12 governs the _path from intent to bytes_, not just which class is called last).

**Concurrency correction, minimized.** `PageOperations.save()`'s synchronous `vault.getPage(pageId)` check — used only to guess whether to enqueue `create` or `save` — is not itself an ADR-011 violation; the guess doesn't need to be correct, because the Gate's own dispatch is what determines correctness, and today it already does that for every kind except `create`. `PagePersistenceCoordinator.runCreate` dispatches _before_ the existing-page guard every other kind goes through, on the reasoning that a `create` target "does not exist in the Vault yet, by definition" — true when `create()` was always eager, false once persistence can be deferred: two rapid `save()` calls on the same still-unpersisted draft can both guess "doesn't exist yet" before either's enqueued operation has run, and both enqueue `{kind:'create'}` for the same id. The Gate's serialization runs them in strict order, but `runCreate` has no guard, so the second one duplicates the disk write and trips `Vault.addPage`'s no-duplicate-id invariant on the second `addPage` call.

Two larger fixes were considered and rejected as more than the gap requires: moving the entire create-vs-save decision into the Gate via a new, richer payload or a unified `upsert`-shaped kind (unnecessary — the asymmetry is confined to one dispatch branch, not structural to the whole Gate); and having `PageOperations` await a new Gate-exposed existence query before enqueueing (this only relocates the same stale, synchronous check to a different caller, it doesn't move the decision to dequeue time). The minimal, sufficient fix: `runCreate` gains the same dequeue-time existence guard every other kind already has — if `vault.getPage(pageId)` already resolves when the operation actually runs, delegate to the existing `writeParseRebuildReplace` helper (already used by `save`) instead of writing a second file and calling `addPage` again. No new `PersistenceOperation` kind, no new payload field, no change to `PageOperations.save()`'s calling convention — this closes the one asymmetry that made the race possible, nothing more.

### 5. Notes vs. Daily Notes

**Revised conclusion — supersedes this ADR's original draft position.** The original evaluation recommended Daily Notes keep eager creation, reasoning from "Daily Notes have deterministic identity." That conflated two independent axes: _how an id is chosen_ (deterministic-by-date vs. collision-free-by-title) and _when persistence happens_. Nothing about deterministic identity requires eager writing — an id/path can be computed deterministically without being written before the user acts. Under the Governing Principle above, that distinction matters: eager creation of today's note happens on **every app launch**, with zero user action — the most extreme case of navigation-adjacent persistence with no explicit content behind it. It is not "Today" being ambient and reliable; it is boot-time writing an empty file the user may never touch.

Three further points, weighed on product terms, not implementation cost, per your direction:

- **Litter, compounded daily.** A skipped week of journaling under eager creation produces seven empty files, propagating to every synced device, forever — a stronger version of the exact "abandoned Untitled.md" problem this ADR exists to solve, except requiring even less user intent (not even a click).
- **Signal integrity.** A future Calendar view showing "which days have an entry" is only a true signal if `Vault` presence means "the user wrote something." Under eager creation, it means "the app happened to be open" — a permanently corrupted signal for the one feature most likely to consume it.
- **Unresolved references are already a planned first-class concept.** `KnowledgeGraphBuilder`/`KnowledgeGraph` already carry `TODO(v1): Track unresolved links` — a link to something that doesn't exist yet is intended to be ordinary, not exceptional. That removes the strongest remaining argument for eager Daily Notes (`"references need something real to resolve to"`): a reference to today, before today has content, is just another unresolved link, same as any other.

**Revised recommendation: Daily Notes adopt the same deferred mechanism as Notes.** What legitimately stays distinct — and was always going to, regardless of persistence timing — is only _identity resolution_: `DailyNoteService`'s deterministic date-based id/path vs. `PagePathResolver`'s collision-free arbitrary naming. That was never a persistence-timing question. One mechanism, one governing principle, two identity strategies feeding into it — not two lifecycle implementations.

### 6. Interaction with existing architecture

- **Vault:** unchanged. Never sees a draft; `addPage` is still only called from the Gate's `create` handler.
- **`PageOperations`:** gains one new method (`openDraft` — see Decision) and one new internal branch inside `save()`. No change to `archive`/`restore`/`move`/`rename`, which only ever operate on ids that already resolve in `Vault`.
- **`DocumentEditing`:** real contract change, decided in [ADR-018](./018-document-editing-identity-decoupling.md) rather than here — `DocumentRegistry`/`DocumentSession` are decoupled from `Page` so a session can exist for an id without a backing `Vault` page.
- **Persistence Gate:** no operation-kind change. Reuses the existing `create` operation kind, plus one dequeue-time existence guard added to `runCreate` (Section 4's concurrency correction — the smallest change that preserves ADR-011's rule-5 principle). See Section 9 for a separate, unrelated gap this surfaces in `runCreate`'s directory handling.
- **`Workspace`:** this is the one real cost, and it should be named plainly rather than assumed away. `Workspace.activePageId` currently always corresponds to a real `Vault` page for every UI consumer that reads `vault.getPage(workspace.activePageId)` (title bar, breadcrumbs, backlinks panel). Opening a draft means `activePageId` can point to an id `Vault` doesn't know about yet. Every such read site needs a fallback when the `Vault` lookup misses — editable content comes from the `DocumentSession` (id + markdown only, per ADR-018 — it holds no title, type, or folder), while title/type/folder for an unpersisted draft come from `PageOperations`'s own descriptor (Decision item 2), never from `DocumentEditing`. This is UI-layer work, not an architecture violation — `Workspace` itself needs no contract change (it already just tracks an id) — but it's real, non-trivial work and is the actual center of gravity of implementing this ADR, not the persistence side. This now also covers the Today entry point, not just New Note.
- **Navigation / Startup:** `NavigationRouter` itself is unaffected. But `Application.bootstrap()`/`.open()`'s Startup sequence is directly affected — see Section 9.
- **Search / References / Backlinks / Sync:** unaffected by construction (Section 1) — this is a genuine, free correctness improvement over the current eager-create behavior, where a still-empty new page (or today's note) could theoretically already be backlinked or indexed before the user typed anything.
- **Future plugins / automation / APIs:** should **not** default to drafts. A programmatic caller handing over full content immediately has no "meaningful edit" threshold to wait for — it should keep using an eager, immediate-persist entry point. Drafts are scoped to interactive, navigation-triggered entry points. This scope boundary should be stated explicitly wherever this ships, so a future contributor doesn't assume every `create()` caller should migrate to `openDraft()`.

### 7. Failure scenarios

- **Closing the app with an open draft:** nothing durable ever existed, so the draft is gone on next launch — consistent with `Workspace`'s existing, explicit, accepted non-persistence invariant (spec §10). Not a regression; a deliberate, named trade-off. (Making pre-first-save content crash-durable would require writing it somewhere before "first meaningful edit," which defeats the entire premise — flagged here as an explicit non-goal, not an oversight.)
- **Switching pages away from an unsaved draft:** the existing onBlur → `save()` UI trigger already fires a save on blur for real pages; for a draft, that same call becomes the promotion trigger. No new UI wiring needed.
- **Deleting a draft:** `PageOperations.delete()` needs _no_ existence check — it closes the session (`DocumentRegistry.close`) and enqueues `{kind:'delete'}` unconditionally, exactly as it already does for a persisted page. If nothing was ever created, the Gate's existing, already-dequeue-time-correct `if (!current) return abandoned` guard handles it with zero new code. An earlier draft of this ADR proposed a synchronous skip-check instead; rejected once examined, because it could skip past an in-flight, not-yet-executed `create` for the same id and let a "deleted" draft be silently resurrected when that create later ran.
- **Opening the same draft twice:** ill-defined for something with no stable identity until persisted; "the same draft" can only mean "the same already-open session," which the existing open-session-reuse pattern already covers. For Daily Notes specifically, "today" is a deterministic id — opening it twice in the same session must resolve to the same session, not two independent drafts.
- **Duplicate daily note drafts:** bounded the same way duplicate regular-note drafts are — the deterministic id means a second "open Today" resolves to the same already-open session, not a second draft.
- **Duplicate untitled notes:** actually improves. Today, double-clicking "New Note" immediately reserves two real, collision-suffixed files. Under this design, two unsaved drafts reserve nothing; collision-free naming only fires for whichever one(s) actually get saved. Fewer accidental `Untitled 2`/`3` files from double-clicks.
- **First save:** the create-branch described in Section 4. For Daily Notes, this is also where directory scaffolding for a new month must actually land if `ensureDirectoryForToday` is ever removed — see Section 9.
- **Save failure on first save:** the Gate's existing per-queue failure isolation applies unchanged — a failed `create` leaves the draft as a draft (`DocumentSession.markSaveFailed`), retryable, exactly like any other failed save today. No new failure machinery.
- **Persistence conflicts on the resolved path:** bounded by the same synchronous-collision-check-before-enqueue behavior `PageOperations.create()` already has today. Not a new race this ADR introduces. For Daily Notes across two devices, deferred creation is a strict improvement over today: both devices open in-memory drafts for the same deterministic id independently; nothing collides until one of them actually saves, at which point it's an ordinary first-save-wins case — a smaller, later collision surface than today's concurrent `ensurePage` race.

### 8. Long-term consistency

New Note, Today, calendar-date selection, and any future "get me to a page" entry point (search jump, an unresolved-reference click, a future automation `navigate` call) converge on one mechanism: resolve-or-draft, never persist on navigation. There is one page-resolution flow — not two competing ones — because the _existence check_ (`vault.getPageByPath`/`getPage`) is the same operation every caller already performs; only _how the target id/path was computed_ differs (arbitrary + collision-free vs. deterministic-by-date), and that was always going to differ regardless of this decision.

### 9. Does `ensureDirectoryForToday` survive?

Challenged directly, rather than assumed as harmless scaffolding, because the Governing Principle's literal claim — "opening, navigating, or viewing never creates durable knowledge" — has to be checked against it, not exempted from it by habit.

**What it actually does today:** creates the year/month directory before the Vault's one startup scan, unconditionally, on every boot, regardless of whether the user does anything. Under a literal reading, this is exactly the pattern being eliminated everywhere else.

**Why it isn't the same violation as `ensurePage`, once checked precisely:**

- An empty directory carries no authored content, no title, no claimed fact — nothing a user wrote. It is not "knowledge" in the sense the principle is protecting; it's inert structure, indistinguishable from any other empty folder in the tree.
- It is directly precedented, not a novel exception: `VaultInitializer.initialize()` already does exactly this for every reserved folder (`Inbox`, `Archive`, `Templates`, etc.) — and even for reserved _files_ with placeholder contents — unconditionally, pre-scan, on every boot, today, already accepted as correct. `ensureDirectoryForToday` is the same category of action (structural, pre-scan, no user intent), not a new kind of bypass.

**Why it can't simply be deferred to first-save the way the page write can — a real structural gap, not a preference:** checked directly against the code, the Gate's `create` operation (`PagePersistenceCoordinator.runCreate`) calls `writeFile` only — it never calls `createDirectory`, unlike `move`/`archive`/`restore`, which go through `MoveService` and do. More importantly: **`Vault` has no live mutation method to add a new `Folder` mid-session.** Its public API (spec §3) lists `addPage`/`replacePage`/`removePage`/`updatePagePath`/`moveFolder` — no `addFolder`. Folders enter `Vault` exactly once, via the startup scan (`VaultBuilder`), and never again. This is why `FolderOperations.create()` doesn't exist in the real codebase today at all — it's open backlog, blocked on exactly this gap (ADR-012).

Consequence: if the month directory isn't real before the one startup scan, no `Folder` for it can ever enter `Vault` for the rest of that session — not next week, not on first save, regardless of when the write happens. Deferring `ensureDirectoryForToday` to first-save would silently require inventing a new `Vault` capability (`addFolder`) that doesn't exist and that this ADR was never scoped to build. Per `implementation-rules.md` §5 ("implementing the requested feature would require inventing a new architecture... stop, and produce a proposal before implementing"), that's not a decision to make as a side effect of this one.

**Disposition: `ensureDirectoryForToday` is retained as temporary structural scaffolding, not a permanent exception.** The absence of runtime folder registration — `Vault` has no live `addFolder` mutation — is an independent architectural limitation, not something this ADR introduces or is responsible for solving. It already exists today, independently of drafts, and it is what already blocks `FolderOperations.create()` (ADR-012's open backlog item). This ADR deliberately does not introduce runtime folder mutation capability: doing so would mean designing a new `Vault` mutation method and (per Rule 2's ownership model) very likely a new Gate operation shape for folders, which is materially new architecture, not a scoping detail of the draft-page-lifecycle question this ADR is actually about. `ensureDirectoryForToday` stays exactly as it is — directory scaffolding only, never page content, never a Gate call, precedented by `VaultInitializer`'s existing pre-scan folder/file creation — for as long as that limitation exists.

**Named follow-up, explicitly independent of this ADR:** designing runtime folder registration (`Vault.addFolder` or equivalent, plus whatever Gate shape it implies) is separate architectural work that would let month-directory creation move to first-save time too, and would also be what finally unblocks `FolderOperations.create()`. It should be scoped and designed on its own terms — with its own ADR — not folded into this one as a side effect. Until it lands, `ensureDirectoryForToday`'s status here is "temporary because the dependency is temporary," not "accepted as a permanent design choice."

## Decision

Adopt a draft lifecycle, scoped narrowly:

1. **No `Vault`/`PageStatus` change.** Drafts never enter `Vault`. `PageStatus` stays `'active' | 'archived'`.
2. **`PageOperations` gains `openDraft(options: CreatePageOptions): Promise<string>`** — generates an id, opens a `DocumentSession` for it via `DocumentRegistry`, calls `Workspace.openPage(id)`, returns the id. No Gate call, no `Vault` call. `create()` is unchanged and remains the eager, immediate-persist entry point for non-interactive/programmatic callers. `PageOperations` also holds, alongside the session, the minimal descriptor (`folderId`, `PageType`, optional seed title) a draft needs before it has a real `Page` — this is the descriptor ADR-018 refers to and explicitly declines to own; `PageOperations` is where it lives, not `DocumentEditing` and not a new type shared between the two ADRs.
3. **`PageOperations.save()` gains one branch:** if `vault.getPage(pageId)` is undefined, resolve a collision-free path (`PagePathResolver`) and enqueue `{ kind: 'create', ... }` instead of `{ kind: 'save', ... }`. This branch and `create()`'s existing body **must** call one shared private helper for path resolution — no duplicated business-rule logic between them (Rule 4). This remains an optimistic guess, not a correctness guarantee — see item 4.
4. **The Persistence Gate's `runCreate` dispatch gains one dequeue-time existence guard** (Section 4's concurrency correction) — the single Gate-level change this ADR requires, shared by every caller of `create` (eager `create()` and a promoted draft's first save alike), and the smallest change that preserves ADR-011's rule-5 principle that state-dependent decisions are resolved inside the serialized queue, not synchronously beforehand.
5. **`PageOperations.delete()`/`close()` require no existence check.** `delete()` enqueues `{kind:'delete'}` unconditionally, exactly as it already does for a persisted page, relying on the Gate's existing (already dequeue-time-correct) abandon-if-missing guard. `close()` never calls the Gate and needs no change. See Section 7's "Deleting a draft" for why the earlier, rejected design (a synchronous skip-check) was unsafe.
6. **Daily Notes adopt the same mechanism.** `DailyNoteService.ensurePage()` (the Gate-writing method) is retired. `DailyNoteService` keeps owning date→path computation and directory scaffolding (`ensureDirectoryForToday`, see Section 9) — identity resolution, not persistence timing, which was always its real job.
7. **The Startup sequence changes.** `Application.bootstrap()` no longer ensures today's page through the Gate. `Application.open()` — currently `pageOperations.open(vault.getPageByPath(todayNotePath).id)`, which assumes the id already resolves — becomes a resolve-or-draft call: open the existing `Vault` page if present, otherwise `openDraft` at the deterministic today-id. `ensureDirectoryForToday` still runs during `bootstrap()`, unchanged (Section 9). **This explicitly supersedes [ADR-014](./014-phase4-composition-root-and-navigation-cleanup.md) Decision 1**, which stated its Startup-sequence resolution "closes ADR-011's documented bootstrap exception for real, rather than deferring it again" — that closure was correct for the architecture as it stood then; this ADR reopens exactly that one step (the `ensurePage`-through-Gate call), for the reasons in Section 5, and no other part of ADR-014's resolution. ADR-014 Decision 2's specific reason for calling `attachVault()` inside `bootstrap()` (needing the real Gate to ensure today's note before `bootstrap()` returns) no longer strictly applies once that ensure-step is removed. `attachVault()` stays called inside `bootstrap()` anyway, as a deliberate decision rather than an unexamined side effect: `Application.open()`'s resolve-or-draft call still needs `pageOperations` constructed before it runs, and there is no product reason to revert to the three-call sequence ADR-014 replaced.
8. **UI read sites keyed on `workspace.activePageId`** need a fallback when `vault.getPage` misses — content from `DocumentSession`, title/type/folder from `PageOperations`'s descriptor (item 2), never a title from `DocumentEditing` — scoped, named UI work, not an architecture change, but the largest real cost of adoption. This now includes the Today entry point, not just New Note.
9. **UI actions that only apply to persisted pages — archive, restore, delete-via-menu, move, rename — are disabled while `workspace.activePageId` refers to a draft** (`!vault.getPage(activePageId)`), rather than left reachable and silently abandoned by the Gate's existing guard. This matches the standard [ADR-016 Finding A](./016-phase6-cleanup-and-migration-close.md) already set for live-but-not-yet-functional controls: disabled, not silently inert. `PageOperations.delete()`'s own behavior (item 5) is unaffected by this — this item is about which UI controls are reachable, not about the facade's API.
10. **`architecture-specification.md` §5 (Persistence Gate), §6 (`PageOperations`), and the Startup sequence are amended** to add `openDraft`, document `save()`'s existence-branch, record `runCreate`'s new existence guard, and correct the Startup sequence's `ensurePage`-through-Gate step, once this ADR is accepted — per `implementation-rules.md` §4's divergence process, the spec is updated _after_ acceptance, never as an incidental part of an implementation PR.
11. **This ADR depends on [ADR-018](./018-document-editing-identity-decoupling.md)** for `openDraft()` to be implementable at all. ADR-018 is scoped and justified independently — it is not a sub-decision of this ADR, and should be accepted (or rejected) on its own architectural merit.

## Alternatives Considered

- **Add `'draft'` to `PageStatus`, keep drafts in `Vault`.** Rejected in Section 2 — permanent filtering burden on every current and future `Vault` consumer, and a structural mismatch with `Vault`'s path/id invariants.
- **A new `DraftOperations` facade or "Drafts" subsystem.** Rejected — fails Rule 6's bar for a new subsystem (not a genuinely new category of responsibility) and Rule 14 ("add a method to an existing facade before adding a file"). Would also reintroduce exactly the ownership fragmentation (two files for "what can happen to a page") the six-file-to-two-facade migration (ADR-002) existed to eliminate.
- **Push the persist-or-not decision into `DocumentEditing`.** Rejected — `DocumentEditing` owns in-memory state only (spec §9 Ownership); "should this be written yet" is business policy, which Rule 5 requires to live in `PageOperations`, not its infrastructure.
- **Keep Daily Notes on eager creation, Notes on deferred creation.** This ADR's original position — reconsidered and rejected in Section 5 under the Governing Principle: it optimized for "smallest implementation diff" over long-term product consistency, treated a difference in identity resolution as though it implied a difference in persistence timing, and left the app's own boot sequence as the single largest violation of "navigation never persists" left standing.
- **Add a `create(options, { immediate: boolean })` flag instead of two methods.** Rejected — a boolean that silently switches whether a Gate call happens is exactly the kind of implicit branching this codebase's facades avoid elsewhere; two named methods (`create`, `openDraft`) sharing one internal helper is clearer about what a caller is actually asking for, and each method adds real, distinct behavior (satisfies Rule 3's "no unconditional forward" concern in spirit for the calling convention, even though the underlying write logic is shared).
- **Defer `ensureDirectoryForToday` to first-save, for full consistency with the page-write timing.** Rejected for now in Section 9 — requires runtime folder registration (`Vault.addFolder` or equivalent), an independent architectural limitation this ADR deliberately does not take on; recorded as a named, disclosed follow-up with its own future ADR, not improvised as a side effect of this one.
- **Move the entire create-vs-save decision into the Gate via a new, richer `PersistenceOperation` payload or a unified `upsert`-shaped kind.** Rejected in Section 4's concurrency correction — the race is confined to one dispatch branch (`runCreate` lacking the existence guard every other kind already has), not structural to the whole Gate; a new kind or payload shape would be more machinery than the actual gap requires.
- **Have `PageOperations` await a new Gate-exposed existence query before enqueueing, instead of guessing.** Rejected in Section 4 — this only relocates the same synchronous, stale-by-construction check to a different caller; it doesn't move the decision to dequeue time, which is the actual property ADR-011 requires.
- **Keep `PageOperations.delete()`'s proposed synchronous skip-check** (an earlier draft of this ADR's own position). Rejected once examined — it can skip past an in-flight, not-yet-executed `create` for the same id, letting a "deleted" draft be silently resurrected when that create later executes. Removing the check entirely and relying on the Gate's pre-existing abandon-if-missing guard is both safer and less code.

## Consequences

- `PageOperations`, `DocumentEditing` (per ADR-018), and `PagePersistenceCoordinator` (one guard clause, Section 4) carry the new logic for the draft mechanism itself; `DailyNoteService` loses its Gate-writing method; the Composition Root's Startup sequence changes its today's-note step. Every other subsystem (`Vault`, Sync, Ingest, Platform, Navigation) is untouched, verified section-by-section in Section 6.
- The UI layer carries the real implementation cost, now for two entry points (New Note and Today, plus any future calendar-date selection): every read of `vault.getPage(workspace.activePageId)` needs a not-yet-persisted fallback. This should be scoped and estimated as its own piece of work before starting, not discovered mid-implementation.
- `shouldPromoteDraft`, named in spec §6 since before any draft concept existed and recorded as a permanent omission in ADR-012, gets a real implementation for the first time — as `!vault.getPage(id)`, not as new machinery.
- No new `PersistenceOperation` kind, no new `PageStatus` value, no new subsystem, and no runtime folder mutation capability introduced. The only Gate-level change is one dequeue-time existence guard added to `runCreate` (Section 4) — smaller than the payload/kind changes originally considered and rejected there. One narrow, temporary exception remains: `ensureDirectoryForToday`'s pre-scan directory scaffolding (Section 9), kept only because runtime folder registration doesn't exist yet as an independent architectural matter — not accepted here as a permanent design choice, and not this ADR's problem to solve.
- The Governing Principle stays scoped to this ADR, not `ARCHITECTURE_RULES.md`, until implementation validates it in practice.

## Why This Approach Is Preferred

It answers the assessment's own standing question (implementation-rules.md §6): after this change, is there still exactly one file to read to understand a page's whole lifecycle, and exactly one write path underneath it? Yes on both counts — `PageOperations` still owns the whole lifecycle including its newly-earlier start for both Notes and Daily Notes, and the Gate's `create` operation is still the only way a page's first bytes reach disk, called from exactly one shared internal helper regardless of whether the caller was eager `create()` or a promoted draft. It also answers a question the original draft of this ADR didn't ask clearly enough: does the _user's mental model_ stay uniform across every way of arriving at a page? After this revision, yes — nothing you navigate to is ever real until you write in it, with exactly one disclosed exception (empty directory scaffolding, not content), rather than a rule that quietly has a different answer depending on which button you clicked.

## Amendment (Description milestone): promotion trigger generalized to any committed, persistent, user-owned change

**Context.** Section 4 defined "first meaningful edit" as "the first `PageOperations.save(id, content)` call for an id `vault.getPage(id)` returns undefined for" — deliberately not scoped to body content specifically, but the only trigger that existed when this ADR was written was the body editor's blur-commit. The Description milestone's metadata work (`updateMetadata`) and draft-title work (`updateDraftTitle`) made two more triggers real, and product research and impact analysis (draft-promotion-trigger discussion, durability-model work) established that a title commit or a metadata commit (description, favorite, icon, cover, and any future `EditablePageMetadata` field) is exactly the same category of "explicit user content that reaches the Persistence Gate" the Governing Principle already names — not a new kind of trigger requiring new architecture, a wider application of the one this ADR already defined generically.

**Decision.**

1. **The promotion rule generalizes**: any committed, persistent, user-owned change — title, body, or an editable metadata field — made through an interactive draft workflow promotes the draft exactly once. "Committed" is verified by `PageOperations` itself, not assumed from the caller: `updateDraftTitle` compares the incoming title against `descriptor.title`; `updateMetadata`'s draft branch compares each patched key against `resolvePageMetadata({})` — the same frontmatter-defaulting logic `PageBuilder` already needs for scanning, extracted so promotion asks an existing question rather than introducing a new "defaults" concept (see the dependency-direction verification in the implementation discussion: `resolvePageMetadata` lives in `vault/ingest/`, alongside `PageBuilder`, imported downward by `PageOperations` exactly as `VaultPath` already is).
2. **Every trigger converges on the same shared helper.** `persistDraft(id, body, metadataPatch?)` — the one private helper Section 4 already required `create()` and `save()`'s promotion branch to share — gained an optional metadata parameter rather than a second creation path. No new `PersistenceOperation` kind, no new `Vault` mutation method.
3. **Daily Notes are excluded from the title and metadata triggers**, not from promotion generally. A Daily Note's title is derived from its date and never consumed by `persistDraft`'s deterministic-path branch, so committing it (or a metadata field, which has no in-memory home on a draft before promotion) carries no user intent to make today's note real — only an actual body or metadata commit representing genuine content does. Body-triggered promotion is unchanged for Daily Notes, exactly as before this amendment. The exclusion reuses existing state (`DraftDescriptor.deterministicPath`, already set only for `openAtPath`-originated drafts) — no new field.
4. **`PagePersistenceCoordinator.runCreate`'s existing-branch gained a metadata-preservation fix**, required by this generalization and not optional: with only body able to trigger promotion, a losing `'create'` in the existing dequeue-time race guard (Section 4's original concurrency correction) had no metadata to lose. With title and metadata now also triggering promotion, a losing `'create'` can be a metadata-only promotion attempt whose entire payload would otherwise be silently discarded. The fix extracts only the explicitly-present editable-metadata fields from the losing operation's parsed frontmatter and merges them onto the winning page's metadata before the existing-branch's `writeParseRebuildReplace` call — never `created`/`modified`/`status`/etc., which the losing attempt's content is stale for regardless.
5. **Destination-path (title) reconciliation across a genuine promotion race is explicitly out of scope for this amendment.** When concurrent promotion attempts propose different destination paths, the first successful creation determines the initial path. Reconciling subsequent destination-path changes belongs to the future rename capability and is intentionally outside the scope of draft promotion.

**Alternatives considered.** A per-field hardcoded defaults table for the metadata "committed change" check — rejected: it would be a new domain concept maintained solely for promotion's benefit, duplicating logic `PageBuilder` already owns for an unrelated reason, and would need updating every time a new `EditablePageMetadata` field is added (see the dependency-direction and duplication analysis in the implementation discussion). Extending `runCreate`'s fix to also reconcile a losing operation's destination path — rejected as scope creep into the rename capability (Point 5, above); the guarantee this milestone owns is exactly-once creation with no lost metadata and no errors, not path arbitration.

**Consequences.** `architecture-specification.md` §5/§6 get the same small addendum already scheduled by this ADR's Decision item 10 — `save()`'s promotion branch description broadens to name all three triggers, not just body. Future `EditablePageMetadata` fields (attachments, if ever modeled as metadata; any other editable page-level field) require zero changes to the promotion mechanism itself — the generalization's whole point, verified against a full sweep of foreseeable future operations (templates, AI-generated content, attachments, plugins) during the impact analysis, none of which needed a special case.

## Amendment 2 (Cover Image milestone): Daily Note drafts participate in the metadata trigger

**Context.** The prior amendment's Decision item 3 excluded Daily Notes from _both_ the title and metadata triggers, reasoning that "nothing about interacting with a Daily Note's not-yet-meaningful pre-promotion state should make today's note real." That reasoning conflates two different things: _incidental_ interaction with an unopened, unedited Daily Note (which must never persist anything — the Governing Principle's whole point), and a _deliberate, explicit_ user action performed through a real UI control the user chose to activate (Cover image from the topbar overflow menu). Setting a cover is not something that happens by merely opening or viewing today's note; it requires the same kind of affirmative intent as typing into the body — the user picked a specific menu item and submitted a URL. Excluding it from promotion means "Cover image" cannot function at all for a Daily Note draft (the only way to reach `PageOperations.updateMetadata()` for one, since a Daily Note draft is the state a fresh "Today" is in until its first body edit), which is a capability gap, not a safety property.

**Decision.**

1. **`updateMetadata()`'s draft branch no longer excludes a `deterministicPath` (Daily Note) draft.** It participates in the metadata trigger exactly as an ordinary Note draft already does: a patch is checked against `resolvePageMetadata({})` for a genuine committed change (unchanged check, no new logic), and a committed change promotes via the same shared `persistDraft(id, body, metadataPatch)` helper `save()`'s body trigger and an ordinary Note's metadata trigger already use — `persistDraft` already resolves a `deterministicPath` draft's destination and folder chain correctly (that is how `save()`'s body trigger already promotes a Daily Note draft today), so no change to `persistDraft` itself is needed.
2. **The title trigger remains excluded for Daily Notes**, unchanged from the prior amendment — a Daily Note's title is derived from its date and is never user-committed, so there is no affirmative user action for `updateDraftTitle()` to represent here. Only the metadata trigger's exclusion is reversed by this amendment.
3. **No new abstraction, no field-specific special case.** The fix removes a conditional (`descriptor.deterministicPath` check) from `updateMetadata()`'s existing draft branch; it does not add a cover-specific code path. Every `EditablePageMetadata` field (description, icon, cover, favorite) now promotes a Daily Note draft the same way, consistent with how they already all promote an ordinary Note draft — a single rule, not one rule per field.

**Alternatives considered.** A cover-specific bypass (checking `'cover' in patch` before applying the exclusion) — rejected: it would special-case one `EditablePageMetadata` field over the others for no principled reason, reintroducing exactly the kind of per-field business-rule duplication `implementation-rules.md` rule 4 forbids, and would need revisiting the next time a different metadata field needs the same capability (e.g. a future "set icon" or "add description" action on a Daily Note draft would hit the identical gap).

**Consequences.** `architecture-specification.md` §6's invariant "Daily Note drafts (`deterministicPath` set) participate only via `save()`'s body trigger — `updateDraftTitle()`/`updateMetadata()` never promote one" is corrected to state that `updateMetadata()` now promotes a Daily Note draft too, on a genuine committed metadata change, mirroring an ordinary Note draft — only `updateDraftTitle()` remains excluded. No `PersistenceOperation` kind changes, no `Vault` mutation method changes, no facade signature changes.

## Sequencing Recommendation

**Revised — no longer independent of Calendar.** The original version of this ADR argued Daily Notes were out of scope and this could ship whenever, unrelated to Calendar. That no longer holds: Daily Notes are now in scope (Section 5), and Calendar is the feature most likely to consume "does this day have a real entry" as a signal (Section 5's signal-integrity point). Recommend implementing this ADR **before** Calendar ships any day-has-entry indicator, so that indicator is built once, correctly, rather than built against eager-creation semantics and reworked later. Calendar work that doesn't depend on that signal (month/week navigation UI, date picking itself) has no hard dependency and can proceed in parallel.
