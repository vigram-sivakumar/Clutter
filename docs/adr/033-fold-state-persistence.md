# ADR-033: Fold-State Persistence — `.clutter/workspace.json`'s First Real Reader/Writer

**Status:** Accepted

## Context

CM6's fold state (`codeFolding()`, wired at `createEditorView.ts:291`) already lets a user fold a heading, list, or fenced-code block, but that state has never survived anything: `MarkdownEditor.tsx` destroys and recreates its `EditorView` on every note switch (`PageHost.tsx`'s `<MarkdownEditor key={activePageId}>`), and each fresh `EditorState` starts with no folds. `editorHistoryCache.ts` already bridges an equivalent gap for undo/redo history and scroll position across that same destroy/recreate cycle — but its own doc comment is explicit that it is "session-lifetime, in-memory only, deliberately — not a persistence mechanism," backed by a plain `Map` that is discarded on app restart.

Product now requires fold state to survive an app restart, not just a note switch within one running session:

1. Fold a section, switch notes, come back → still folded (same requirement `editorHistoryCache` already meets for history/scroll).
2. Quit the app, reopen it, open the same note → still folded (a genuinely new requirement — nothing in the app persists any editor UI state today).

## Why `editorHistoryCache` cannot be extended for this

`editorHistoryCache` is correct for what it does and is left untouched by this ADR. It cannot become the source of truth for fold state because the two requirements have fundamentally different lifetimes:

- `editorHistoryCache`'s `Map` lives in a JS module scope, reset to empty on every full page reload/app restart. There is no code path that ever writes it to disk, and giving it one would mean smuggling a durable-persistence concern into a module whose entire documented contract ("this cache can only ever make session preservation better than the current baseline, never worse") assumes the opposite: that losing its contents is always harmless.
- Fold state's own persistence must instead be loaded once at boot (before any note is even opened) and be readable independent of whether that note was ever opened this session — `editorHistoryCache` has no boot-time load step at all, by design (`MarkdownEditor.tsx`'s mount effect is the *only* place it's ever populated).

Conflating the two would make `editorHistoryCache` responsible for a durability guarantee it was explicitly built to not provide, the exact kind of scope-creep-by-convenience `ARCHITECTURE_RULES.md` rule 5 (no responsibility crossing a subsystem boundary as a side effect of unrelated work) warns against.

## Decision

A new, narrowly-scoped `FoldStateStore` persists exactly one thing — per-`pageId` CM6 fold ranges — through the existing, previously-dead `.clutter/workspace.json` reserved file, using `VaultFileSystem` directly, outside the Persistence Gate. Nothing else `Workspace` tracks (open tabs, sidebar state, navigation history — see ADR-006/021/027) is touched, persisted, or generalized by this change.

### Persisted shape

```jsonc
// .clutter/workspace.json
{
  "foldState": {
    "<pageId>": {
      "doc": "<the page's exact Markdown source at the moment folds were captured>",
      "fold": [12, 340, 512, 780]   // flat [from, to, from, to, ...] — CM6 foldState's own JSON shape
    }
  }
}
```

- **`fold`** is exactly what `@codemirror/language`'s `foldState` field already serializes to. Confirmed directly against the installed `@codemirror/language@6.12.4` source (`node_modules/@codemirror/language/dist/index.js`): `foldState`'s `StateField.define({...})` spec already defines both `toJSON`/`fromJSON`, producing/consuming a flat `[from, to, from, to, ...]` number array — the same mechanism `EditorState.toJSON({fold: foldState})` uses internally. No custom serializer is needed on Clutter's side, unlike `historyField` (whose bespoke `{done, undone}` shape `editorHistoryCache` already handles).
- **`doc`** is the staleness guard, reusing the exact strategy `editorHistoryCache`/`createEditorView.ts` already use for history restoration: `createEditorView.ts`'s exported `docTextMatches(serialized, doc)` checks `serialized.doc === doc` — a persisted fold entry is shaped as `{doc, fold}`, so the same function validates it with zero new code. A restore is only ever applied when the note's current content is byte-identical to what it was when the fold was captured; any edit (this session, a prior session, an external sync) invalidates that page's persisted fold entry, and it is silently dropped in favor of the normal unfolded default — never partially restored onto content it no longer matches. This directly satisfies edge cases "document changes while a region is folded" and "content inserted above a folded region" from the original request: both change `doc`, both fail the match, both fall back to unfolded rather than restoring corrupted ranges.
- Storing the full document text (not a hash) trades some file size for reusing an already-verified-correct mechanism unchanged; see Alternatives Considered.

### Storage location, ownership, and wiring

- **`.clutter/workspace.json`** — the reserved file `ReservedResources.ts:96-99` already declares (seed contents `'{}'`) but that, per ADR-006/021/027, nothing has ever read or written. This ADR is its first real reader/writer. The file is read as a whole at boot; any top-level keys besides `foldState` (none exist today, but a future ADR — e.g. persisting open tabs — might add one) are read back and re-written unchanged, so this feature can never silently clobber a sibling key a later feature adds.
- **`FoldStateStore`** (`apps/app/src/core/application/editor/FoldStateStore.ts`, new file) owns this file end-to-end — one reader, one writer, matching the shape `TagOperations` already establishes for `.clutter/tags.json` (`apps/app/src/core/application/tags/TagOperations.ts`) and `ResourceArchiveMetadataStore` for `.clutter/resource-archive.json`. It is **not** a method on `Workspace`: `Workspace` is zero-dependency, in-memory-only navigation state by explicit, twice-reaffirmed design (ADR-006, ADR-021), and fold state is editor content state, not navigation state — giving `Workspace` I/O or a fold-state field would violate both properties for a capability that isn't actually workspace-navigation-shaped. `FoldStateStore` sits alongside `Workspace`, constructed in the Composition Root the same way, but is its own file.
- **Boot-time load**: `Application.bootstrap()` reads `.clutter/workspace.json` once, the same inline "read a small `.clutter/*.json`, tolerate absence" shape already used for `tags.json` (`Application.ts:165-178`) — parses `foldState` into an in-memory `Map<pageId, {doc, fold}>`, constructs `FoldStateStore` with it, and exposes it as `application.foldStateStore` (a plain public field, matching `application.taskOperations`/`application.resourceOperations` — no facade indirection, since there is no business decision here to own, only storage).
- **Session-time writes**: `FoldStateStore.set(pageId, entry)` updates the in-memory map and fires an async, best-effort whole-file write via `ensureClutterDirectory` + `VaultFileSystem.writeFile` — not a read-merge-write per call (unlike `TagOperations.updateMetadata`, which re-reads before every write because nothing else keeps `tags.json`'s state in memory across calls). `FoldStateStore` is different: it is the sole owner of the in-memory map for the entire session, loaded once and kept authoritative from boot forward, so serializing straight from memory on every `set()` is correct and avoids an unnecessary read on every note switch. `MarkdownEditor.tsx`'s existing unmount cleanup (`MarkdownEditor.tsx:894-921`, right where `editorHistoryCache`'s `setCachedEditorSession` is already called) calls `foldStateStore.set(pageId, serializeFoldState(view))` alongside it — same call site, same moment, independent cache.
- **Restoration**: `createEditorView.ts` gains a new, independent `restoreFoldJSON?: unknown` option (not merged into `restoreHistoryJSON`'s existing `fromJSON` call — see Alternatives Considered for why). Validated with the same `docTextMatches` check; on success, `foldEffect` (from `@codemirror/language`, already exported alongside `foldState`) is dispatched for each `[from, to]` pair immediately after the `EditorView` is constructed. `MarkdownEditor.tsx`'s mount effect passes `application.foldStateStore.get(pageId)` in, the same place `getCachedEditorSession(pageId)` is already read.

### Why this does not use the Persistence Gate

`.clutter/workspace.json` is not Vault domain content — it is not a `Page`, a `Folder`, or anything `Vault.addPage`/`replacePage`/`removePage` models. `ARCHITECTURE_RULES.md` rule 2's own Scope paragraph draws this line explicitly: the Gate governs Vault content only, and "Clutter-owned application infrastructure or configuration — caches, indexes, plugin state, `.clutter/*` files" are named as outside it by design. `TagOperations` and `ResourceArchiveMetadataStore` are the two existing, working precedents for writing a `.clutter/*.json` file directly through `VaultFileSystem`; `FoldStateStore` follows the identical shape, making this the third instance of an already-established pattern, not a new one.

### Failure behavior

- **File missing** (fresh vault, or a vault that predates this feature): treated exactly like `tags.json`'s missing-file case — falls back to `EMPTY_WORKSPACE_STATE_FILE_CONTENTS` (`'{}'`), yielding an empty fold-state map. No note has any persisted folds; every note opens unfolded, matching today's behavior exactly.
- **File present but malformed JSON, or `foldState` present but the wrong shape** (not an object, an entry missing `doc`/`fold`, `fold` not an even-length number array): caught and discarded at load time, per-entry where possible (one corrupt entry doesn't invalidate the whole file) and whole-file where the JSON itself doesn't parse — logged via `console.warn`, never thrown. This is a deliberate, explicit divergence from `TagOperations`/`Application.bootstrap()`'s existing tags-read, which does not guard `JSON.parse` at all: those call sites have never needed to, since nothing generates malformed `tags.json` today, but `workspace.json` is new, user-restart-sensitive, and its own persisted shape has no other validation layer — the app must never fail to boot because a fold-state file was corrupted by an interrupted write or a manual edit. Confirmed as the correct call under `implementation-rules.md`'s divergence process: a stricter, safer failure mode than existing precedent, justified by this feature's specific boot-blocking risk, not a silent inconsistency.
- **A persisted entry's `doc` no longer matches the note's current content**: not a failure — the normal, expected `docTextMatches` miss, silently falling back to unfolded for that one note, exactly as history restoration already does.

## Alternatives Considered

- **Merge fold data into `restoreHistoryJSON`'s existing `EditorState.fromJSON({history, fold})` call**, since `foldState` is a plain CM6 `StateField` like `historyField`. Rejected: `restoreHistoryJSON` comes from session-lifetime `editorHistoryCache` (reset every app restart) while fold data comes from the newly cross-restart-durable `FoldStateStore` — two sources with genuinely different lifetimes and independent staleness outcomes (a note could have valid persisted folds but no session history cache entry, e.g. right after an app restart, or vice versa mid-session after an external edit invalidates only the fold entry). Forcing them through one `fromJSON` call would require the two staleness checks to agree before either could be applied, discarding a valid fold restore whenever history happened to be stale (or was simply absent) for unrelated reasons. Dispatching `foldEffect` independently, right after construction, keeps the two mechanisms — and their two different failure/staleness stories — decoupled, matching how `restoreScrollEffect` is already deliberately kept as its own gated option rather than folded into the same `fromJSON` payload.
- **Store a hash of `doc` instead of the full text**, to shrink `workspace.json`. Rejected for this change: it would mean writing and maintaining a second, disk-only staleness check distinct from `docTextMatches`'s in-memory one, for a file whose size (one string per *currently folded* note, not per note in the vault) is not expected to be a real problem at product scale. The persisted shape's own doc comment will flag this as the first thing to revisit if it ever is — swapping `doc: string` for `docHash: string` is a compatible, localized change to `FoldStateStore` alone, not a reason to design differently now.
- **Fold `FoldStateStore` into a general `WorkspaceSnapshot`** covering every field `Workspace` holds (open tabs, sidebar visibility, nav history), per the extension point `architecture-specification.md:665` originally named. Rejected — explicitly out of scope for this ADR, per the product requirement it responds to (fold state only). Building a generic snapshot abstraction now, for fields with no confirmed persistence requirement yet, would repeat exactly the "half-built, unused infrastructure" pattern ADR-006 already flagged and declined to build speculatively. If/when tabs or nav history need to persist too, that is a separate, later ADR — at which point whether it reuses `FoldStateStore`'s file-read/write shape, generalizes it, or stays a second sibling file is that ADR's decision to make with real requirements in hand, not this one's to pre-guess.
- **Give `Workspace` the I/O itself** (a `load()`/`save()` pair on the class). Rejected: breaks `Workspace`'s explicit zero-dependency, in-memory-only contract (ADR-006's Consequences: "`Workspace`'s zero-dependency status... is preserved exactly") for a capability (editor content state) that isn't navigation state in the first place — `FoldStateStore` as a sibling file, constructed alongside `Workspace` in the Composition Root but never imported by it or importing it, keeps both invariants intact.

## Consequences

- `.clutter/workspace.json` goes from permanently-dead reserved-file infrastructure to a real, narrowly-scoped store — the first concrete instance of the extension point `architecture-specification.md:665` and ADR-006 both named but explicitly declined to build speculatively. `architecture-specification.md` §10 (`Workspace`) gains a short note that fold state is persisted separately, by `FoldStateStore`, not by `Workspace` itself, so a future reader doesn't assume `Workspace`'s own "does not persist across restarts" line covers fold state too.
- `ReservedResources.ts` gains named constants (`WORKSPACE_STATE_RELATIVE_PATH`, `EMPTY_WORKSPACE_STATE_FILE_CONTENTS`) mirroring `TAG_METADATA_RELATIVE_PATH`/`EMPTY_TAG_METADATA_FILE_CONTENTS` exactly, so `RESERVED_RESOURCES`'s existing `.clutter/workspace.json` entry, `Application.bootstrap()`'s load, and `FoldStateStore`'s write all share one literal instead of three copies.
- `editorHistoryCache.ts` is unchanged — this ADR adds a second, independent cross-restart cache next to it, not a modification of its session-lifetime contract.
- `createEditorView.ts` gains one new, independently-gated option (`restoreFoldJSON`) and one new dispatched-effect step; `restoreHistoryJSON`/`restoreScrollEffect`'s existing behavior and gating are untouched.
- **Future extensibility**: a later ADR persisting a second kind of workspace field (open tabs, say) has two working precedents to choose from — extend `FoldStateStore`'s file with a sibling top-level key (already safe, since unknown keys round-trip today), or add a second, equally narrow sibling store next to it. Neither choice is foreclosed by this ADR; a generic `WorkspaceSnapshot` abstraction remains available to propose later if and when a third or fourth persisted field makes the duplication across sibling stores genuinely costly — not before.

## Why This Approach Is Preferred

It turns a named-but-declined extension point into exactly the "deliberate, scoped addition... if/when session-restore-on-reopen becomes an actual product requirement" ADR-006 said this would need to be, using only machinery already proven correct elsewhere in the codebase (`VaultFileSystem` read/write, `ensureClutterDirectory`, the `TagOperations`-shaped single-owner `.clutter/*.json` pattern, `docTextMatches`'s staleness check, CM6's own built-in `foldState` serialization) — no new abstraction, no Gate involvement, and no expansion of `Workspace`'s carefully-preserved zero-dependency, in-memory scope.

## Amendment: Extending fold-state persistence to note embeds

**Context.** The original Decision above scoped fold-state persistence to the top-level, editable `MarkdownEditor` only. A follow-up product requirement extends it to note embeds (`![[Other Note]]`, rendered inline as a nested, permanently read-only CM6 `EditorView` — `NoteEmbedWidget.ts`): folding a heading/list/fenced-code block *inside* an embedded note's own rendered content must persist the same way, keyed by the **embedded note's own stable `pageId`**, surviving the host note being closed and reopened — using this ADR's existing `FoldStateStore`, not a second mechanism.

This matters architecturally because a note embed's nested view has a genuinely different lifecycle than the top-level editor's: it is not one-per-`pageId` at a time (the top-level editor's whole model, via `key={activePageId}`) — the same page can be embedded multiple times simultaneously, in one host note or across several, each occurrence its own independent `EditorView` instance. Before amending the Decision, this needed to be checked against `FoldStateStore`'s `pageId`-keyed map to confirm it still holds.

**Investigation findings** (full detail in the implementation's own file-level doc comments):

- `NoteEmbedWidget.toDOM()` already constructs its nested view via the *same* `createEditorView()` factory this ADR's Decision instrumented (`NoteEmbedWidget.ts`, the `createEditorView({ doc, parent, readOnly: true, extensions })` call) — there is no separate, lower-level `EditorView` construction path to wire up. `restoreFoldJSON`/`serializeFoldState` apply unchanged.
- The embedded page's stable `pageId` is already resolved and threaded to exactly this call site: `resolvePageEmbed.ts`'s `createPageEmbedResolver()` returns `PageEmbedResolution.pageId` (`Vault`'s real page id, the same identity `DocumentSession`/`DocumentEditing` use per ADR-018) — already read at `NoteEmbedWidget.ts`'s `eq()` and `Expand` handler. No new identity plumbing is needed; `FoldStateStore.get/set(resolution.pageId, ...)` is a direct, correct call.
- `NoteEmbedWidget`'s `eq()` (comparing `path`/`pos`/`to`/`ui.revealed`/`ui.broken`/`resolution.{pageId,title,markdown,icon,emoji}`) already keeps the *same* nested `EditorView` instance alive across unrelated decoration rebuilds (scrolling, an edit elsewhere in the host note, a sibling embed's own re-render) — `destroy()`/`toDOM()` only fire when the embedded content itself actually changes or the widget's range is removed (host note closed, embed deleted). This is exactly the condition under which capture-then-restore is correct: an `eq()`-preserved instance needs no restore (it never lost its live fold state); a genuine `destroy()`+`toDOM()` cycle is precisely a "close and reopen" event for that occurrence.
- **Today, `readOnly: true` unconditionally omits `codeFolding()`/`foldToggleDecoration()`/`foldKeymap`/`foldAwareArrowKeymap`** (`createEditorView.ts`'s `readOnly ? [] : [...]` gates) — a note embed has no fold state or fold UI to begin with. This is the one place the prior implementation must change, not just be reused.
- Multiple simultaneous embeds of the same page share no view/registry — each is fully independent. Consequence: if two live occurrences of the same embedded page are folded differently at once, whichever's `destroy()` fires last wins the one persisted `FoldStateStore` entry for that `pageId`. **Accepted, not solved** — the same class of best-effort, last-write-wins behavior `FoldStateStore` and `editorHistoryCache` already accept for the ordinary case of two rapid page switches; coordinating multiple simultaneously-open occurrences of one page's fold state would be new, unrequested machinery (multi-view synchronization) for a scenario ("I have the same note embedded twice and folded them differently right now") the product requirement doesn't ask for. **Restoration is unaffected by this** — every occurrence, at its own construction, reads whatever `FoldStateStore.get(pageId)` currently holds, so all simultaneous embeds of one page always open consistent with the same last-persisted state, per the "multiple embeds of the same note should restore the same underlying fold state" requirement.

**Decision.**

1. **`createEditorView.ts` gains a new, independent `enableFolding?: boolean` option, decoupled from `readOnly`** — defaulting to `!readOnly` (preserving today's exact behavior for both existing callers: the top-level editor, `readOnly: false`, still gets folding; nothing else changes for it). `NoteEmbedWidget.ts` is the first caller to pass `readOnly: true, enableFolding: true` together — folding becomes possible inside a note embed while it remains fully non-editable (CM6 fold commands are non-mutating; `blockReadOnlyEdits`/`EditorView.editable.of(false)`, gated purely on `readOnly`, are completely untouched). The fold-related extensions (`codeFolding()`, `indentedParagraphFoldService()`, `foldToggleDecoration()`, `foldKeymap`, `foldAwareArrowKeymap`) switch from gating on `readOnly` to gating on `enableFolding`.
2. **No `FoldStateStore`/persisted-shape change.** The embedded page's `pageId` is simply another key in the same `Map<pageId, {doc, fold}>` — a host note and a note embedded inside it (or inside several) each get their own independent entry, keyed correctly, with zero schema change.
3. **Restore, in `NoteEmbedWidget.toDOM()`'s `createEditorView()` call:** `enableFolding: true, restoreFoldJSON: getFoldStateStore()?.get(resolution.pageId)` — same `docTextMatches`-gated mechanism as the top-level editor, so an embedded note whose content has since changed (edited directly, or via a different embed occurrence) never restores stale fold ranges onto it, satisfying the "stale/changed embedded document content" test case the same way the top-level editor already does, with zero new code.
4. **Capture, in `NoteEmbedWidget.destroy()`:** before `this.nestedView?.destroy()`, call `getFoldStateStore()?.set(resolution.pageId, serializeFoldState(this.nestedView))` when `this.resolution` is non-null (a broken embed has no page to key by — nothing is captured). This is the one genuinely new hook — `destroy()` previously did nothing but tear down the view.
5. **Threading:** a `getFoldStateStore: () => FoldStateStore | undefined` getter, matching the existing injected-closure/freshness-ref convention every other embed callback already follows (`getOnOpenPage`, `getOnOpenNoteEmbedMenu`) — `MarkdownEditor.tsx` (a `foldStateStoreRef`, read fresh, same pattern as `onOpenPageRef`) → `buildEditorExtensions.ts`'s `BuildEditorExtensionsOptions`/call into `embedLivePreview()` → `embedLivePreview.ts`'s `EmbedLivePreviewOptions` → both `NoteEmbedWidget` constructor call sites (resolved and broken, for a uniform constructor signature) → recursively into the nested `buildEditorExtensions({...})` call `embedLivePreview.ts` already makes for a further-nested embed, the same way `ancestry` is already threaded one level deeper at each recursion. This means an embed nested inside another embed also gets independent fold persistence, keyed by its own `pageId`, at every depth — no depth-specific logic needed, matching every other resolver already threaded this way.
6. **Not conflated with `NoteEmbedWidget`'s existing whole-embed "Collapse note" toggle** (`ImageUiState.collapsed`, the chevron in the widget's own header). That is a different, pre-existing, unrelated mechanism — collapsing the entire rendered embed card — and is untouched by this amendment. This amendment is about CM6's own per-heading/list/fenced-code fold state *inside* the nested view's content, which did not exist in any form before this change.

**Alternatives considered.**

- **Coordinate multiple simultaneous embeds of the same page so none can "lose" a fold via last-write-wins.** Rejected — see the investigation finding above: this would require a live registry of open `EditorView` instances per `pageId` with some kind of merge or broadcast-on-fold behavior, which is new, unrequested cross-instance synchronization machinery for a scenario the product requirement doesn't describe (it asks for independent fold states across *different* embedded notes and consistent restoration across *simultaneous* embeds of the *same* note — both already satisfied without this).
- **A second, embed-specific persistence key/namespace (e.g. `foldState[pageId][embedOccurrenceId]`).** Rejected — this would special-case "this pageId happens to be viewed via an embed" as a distinct kind of fold state from "this pageId happens to be open as the top-level note," when the product requirement is explicit that they're the same thing: the fold state belongs to the *document*, not to whichever surface is currently rendering it. One `pageId` key naturally means "however many surfaces render this page at once, they're all showing (and, on close, persisting) the same document's fold state" — which is also why a note opened directly and *then* embedded elsewhere sees the same persisted folds either way, not two disconnected states for one document.
- **Route embed fold-state capture through `MarkdownEditor.tsx`'s own unmount cleanup instead of `NoteEmbedWidget.destroy()`.** Rejected — an embed's nested view is destroyed and recreated far more often than the host note switches (any unrelated edit that changes `eq()`'s inputs), and a host note can contain many embeds at once; the host's own unmount cleanup has no visibility into which embed widgets currently exist or their `nestedView`s. `WidgetType.destroy()` is CM6's own correct, existing lifecycle hook for exactly "this widget's rendered resources are going away" — reusing it (the same way the host editor's own unmount cleanup is the correct hook for *its* teardown) keeps capture co-located with the object whose state is being captured.

**Consequences.**

- `createEditorView.ts`'s `CreateEditorViewOptions` gains `enableFolding?: boolean`; every existing call site (the top-level editor) is unaffected by the new default. `docs/editor-architecture-decisions.md`'s "note embeds: nested read-only `EditorView`... no fold toggle, no fold state" framing is updated to reflect that folding is now independently enabled for embeds — the "one continuous, fully-expanded piece of content" rationale for *omitting fold* no longer holds by default (it was never a rationale against non-mutating navigation affordances specifically, just the blanket `readOnly` omission that happened to include fold); everything else about a note embed staying non-editable is completely unchanged.
- `EmbedLivePreviewOptions`/`BuildEditorExtensionsOptions` each gain one new optional field (`getFoldStateStore`), threaded the same way every other injected accessor already is — no new construction pattern.
- `NoteEmbedWidget.destroy()` gains its first real body beyond `view.destroy()`.
- No `.clutter/workspace.json` shape change, no `FoldStateStore` API change — this amendment is purely about *which call sites* now use the existing mechanism, not what it stores.

## Why This Amendment Is Preferred

It extends fold persistence to embeds using every mechanism this ADR already built — the same store, the same restore/capture functions, the same `docTextMatches` staleness gate, the same injected-getter threading convention every other embed callback follows — with exactly one new capability (`enableFolding`, decoupled from `readOnly`) and one new hook (`NoteEmbedWidget.destroy()`'s capture call). The `pageId`-keyed model this ADR chose for the top-level editor turns out to need no change at all for embeds: a page's fold state belongs to the page, and `FoldStateStore`'s map was already shaped that way before any embed-specific requirement existed.

## Second Amendment: the outer "collapse this whole embedded note" toggle is a different mechanism, not CM6 `foldState`

**Context.** A note embed's rendered card has two visually similar, but mechanically unrelated, collapse affordances: the chevron inside the embedded content (folds one heading/list/fenced-code section of the *embedded* note's own body — the first amendment above), and a second chevron in the card's own header (collapses the *entire* rendered card — pre-existing "Phase 2" behavior, `NoteEmbedWidget.ts`'s own `collapseButton`). Only the first survives an app restart today; the second does not, and a request came in to fix that too, "using the same fold-state persistence architecture."

**Investigation finding.** The header's whole-card collapse is **not** CM6's `foldState`/`codeFolding()` mechanism at all, and never has been — `NoteEmbedWidget.ts`'s own doc comment already said so before this amendment ("there is no `foldService`/`foldEffect`/fold state applicable to it here"). It is `ImageUiState.collapsed` (`imageUiState.ts`), a plain boolean field inside a *different* CM6 mechanism: `imageUiStateField`, a `StateField<RangeSet<ImageUiValue>>` that lives in the **host** document's own `EditorState`, keyed by the embed reference's own `[from, to)` position in the host's Markdown (mapped across host-document edits via `RangeSet.map`, CM6's standard per-position-UI-state pattern — the same field also tracks `revealed`/`broken`/`displayMode`/`pendingFirstLeave` for ordinary Image/PDF embeds). The first amendment's `restoreFoldJSON`/`serializeFoldState` machinery only ever reads/writes `@codemirror/language`'s `foldState` field via `EditorState.toJSON({fold: foldState})` — `imageUiStateField` was never part of that serialization, by construction, not by omission. This is also why the collapse toggle doesn't even survive a plain **note switch** today (a gap that predates this ADR entirely): `editorHistoryCache`'s `restoreHistoryJSON` only ever captures `historyField`.

**Decision.** Persist `ImageUiState.collapsed` through a **second, independent** structure inside `FoldStateStore`/`.clutter/workspace.json` — never folded into the existing per-pageId `{doc, fold}` entry, and never sharing a mutation path with it, per the explicit "do not merge these" requirement:

1. `FoldStateStore` gains a second in-memory map, `embedCollapse: Map<hostPageId, Map<embeddedPageId, boolean>>`, persisted as a sibling top-level JSON key (`"embedCollapse"`, alongside the existing `"foldState"` key) — `getEmbedCollapse(hostPageId, embeddedPageId)` / `setEmbedCollapse(hostPageId, embeddedPageId, collapsed)`. Kept as a genuinely separate map (not a field folded into `PersistedFoldEntry`) specifically so `MarkdownEditor.tsx`'s unmount cleanup (writes the host's own top-level `{doc, fold}` via `set()`) and `NoteEmbedWidget`'s collapse-toggle click (writes `embedCollapse` via `setEmbedCollapse()`) can never race-clobber each other — they touch different in-memory structures, so whichever fires first or last, both always persist correctly regardless of order.
2. Keyed by `hostPageId` (whichever document's own Markdown contains the `![[...]]` reference — the immediate container, not necessarily the top-level open note, for a multiply-nested embed) mapped to `embeddedPageId` — satisfying "different host notes containing the same embedded note don't accidentally share the host's outer-fold state" by construction: two different `hostPageId`s are two different outer `Map` entries.
3. **Captured at click time, not at `destroy()`.** Unlike CM6 fold state (which only ever exists live inside an `EditorState`, with `destroy()` as the one natural capture point), the collapse toggle already has a single, discrete user-action moment — its own click handler — so `NoteEmbedWidget.ts`'s `collapseButton` click listener calls `getFoldStateStore().setEmbedCollapse(hostPageId, resolution.pageId, collapsing)` directly, immediately, alongside its existing `setImageUiState` dispatch. `NoteEmbedWidget.eq()` already deliberately excludes `collapsed` from its rebuild-triggering comparison, so this same widget instance (and therefore this same click handler closure) can live for the rest of the session — no destroy-time capture is needed or added.
4. **Restored at construction, gated on "no live entry yet."** `embedLivePreview.ts`'s `buildDecorations()` seeds a resolved note embed's initial `collapsed` from `getFoldStateStore().getEmbedCollapse(hostPageId, pageResolution.pageId)`, but *only* when `imageUiState.ts`'s new `hasImageUiStateEntry(state, pos)` reports no live entry at that position yet this session — a live entry (this session already toggled it, or wrote one for any other reason) is always authoritative and must never be second-guessed by a persisted value that could be stale relative to it. This mirrors `restoreFoldJSON`'s own "never a partial/best-effort restore" posture, applied to a different field.
5. **`hostPageId` threading is new** (nothing needed it before this amendment): `MarkdownEditor.tsx` passes its own `pageId` as `hostPageId` into `buildEditorExtensions()`; a resolved note embed's own recursive `buildEditorExtensions()` call (building *its* nested embeds' extensions) passes `resolution.pageId` as the *next* level's `hostPageId` — the exact same one-level-deeper threading `ancestry` already uses, so a multiply-nested embed's own outer-collapse state is correctly attributed to its immediate container at every depth, not the top-level session root.
6. `FoldStatePersistence` (the structural, `core/application`-import-free interface `codemirror/embed/` uses in place of the concrete `FoldStateStore` class — see the first amendment) gains `getEmbedCollapse`/`setEmbedCollapse` alongside `get`/`set`.

**Alternatives considered.**

- **Fold `embedCollapse` into `PersistedFoldEntry` as a new field** (e.g. `{doc, fold, embedCollapse}`). Rejected — this is exactly the "single fold state" merge the request explicitly ruled out, and for good reason: it would force `MarkdownEditor.tsx`'s cleanup (which only knows the host's own `{doc, fold}`) and `NoteEmbedWidget`'s click handler (which only knows one `embeddedPageId → collapsed` pair) to each read-modify-write the *same* object, reintroducing exactly the clobber race a two-map design avoids for free.
- **Capture at `destroy()`, mirroring CM6 fold state exactly.** Rejected — `collapsed` already has a real, single user-action trigger (the click); waiting for `destroy()` would mean losing the toggle if the widget instance simply outlives the click without ever being torn down before the host note closes (the common case, since `eq()` excludes `collapsed`), or would require a second write path with no advantage over writing once, immediately, at the moment the fact becomes true.
- **Give `ImageUiState.collapsed` its own cross-restart serialization inside `imageUiStateField` itself** (mirroring how `foldState` already self-serializes). Rejected — `imageUiStateField` intentionally bundles five unrelated concerns (`revealed`/`displayMode`/`broken`/`pendingFirstLeave`/`collapsed`) for ordinary Image/PDF embeds too, none of which have (or need) cross-restart persistence; teaching the whole field to serialize would either persist all five (scope creep, no product requirement for the other four) or require picking `collapsed` back out again at the serialization boundary anyway — no simpler than reading it directly in `embedLivePreview.ts`, which already computes `baseUi` from this field on every rebuild.

**Consequences.**

- `.clutter/workspace.json` gains a second top-level key, `"embedCollapse"`, sibling to `"foldState"` — both round-trip through the same file, same `ensureClutterDirectory`/`VaultFileSystem` write path, same missing/malformed-tolerant load.
- `EmbedLivePreviewOptions`/`BuildEditorExtensionsOptions` gain one new **required** field, `hostPageId` — deliberately not optional, since there is no safe default that wouldn't risk silently attributing collapse state to the wrong document. Every existing test call site needed updating to supply one; production call sites (`MarkdownEditor.tsx`, `embedLivePreview.ts`'s own recursive build) already had the right value in scope.
- `NoteEmbedWidget`'s constructor gains one new parameter, `hostPageId`; `FoldStatePersistence` gains two new methods.
- No change to the first amendment's own mechanism (`enableFolding`, `restoreFoldJSON`/`serializeFoldState`, the embedded page's own `pageId`-keyed CM6 fold ranges) — this amendment adds a second, parallel persisted structure next to it, never modifying it.
