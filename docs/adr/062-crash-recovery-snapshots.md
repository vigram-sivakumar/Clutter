# ADR-062: Crash recovery — session-tagged snapshots of unsaved work, kept outside the vault

**Status:** Proposed (implemented in the working tree; the desktop-app behaviour — force-quit, the real data directory — is not yet verified, see *Verification*). Builds on [ADR-001](./001-single-persistence-gate.md), [ADR-053](./053-persistent-parsed-note-cache.md) and `docs/durability-model.md`.

## Context

Unsaved work lives only in memory (`DocumentSession` for a body, `FieldEditState` for a title or description, a draft descriptor for a note that has no file yet). A crash, Force Quit, logout or Dock Quit bypasses the close flow, so everything typed since the last successful save is lost. `durability-model.md` records this as the *Committed* stage's accepted limit. No other mechanism preserves editor revisions: `editorHistoryCache` is session-lifetime, `localStorage` holds UI preferences, and `.clutter/workspace.json` keeps a note's source only as a fold-state staleness guard.

## Decision

1. **Recovery snapshots are a separate safety net; the vault stays the source of truth.** They are application infrastructure, not page content, so they do not go through the Persistence Gate (`ARCHITECTURE_RULES.md` rule 2 scopes the Gate to vault domain content) and never write into a vault.
2. **Where.** `<appData>/recovery/<vaultKey>/<note>.<session>.json` (macOS: `~/Library/Application Support/<bundle id>/recovery`), via the fs plugin and the `$HOME/**` scope the app already has; no new native code or capability. The web runtime has no data directory: it uses `localStorage` (a development surface). `vaultKey` is `space-<Space profile id>` when the Space has one (stable across a folder rename), else `root-<fingerprint of the root path>`; both are read.
3. **What.** One JSON record per note with unsaved work, holding only the unsaved fields (body with the editor revision, title, description), the note's id, label and path, a draft's folder/type/tags, and the vault's own values at capture time (a fingerprint of the body, the saved title and description). No credentials, preferences or other state. A draft is told apart by `kind`, never by id.
4. **Session-tagged files.** Each session writes only `<note>.<session>.json`, where the session tag is a random UUID (older records carry an 8-hex-digit tag; both are read, nothing is renamed or migrated, and the tag is the last dotted part of the name, so a note id cannot be mistaken for one). A record left by a crashed session is never overwritten by the next session editing the same note, and a session only ever removes its own files. Before a session writes or discovers anything it lists its directory; a file already carrying its tag (a collision) makes it draw a new tag, and if every draw clashes it writes nothing rather than overwrite.
5. **When.** A snapshot is written 1000 ms after the last change and at least every 2000 ms of continuous editing (`RECOVERY_DEBOUNCE_MS = 1000`, `RECOVERY_MAX_WAIT_MS = 2000`, set in `RecoveryJournal.ts`; an earlier revision of this ADR said 5 s, which was the first implementation's value; a write measured a few milliseconds, so the shorter bound costs little), never per keystroke. Measured in the isolated real app: about 1.01 s after the last keystroke, and a write about every 2.15 s while typing continuously. It is also written at once, in the background, when the user navigates away from the active note (`PageOperations.flushActivePage`) and when the page becomes hidden, and, awaited, before the Space-switch prompt (`Application.snapshotUnsavedWork`) so what that prompt says about a recovery copy is true. Every snapshot carries a per-note, per-session `sequence` counter. Each write reads the note's state when it runs, one note's writes run strictly one after another, so a delayed older snapshot cannot replace a newer one. Writes are temp-file-then-rename (`<record>.json.tmp`, then rename), so a failed write leaves the earlier record intact; a failed write retries up to 3 times, 5 s apart, and never changes the outcome of the vault save. A snapshot is also written at shutdown and when the vault is lost.
6. **Cleanup is revision-aware.** A record is removed only when, at that moment, the note has nothing unsaved in any channel (body, title, description). Saving revision N while N+1 is waiting leaves the record, rewritten with N+1. A record is removed also on explicit Discard, after a "save as new note" succeeded, or, for the original of a Restore into the editor, together with this session's own record once the note has nothing unsaved (item 8). A failed vault save keeps the records, and a failed removal is retried.
7. **Startup.** After the vault loads, records from earlier sessions are classified against the vault: **already-saved** (the vault holds the recovered text: record removed), **recoverable** (the vault still matches the snapshot's base), **conflict** (the vault changed, or the note is archived), **missing-note**, **draft**. Nothing is applied automatically. If the vault cannot be opened, nothing is classified and no record is removed. Unreadable or malformed files are ignored and left in place.

   **Interrupted snapshots.** A kill between the temp-file write and the rename leaves a complete newer record only in `<record>.json.tmp`. Discovery reads both files of a note and session with the same checks (schema; the record's note and session match the file name; the record belongs to that vault directory) and orders them by `sequence` (`compareFreshness`), never by file time. **Discovery is read-only: it never writes, renames, promotes or deletes anything.** A valid `.tmp` record is a candidate where it is, so there is no destination to race for and the only copy of the newest snapshot is never opened for writing. An incomplete `.tmp` (it does not parse) might be a write still in progress, and one that cannot be read says nothing about what it holds, so neither is deleted; they are counted as unreadable and left.
   - A `.tmp` newer than the committed record is the candidate; the older committed record (or a malformed one) is resolved with it when the user restores or discards it, never before. A `.tmp` older than, or identical to, a valid committed record is not offered and is likewise removed only when that candidate is resolved. A file that could not be read, or belongs to another note, is never attached, offered or deleted.
   - Records written before `sequence` existed fall back to the editor revision, then the capture time; two such records at the same position with different content are both kept and both offered.
   - One candidate per note and session, so repeated or concurrent discovery neither duplicates nor loses a record. Records from different sessions are separate candidates unless they hold identical recovered content (see item 8). Several simultaneously running Clutter instances on one data directory are not supported: another live session's in-flight `.tmp` is indistinguishable from an interrupted one. Garbage that is never resolved (a malformed `.tmp` left by a crash mid-write) stays on disk; it is harmless and is not worth a deleter that could race a writer.
   - The one cleanup outside the user's decision is a record whose recovered text, title and description the vault already holds in full (`already-saved`, decided by comparing with the vault, never by whether the file parses): it is redundant, and left alone it could later be resurrected as a stale conflict.
8. **Restore never overwrites.** *Recoverable*: the text re-enters the editor as an ordinary unsaved edit (`commitEdit`/`commitTitle`/`commitDescription`) and is saved by autosave through the Gate. *Conflict*, *missing-note*, *draft*: the only offer is a new note (`PageOperations.create`, collision-free naming). Closing the dialog keeps every record; a persistent notice (top bar for the open note, a toast for other notes) reopens the review.
   - **Re-checked at Restore.** The classification is made again at the moment of Restore. If the vault changed since startup, or the note has unsaved work of its own that is not this record's text (typed since, or restored from another record of the same note), the text is saved as a new note instead of replacing what the editor holds, so restoring one of two records of a note never overwrites the other. If the editor already holds exactly this record's text (an earlier Restore failed to protect it and was kept), Restore finishes that restore instead of creating a second note.
   - **The hand-off keeps the original until the vault save.** Restore first writes this session's own record holding the restored text (`snapshotNow` reports the outcome of that very write, so an older snapshot of the note never counts as protection); only then is the original handed to the journal (`adopt`), which keeps it until the note has nothing unsaved (the vault save succeeded) and removes it together with this session's own record, retrying a failed removal. At every boundary at least one valid record holds the content: before the protecting write, the original; during it, the original (writes go to a temp file, then rename); after it, both; on a failed vault save, both, with the "Couldn’t save changes" notice and Retry showing; after the save, neither (removed, retried on failure, and a record that never could be removed is dropped at the next startup because the vault already holds its text). A newer edit made during or after the restore rewrites this session's record; the original keeps the older revision until the save.
   - **Duplicates after a crash.** If the process ends between the protecting write and the save, both records survive. Records of the same note with identical recovered text, title and description, and the same classification, are offered once, as the newest of them with the others attached; nothing is deleted at discovery, and resolving the candidate removes all of them. Records whose content differs in any way (a newer edit, another session's different revision) are never merged and stay separate candidates; restoring one into the editor makes the other a new note, never a loss.
9. **Closing with unsaved changes** ("Close without saving?" / "Close anyway") writes a recovery snapshot as the Application closes (`Application.close`), and keeps the record. The dialog says what is true: the changes won't be saved to the vault, a recovery copy may be available when Clutter opens again, and it might not include the latest edits. It does not promise recovery: no copy is written if the recovery location cannot be written.
10. **Leaving a Space** takes a recovery snapshot first. If it is confirmed on disk the dialog says the changes are not saved to this Space and a recovery copy is kept for when the user returns ("Switch anyway" / "Keep editing"); if not, it keeps the old "will be lost" wording. Nothing is deleted on switching.
11. **Discard asks first.** The Discard button on a recovery candidate shows an inline confirmation naming the note and saying the recovery copy is permanently removed; Cancel changes nothing, and only the confirmed record is deleted.

## Limits (not guaranteed)

- Edits made after the last completed snapshot are lost: up to about 1 s after the last keystroke, 2 s while typing continuously, plus the time of one write. The guarantee is exactly this, and no stronger: a snapshot revision that was safely committed (renamed into place, or found complete in a `.tmp` file) is recoverable, subject to the filesystem's own durability; nothing newer is promised. A crash while a write is in flight leaves the previous record.
- Atomicity is a same-directory rename; there is no `fsync`, so power loss may lose the newest snapshot (never corrupt an older one, as far as the rename guarantees).
- Table normalisation can make a saved note differ from the recovered text; the result is a *conflict*, which still offers a new note, never a loss.
- Recovery data is a **second copy of user content** (possibly sensitive) outside the vault, unencrypted, in the app's data directory. It is removed on a confirmed save or an explicit discard. A stale record for a deleted vault stays until the user discards it; there is no age-based deletion because deleting unsaved work without being asked is the failure this feature exists to prevent.
- A session tag is a random UUID, and a tag already present on disk is never reused, so one session cannot silently overwrite another's record. Records from before UUID tags keep their 8-digit tag and are read unchanged.
- When the recovery location cannot be written (permissions, disk full) no snapshot exists. A failed write is retried 3 times, 5 s apart, and reported; the Space-switch prompt and the close dialog do not depend on it, which is why the close wording says a copy *may* be available.
- Until a restored note's vault save is confirmed, the text lives in the editor, in this session's protecting record and in the original record. If the save fails the usual "Couldn’t save changes" notice with Retry appears and both records stay. Neither record is flushed to durable storage (no `fsync`), so the original is the better of the two against sudden power loss only because it was written earlier, not because anything guarantees it.
- Several records of one note (different sessions) with different content are separate candidates, told apart by their capture time. At most one of them can be restored into the note's editor; the others are saved as new notes, so none is overwritten, and each stays until it is restored or discarded. Identical ones are offered once.
- Other Spaces' records are never touched (keys differ), and a renamed Space keeps its records when it has a profile id.

## Alternatives considered

- *Writing recovery into the vault (`.clutter/`)*: a second write path beside the Gate, visible to Sync and the watcher, and unavailable exactly when the vault is.
- *A fixed file per note*: a new session editing the same note would overwrite the crashed session's record.
- *Journalling every keystroke*: more I/O and a larger design for a bounded gain.
- *A new Rust writer*: the fs plugin's rename already gives atomic replacement for a file this small, and the existing capability covers it.

## Verification

Unit and integration tests cover the journal, classification, restore, discard, the app-wide status and the Tauri storage against a mocked fs plugin. The web runtime was exercised in a browser with forced failures and reloads. Hardening reviews after the above found and fixed: promotion of an interrupted `.tmp` rewrote the file before renaming it (an interruption or a failed rename could destroy the only copy of the newest snapshot; promotion was removed altogether), discovery could delete a `.tmp` that was merely unreadable or still being written (discovery is now read-only), cleanup of this session's own record was never retried after a failed removal, `snapshotNow` could report an older snapshot as protection for newer state, Restore applied a stale classification over a note that had changed or already held another record's restored text (and, once guarded, a Retry after a failed Restore would have saved a duplicate note), and Restore removed the original record before the vault save (it is now kept until then). Each has a regression test. A timing run that once returned no record was reproduced once in 10 further runs; in that run the editor itself never received the typed text, so there was no unsaved edit to snapshot: a limitation of the WebDriver typing in the harness, not of the journal.

Real-app evidence (isolated Tauri app with its own bundle identifier and a throwaway vault, driven over the embedded WebDriver, `SIGKILL` as the crash): a kill caught while a `.tmp` existed is recovered from the `.tmp` on relaunch (nothing renamed, rewritten or deleted), repeatedly, without duplicates, and the `.tmp` is removed only when the candidate is restored; a malformed `.tmp` beside a valid record is left alone; a process killed after Restore and before the vault save leaves the original and the protecting record, offered once after relaunch, and resolving it removes both; session tags in the file names are UUIDs; a Restore whose protecting write failed (recovery folder made unwritable) keeps the original, shows the failure, and a second Restore finishes it without creating a duplicate note; failed restoration keeps the record, shows the failure, protects a newer edit, and removes the record only after the later successful save; Discard confirm/cancel; Space switch with the new wording and return. **Not verified:** Force Quit and power loss, a signed/notarized build, and the page-hidden trigger from a real minimize (WebDriver minimize does not change `visibilityState`; the trigger was checked with a synthetic `visibilitychange`).
