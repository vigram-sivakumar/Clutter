# ADR-073: Multiple windows — preferences belong to Clutter, navigation belongs to windows

**Status:** Proposed (storage direction approved; this revision awaits final approval; nothing here is implemented). Amends [ADR-056](./056-spaces-are-application-level-and-switching-reopens-the-application.md) decision 1 (the registry's *storage and mutation*: it moves from `localStorage` to a single Rust owner with serialized, durable mutations — the swap ADR-056 itself reserved), decision 3 (one open `Application`; the watcher is one native slot; `activePath` is also "the open Space"), and its loss-fallback amendment (a shared transition for external loss); and [ADR-035](./035-persist-workspace-session-state.md) §1–2 (the *storage location* of the session snapshot; its runtime ownership is unchanged). Relies on, and does not change, [ADR-071](./071-cross-instance-note-moves-relocate-by-page-id.md) (several instances over one disk), [ADR-070](./070-welcome-content-is-provisioned-by-the-welcome-screen-entry-point.md), the Persistence Gate, `VaultSyncService`, and the macOS Trash path ([ADR-072](./072-delete-permanently-moves-the-item-to-the-macos-trash.md)). Adds no subsystem to the twelve, no Gate operation, no write path for notes.

## Principle

> One Clutter application, multiple independent windows, one globally shared configuration.
> Preferences belong to Clutter. Navigation belongs to individual windows.
> Windows coordinate and adapt to shared changes; they never prevent a user from performing an operation.
> There is one Space collection. Windows navigate independently but never hold separate or contradictory views of which Spaces exist.

A window is **not** a profile, a configuration, or a copy of the application. It is a view onto the application with its own navigation.

**Global:** the Space collection (the registry), Space configuration, application preferences, per-Space preferences.
**Per window:** its active Space (while that Space exists), active note, folders, tabs, navigation history, cursor, selection, current sidebar section, transient UI.
When a global Space change affects a window's current Space, that window adapts by the **existing** flows (Welcome, switch, removal fallback, rename, change location) — never by a second, window-specific mechanism.

**No cross-window restrictions.** Nothing in the normal experience is blocked and no confirmation or warning is added because another window has the same Space open. The only dialog that can appear is one that already exists for a genuine destructive conflict (§6.1, unsaved work that cannot be saved or protected and cannot be carried over). *Coordination* (for example, a second window waiting for the first to finish registering the same folder) preserves one shared collection; it is not a restriction on what the user may do.

## Context

`File → New Window` does not exist because Clutter is single-window by construction (`app_menu.rs`; ADR-056 decision 3). Investigation found:

- **One `Application` per webview.** Each Tauri window is a separate webview with its own JavaScript heap, so a second window necessarily has its own `Application`, `Vault`, `DocumentRegistry`, `VaultSyncService` and `Workspace`. A single in-process `Vault` shared by two windows would require moving Vault ownership into Rust (rejected below). The architecture already supports this shape: ADR-071 — "several Clutter instances can open one vault… the only thing they share is the disk."
- **Global preferences are already single-owner**: about 20 `clutter-*` keys plus `clutter-theme`, `clutter-sidebar-width`, `clutter-startup-behavior`, in the webview origin's `localStorage`, shared by every window. What is missing is *propagation*: nothing listens for `storage` events. Each is a scalar, so last write wins and every window converges on it; they do not need atomic read-modify-write.
- **The Space registry is not a scalar and is not safe for two writers.** `clutter.spaces.v1` is one blob (`{ paths, activePath, pendingRename? }`) loaded once into React state and rewritten whole. `localStorage` gives synchronous reads and writes and `storage` events give *notification*, but **neither gives atomic read-modify-write across webviews** (separate WebContent processes), and a lazily flushed write can be lost on a crash (ADR-056 already notes this). Two windows would silently overwrite each other, register the same folder twice, or disagree about the order of changes.
- **Four single-window assumptions**: the Rust watcher is one global slot and broadcasts (`emit`); the `main` label is hardcoded (capabilities, `AUTHORIZED_WINDOWS`, zoom, reveal, startup watchdog); menu events are broadcast; `activePath` doubles as "the Space this process has open".
- **Navigation state is in-memory per `Application`, except one key.** `Workspace` (active view, history stacks, sidebar chrome) is non-persisted (ADR-006/021). `WorkspaceSessionStore` persists a snapshot into the *Space's* `.clutter/workspace.json` (`workspaceSession`, ADR-035). There are no tabs yet; history stacks are not persisted. That key is one value per Space, so two windows overwrite each other, and a window's *Space* is part of its navigation, which a Space's own file cannot record.
- **Recovery discovery** (`RecoveryJournal.discover`) skips only its own session, so a second window opening would offer another live window's unsaved snapshots as crash recovery. Recovery records are keyed by Space (vault key) and live in the app data directory, outside the Space.
- **Today a Space change in one window would be read by another as loss.** Renaming a Space folder moves its root; another window's `verifyRoot()` finds the old path gone, seals its filesystem and runs its own lost-Space fallback (ADR-056 amendment).
- **The existing removal flow** (`removeActiveSpace`, ADR-056): the removing window takes the first of `fallbackCandidates(active)` (other registered Spaces whose folders probe as available, in registry order starting after the removed one, wrapping) that it can activate and prepare; the removed entry is forgotten only once that replacement has **opened** (`confirmOpened`); if none opens, the Application is closed (flushing), the entry removed, `{ paths, activePath: null }` stored, and the Welcome dialog takes over. A failed close removes nothing. The Welcome dialog also provisions the first Space (ADR-070): a Space is registered only after its welcome content is installed and verified. This ADR reuses that flow for every window and adds no other fallback.
- **Facts used for rename.** `renameActiveSpaceFolder` already records `pendingRename` *before* touching the folder, quiesces (`quiesceForRename`: drain, flush, seal only when provably clean, otherwise restore admission), claims the destination exclusively in Rust (`rename_space_folder`, non-recursive `create_dir`, no overwrite), verifies the Space id at the new path, and migrates path-derived ids once (`migrateRenamedRootState`). `Application.handleRootLost` already flushes the recovery journal before discarding. There is no Space-level archive today; archive exists for pages and folders (ADR-026), kept consistent across instances by `VaultSyncService`.

## Decision

### 1. Three kinds of state, three owners — never mixed

| Kind | Owner and storage | Shared by | Examples |
|---|---|---|---|
| **Application preferences** (scalar) | The origin's `localStorage` (one store; no per-window copy) | Every window, live | theme, header separator, editor/typography, date/week/format, list limits, startup behaviour, **sidebar width and sidebar visibility**, **view zoom (text size)**, every app-level setting |
| **Space collection** (structured, concurrently written) | The **Space Coordination Store** (§2), one Rust owner per application process, serialized and durable | Every window, live | the registry (list of Spaces, last-opened Space, pending rename), Space change notices |
| **Space preferences** | The Space's own `.clutter/*` (unchanged) | Every window that has that Space open, live | Space profile/avatar, collection view config, tasks view config, tag expansion, fold state, references display, preferred templates, default note folder |
| **Window session (navigation)** | Per-window records, §3 | Only that window | which Space it shows, active view, navigation history, **currently selected sidebar section (tab)**, folder/section expansion, (future) tabs, selection, cursor, window frame |

A setting is an application preference if changing it should change *every* window; it is window state if it describes *where this window is*. Transient UI (dialogs, popovers, hover, drag, focus, selection, the narrow-window sidebar override) is neither: it is component-local and never persisted (unchanged).

### 2. Shared state: scalar preferences propagate; the Space collection is serialized and durable

**Scalar preferences.**
- **No new store.** The value stays in `localStorage`; `storage` events are only a *change notification* that invalidates caches and calls each module's existing listeners. No state travels in the event and none is duplicated (not IPC synchronization). Notification is not atomicity, which is acceptable here because a scalar needs only last-write-wins and every window re-reads the stored value.
- **One shared helper** gives each `subscribe*` the `storage` hook for its own key (mechanical edit; no preference-factory refactor). `useTheme` drops its cached `current` and re-applies `data-theme`. Modules mirroring a preference onto the DOM (`installMarkdownItalicFontSync`, `installPreserveBulletStyleSync`) re-sync through their existing subscription.
- **Sidebar visibility** becomes an application preference (a new key). `Workspace` stays non-persisted and storage-free (ADR-006/021): the Composition Root/`AppShell` bridges the preference to `workspace.setSidebarVisible`, the same place that already carries visibility across a Space switch ("the user's, not the Space's"). It is removed from the per-window session record. **View zoom** becomes an application preference too (applied to every window, persisted; it is not persisted today). The narrow-window sidebar override stays transient and per window.
- **If `storage` events do not cross webviews** (verified in Phase 0, E12): the Coordination Store's notification channel (below) also carries the changed *key name* (never the value), and windows re-read the key.

**The Space collection — the Space Coordination Store (Rust, `src-tauri/src/space_coordination.rs`, Platform layer).** One native owner; windows are clients.

1. **One owner.** There is exactly **one** store per Clutter application process, held in Tauri managed state and shared by every window of that process. Several independent Clutter *processes* sharing one registry are **outside this ADR's scope** (ADR-071's multiple instances concern the Vault on disk, not the registry); the design does not try to coordinate them, and the atomic replacement in point 3 only guarantees the file is never torn if one ever happens.
2. **Serialized mutations — intents, not documents.** All registry changes go through the store; the webview can neither write the file nor submit a whole registry. The store holds the authoritative state `{ rev, registry, notices[] }` behind **one mutex**. A mutation command carries an **intent** and the *identity* it was decided about, never a snapshot:
   `add_space(path)`, `remove_space(path, spaceId, fallback)`, `replace_space(from, to, spaceId)` (change location), `begin_rename` / `complete_rename`, `set_last_opened(path)`, `publish_lost(path, fallback)`, `legacy_merge(…)`. Every intent also carries an `opId` (point 3). Under the mutex the store (a) takes the **latest** state, (b) checks the intent's **preconditions** against it, (c) validates the **invariants** (below), (d) builds the next state, (e) persists it (point 3), and only then (f) publishes it and acknowledges. There is no revision-compare-and-retry protocol and no replay: `rev` is a monotonic counter the store increments, used for ordering and change detection, never as a caller-supplied precondition.
   - **Invariants** validated before every commit: canonical paths are unique (R2); every entry has a non-empty canonical path; `lastOpened`, if set, is a registered path; `pendingRename`, if set, names a registered entry; a `removed`/`lost` notice's `fallback` is `null` or a registered path other than `from`; the document's schema version is known. A commit that would violate one is refused whole, and nothing changes.
   - **The mutation logic moves into Rust**, ported from the pure functions in `spaceRegistry.ts` (`withActiveSpace`, `withReplacedSpace`, `withoutSpace`, `withoutActiveSpace`, `withRenamedActiveSpace`). Two implementations of one capability would violate "one owner per capability", so the TypeScript mutators are retired; `spaceRegistry.ts` keeps types and read-only selectors (`fallbackCandidates`, display names). The existing registry unit tests are extracted into shared fixture vectors and run against the Rust implementation (they become the port's conformance suite).
   - **Stale operations are re-evaluated, never replayed (§6.6).** Every non-`add` intent names its target by *(path, Space id)*. It applies only if that entry **currently exists with that identity**; otherwise the store answers `Stale { current, notice }` and **commits nothing**. The window then re-resolves against the returned current state and the notice chain and issues a *new* intent if one still makes sense. Only `add_space` creates an entry, only as a user's explicit action, and it is idempotent by canonical path; `replace_space`, `begin_rename`, `complete_rename` and `set_last_opened` can **never** recreate an entry that another operation removed. A removal's `fallback` is re-validated against the current registry; if it has been removed meanwhile the store answers `Stale` and the removing window re-chooses (this is the removal operation deciding, §6.5).
3. **Durable commits.** A mutation is acknowledged, and its state published to any reader, **only after every required flush has been confirmed**. Nothing is "acknowledged but unconfirmed".
   - **Required flushes.** The store requires the atomic writer's `Durability::Confirmed` for *every* write it makes under `<app data>/spaces/`: the temporary file flushed with `F_FULLFSYNC`, the `rename(2)`, and the directory flushed with `F_FULLFSYNC`. A volume that rejects `F_FULLFSYNC` (the writer's `Unconfirmed`/fallback-to-`fsync` outcomes) does **not** satisfy the requirement, and neither does any failed flush. At launch the store runs a capability probe on its directory with the same writer; if the required flushes are unsupported it starts **read-only** (`StoreUnavailable`): reads serve what is on disk, every mutation is refused with the existing failure notice, and nothing is ever acknowledged without confirmation. (The app data directory is on the system volume, so this is expected never to occur; it is specified so the failure mode is explicit rather than silent.)
   - **Two failure classes, decided by whether the replacement took effect.**
     - **Pre-replacement failure** (the temporary file could not be written or flushed, or the `rename` did not take effect): the target is provably unchanged. The commit is refused with an error, the temporary file is removed, the in-memory state is not advanced, no notification is emitted, and the caller may retry with a new intent.
     - **Post-replacement indeterminate outcome** (the `rename` took effect — or the writer cannot establish that it did not — but the directory flush failed, was unconfirmed, or the process lost the result): the new file may or may not survive a power loss. The store does **not** acknowledge success and does **not** publish the new state. It returns `Indeterminate { opId }` and **reconciles under the mutex before serving any other mutation**: it re-inspects the target with the writer's `inspect` primitive (is the target still revision *N*, or revision *N+1* with the expected checksum?) and retries the directory flush with `confirm_durability` a bounded number of times (proposed 3 attempts over ≈ 2 s). If the inspection shows revision *N*, the commit is reclassified as a pre-replacement failure (nothing happened). If it shows *N+1* and the flush is then **confirmed**, the commit is promoted: the snapshot is published, `space-coordination:changed` is emitted, and the operation's recorded outcome becomes `Committed`. If it cannot be confirmed, the store enters **degraded** state: it keeps serving the last confirmed snapshot, refuses further mutations (`StoreDegraded`), and keeps retrying the confirmation on a slow timer until it succeeds or the process exits. The next launch adopts whatever the disk holds (startup recovery below), so an `Indeterminate` operation may turn out to have been committed.
     - **The caller's contract for `Indeterminate`.** Every intent carries an **`opId`** (a UUID). The document records the most recent 256 `{opId, rev}` pairs, and `operation_status(opId)` distinguishes **four** answers: **`Committed(rev)`** (confirmed committed), **`NotCommitted`** (the store saw the operation and *confirmed* it did not commit), **`Indeterminate`** (the store is still reconciling it, or is degraded and cannot yet confirm), and **`UnknownOpId`** (the store has no record of that id — never submitted, or aged out of the 256-entry window). An intent retried with an `opId` that has already committed returns that result and applies nothing again. **An `Indeterminate` operation is never blindly repeated**: the window waits for `Committed` or `NotCommitted` (via `operation_status` or the reconciliation notification) and only then decides, by issuing a *new* intent with a new `opId` if one still applies; an intent whose target no longer matches is answered `Stale` as usual. `UnknownOpId` after a restart means the operation did not commit (an unacknowledged operation that landed is in the recorded list), but a caller treats it only as "not recorded" and re-evaluates against the current registry rather than assuming either outcome.
   - **Commit point and acknowledgement.** The commit point of revision *N+1* is the **confirmed replacement of `registry.json`** (rename done, file and directory flushes confirmed). The acknowledgement, the published snapshot, the notification and `operation_status = Committed` all happen strictly after it. The bytes that exist on disk before that point are *not* a committed snapshot, and no window ever reads the files: windows read only the in-memory snapshot, which advances only at the commit point. Revisions published to windows are therefore consecutive (*N → N+1*) with no gap, and an unpublished *N+1* that reached the disk is invisible until reconciliation or the next launch confirms it.
   - **Files and the previous generation (`registry.prev.json`).**
     - **Contents.** `registry.prev.json` is **byte-for-byte the last confirmed committed document**: when `registry.json` holds revision *N* (confirmed), `prev` holds revision *N* or *N−1*, never anything newer or unconfirmed. It is written only from bytes the store already confirmed, never from an in-flight document.
     - **Write order** for revision *N+1* (all by the same writer, all requiring `Confirmed`): **(1)** replace `registry.prev.json` with the bytes of confirmed revision *N* — after this, `prev.rev = main.rev = N`; **(2)** replace `registry.json` with revision *N+1*. Step 1 is not the commit point; step 2 is. A failure in step 1 (including an indeterminate directory flush of `prev`, which holds already-confirmed bytes anyway) refuses the whole commit as a pre-replacement failure of the *mutation*: `registry.json` is untouched and the store state does not advance.
     - **Invariant.** At every instant `prev.rev ≤ main.rev ≤ prev.rev + 1`; `prev` is never ahead of `main`; neither is ever a partial write (the writer replaces atomically).
     - **Format.** `{ schema, rev, registry, notices, ops, legacy, checksum }`, `checksum` = SHA-256 of the canonical serialization of the other fields. An unknown future `schema` is refused read-write rather than reinterpreted.
   - **Startup recovery** (before any window is served; nothing is served until it completes):
     1. Remove stray temporary files the writer's naming scheme identifies (they never replaced anything).
     2. Parse and validate (`schema`, `checksum`, invariants) `registry.json` and `registry.prev.json` independently.
     3. Adopt as follows:

        | `main` | `prev` | Action |
        |---|---|---|
        | valid | valid | adopt the **higher `rev`** (normally `main`; an unpublished-but-landed *N+1* is adopted, and its `opId` is then `Committed`); a `prev` ahead of `main` cannot occur by the invariant and, if seen, is adopted with a diagnostic |
        | valid | invalid or missing | adopt `main`; `prev` is regenerated by the normalization step below |
        | invalid | valid | adopt `prev`; move `main` to `registry.corrupt-<time>.json` (never deleted); diagnostic and a startup notice: the most recent Space change may be missing (this is media/filesystem damage, the only case in which an *acknowledged* commit can be lost, and at most the last one) |
        | invalid | invalid | move both aside; report `Unreadable`; the first window re-seeds from the legacy baseline and the legacy blob (point 7); recovery records are unaffected |
        | unknown `schema` | — | refuse read-write; serve nothing from it; report the version mismatch |

     4. **Normalize** the adopted document: write `prev` ← the adopted bytes and, if `main` was invalid, missing or older than the adopted document, `main` ← the adopted bytes (each by the writer, requiring `Confirmed`), and confirm `main`'s durability with `confirm_durability`. Only then is the snapshot published to windows. If normalization cannot be confirmed the store starts read-only (as for an unsupported volume).
   - **Reads never wait on a write.** A committed snapshot (`Arc`) is swapped in only at the commit point. Mutations run on a blocking pool, never on the async runtime or the UI thread; a slow disk delays other *mutations*, never reads.
4. **Claims** (in-memory, same-process window coordination; exclusive; not persisted). `claim_space(canonicalPath)` → `Claimed { claimId, fence, expiresAt }` or `Held { holderWindow }`. A claim coordinates **provisioning side effects** on an empty folder (Welcome content, ADR-067/070) — the filesystem writes themselves, not only the later registry commit.
   - **The lease and the fence.** A claim is a lease (proposed 30 s on a monotonic clock) that the holder renews by heartbeat at the start of every provisioning step and at least every 5 s. Every claim has a strictly increasing **fence** token (per store, never reused). The registry intent that registers the Space (`add_space`) must present the current `claimId` and `fence`; a revoked or superseded one is refused (`ClaimRevoked`), so a stale holder can never register or create a second entry.
   - **Destroyed windows.** Rust observes the window's destroy event and releases every claim it held; the first waiter takes the claim over. A destroyed webview runs no further provisioning code (only an already-issued native write could still land; see the side-effect rules).
   - **Hung or silent holders.** A lease that is not renewed expires; the next waiter takes the claim over with a **new fence**, and the previous holder is told `ClaimRevoked` at its next heartbeat or step.
   - **Side-effect safety — the lease alone is not relied on.** A holder that is merely *slow* (not destroyed) can resume after a takeover, so every filesystem effect of provisioning is made safe against a late or duplicate runner at four independent layers:
     1. **Step permits.** The provisioning service asks the store for a permit (`claim_step(claimId, fence)`) before each ledger-advancing step and aborts on `ClaimRevoked`. This bounds a late runner to the one step already in flight; it cannot be made atomic with the write that follows it (check-then-act), so it is not the safety argument.
     2. **Create-only, deterministic effects.** Every content write is create-only (`createFromSource`, an exclusive directory create, a no-clobber binary write; ADR-067) with bytes fixed by the shipped manifest, so two runners can only ever create the **same bytes at the same path**; a late runner's write finds the entry present and is refused, never overwriting. (The Space has never been shown, so no user edit or deletion can be in the way: the ledger's `shown` flag, ADR-067 G6.)
     3. **Fenced ledger.** The Space's `welcomeInstall` ledger records the runner's `claimId`/`fence` (a backward-compatible optional field; absent in older ledgers, read as "no fence"). Every ledger advance is a guarded merge that is refused when the stored fence is greater than the writer's, and `complete`/`abandoned` never regress. A late runner therefore can neither double-increment `attempts` nor move a completed install backwards.
     4. **The taker verifies the final filesystem state before it registers.** The taker resumes from the ledger and **re-verifies the installed content** (the existing "installed and verified" gate) immediately before `add_space`, so a duplicate or half-applied late write is detected and finished by create-only completion rather than assumed away.
   - **Explicit limitation.** Fencing and leases **cannot cancel a filesystem operation that is already running** (a native write issued before the takeover completes regardless). The design therefore never relies on cancellation: it relies on layers 2–4 (create-only deterministic effects, the fenced ledger, and the taker's verification of the *final* on-disk state before registration).
   - **Provisioning is resumable, not merely retryable.** Interruption at any step (crash, destruction, lease expiry, a failed write) leaves the ledger at `installing`; the next holder continues from the ledger, never reinstalls or overwrites, and ADR-067's "at most the in-flight entry may be missing" bound is unchanged. Provisioning is idempotent by construction (create-only plus the ledger).
   - **The claim is not the safety net for duplicates.** Duplicate registration is prevented by the uniqueness invariant in point 2 even if a claim were lost; the claim and the layers above keep the *filesystem effects* single.
5. **Notifications are invalidation signals only.** After each commit point Rust emits `space-coordination:changed { rev }` to every window. It carries no state and a window never acts on it directly: it **reconciles** (reads the authoritative confirmed snapshot, applies notices with `rev` greater than the last it applied, refreshes its list). Delivery may be dropped, delayed, duplicated or reordered without harm, because reconciliation is also triggered by:
   - **window startup** (before it shows a Space or Welcome);
   - **focus, visibility and system-resume** events (before the window becomes interactive again);
   - **before every registry-dependent operation** (open, switch, remove, rename, relocate, add, opening the Space selector) — and every mutation response returns the fresh confirmed state, so a mutating window reconciles by construction;
   - a **bounded backstop**: while a window is visible it reconciles at least every **30 s** (proposed). A hidden window does not poll; it reconciles on becoming visible;
   - **reconciliation after an indeterminate commit** (point 3): promotion emits the same notification, and a window waiting on `operation_status` re-checks on its backstop.
   A dropped notification can therefore delay convergence by at most the backstop interval for a visible window, and cannot leave any window permanently inconsistent. A reconciliation with nothing new is a cheap in-memory read. Notifications are only ever emitted for confirmed snapshots.
6. **Recovery is independent of the registry** (full rule in §6.5). The store neither reads nor writes recovery records, and no registry mutation, registry corruption or startup `Unreadable` can delete, hide or reinterpret one.
7. **Migration and downgrade.** The legacy blob is `clutter.spaces.v1`; the store cannot read the webview's `localStorage`, so the first window of every launch passes the raw text to `coordination_reconcile_legacy(blob)` (idempotent, serialized under the mutex).
   - **Persisted original baseline.** The first import writes **`<app data>/spaces/legacy-import.json`**, create-only and never modified afterwards (so even a total loss of both registry generations leaves it): `{ schema, importedAt, rawBlob, blobDigest, baseline: [canonical paths in blob order, with the original strings] }`. It is written and confirmed *before* the first registry document, so a crash between the two leaves the baseline in place and the next launch imports **from the baseline**, not from whatever the blob has become.
   - **The legacy blob is preserved.** The new version never writes, rewrites or deletes `clutter.spaces.v1`; it stays byte-identical. The import reads it exactly as `loadSpaceRegistry` does today (canonicalization, malformed entries dropped).
   - **What an older version does afterwards.** An older build knows nothing of the store: it reads and writes the blob as it was at the moment of upgrade — Spaces added, removed, renamed or reordered in the new version since are **not** visible to it, and its own changes are **not** visible to the new version while it runs. There is no dual writing; a second writer is exactly the problem this ADR removes. Nothing is lost or corrupted either way.
   - **Distinguishing old-build additions from Spaces the new version removed.** The registry document carries `legacy.consumed`: the set of canonical paths that have **ever been accounted for**, initialized to the baseline and only ever **growing**. On each launch, if the blob's digest differs from the last merged digest (`legacy.mergedDigest`), the store computes `additions = canonical(paths(blob)) − legacy.consumed`. Because every baseline Space is in `consumed` — whether it is still registered, was removed by the new version, or was renamed — **a baseline Space removed by the new version can never be an addition and is never resurrected**, whatever the blob now says. A Space the new version added never appears in the blob (the new version does not write it), so it can never come back through the merge either.
   - **What the merge does.** In **one** durable mutation (`legacy_merge`): each addition whose folder still exists and which is not already registered is registered by the normal `add_space` rules (uniqueness included); if an addition's folder carries the **Space id** of a registered entry whose own folder is missing (the old build renamed or moved it), that entry is **replaced** instead of duplicated; every addition is added to `consumed` *whether or not it was registered* (so a Space the user later removes cannot return on a later merge) and `mergedDigest` is updated. Removals, renames and reordering made in the old build are **ignored** (nothing destructive can result; the user can repeat them). The merge is idempotent: re-running it for the same digest changes nothing.
   - **Total loss of both generations.** The baseline file survives. The first window re-seeds the registry from the *current* blob through the same import (`consumed` re-initialized from the baseline), and shows the startup notice. Removals made by the new version cannot be recovered in that case (the data recording them is gone, and this is the only situation in which a removed baseline Space can reappear); the quarantined files are kept for manual inspection.
   - **Rollback of the store itself.** An older build that ignores `<app data>/spaces/` leaves it untouched.
8. **Window registry (liveness).** A small in-memory module (introduced in Phase 1, consulted by the store) keeps `windowLabel → { openRoot, pinnedNoticeIds }`, updated by the window's own commands and removed when the window is destroyed. It is used only for coordination: who must acknowledge a rename (§6.2), which notices are pinned against pruning (§6.1), which recovery sessions and which window records are live (§3, §5), and claim release. It is never used to refuse a user operation.

This is not IPC state synchronization: there is **one owner** of the shared collection (Rust), windows hold no copy they must reconcile beyond re-reading it, the event carries no state, and there is no distributed protocol. It is the "native store" ADR-056 listed as a contained later swap behind `loadSpaceRegistry`/`saveSpaceRegistry`.

### 3. Window session: one record per window, owned by that window alone

One `localStorage` key **per window**, `clutter.window.<windowId>.v1` (a window is the only writer of its own key, so no two windows ever read-modify-write the same value — a single shared blob would reintroduce the lost-update hazard §2 removes; windows are enumerated by key prefix):

```
{ version: 1,
  window: {
      spacePath: string | null,        // this window's own Space
      spaceId:   string | null,        // that Space's stable id, for relocation resolution (§6)
      session: <active view, currently selected sidebar section (tab), collapsed sections, expanded folders, daily-notes expansion>,
      frame: { x, y, width, height } | null,
      state: 'open' | 'closed',
      updatedAt, closedAt? } }
```

- `windowId` is a UUID owned by the window's JavaScript (from the URL it was created with, or generated); Rust labels windows `w-<windowId>` and never reads the records.
- **Each live window writes only its own record**, by replacing its own key, debounced with the existing 400 ms. A window cannot overwrite another window's session or any preference, and no navigation is written into a Space folder. (The one exception: a Space change may rewrite the *dead* — closed or crashed, per the window registry — records of the affected Space, §6; no live window writes them.)
- **Ownership of runtime state is unchanged.** `Workspace` and `DailyNotesSidebarState` stay the runtime owners with no storage dependency. Only the persistence boundary changes: `WorkspaceSessionStore` keeps its seed/attach/flush lifecycle and observer logic but writes through a storage adapter to the window's record. Sidebar visibility is no longer part of it (§2).
- **The per-Space `workspaceSession` key stops being written.** It is read once, read-only, as a migration seed when a Space has no window record. Clutter never deletes it.

**Lifecycle of a record:**

| Event | Record |
|---|---|
| Window created / navigates / changes Space | created or updated, `state: 'open'` |
| Window **manually closed** while other windows remain and the app is not quitting | `state: 'closed'`, `closedAt` set; flushed first. **Not restored at the next launch** |
| **Quit**, or the **last** window closed | stays `'open'` — restored at next launch |
| Crash / kill | stays `'open'` — restored at next launch |
| Next launch | the launch window adopts the most recently updated `'open'` record; every other `'open'` record is recreated as a window (own Space, own frame, own session) |
| Retention | closed records are kept for a **bounded** number/age (proposed: 20 records or 30 days; always the latest closed one per Space), pruned at launch and on write |

**Restore follows startup behaviour.** A restored window reopens its own Space; its *view* follows `startupBehavior` exactly as now (`last-opened-note` restores the record's `activeView`; `todays-note` opens Today's note; its current sidebar section is restored). A single-window user sees no change. A **new window** (File → New Window) opens the last-opened Space with `startupBehavior`, using the most recently updated record (open or closed) of that Space for `last-opened-note`; it never copies another live window's session. **Reopen Closed Window is not part of v1**; the retained closed records are only a bounded history that also serves `last-opened-note`.

**Durability.** `localStorage` may flush lazily; losing the last moment of navigation after a crash is acceptable (it is not user content). The adapter is behind an interface so the records can move to the Coordination Store later.

### 4. Window navigation independence

Active view and history (ADR-027), the currently selected sidebar section, folder/section expansion, selection, editor cursor, `DocumentRegistry` and sessions, dialogs: all in memory per `Application`, built for that window's Space. Windows may show different Spaces or the same Space. Sidebar *width*, *default tab* and *visibility* are global (§2); which section is currently selected is per window.

### 5. Native layer: windows are labelled, watchers and menus are per window

- **Window creation** in Rust from the menu handler (`WebviewWindowBuilder::from_config` on the `main` template; label `w-<windowId>`; created hidden; cascaded from the focused window). Capability `windows: ["main", "w-*"]`; `AUTHORIZED_WINDOWS` becomes a pattern check.
- **Reveal and startup recovery per window.** `frontend_ready` reveals the calling window. The watchdog/retry dialog stays for the launch window only; a secondary window that fails to start is closed with a notice.
- **Watcher per window.** The single `VaultWatcherState` slot becomes a map keyed by window label, with the existing token-ownership rule applied per label. Events go out with `emit_to` the owning window; the frontend listens window-scoped. `SelfWriteRegistry` stays per `Application`, so another window's save is an external change here — the ADR-071 cross-instance path.
- **Menu routing to the focused window.** File/Go/Settings/Copy-Link events go to the focused window only; `set_copy_page_link_enabled` follows the focused window. **File → New Window** uses **⌥⌘N** (⌘N and ⇧⌘N are taken); the native menu owns it, and the Keyboard shortcuts dialog (`shortcuts.ts`, `owner: 'native'`) and the `app_menu.rs` accelerator test are updated together.
- **ADR-056 decision 3 amended:** "at most one `Application` is ever open" becomes "at most one per window"; the prepare/commit switch is unchanged *within* a window. `SpaceLifecycleGuard` stays per window and only serializes that window's own Space operations.
- **Recovery.** A live window's recovery session is excluded from another window's `discover()`; records of dead sessions are discovered as today.

### 6. One shared Space collection; Space changes across windows

#### 6.0 The collection is global; what each change does to every window

Every window shows the same list, read from the Coordination Store and refreshed on `space-coordination:changed`. The only tolerated difference is transient: a window that cannot yet leave a removed or lost Space (§6.5) until its work is safe.

| # | Change (made in any window) | Windows whose current Space is affected | Windows on other Spaces / in Welcome |
|---|---|---|---|
| 1 | **Remove the current Space** | Follow the existing removal flow to the **one fallback chosen by the removing window and shared in the notice** (§6.5) | Update the list only |
| 2 | **Remove the last remaining Space** | Notice carries *no fallback*: each window closes its `Application` as the removing window does and shows the existing **Welcome** dialog | A window already in Welcome stays there |
| 3 | **Add a Space when none exist** | — | Every window in Welcome **leaves it and opens the new Space** by the normal open path (the Space is registered only after the adding window finished provisioning, ADR-070, so nothing is installed twice) |
| 4 | **Add a Space when others exist** | — | The new Space appears in every list; no window changes its active Space; each user navigates to it independently |
| 5 | **Rename a Space** | Re-root with id rebase (§6.2); navigation and unsaved work kept | List, names and references (selector, breadcrumbs, window title, the Settings page keyed by the Space's path) update |
| 6 | **Relocate a Space** (Change location) | Reopen at the new location (§6.3); navigation and unsaved work kept | List updates |
| 7 | **Folder moved or deleted outside Clutter** | Follow the **first detecting window's published transition** to one shared fallback (§6.5) | Update the list only |

#### 6.1 Mechanism (shared by every case)

- **Space change notices** live in the same Coordination Store document (bounded: proposed 50 entries / 90 days, except notices a window still has a pending transition for, which that window pins through the window registry, §2.8): `{ rev, kind: 'added' | 'renaming' | 'renamed' | 'moved' | 'removed' | 'lost', from?, to?, fallback?, spaceId, originWindowId, at }`. A notice is committed **in the same durable mutation as the registry change it describes** (§2, points 2–3) and its `rev` is its order. It is a notification and relocation history, not a second source of truth: the registry holds the resulting state. A window that missed notices (opened later, restored from an old record) reconciles from the registry plus the notice chain `from → to`.
- **Adapt rule.** A window acts on a notice only if its *current* Space path equals `from` (a Welcome window acts on `added` when the collection was empty). Applying is idempotent (each window remembers the highest `rev` it applied per path) and ordered by `rev`. A window's handling is queued behind its own `SpaceLifecycleGuard` and the existing stale-ticket supersession in `AppShell`, so it never overlaps that window's own operations. A notice whose `from` the window has already left is stale and ignored.
- **Chains.** If a fallback is itself removed or lost before a window reaches it, the window follows the notice chain (`S → F`, then `F → G`) instead of recomputing anything.
- **Verify before adapting** (rename and relocate). The new location is accepted only if the Space id read at `to` equals the notice's `spaceId` and `from` no longer holds it (the check `reconcilePendingRename` already uses). Anything unconfirmed falls into the lost flow (§6.5), never a guess.
- **Re-rooting a window (rename and relocate).** The window builds a fresh `Application` at `to` through the existing prepare/commit while its old one is clean-and-sealed or flushed (§6.2), and carries its navigation across by a pure **id rebase**: the same prefix rewrite `migrateRenamedRootState` applies to persisted state (an id is path-derived only if it starts with `<oldRoot>/`; stable ids, the Space id, names, tags and relative paths are untouched), applied to the window's in-memory navigation snapshot — active view, history stacks, expanded folders, open note ids. The snapshot is taken at quiesce time, before the rename's filesystem events can reach Sync. Editor cursor and selection are restored best-effort when the note is the same and unchanged.
- **Unsaved work is never dropped and does not need a question in the ordinary case.** A window re-rooting or falling back first flushes. Anything it could not flush is protected as a recovery snapshot (`protectAll`) and **carried over automatically** to the same note in the new Application when the note's content on disk still matches the snapshot's recorded base (the journal fingerprints the vault base). Only when the disk content has genuinely diverged does the existing recovery prompt ask — the one real destructive conflict.

#### 6.2 Rename

Initiated in window A (`renameActiveSpaceFolder`, or the inactive-rename path), with window B on the same Space:

1. A records `pendingRename` and appends a `renaming` notice (one commit).
2. B, seeing `renaming` for its Space, runs the existing `quiesceForRename()`: drains and flushes, seals only when provably clean, otherwise restores admission and leaves its unsaved work to the snapshot-and-carry-over path. B acknowledges (through the window registry).
3. A waits a bounded **2 seconds** for acknowledgements from the windows the registry lists on that root, **then proceeds regardless** — a slow or hung window never blocks the user, and there is no dialog.
4. The rename runs (existing exclusive claim in Rust). A commits `renamed` together with the registry move, and migrates persisted Space state once (existing).
5. B verifies (§6.1), re-roots to the new path with the id rebase, and shows the new name immediately. Active view, history, expansion and open notes survive; unsaved work is carried over.
6. Each live window rewrites its own record on re-root; A rewrites only dead windows' records for that Space (§3).

#### 6.3 Move

Clutter has no in-app move of an *open* Space folder. A Space's folder moves in two ways:

- **Clutter-initiated relocation** — the existing *Change location* / replace-entry flow (`withReplacedSpace`), which a user runs on a Space whose folder is missing. It commits `moved` with the registry replacement. Every window whose Space is that missing path (already lost, or showing Welcome) verifies the Space id at the new location and **reopens it there automatically**, carrying navigation and unsaved work as in §6.1. Windows on other Spaces only refresh their list.
- **Moved outside Clutter (Finder, another tool)** — is *external loss* (§6.5); ADR-056's "no relocation detection" stands. A later *Change location* in any window brings every affected window to the new place through `moved`. This ADR adds no disk-wide relocation search.

Moves of **notes and folders inside a Space** are not Space operations: they remain with `VaultSyncService` and cross-instance relocation by page id (ADR-071 and the folder-move work), unchanged.

#### 6.4 Archive

There is no Space-level archive today. Page and folder archive is Vault state and already propagates through the filesystem: window A archives, window B's watcher feeds `VaultSyncService`, B's Vault, selectors and views reflect the archived state, and B's dirty sessions are protected by the existing external-change handling (ADR-026/071; archive metadata repair writes are guarded). **This ADR changes nothing there.** A future Space-level archived state would be Coordination Store state and follow §6.1.

#### 6.5 Remove, and external loss: one shared transition

Removal and external loss use **one principle and one transition shape**: the operation (or the first detector) decides the fallback once, publishes it in a notice, and every affected window follows that decision by the existing flow. No window calculates a fallback for a change another window has already published.

**Remove from Clutter** (forget the registry entry; the folder is never touched):

1. The removing window (A) runs `removeActiveSpace` / `removeSpace` exactly as today: it takes the first available fallback candidate it can open (or none), and forgets the entry only once the replacement has opened (or, with none, after closing and flushing).
2. At that point, A sends `remove_space(S, spaceId, F)`; the store commits the registry change and one `removed` notice carrying `{ from: S, fallback: F | null }` in one durable mutation — **F is the Space A's flow actually opened**, or `null` when none opened. A does **not** wait for any other window. If F has been removed meanwhile, or S already changed, the store answers `Stale` and commits nothing; A re-decides from the current registry (following the notice chain if its own Space F was itself removed) and issues a new intent; it never resubmits the old one.
3. Every other window whose current Space is S follows the notice with the **same transitions the existing flow uses**:
   - `F` is a path: the window switches to F through the existing switch (flush, prepare, commit). It enters F by the normal open rules (`startupBehavior`; global sidebar preferences) and keeps **its own** navigation from then on; it does not inherit A's view.
   - `F` is `null`: the window closes its `Application` (flushing, as A's `closeApplication` does) and shows the existing Welcome dialog.
4. A window that fails to **open F** keeps the existing failed-switch behaviour (`openFailed`: it stays on what it had, the failure is reported). If F is unusable for that reason (for example unsupported volume), the window publishes a `lost`-style notice for F (below), so the chain continues from the shared record rather than from a private search.

**Folder moved or deleted outside Clutter** (no initiator):

1. A window detects it through the existing `verifyRoot` (focus/visibility check or watcher hint), seals its filesystem and, **before opening anything**, resolves the fallback once with the existing `fallbackCandidates(lost)` (registry order; folders that probe as available; never the lost one).
2. It publishes `lost { from: L, fallback: F | null }` with a **commit-if-absent for the current loss episode of L**: the first commit wins; a window that loses the race reads the winner's notice and uses its fallback instead of its own. An *episode* ends when any window successfully opens L again or the app relaunches, so a loss in an earlier launch never decides a new one.
3. Every window on L — the detector included — then follows that one notice by the removal transitions above (switch to F, or Welcome for `null`). The registry entry for L is left as stored (ADR-056: a lost Space's entry is never edited by loss).
4. Startup is the same: windows restored onto a missing Space follow the first publisher.

**Unsaved work and the automatic retry (both cases).** Before transitioning, a window flushes; whatever it cannot flush is protected as a recovery snapshot through the existing journal (`protectAll`). The transition proceeds as soon as every dirty session is **either saved or protected by a recovery record that was written successfully**.
- If neither is yet true, the window **stays on its current Space with its work intact**, records the pending transition (the notice id, so the **original shared fallback** is used), and **retries the same transition automatically**: it is triggered by the existing save-success and recovery-write completions of that window's sessions, with a low-frequency re-check as a backstop. The user never has to leave the Space to complete an already-requested removal.
- The retry **never recalculates a fallback**. It follows the pinned notice and, if that fallback has since been removed or lost, the notice chain (§6.1).
- A window waiting to retry is the only place a window shows a Space absent from the collection; it is loss-free and ends on its own.
- **Recovery** (requirements: unsaved content is durably preserved, removal never waits indefinitely for other windows, and records are discoverable independently of registry membership). Recovery records live in `<app data>/recovery/<vault key>/` (`recovery_store.rs`, which already writes each record whole-or-nothing with `sync_all` on the file and its directory) and are owned by the recovery store, **not** by the registry or the Coordination Store.
  - **Each window protects its own work, on its own timeline.** There is no cross-window barrier. The removing window A mutates the registry as soon as **A's own** work is safe (A's flow: switch away, forget once the replacement opened). It does not wait for any other window, and a hung or unflushable window can never delay or block a removal. Every other affected window, upon reconciling the `removed`/`lost` notice, flushes and protects **its own** dirty sessions and transitions only after **its own** content is saved or its recovery record write has **returned success**; if that is not yet true it stays and retries as above. A window's dirty work is protected while it waits, because the recovery journal writes records for dirty sessions independently of registry membership: the journal never consults the registry, and a record's validity does not depend on the Space still being listed.
  - **No instant of exposure.** A window's unsaved content is, at every moment, either in the saved file or in a durably written recovery record **or** still in that window's own live session (which has not yet left the Space). Removing a Space from the registry does not discard any window's live session; the window leaves the Space only through its own transition above.
  - **Self-describing, backward compatible.** New records carry `spaceId`, `lastPath` and `name` and a record `schema`. All new fields are **optional**: **existing records are never rewritten or migrated eagerly** and remain valid exactly as they are; a record without them is a *legacy record*, matched by its existing vault key as today and listed with `spaceId: null`. A legacy record is enriched only when its session next writes it. Readers ignore unknown fields (a Phase 5 test replays fixtures of existing records through the new reader and new records through the existing one, so a downgraded build still reads them or skips them without harm). Records written under a path-derived key are matched by key until a Space id is present.
  - **Discoverable without a registry entry.** `recovery_list()` enumerates the key folders directly (it takes no registry input) and returns, for each record, key, name, `spaceId` (or `null`), `lastPath` (or `null`) and mtime. The existing recovery prompt offers a record whenever its Space is next opened or re-added (matched by `spaceId` when present, by key otherwise); records whose Space is in no registry entry stay enumerable and are never deleted by any registry operation, quarantine or startup recovery. How a user is later *shown* such orphaned records is out of scope for this ADR.
  - **Not the live windows' records.** A live window's own session is excluded from another window's `discover()` (§5); records of dead sessions are offered as today.

**On loss, every dirty session is protected as a recovery record before the Application is discarded** (the code already flushes the journal; a test guards that no dirty session can be dropped without a record). Unsaved edits that existed only in a lost Space are offered for recovery instead of being "dropped" as ADR-056 accepted.

The removing window keeps ADR-056's order (switch away first, forget once the replacement opened).

#### 6.5a Add (collection growth)

- **Same folder, two windows.** If two windows add the same folder (or the same empty folder from the Welcome dialog):
  1. The first `claim_space(canonicalPath)` is `Claimed`; it completes the existing flow (including provisioning, ADR-070) and commits the registry entry and the `added` notice, then releases the claim with its result.
  2. The second receives `Held` and **waits for the first operation's result**, showing no warning or confirmation.
  3. When the first has registered the Space, the second **opens the existing Space** by the normal open path instead of creating or provisioning anything. If the first failed or its window was destroyed, the claim is released with a failure and the second takes it over and proceeds.
  Duplicates are impossible even without the claim, because the store's uniqueness invariant compares canonical paths under the mutex (§2, point 2); the claim exists to keep provisioning single, and it is a lease that expires if the first window hangs (§2, point 4).
- **First Space (collection empty → non-empty).** After the adding window commits, every other window in Welcome sees the collection become non-empty, leaves Welcome and opens that Space by the normal open path — not the provisioning path (the Space's ledger is complete; a resumed install is idempotent). Two windows choosing *different* folders register both (next bullet applies to whichever is added second).
- **Further Spaces.** `added` makes every window refresh its list. No window's active Space changes.

#### 6.6 Concurrent operations

All of the following resolve through the Coordination Store's single serialized order and are deterministic across windows.

- **Registry writes**: serialized in the store, each intent applied to the latest state after its preconditions are checked (§2, point 2): no lost update. Two windows adding, removing and renaming different Spaces at once all take effect, in one order.
- **Stale operations are re-evaluated, never replayed.** An intent whose target (path, Space id) no longer exists as named is answered `Stale` and commits nothing; the window re-resolves against the current registry and notice chain and issues a *new* intent only if one still applies. No window resubmits an old document or snapshot, and no retry can recreate a Space that another operation removed (only an explicit `add_space` creates an entry). A removal whose chosen fallback has since been removed is answered `Stale` and re-decided by the removing window.
- **Same rename twice** (windows A and B rename Space S): the destination is claimed exclusively in Rust, so exactly one succeeds; the loser receives the existing "name taken / already moved" outcome, clears its `pendingRename`, and adapts to the winner's `renamed` notice by Space-id verification. No dialog.
- **Two removals of the same Space**: the second intent finds the entry already forgotten (or the Space id no longer at that path) and is answered `Stale`, committing nothing — the window treats it as already done and follows the first notice; a third window follows the notice with the lowest `rev` and ignores later ones for a path it has already left. A fallback that is itself removed before a window reaches it is followed through the chain.
- **Rename and remove together**: each is a serialized intent checked against current state. A remove aimed at the old path (or the old Space id at that path) answers `Stale` and commits nothing once the entry has moved (the Space survives under its new name; nothing destructive happened; the user can remove it again). A remove that wins first makes the rename's registry step a no-op, and the renamed folder is simply an unregistered folder.
- **Loss detected by several windows at once**: commit-if-absent per episode (§6.5), exactly one notice.
- **Stale paths**: every path-bearing Space operation re-resolves its target against the current registry and the notice chain at execution time; an operation on a path that has since changed is re-issued **once, as a new intent** against the resolved path (never as a replay of the old one), otherwise reported through the existing failure notice.
- **Filesystem events during a change**: a window being re-rooted has quiesced and snapshotted navigation first; the flood of `moved`/`deleted` events for the old root is ignored because that `Application` is sealed and about to be discarded (its in-memory emptied Vault is never persisted or shown — the case ADR-056 already accepts). The new `Application` is built from disk.
- **Conflicting writes** to the same note from two windows: unchanged — guarded atomic writes (`replaceIf`) and Sync's external-change handling (ADR-063/071). Only a genuine content conflict reaches the user, through the mechanism that exists today.

### 7. Space preferences and multiple windows on one Space

Stores that load `.clutter/workspace.json` keys once (`SpaceProfileStore`, `CollectionViewConfigStore`, `TasksViewConfigStore`, `TagExpansionStore`, `FoldStateStore`, `ReferencesDisplayStore`, template stores) become *reloadable on external change*: the `Application` already has a raw-watcher seam for `.clutter/tags.json` (outside `VaultSyncService`); it is extended to `.clutter/workspace.json`, and each store reloads **only its own key**, ignoring its own writes. Per-key merge-write already protects other keys. This closes ADR-064's "not guarded: a second Clutter window" gap. `VaultSyncService` is not modified.

### 8. Lifecycle

- **Close one window**: its `Application` flushes and closes (existing handler); its record becomes `'closed'` if others remain and the app is not quitting. The app keeps running.
- **Last window closed / Quit**: the app exits; records stay `'open'` and are restored at next launch.
- **Quit (⌘Q)** is sequenced by Rust, one window at a time: each runs the existing flush + unsaved-changes flow; if one cancels, the sequence stops, and records of windows already closed stay `'open'`. A record is not marked `'closed'` during a quit sequence.

## Confirmed decisions

1. **Multiple `Application` instances over one shared disk**; no Rust-owned Vault.
2. **Restore windows after quit or last-window close**, following `startupBehavior`.
3. **Manually closed windows are not restored** at the next launch.
4. **Sidebar width, default tab and visibility are global.** The currently selected sidebar section is per window.
5. **Zoom is global and persisted.**
6. **Bounded retention of closed-window records** (proposed 20 records / 30 days).
7. **Reopen Closed Window is not required in v1.**
8. **New Window shortcut: ⌥⌘N.**
9. **Rename acknowledgement timeout: 2 seconds**, after which the initiator proceeds.
10. **Removal and external loss share one transition principle**: the removing window, or the first window to detect loss, publishes the fallback; all affected windows follow it; an unflushable window stays and retries automatically with the original fallback.
11. **Same folder added in two windows**: first claims and registers; the second waits for the result and opens the existing Space; no dialog.
12. **One Rust owner per application process** holds the Space registry, notices and claims. Mutations are serialized under one mutex as intents applied to the latest state; they are acknowledged only after every required flush is confirmed (an unsupported or failed flush is never a success; a post-replacement outcome is `Indeterminate` until reconciled); notifications are invalidation signals backed by reconciliation. Multiple application *processes* are out of scope. Validated in Phase 0 rather than assumed.
13. **Scalar preferences stay in `localStorage`, Space preferences in their `.clutter/*` files, window navigation in per-window records.** Nothing unrelated moves into Rust.

## Alternatives considered

- **Refuse or confirm Space operations while another window uses the Space.** Rejected: it blocks normal use for a coordination problem the windows can solve.
- **Registry and notices in `localStorage`, with `storage` events as the bus.** Rejected as the primary design: events are notifications, not atomicity; the read-modify-write across webview processes is not atomic; lazy flush can lose the registry. A stress test can show a race exists but can never prove one cannot, so the registry's correctness would rest on luck. Phase 0 may still measure it (with and without Web Locks) as **informative, non-gating** evidence; the decision does not depend on the result.
- **A distributed compare-and-swap document (revision check and client-side retry) over the Rust store.** Rejected as unnecessary: there is one owner in one process, so a mutex gives a single writer directly, and shipping whole documents lets a stale snapshot overwrite newer state or resurrect a removed Space. Mutations are intents applied to the latest state instead.
- **Mirroring the registry back into `clutter.spaces.v1` for downgrade.** Rejected: a second writer is the problem being removed. The blob is preserved and a documented additive merge handles an older build's changes (§2, point 7).
- **Lock files or leases on a Space.** Rejected: staleness after a crash, and it is a restriction rather than coordination.
- **Each window independently calculating a fallback** (earlier draft, for loss). Rejected: not guaranteed to agree across windows; replaced by the first-detector notice.
- **One shared `Vault` in Rust, windows as thin views.** Moves the domain model, Gate and Sync out of TypeScript; contradicts ADR-003/008.
- **`SharedWorker` hosting the `Application`.** Tauri IPC and the editor model are webview-bound; fragile in WKWebView.
- **A preference store per window plus IPC sync.** Copies that must be reconciled.
- **Launch-window-only persistence of `workspaceSession`.** Other windows' navigation would not survive; one window would be special.
- **Per-window entries inside each Space's `workspace.json`.** A window's Space is part of its state; entries accumulate in many user folders; navigation would write into Spaces.
- **Disk-wide relocation search for externally moved Spaces.** Contradicts ADR-056's "no relocation detection".

## Consequences

- Single-window behaviour is unchanged: one record adopted at launch behaves like today's `workspaceSession`; the registry behaves as before, now durably and atomically.
- One small new Rust module (`space_coordination.rs`) is the only new native surface for shared state, and the only writer of `<app data>/spaces/`; it never touches notes or the Vault, and it takes no paths from the webview other than Space folder paths that are canonicalized by the existing `canonical_space_path` before they are compared.
- A second window pays a second Space scan and parse (the parsed-note cache, ADR-053, helps; concurrent cache writers are last-writer-wins by design).
- A rename in one window makes the others briefly re-open the Space (as the renaming window already does); navigation and open notes are preserved, editor cursor best-effort.
- Re-rooting depends on the Space id; a window cannot be re-rooted onto a path whose id cannot be verified, and falls to the lost flow.
- A window waiting to retry a removal transition is the single case where a window shows a Space absent from the collection.
- Recovery records of a removed or lost Space are offered when that Space is next opened and are discoverable without any registry entry; they are never deleted by removal.
- The registry mutators are ported from TypeScript to Rust once, with the existing registry tests carried over as shared fixtures; the registry file is not readable by older builds (they keep the preserved legacy blob).
- A window that misses a notification is at most one backstop interval (30 s, visible windows) behind, and is never permanently inconsistent.

## Preserved (explicitly out of scope)

`VaultSyncService` and the cross-instance reconciliation it implements (including the folder-sync and `TwoInstanceFolderWorld` work); the Persistence Gate and every write path; the Trash implementation (`trash_path`, `macos_trash`, `trashFile`) and its automation specs; `DocumentEditing`; the atomic writer.

## Phase 0 — validation plan (no product code merges)

**Purpose:** prove, before any phase builds on it, that the **Rust Space Coordination Store** is correct, durable and crash-safe; that claims, conflict resolution and recovery behave as §2 and §6 assume; and that windows converge even when notifications are lost. Spikes live on a throwaway branch; the **harnesses** (not the spike code) are kept as automation under `packages/automation` and `apps/app/src-tauri/tests` so the same checks gate later phases. Results are appended to this ADR.

**Principles.** Every experiment asserts invariants over final *and intermediate* state, never "it worked once". Randomized runs use jittered delays (0–50 ms) and ≥ 1,000 iterations per scenario, in dev and packaged (and sandboxed) builds, with three windows where relevant. Failure injection reuses the atomic writer's fault-injection seam (`Faults`: fail, fail-after-effect and partial write at each step). **Any lost acknowledged commit, duplicate Space, divergent order, resurrected Space, corrupt persisted document or lost recovery record is a failure; there is no tolerated rate.**

**Invariants.**
- **R1** No lost update: the final registry equals every acknowledged mutation applied exactly once, in `rev` order.
- **R2** No duplicates: one canonical folder is never registered twice, however it is spelled or the adds interleave.
- **R3** One order: `rev` is gap-free and strictly increasing; every window applies notices in the same order.
- **R4** Commit-if-absent: concurrent publishers of one loss episode produce exactly one notice.
- **R5** Claims are exclusive; released on window destruction; a hung holder's lease expires; a waiter takes over; a revoked holder cannot create a second entry.
- **R6** Durability: **nothing is acknowledged, published or notified before every required flush is confirmed** (an unsupported or failed flush is never a success); an acknowledged mutation is present after any process kill or crash; an unacknowledged one is entirely present or entirely absent.
- **R7** Convergence: conflicting operations leave every window in the same state.
- **R8** No resurrection: a stale or retried intent never recreates, renames, replaces or re-opens an entry that another operation removed; nothing is ever applied from an old snapshot.
- **R9** Notification independence: with notifications dropped, delayed, duplicated or reordered, every window converges within the backstop bound (visible) or on becoming visible (hidden), and never stays inconsistent.
- **R10** Recovery independence: no registry operation (including corruption and quarantine) deletes, hides or reinterprets a recovery record; every record, legacy or new, is discoverable with no registry entry; a registry removal never waits on another window, and each window leaves the Space only after its own work is saved or its recovery record write succeeded.
- **R11** Indeterminate outcomes: a failure *before* replacement changes nothing; an outcome *after* replacement is never acknowledged until confirmed, resolves to exactly one of committed or not committed (never both, never an unreported third state), is reported by `operation_status(opId)`, and no window ever sees an unconfirmed snapshot.
- **R12** Generations: at every instant `prev.rev ≤ main.rev ≤ prev.rev + 1`, `prev` is byte-identical to a confirmed document, and startup recovery adopts exactly as the §2 table says.
- **R13** Fencing: a revoked or expired holder resuming after a takeover cannot register, double-advance the ledger, regress a completed install, overwrite content, or create a second entry; final filesystem and registry state equal a single uninterrupted run.
- **R14** Legacy: the baseline is persisted once and never changes; `consumed` only grows; a baseline Space removed by the new version is never resurrected by any re-upgrade; only genuine old-build additions are merged, once.

| E2 | **Durable commit, failure classes and indeterminate outcomes** | `kill -9` at random instants during E1 (≥ 500 kills). A lost acknowledgement (result dropped after rename). | E8 | **Recovery independence and per-window transitions** | Remove, lose, rename and relocate Spaces while two and three windows hold protected-only and dirty work, one of them unflushable or hung; corrupt and quarantine the registry; re-add the Space; replay a corpus of **existing-format recovery records** through the new reader and new records through the existing reader | R10: the removal commits without waiting for any window; each window leaves only after its own save or successful recovery write; no unsaved content is ever absent from file, record and live session; records are never deleted or hidden by any registry operation; `recovery_list()` finds legacy and new records with no registry entry; legacy records still match by key; a downgraded reader tolerates new records |

**Informative, not gating.** **I1** — a baseline of three windows doing unguarded read-modify-write on a registry-shaped `localStorage` key, and **I2** — Web Locks exclusivity and release-on-crash across webviews. They record evidence for the rejected alternative; their results change no decision in this ADR and may be run last.

**Decision gates.** **G1** (after E1–E3, E9): the store is correct, durable, crash-safe, classifies indeterminate outcomes correctly and migrates safely, or the ADR is revised before Phase 1. **G2** (after E4–E8, E10, E11): claims, leases and fencing, stale-operation handling, notification-independent convergence and recovery independence pass, or Phase 5/5b scope is revised. **G3** (after E12): platform assumptions hold, or the affected phase is revised. A failed gate stops the plan and returns to ADR review; it is never worked around in code.

## Phased implementation plan

Each phase is independently verified and committed, and single-window behaviour is re-verified in every phase. No menu item is exposed until Phase 7, so no control is ever wired to an unfinished capability (`implementation-rules.md` §2 rule 12).

**Working-tree discipline.** Folder-sync and Trash work stay untouched; every phase commit stages only its own files. Phases 3, 5 and 5b touch `Application.ts`, `AppShell.tsx` and `core/application/space/*`; any uncommitted work in those files should be committed first, or the phase branched from it.
