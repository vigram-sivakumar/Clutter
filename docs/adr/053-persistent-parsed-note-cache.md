# ADR-053: A persistent parsed-note cache — a content-addressed memo of `FrontmatterParser.parse`, stored in the application cache directory

**Status:** Accepted (approved for implementation, 2026-10-14, with the revisions below incorporated). Builds on [ADR-004](./004-lazy-projections.md) and ARCHITECTURE_RULES.md rule 8 ("derived data is disposable"); sits inside rule 2's scope note (caches are outside the Persistence Gate). Its Platform, Vault Ingest and Composition Root additions (a native cache store and backend seam, an optional memo argument on `VaultScanner`/`DocumentLoader`, a `FrontmatterParser.split`, and the `Application` wiring) amend `architecture-specification.md` §1/§2/§11; the specification is updated with this ADR's acceptance (implementation-rules.md §4).

## Context

Startup on a 1,000-note (5.0 MB) space spends 2.7 s in `VaultScanner.scan` (packaged app, median of 5; see *Baseline*). Of that, ≈1.45 s is synchronous parsing and analysis (`FrontmatterParser.parse`), ≈1.17 s is waiting on one `readFile` IPC per note, ≈0.10 s is `readDir`, and `VaultBuilder.build` (every index) is 9 ms and is not worth caching. On the 11-note space the scan is 102 ms, of which parsing is 11 ms and directory listing 73 ms, so a parse cache cannot help small spaces.

Facts established from the code and the platform that constrain the design:

- **The parse result is a pure function of the file text.** `ScannedPageAnalysis` is documented page-local; the parser reads no clock, locale or environment. It depends on third-party grammar code (`@lezer/markdown`, `@lezer/common`, `@lezer/highlight`, `@codemirror/language`, `@codemirror/state`), so a dependency upgrade can change output with no change in this repository.
- **The immutable `Vault` retains every note body** (`PageBuilder`: `source.markdown = page.content`; 18 non-test files read it). A cache can skip *parsing*, not *reading*, without on-demand loading, which is out of scope.
- **Ingest never writes to disk** (spec §2; Application.ts). Persistence of the cache lives outside Ingest.
- **Ids and paths are not parse output.** They are derived per boot from `frontmatter.id` and the path; duplicate-ID resolution runs after the scan every boot; repair and archive/template reconciliation run after the build.
- **The fs plugin cannot give durable atomic replacement.** `tauri-plugin-fs` `rename` is `std::fs::rename` (atomic replace on POSIX), but its writes open-with-truncate in place and the plugin contains no `fsync`/`sync_all`. Reaching the app cache directory from the webview would also need new fs scope (`$APPCACHE/**`, `fs:allow-appcache-*`). The path API gives `app_cache_dir()` = `<user cache dir>/<bundle identifier>` (`~/Library/Caches/<id>` on macOS).
- **Clutter has no space lifecycle on `main`.** The vault path is a hard-coded constant in `AppShell`; there is no registry, "forget" or "delete space" flow (spaces belong to the onboarding branch, not touched here). Cleanup therefore cannot hook a lifecycle event.

Measured in the packaged app on the 1,000-note dataset (spike, not production code): `JSON.stringify` 3 ms and `JSON.parse` 2–3 ms for a first-draft payload; `crypto.subtle` is available (secure context) and SHA-256 over all bodies took 46 ms sequentially / 4 ms in parallel; sequential `stat` 0.31 s vs 0.56 s for sequential reads (warm); 8-way concurrent reads 0.13 s. The implemented cache measured **1,904,324 bytes (about 1.90 MB, 38% of the dataset's 5.0 MB of Markdown)** for that 1,000-note benchmark dataset. That is a benchmark result, not a guaranteed size: it depends on note content (links, tags, tasks and frontmatter all add entries) and is why the limit below is a separate, defensive 64 MiB. **JSON drops `undefined`-valued keys** (e.g. a task's `dueDate`): 1,000/1,000 entries differed from a fresh parse under strict key-set comparison.

## Decision

### 1. Source of truth and purpose
Markdown files are authoritative. The cache is a memo of `parse(fileText)`. It only ever supplies the result of parsing the *exact text just read from disk*; it never supplies note content, never writes to a note, and cannot cause a file to be overwritten. Deleting it loses nothing.

### 2. What is cached (minimum representation)
One entry per distinct file text, keyed by the **SHA-256 of the file text exactly as `readFile` returned it and as `parse` receives it**. Value: the three things `parse` derives that are expensive or not recomputable by a slice — `frontmatter` (including verbatim unowned lines and key spellings, which the serializer needs), `frontmatterAnalysis`, and `analysis` (tasks, tags, links, embeds, headings, block references, with offsets). Not cached: the body (recomputed by the cheap split), ids, paths, builder output, resource metadata, any index. `ScannedTask.rawText` equals `body.slice(startOffset, endOffset)` and could be dropped; it is **kept** — it is ~14% of the payload at most and removing it adds a reconstruction invariant for a small saving. `FrontmatterParser` is refactored into a cheap `split(content)` and an expensive `analyze(...)` with `parse` as their composition, so cached and uncached ingestion share all code; `parse`'s public contract is unchanged.

### 3. Location, format, identity (outside the space)
- **Location:** `<app_cache_dir>/parse-cache/<spaceId>.json`. Generated data never enters the Markdown space.
- **Access: native commands, not the fs plugin.** A new Platform module `src-tauri/src/parse_cache.rs` exposes `parse_cache_read` (returns `{ spaceId, contents?, problem? }`), `parse_cache_write` and `parse_cache_remove`. They are `async` and do their file work on the blocking pool, never on the main thread. No new webview fs scope or permission is needed (the webview cannot name cache paths), the size cap and path rules are enforced natively, and writes can `fsync`. The webview side depends on a small `ParsedNoteCacheBackend` interface (Platform seam; rules 4 and 11) with a Tauri implementation and an in-memory one for web and tests; the Composition Root picks it. **Internally disableable and safe to clear:** passing a `null` backend to `Application.bootstrap` turns the cache off entirely (nothing read or written), and `parse_cache_remove` or deleting the file is always safe (it is only a miss). A user-facing per-space preference is deferred.
- **`spaceId`:** computed once, in Rust: canonicalize the root path (resolves symlinks and `..`; on failure use the given string), take SHA-256 of its UTF-8 bytes, keep the first 32 hex characters. Filenames never contain the path. Different spaces have different ids (collision probability ≈2⁻¹²⁸). The envelope also records `spaceId` and it is verified on load. A moved or renamed space gets a new id: a miss and a rebuild; the old file is reclaimed by pruning (§9). The id is an **identifier, not a security boundary**: opaque (filenames never contain the path) but unsalted, so anyone who can guess a path can compute its id. No salt is used.
- **Format:** one JSON document `{ "format": 1, "parserFingerprint": "<string>", "spaceId": "<id>", "entries": { "<hash>": <encoded entry> }, "checksum": "<sha256 hex of the entries text>" }`. A single document is sufficient at the measured size; no database.

### 4. Fidelity: structural equivalence is an acceptance criterion
The cached path must construct `Page` objects that are structurally identical to the uncached path, including optional properties that are present-with-`undefined`. The representation is fixed rather than the comparison weakened:
- **Codec preserves `undefined`-valued own keys.** Encoding writes a reserved marker object (`{"$undef":true}`) for every `undefined` property; decoding walks the entry and restores each marker as an own property set to `undefined`. Decoding creates **new objects on every hit** (two files with identical text never share mutable parse results).
- **Verify-on-write.** When a miss is recorded, the entry is encoded, decoded and compared to the original with a strict structural comparator (own-key sets, `Object.is` on primitives, array lengths, plain prototypes). If it is not identical — a marker collision, `NaN`, `-0`, a `Date`/`Map`/`Set`, a sparse array, an unexpected prototype — that entry is **not cached** and parsing continues normally. Encoding happens at record time, before the result leaves the loader, so later mutation by downstream code cannot corrupt an entry.
- Equivalence is therefore both enforced at runtime per entry and proven by the tests below.

### 5. Validation and invalidation
Validation is **content hash plus version**, never timestamps or size. A hit requires: the same text hash, and the cache's `format` and `parserFingerprint` equal to the running build's.
- `parserFingerprint = PARSER_VERSION + the resolved versions of @lezer/markdown, @lezer/common, @lezer/highlight, @codemirror/language, @codemirror/state`, injected deterministically at build time (`vite.config.ts` resolves each package's installed `package.json`). `PARSER_VERSION` is a manual constant bumped whenever repository parse code changes output. **Version injection detects version changes, not arbitrary modification of package contents**: a package edited in place at an unchanged version is not detected. That is managed by lockfile-controlled installs, the golden-corpus test and `PARSER_VERSION`. `PARSER_VERSION` history: 1 = initial; 2 = `coverCredit` became an owned frontmatter key ([ADR-054](./054-cover-credit-for-unsplash-covers.md)), which invalidated all earlier caches. A **golden-corpus test** (checked-in samples, expected output and the version) fails when output changes without a bump, and fails after a dependency upgrade that changes output, so a forgotten bump cannot ship silently. A mismatch discards the whole cache; no migration is attempted or ever needed.
- A hash equal to a stored one means the text is identical; no further check is needed. A hash not in the cache is a miss.

| Case | Behavior |
|---|---|
| Added file | hash absent → parsed → recorded |
| Modified file | new hash → parsed; the old entry is dropped on the next write (not seen) |
| Deleted file | not seen in the scan → entry dropped on the next write |
| Renamed / moved file | same text, same hash → hit regardless of path |
| Duplicate IDs | identical copies share one entry; `VaultBuilder` still reassigns ids every boot and the repair rewrites the file, changing its hash for the next boot |
| Archive / template reconciliation | runs after the build, unchanged; rewritten files miss next boot |
| Corrupt cache data | whole cache discarded (§6) → ordinary parsing |
| Interrupted write | the destination is replaced only by `rename` of a fully written, synced temp file; a torn or empty file from a crash is caught by the checksum |
| Read / permission errors | cache read failure ⇒ treated as no cache; file read failure behaves exactly as today (the scan's existing error path) |
| File changing during the scan | each entry is derived from the single string read for that file (hash and parse use the same string), so a text/result mismatch is impossible; a later change is reconciled by the existing watcher/Sync path exactly as it is today |

### 6. Recovery
Missing file, unreadable file, oversized file, JSON error, wrong `format`/`parserFingerprint`/`spaceId`, checksum mismatch, malformed shape → the cache is treated as empty, a diagnostic is logged, and startup proceeds exactly as today, then writes a fresh cache. Cache code never throws into bootstrap and never blocks editing. If `crypto.subtle` is unavailable the cache is disabled and ingestion is unchanged.

### 7. Initialization invariants
The memo is consulted inside `DocumentLoader.load`, below `VaultScanner`. Directory order, per-file order, `VaultScanResult` shape, `VaultBuilder`, duplicate-ID repair, archive/template reconciliation, `attachVault` ordering and the Gate are untouched. The Vault is built from a complete scan result as now — never partially, never from the cache alone. `VaultScanner`/`DocumentLoader` take an optional memo argument defaulting to "none", so every existing caller and test is unchanged; the memo exposes read-only `get(hash)`, and the loader records misses. Ingest does not write.

### 8. Persistence: atomic, durable, multi-instance safe
Writes happen in Rust: create a **uniquely named** temp file in the same directory (the pid separates live processes, the nanoseconds separate a reused pid from a crashed run's leftovers, and a process-wide sequence number separates threads of one process, which the microsecond-granular clock alone does not) (`<spaceId>.json.<pid>.<sequence>.<nanos>.tmp`, `create_new`), write all bytes, `sync_all`, `rename` over the destination (atomic replace, also when the destination exists), then best-effort `fsync` of the directory. The checksum remains as defense in depth against media faults and platforms where a crash can expose an unflushed file. On any failure the temp file is removed.
- **Two instances, one space:** each writes its own temp file; the last `rename` wins; readers always see a complete old or complete new file. The cache is a pure memo, so any complete cache is valid for any instance with the same fingerprint; the only cost of the race is that one instance's new entries may be lost and re-parsed once. No lock files for the cache itself (they go stale) and no merge-on-write (complexity). Instances with different fingerprints discard each other's files; that costs reparsing, not correctness.
- **Temporary-file cleanup is best effort and does not treat age as proof of death** (a suspended app can be idle for hours). A writer holds an exclusive advisory lock (`flock`) on its temp file until the rename; the OS releases it on process exit. Cleanup removes a `<id>.json.<pid>.<sequence>.<nanos>.tmp` only if it is at least a minute old **and** its lock can be acquired, i.e. no live writer holds it. If cleanup still races a live writer (for instance in the instant before the writer takes its lock), the writer's `rename` fails and that one cache write is lost; the initialized Vault and user content are unaffected.
- **Scheduling: off the critical path.** `application.open()` returning does not mean the workspace has rendered or painted, so the write is not scheduled from the Composition Root. `AppShell` schedules `application.persistParsedNoteCache()` from an effect that runs after the workspace commits, through `scheduleAfterFirstPaint`: after two animation frames and a macrotask (a painted frame), with a 3 s timeout fallback because a hidden window schedules no frames. The main-thread work is small (entries are already encoded and verified at record time; the write assembles the envelope text and a SHA-256 checksum); disk I/O is native, on the blocking pool. No worker or job framework is introduced. The cache is read once at boot and written at most once per boot, from the scan's own results, and **skipped when nothing changed** (no misses, no dropped entries, file already present). It never delays window reveal, workspace usability, the editing Gate or shutdown: `Application.close()` cancels a write that has not started and **does not wait for one in flight** (atomic replacement makes an interrupted write harmless). Session-time parsing (Sync, the Gate) neither reads nor writes the cache, so watcher events, pending writes and conflict resolution cannot race with it. A note edited in a session is reparsed once at the next launch, then cached.

### 9. Size policy, cleanup, privacy
- **Size limit:** 64 MiB maximum serialized size per space (provisional, defensive, not measured). Enforced in Rust on write (and rejected early in JS) and on read (checked via file metadata before reading). Over the limit: skip caching, keep ordinary parsing, remove any stale cache file for that space, and log a structured diagnostic (`status`, `reason: oversize`, `bytes`, `entries`, `limit`). No LRU eviction. If very large spaces become important, **partitioned cache files** (for example by hash prefix) are the natural next step and are deliberately not built now.
- **Retention: 90 days since last use** (provisional), not since last write. "Used" means read: a successful read refreshes the cache file's modification time **only if it is more than a day old** — one metadata write at most per day, never a rewrite of the JSON. (Access time is not used: it is unreliable under `noatime`/`relatime`.) An actively used cache therefore survives indefinitely even though an unchanged space never rewrites it.
- **Cleanup:** there is no space-removal event on `main`, and none is invented. (a) `parse_cache_remove(root)` exists for a future space-removal feature to call. (b) Beside each read, Rust deletes **only** regular files in `<app_cache_dir>/parse-cache/` named exactly `<32 hex>.json`, that are not the current space's, and whose last use is more than 90 days ago, plus abandoned temp files (above). Symlinks, directories and any other name are skipped, nothing outside that directory is ever touched, and the Markdown space is unreachable by construction. (c) The OS may purge `~/Library/Caches` at any time; a vanished file is simply a miss.
- **Privacy:** the cache is **not encrypted** and holds content-derived plaintext — heading titles, link and embed targets, tags, task text (`rawText`), alias values, and frontmatter including unrecognized properties — plus SHA-256 digests of note text (guessable for short or low-entropy notes). It lives outside the space, readable by the user's other processes, not covered by whatever protects or excludes the space (backups typically exclude `~/Library/Caches`; at-rest protection is FileVault's), and it can **outlive a deleted space** until pruned. It is therefore not a place for secrets; users who treat a space as sensitive should know a derived copy of its metadata exists. Mitigations are the age pruning, `parse_cache_remove`, and the size cap. The cache can be disabled internally (null backend) and cleared safely; a user-facing per-space preference is deferred.

## Alternatives Considered

- **Cache inside the space (`.clutter/cache/`).** Rejected after review: pollutes the user's folder, creates cloud-sync conflict copies, and ships derived data with the space.
- **fs plugin with `$APPCACHE` scope.** Rejected: widens the webview's file access, offers no `fsync`, no unique temp naming and no native size cap. Rust commands are least-privilege and fit Platform's existing pattern (`vault_watcher.rs`, `vault_asset_scope.rs`).
- **Cache bodies and trust `mtime`+`size`, skipping reads.** Rejected: duplicates user content, and a false hit puts stale text into the Vault, from which the Gate could overwrite a newer file.
- **Path-keyed manifest validated by `mtime`/`size`.** Rejected: weaker correctness, misses on rename, still needs the reads.
- **Make extractors omit `undefined` keys instead of a codec.** Rejected for now: modifies producers; the codec leaves them untouched. (It remains a valid later simplification.)
- **SQLite; persisted indexes; refresh-on-save; sidecar files.** Out of scope or rejected as before.

## Consequences

- Warm launches stop paying the synchronous parse share (≈1.45 s of 2.7 s at 1,000 notes). **Reading remains.** No scan time is promised until the integrated implementation is measured; bounded-concurrency reads are a separate step, measured afterwards.
- Benefit scales with note count; none for small spaces; the regression guard is that an unchanged launch must not be slower than the baseline on either dataset.
- Adds Platform surface (three commands, `sha2` as a direct dependency — already in the dependency graph — and the backend interface) and a maintenance obligation (`PARSER_VERSION`, enforced by the golden-corpus test).
- Cached data persists in `~/Library/Caches/<id>` (privacy section above).
- Mac App Store compatibility is **not claimed**: `app_cache_dir()` resolves inside the container under App Sandbox, but sandboxing and notarization remain unverified.

## Testing (implementation acceptance criteria)

**Page equivalence (exact strategy).** For a corpus (checked-in golden samples plus a generated vault) run two ingestions: A with no memo; B with a memo populated by a first scan, serialized to a string, decoded by the real codec, and used for a second scan that must hit for every file (a spy asserts `analyze` was never called). Then assert, with Vitest **`toStrictEqual`** (which treats `undefined` properties, prototypes and sparse arrays as significant): (1) the two `ScannedPage[]` are identical; (2) each `Page` built by `PageBuilder`, and the whole `Vault` from `VaultBuilder`, are identical, plus tags, tasks, embeds and knowledge-graph projections through their public queries. Meta-tests assert the corpus exercises each optional property both present and absent (task `dueDate`/`completedAt`, link and embed `heading`/`blockReference`/`alias`, frontmatter variants: no id, duplicate keys, unowned lines, key spellings, CRLF, code fences). A **canary** asserts that a naive `JSON.parse(JSON.stringify(...))` of the same data is *not* strictly identical, so the harness provably detects the spike's failure mode. A mixed run (some hits, some misses) and a fuzz test of the codec (nested `undefined`, empty arrays, unicode, `__proto__`/`$undef` keys, `NaN`, `-0`, `Date` — unsupported shapes must be refused, not degraded) complete the set.

**Cache behavior** (in-memory backend): corrupt JSON, truncation, wrong checksum with valid JSON, wrong `format`/`parserFingerprint`/`spaceId`, malformed entry, oversize file, missing file, backend read/write errors; unchanged, one changed, subset changed, added, deleted, renamed/moved, identical files, duplicate IDs (reassignment and repair unchanged), external edit while closed including same size and preserved mtime (must miss), fingerprint bump rebuild, full rebuild after discard; `close()` with a write in flight; the Vault is identical with the cache present, absent and corrupt.

**Rust unit tests** (`parse_cache.rs`, std temp dir): replacement when a destination exists; interrupted write (temp present, destination old or absent); unique temp names under two simultaneous writers; stale-temp reclamation (and a fresh temp preserved); oversize rejection on read and write; prune deletes only matching old regular files and never follows symlinks or touches decoys, directories or other names; `spaceId` is stable and path-independent in the filename.

**Packaged app:** the benchmark below, a corrupt-cache launch, a kill during a cache write, and two simultaneous instances on one space.

## Benchmark plan

**Method.** Official `tauri build --bundles app` in an isolated scratch copy with temporary instrumentation (never in the repository); the same harness, datasets and metrics before and after. Datasets: 11-note space; 1,000-note, 5.0 MB synthetic space (checked-in generator, fixed content). At least 5 runs per scenario; report **medians and min/max**; discard any run whose page became hidden before the workspace was usable (reported as a count); label every result warm (OS file cache warm; true cold needs `purge`, unavailable) and note the first exec of a fresh binary separately.

**Scenarios.** (1) first launch, no cache; (2) unchanged relaunch; (3) one changed note; (4) subset changed (~10%); (5) files added; (6) files renamed (cache hits expected); (7) files deleted; (8) full rebuild after invalidation (fingerprint bump / corrupt cache); (9) oversize cache path (synthetic limit); (10) corrupt cache launch.

**Measured separately:** window visibility (OS window list, independent of the page); workspace usability (`AppLayout` committed plus next frame); file reading; hashing; cache load + decode; parse; Vault and index construction; main-thread responsiveness (timer-drift stalls while visible); cache file size. A faster window reveal is never reported as a faster workspace start.

**Baseline (current `main` + startup-reliability changes, no cache; 5 kept runs, 0 discarded).**

| | window visible | usable | scan | read wait | parse | readDir | build | max stall |
|---|---|---|---|---|---|---|---|---|
| 11 notes | 751 ms (726–788) | 826 ms (807–862) | 102 ms (86–110) | 13 ms | 11 ms | 73 ms | 2 ms | 51 ms |
| 1,000 notes | 768 ms (732–795) | 3421 ms (3391–3689) | 2704 ms (2675–2936) | 1172 ms (1114–1321) | 1449 ms (1424–1501) | 101 ms | 9 ms | 0 ms |

(First exec of a freshly built binary, discarded: window 1738 ms, usable 1988 ms.) The main thread is not blocked during the large scan — parsing is chunked between awaits — so the cost today is elapsed time showing the startup frame, not a frozen UI.

**Sequence.** Baseline (done) → implement the cache → repeat the full matrix → only then, as a separate step, bounded-concurrency reads (limit 8, deterministic ordering, no partial state on failed reads), benchmarked on top of the cache so each optimization's contribution is separable.

## Observations from packaged testing

- **One run with no cache file, cause unknown.** In packaged-app testing of two simultaneous instances on one 1,000-note space (no cache present, both instances terminated 14 s after launch), one run of 17 left no cache file. The Vault, the Markdown files and the cache directory were otherwise unaffected: no corrupt cache and no stray temp files. The cause is **unknown**. It was not reproduced: the 14 later paired runs (6 observed for 16 s and 8 for 14 s) and 6 single-instance runs each produced a valid 1,000-entry cache. No explanation is asserted here.

## Resolved by review, and deferred

Resolved: location is the application cache directory outside the space; the space id is the first 32 hex characters of the SHA-256 of the canonicalized root, unsalted, an identifier and not a security boundary; the fingerprint is `PARSER_VERSION` plus build-time dependency versions (which detect version changes, not content modification); caching is internally disableable and safe to clear; the size limit is 64 MiB per space and retention 90 days since last use (both provisional and unmeasured).

Deferred: a user-facing per-space preference to disable the cache; partitioned cache files for very large spaces; bounded-concurrency reads (a separate, later optimization benchmarked on top of this one).
