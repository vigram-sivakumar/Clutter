# ADR-031: App-Initiated Body Mutation Routing — `DocumentSession` as the Sole Current-Content Owner

**Status:** Accepted (design frozen; implementation approved and complete — see Implementation Record below; not yet committed, pending review)

## Context

`TaskOperations.mutate()` (`core/application/task/TaskOperations.ts:77-118`) toggles a task's completion state and patches its inline `@key:value` metadata by reading `page.source.markdown` from `Vault` directly, rewriting the target line, and enqueueing the result through the Persistence Gate's `'save'` kind — unconditionally, regardless of whether the page has an open `DocumentSession`. Its own doc comment (lines 19-35) states this explicitly: *"Does not know about DocumentSession/SaveCoordinator — a task mutation from the sidebar is not a document-revision event."*

That reasoning holds only while the page is closed. If the page is open in the editor — clean or dirty — this write path bypasses `DocumentSession` entirely: `Vault`/disk receive the task mutation, but `session.currentRevision` does not. The session does not know its own baseline just changed underneath it. The next save this session performs (autosave or explicit) persists `session.currentRevision.markdown`, which does not contain the task mutation — silently reverting it. This is not hypothetical for a dirty session (the user has unsaved prose elsewhere in the same document) and is a real, if narrower, staleness risk even for a clean session (the two writes race: whichever of the task mutation's Gate write or the session's own eventual save lands last wins, with no ordering guarantee between them today).

This is not a `TaskOperations`-specific defect. The same shape — an app-initiated operation that computes new Markdown body content and must decide where that content goes when a `DocumentSession` may already be open for the target page — applies to every present and future body-mutating capability: task completion and reopening, formatting commands, template insertion, bulk transformations, and AI-assisted edits. A fix scoped to `TaskOperations` alone would leave every later feature to independently rediscover and re-solve the same problem.

A preceding architectural review (recorded in this ADR rather than in a separate document, per `implementation-rules.md`) ruled out the tempting existing precedents as not actually applicable:

- **`PageOperations.delete()`** is not a body-mutation precedent — it is a destructive page-lifecycle operation (closes the session, then enqueues a disk delete) with no "what should the new content be" question to answer.
- **`EffectivePageState`** ([ADR-020](./020-effective-page-state-projection.md)) is a read-time reconciliation projection over `Vault` and `DocumentEditing` for presentation purposes. It has no write authority and cannot be the mechanism that decides where a write goes.
- **`Conflict`** (`durability-model.md` Stage 3, "Reconciled") is explicitly scoped to reconciling `Vault` against externally-made filesystem changes detected by `Sync`. It has no defined meaning for a same-process app-initiated write racing an open session — extending it to cover that case would conflate two structurally different problems (a second local writer vs. a genuine second process/device) that `durability-model.md` itself warns against conflating.
- **`DocumentRegistry` access from `TaskOperations` directly** is architecturally *possible* (`DocumentRegistry.get(pageId)` is public within `application/`) but would relocate today's one-off gap into a second facade re-implementing session-awareness, rather than establishing it as a rule every current and future body-mutating facade is checked against.
- **No merge/patch primitive exists in `DocumentEditing` today.** `DocumentSession.commit(transaction: DocumentTransaction)` takes a complete replacement Markdown string (spec §9, `DocumentSession.commit`); `DocumentTransaction` is not a diff or patch type. Any model requiring reconciliation of two independently-computed Markdown strings would need to invent a merge engine that does not exist and that no current requirement justifies building.

## Evaluation Summary

Four models were compared for the general rule "what happens when an app-initiated body mutation targets a page that has an open `DocumentSession`":

| | A — session is sole current-content owner (adopted) | B — durable-first, reconcile after | C — new mutation-application coordinator class | D — reject/defer while dirty |
|---|---|---|---|---|
| Concurrent owners of "current content" | One, always (session if open, else `Vault`) | Two (`Vault` and session) simultaneously | One (same as A) | One, but mutation blocked while dirty |
| Requires a merge/patch engine | No | Yes, for the dirty case | No | No |
| Data-loss risk | None — mutation composes onto whatever is already committed | Real — dirty-session case has no safe resolution without a merge engine | None (same as A) | None, but the mutation itself is refused |
| New abstraction | One method on existing `PageOperations` | None, but two competing writers | A new coordinator/service class | A policy flag/guard |
| Violates an existing immutable rule | No | Yes — two owners of one capability's current state contradicts rule 1/ARCHITECTURE_RULES.md | No | No |
| Scales to future body-mutating features | Yes — every future feature is `(markdown) => markdown` through one dispatch | No — every feature re-litigates the dirty-case policy | Yes (functionally identical to A) | No — every feature inherits the same "can't run while typing" restriction |
| User-facing behavior | Task toggle always succeeds and is preserved | Task toggle may silently lose data or need a blocking merge prompt | Same as A | Task toggle refused or queued while any part of the document is unsaved |

**B** is disqualified outright: it requires two simultaneous writers of "current content" for the same page, which is the specific failure mode `ARCHITECTURE_RULES.md` rule 1 ("every capability has exactly one owning facade") and rule 3 (`Vault` mutated only by the Gate and Sync) exist to prevent — not a style preference, a violation of an already-immutable rule.

**C** is functionally identical to A's dispatch logic; introducing a dedicated class for it is unwarranted (see Alternatives Considered).

**D** is safe but wrong for the motivating case — toggling a task while unsaved prose sits elsewhere in the same open document is a mainline flow, not an edge case, and blocking it would force every future body-mutating feature to invent its own escape hatch from the same restriction.

## Decision

Adopt **Model A**, stated as a standing rule, not a `TaskOperations`-specific fix:

1. **`DocumentSession` is the exclusive owner of a page's current content for as long as a session is open for that page.** No other subsystem writes content for that page while the session exists. This is a direct extension of `DocumentEditing`'s existing documented ownership (spec §9: "Owns in-memory edit state only") to cover writers other than the editor's own keystrokes.

2. **`PageOperations` gains one new method, the canonical (and only sanctioned) entry point for app-initiated body mutations:**
   ```ts
   mutateBody(pageId: string, transform: (markdown: string) => string): Promise<void>;
   ```
   `transform` is a pure function from current Markdown to new Markdown — the same shape task completion, formatting commands, template insertion, bulk transforms, and AI-assisted edits all reduce to.

3. **Precondition checks, evaluated before either branch runs:** page-not-found (no `Vault` page *and* no open session) and archived-page (the page exists in `Vault` and `page.metadata.status === 'archived'`, checked regardless of whether a session happens to be open) — mirroring `save()`'s own existing check ordering exactly, including its message text.

4. **Dispatch rule, evaluated inside `mutateBody` after the precondition checks pass:**
   - If `documentRegistry.get(pageId)` returns a session, the mutation targets that session: read `session.currentRevision.markdown`, compute `transform(markdown)`, and call **`this.commitEdit(pageId, result)`** — not `session.commit()` directly. `commitEdit()` is what commits the transaction *and* arms the existing `SaveCoordinator` autosave timer (`saveCoordinator.scheduleSave(...)`); calling `session.commit()` directly would commit the mutation into the session but leave it with no scheduled persistence, silently stranding it until some unrelated trigger (a keystroke, a blur) happened to call `requestSave()` afterward. Routing through `commitEdit()` is what makes "persistence follows the session's own existing save lifecycle" true rather than aspirational. `Vault`/the Gate are not touched by this branch.
   - If no session exists, the existing `Vault`/Gate path is used unchanged: compute `transform` against `page.source.markdown` and enqueue `{ kind: 'save', content }` through `PagePersistenceCoordinator`, the same pattern `TaskOperations.mutate()` already implements today for the closed-page case. (`PageOperations.save()` itself cannot be reused here — it requires an open session and throws without one — so this branch calls `coordinator.enqueue` directly, exactly as `TaskOperations.mutate()` already did before this ADR, just relocated.)
   - This is a dispatch between two already-sanctioned write paths (`DocumentSession.commit`, via `commitEdit()`, for in-memory current state; the Gate for disk), not a third path. It does not relax `ARCHITECTURE_RULES.md` rule 2 (Gate is the sole disk writer) or rule 12 (one write path per capability): the *capability* ("mutate a page's body") gains exactly one owning entry point (`PageOperations.mutateBody`), which is what rule 12 requires — it was previously missing one.

5. **A session-branch mutation is not required to persist synchronously**, and must not be given a new, separate persistence trigger to do so. It joins the session's ordinary Committed→Durable lifecycle (`durability-model.md` Stage 1→2) — an autosave debounce or an explicit save from the UI is what eventually calls `PageOperations.save()` for that content, exactly as for a typed edit. This is a deliberate non-goal, not an oversight: inventing an immediate-persist path for programmatic mutations only would create a second, inconsistent notion of "when does an app-initiated change reach disk," undermining the single-lifecycle point of this decision.

6. **Feature facades — `TaskOperations` named specifically, and any future body-mutating facade — must not access `DocumentRegistry` or `DocumentSession` directly, and must not read `Vault`/write through the Gate for body content on their own.** They call `PageOperations.mutateBody()`. This keeps `PageOperations` as the one place per `ARCHITECTURE_RULES.md` rule 1 that decides "whether and how" a body mutation happens, with `TaskOperations` (and future facades) reduced to *what* the mutation is (a `transform` function and its precondition checks), not *how* it reaches the document — the same responsibility split rule 1 already draws between `PageOperations` and the UI for every other page capability.

## Relationship to Existing Rules and ADRs

- **`ARCHITECTURE_RULES.md` rule 1** (one owning facade per capability) is what this decision closes a gap in, not what it amends: "mutate a page's body from outside the editor" previously had no single owning facade method — `TaskOperations` implemented its own ad hoc version. `PageOperations.mutateBody()` is that owning method now.
- **`ARCHITECTURE_RULES.md` rule 2** (Gate is the sole disk writer) and **rule 12** (one write path per capability) are unchanged and unrelaxed — see Decision point 3.
- **[ADR-018](./018-document-editing-identity-decoupling.md)** established that `DocumentEditing` (`DocumentSession`/`DocumentRegistry`) has zero knowledge of `Page`/`Vault`. This ADR preserves that boundary exactly: the session-vs-Vault dispatch decision lives in `PageOperations`, which already pairs session state with domain metadata for other purposes (ADR-018 Consequences, point 2) — `DocumentEditing` itself gains no new responsibility or dependency.
- **[ADR-020](./020-effective-page-state-projection.md)** (`EffectivePageState`) is unaffected — it remains read-only reconciliation for presentation and has no write role in this decision.
- **`durability-model.md`** — see the amendment below; this ADR does not add a new stage, it broadens Stage 1's description of what can enter it.

## Alternatives Considered

- **Model B (durable-first, reconcile a clean session after, special-case dirty).** Rejected: requires two simultaneous owners of "current content" for an open page, contradicting `ARCHITECTURE_RULES.md` rule 1/rule 3 directly rather than merely being unwieldy. Its dirty-session case has no resolution without inventing a merge engine this codebase has no other use for.
- **Model C (a dedicated `DocumentMutationService`/coordinator class implementing the same dispatch).** Rejected: the dispatch logic is five to ten lines, and `PageOperations` already brokers between `DocumentRegistry` and `Vault`/the Gate for every other page operation (open/save/close/archive/etc.). A new class for this one additional dispatch is the same "coordinator introduced to patch one method" shape already identified as a smell for routing this through `TaskOperations`+`DocumentRegistry` directly — moving the smell to a new file doesn't remove it. Folding the dispatch into `PageOperations` as a method reuses the facade whose documented responsibility (spec §6) is already "the one file every caller calls for anything page-related."
- **Model D (reject or queue the mutation while the session is dirty).** Rejected as the default per the Evaluation Summary — safe but user-hostile for the mainline case, and it does not remove the need for a routing rule, it just adds a rejection condition on top of one that would still be required for the clean-session case. Not needed as a fallback either, since Model A resolves the dirty case without data loss or blocking.
- **A fifth, novel model.** None was found. Every considered alternative either collapsed into Model A's dispatch logic (C) or reintroduced a rejected property of B or D under different packaging.

## Consequences

- `docs/architecture-specification.md` §5 (Persistence Gate), §6 (`PageOperations`), and §9 (`DocumentEditing`) are amended in this same documentation pass to state this routing rule as part of their frozen contracts (see this ADR's companion doc edits).
- `docs/durability-model.md` Stage 1 ("Committed") is amended in this same pass to state that an app-initiated mutation routed through `PageOperations.mutateBody()`'s session branch enters Committed exactly as a user keystroke does — same guarantee, same non-guarantees, no new stage.
- `docs/architecture-compliance-checklist.md` gains one item (Application Layer Rules) checking that a PR adding or modifying an app-initiated body mutation routes through `PageOperations.mutateBody()` rather than reading `Vault`/`DocumentRegistry`/`DocumentSession` directly from a feature facade.
- **`TaskOperations.mutate()` is rewritten** to call `PageOperations.mutateBody()` instead of reading `Vault` and enqueueing the Gate directly (see Implementation Record below).
- **Implementation Note (superseded — see Implementation Record):** this ADR was originally accepted design-only, with implementation withheld pending explicit approval. That approval was subsequently given; the Implementation Record below documents what was actually built.

## Implementation Record

Implemented as designed above, with one refinement discovered during implementation and one explicit product decision, both recorded here so this ADR reflects the shipped contract rather than only the original design intent:

- **`PageOperations.mutateBody()`'s session branch calls `this.commitEdit(pageId, transform(session.currentRevision.markdown))`, not `session.commit()` directly** — see Decision point 4 above, corrected from the original text during implementation once tracing the autosave path showed `session.commit()` alone never arms `SaveCoordinator`.
- **`TaskOperations`'s constructor changed from `(vault: Vault, coordinator: PagePersistenceCoordinator)` to `(pageOperations: PageOperations)`.** Neither prior dependency was used anywhere else in the class once `mutate()` stopped reading `Vault`/the Gate directly, so both were dropped rather than kept alongside the new one. `Application.ts`'s construction of `TaskOperations` (already ordered after `PageOperations`) was updated to pass `this.pageOperations`.
- **Task line lookup moved inside the `transform` closure**, not left as a value computed before calling `mutateBody()`. `TaskOperations.mutate()` now passes `(markdown) => { const lines = markdown.split('\n'); const lineIndex = lines.indexOf(rawText); ... }` — the line search runs against whatever Markdown `mutateBody()` supplies (the open session's current, possibly dirty content, or the Vault's durable copy), never against a Vault snapshot captured before dispatch. This is the specific mechanism that fixes the bug in this ADR's Context: a task toggled while unrelated prose is dirty in the same open session now finds its line in the session's current content, not stale Vault content.
- **Abandoned-write error text is preserved exactly, via a typed error rather than string-matching.** `PageOperations.mutateBody()` throws a new, exported `MutateBodyAbandonedError extends Error` (carrying `pageId` and `reason`) when the Gate's no-session-branch write comes back `{ status: 'abandoned' }`, instead of a plain `Error`. `TaskOperations.mutate()` catches specifically `error instanceof MutateBodyAbandonedError` and rethrows `Failed to update task "${task.text}": ${error.reason}` — byte-identical to the message `TaskOperations` threw before this ADR. Page-not-found and archived-page errors are not caught or rewrapped by `TaskOperations` at all; `mutateBody()` already throws them with the exact same text `TaskOperations` used to throw itself, so they propagate unchanged. This was a deliberate, reviewed departure from the ADR's original Decision text (which did not specify the abandoned-write error's exact shape) — a plain generic `Error` was considered and rejected in favor of `MutateBodyAbandonedError`, so the one caller needing task-specific phrasing for this failure mode doesn't have to pattern-match an error message string. This is a small, purpose-built type (one class, two readonly fields), not a new coordinator/merge/conflict mechanism — it does not change the Decision or Alternatives Considered above.

## Why This Approach Is Preferred

It answers the same standing question every prior ADR in this series judges itself against: does this keep exactly one thing owning exactly one concern? Yes — "who owns a page's current content" already had a clean answer for editor keystrokes (`DocumentSession`, when open) and for closed pages (`Vault`); the only gap was that app-initiated mutations weren't required to ask the question at all. This ADR closes that gap with the smallest possible extension — one dispatch method reusing two already-owned, already-correct write paths — rather than inventing a new synchronization mechanism, a merge engine, or a second notion of "current content." It is also the option every future body-mutating feature composes with for free: task completion, formatting commands, template insertion, bulk transforms, and AI-assisted edits are all, at the point they reach `PageOperations`, nothing more than a `(markdown) => markdown` function — the same shape spec §9 already named `DocumentTransaction` as being "sized for today and shaped for tomorrow" to support.
