# ADR-063: Atomic vault saves — one native writer that replaces a file whole, on supported volumes only, and reports exactly what happened

**Status: In force — atomic saves are the only saving system (see "The only saving system" below).** Original status line, kept for history: Proposed (Stages 1 and 2a of the plan below: this ADR, the native module `apps/app/src-tauri/src/atomic_replace.rs` with its flush-only and inspection operations, three registered Tauri commands (`src-tauri/src/atomic_commands.rs`) and the TypeScript contract (`src/core/vault/atomicWrite/`). **Nothing in the application calls any of it**: production saves still use the fs plugin's in-place `writeTextFile`, unchanged). Builds on [ADR-001](./001-single-persistence-gate.md) (one write path through the Persistence Gate), [ADR-043](./043-sync-never-trusts-a-paired-rename-destination.md), [ADR-057](./057-filesystem-first-created-and-last-edited.md) (Created is the file's birth time) and [ADR-062](./062-crash-recovery-snapshots.md) (crash recovery). Uses the vocabulary of `docs/durability-model.md`; it strengthens the *Durable* stage and changes no other stage.

## Context

Every text file the application writes into a vault goes through `VaultFileSystem.writeFile`, whose only implementation, `LocalFileSystem.writeFile`, calls the Tauri fs plugin's `writeTextFile`. The plugin (`tauri-plugin-fs` 2.5.2, `write_file_inner`) opens the destination with `truncate: true, create: true` and writes in place, with no temporary file and no flush. A crash, a full disk or a failing write between the truncation and the last byte leaves the note empty or partial, and the retry machinery (`SaveCoordinator`: 2, 4, 8, 16, 30 s) assumes the old file is still there. ADR-062 keeps the *unsaved* text safe; nothing keeps the *saved* file safe.

`LocalFileSystem.writeFile` has more callers than notes. Replacing it changes all of them. The table is the call-site matrix (line numbers as of this ADR); *Intent* is what each caller means (decision 11), *Concurrency* is what it can assume today.

Binary writes and `copyFile` (assets) are separate primitives and are not part of this decision.

**Known corruption amplifier.** `workspaceStateFile.ts` reads the file, treats a parse failure as an empty object, merges one patch and writes the result. A truncated `workspace.json` therefore silently becomes a file holding only the latest patch. Atomic replacement removes the usual cause; the migration must still cover it (see *Scope of migration*).

Two measured constraints shape the design. First, `rename` over a file gives the replacement a **new inode and a new birth time**; ADR-057 defines Created as the birth time, so a naive temp-and-rename would reset Created on every save. Second, macOS FSEvents gives the watcher no rename correlation; the watcher side is a later stage (below).

## Decision

1. **One native writer, `atomic_replace::replace`**, writes a complete new file and replaces the destination in a single same-directory rename. It is the only way a vault file is replaced once it is wired; there is no second path.
2. **Mechanism.** In order: validate the target (symlink, kind, read-only, scope) and the volume; create a hidden, unique, fixed-length temporary file in the destination's own directory (`.clutter-tmp.<pid>.<n>.<nanos>`, 47 bytes, never derived from the note's name); write the complete contents; for an existing file copy its metadata (`fcopyfile`: mode, owner, flags, ACLs, extended attributes including Finder tags), restore its **birth time** (`fsetattrlist`, because the copy does not carry it), set the modification time to now, and verify the temporary file really carries all of it; flush the finished file (`F_FULLFSYNC`, falling back to `fsync` and reporting the gap); verify the target once more; rename (`rename(2)` over an existing file, `renamex_np(RENAME_EXCL)` for a new one); flush the parent directory; remove only what this operation created.
3. **Atomicity is not durability.** The rename makes the replacement all-or-nothing *visible*: a reader, or a crash, sees the old file or the new file, on a volume where same-directory rename is atomic. The flushes are *requests* that the data and the directory entry reach permanent storage. `F_FULLFSYNC` is the strongest request macOS offers; it is not a proof against every drive, controller or power failure, and power-loss behaviour is **untested**. Where a flush is rejected or fails, the result says so (`Durability::Unconfirmed`) instead of claiming more.
4. **Supported locations: ordinary local APFS only.** The destination directory's filesystem type is read (`fstatfs`) before anything is created; anything but APFS is refused with `UnsupportedFilesystem`. **APFS detection does not establish that a directory is local and unmanaged.** A folder inside iCloud Drive, Dropbox, OneDrive or another File Provider location sits on APFS, reports `apfs`, and passes this check, yet a provider may intercept renames, evict or re-materialise files, or sync the hidden temporary files. This ADR establishes **no** supported method for detecting such a location reliably, and does not claim to: **cloud-managed locations remain unverified even though their volume is APFS**, and the application must not describe a vault in one as protected. The policy is therefore: ordinary local APFS is the intended target; cloud-managed locations are unverified; every other filesystem (an earlier milestone observed the primitives on exFAT disk images, which is not evidence for production use; SMB and NFS were never tried) is unsupported until tested. A volume that rejects `RENAME_EXCL` or any other required step is refused with `UnsupportedOperation`. **No location, supported or not, ever falls back to an in-place or truncating write**; an unsupported vault fails visibly (the existing "Couldn’t save changes" path with a specific reason) and safely (the old file untouched, unsaved work still protected by ADR-062). Widening the list is a later, evidence-based amendment; so is any attempt to recognise File Provider locations.
5. **Metadata.** Mode, owner, flags, ACLs and extended attributes are copied and verified; **birth time is restored exactly** (a volume that stores less than sub-second precision is reported, never silent); the modification time is the time of the save. Anything that cannot be preserved refuses the write (`MetadataPreservationFailed`), it is not dropped. Hard links to the old file are broken (the link keeps the old content); another process holding the old file open keeps the old content; symlink targets are refused (`UnsupportedSymlink`), never written through; read-only files are refused, as an in-place write would be.
6. **Concurrency.**
   - A **native per-path lock** (in-process, on the canonical path) serialises replacements of one path and is retained. The Persistence Gate and Sync serialise per page identity in TypeScript, but this ADR does **not** assume that covers every physical-path write (`.clutter/*.json`, `.folder.md`, duplicates, two callers addressing one file by different routes), so the native layer defends itself.
   - **Lock identity.** The key is the canonical path, case-folded: on case-insensitive APFS `Note.md` and `note.md` are one file and share one lock (tested; over-folding on a case-sensitive volume only serialises two writers that did not need it). Names that differ only in Unicode normalisation (NFC versus NFD) are one file on APFS but two keys; folding them needs a normalisation table the module does not have, so this is a **documented limitation**, not something worked around: callers must spell a path as the scan spelled it. The key is the *path*, not the inode, because a replacement changes the inode.
   - **Expected-content validation lives inside the native operation.** A request may carry `ExpectedContent(bytes)`: the replacement proceeds only if the destination currently holds exactly those bytes, checked once early (to avoid wasted work) and **again immediately before the rename**, by reading the path itself and checking it is still the same file (device + inode). Anything else is `StaleExpected`: the write is **aborted, the destination is left as it is, and the caller reconciles from disk** (for Sync: the existing reconcile path) rather than overwriting. This is how Sync's repair writes (`persistSyncedPageDocument`, `.folder.md` repairs) stop overwriting an external edit with stale in-memory content. An unconditional write also refuses (`TargetChanged`, retryable: the retry starts again from the file that is there now) if the file at the path is no longer the file whose metadata was copied, so metadata is never stamped onto a different file.
   - **What this protects, and what it cannot.** It protects against *cooperating Clutter writers* completely. Against *external applications*, which do not take Clutter's lock, it narrows the window to the interval between the final comparison and the rename (microseconds) but cannot close it: an external atomic save landing in that interval is overwritten, and an external in-place write to the old file during the operation is lost with the old file. The earlier `RENAME_SWAP` compare-and-swap was **rejected** (see *Alternatives*): it did not close that window either.
7. **Outcomes.** (How the application handles each, exactly, is decision 13.) The writer never returns a bare error. `ReplaceOutcome` distinguishes, and callers must handle separately:
   - **Not committed** — the replacement did not occur and the original remains intact (verified from file identities, not assumed). Reasons include `InsufficientSpace`, `PermissionDenied`, `ReadOnlyTarget`, `UnsupportedSymlink`, `UnsupportedFilesystem`, `UnsupportedOperation`, `StaleExpected`, `TargetChanged`, `TargetMissing` (replace only), `MetadataPreservationFailed`, `DestinationExists` / `DestinationAppeared` (create only), `OutOfScope`, `Io`. Handling: the save fails through the existing mechanism: the page stays dirty, the failure notice shows, automatic retries run only for reasons that can change (`InsufficientSpace`, `Io`, `TargetChanged`, `PermissionDenied` for a moment); permanent reasons (`ReadOnlyTarget`, `UnsupportedSymlink`, `UnsupportedFilesystem`, `UnsupportedOperation`, `OutOfScope`) skip the retry budget and show their specific reason; `StaleExpected` and `TargetMissing` are never retried: the file changed or vanished behind the app and Sync reconciles; `DestinationExists` is never retried as a replace (decision 11). The recovery record is kept.
   - **Committed, durability confirmed** — the new content is installed and every flush succeeded. The note is saved; the recovery record is removed as usual (ADR-062).
   - **Committed, durability unconfirmed** — the new content is installed and visible, but a flush was rejected or failed (`FileFsyncOnly`, `DirectoryFsyncOnly`, `DirectorySyncFailed`). The vault model takes the new content (it *is* what is on disk) and the note is not shown as failed, **but this is not a normal save failure and must not be retried by rewriting**: the new file is already in place, and rewriting could replace a valid newer state. **The recovery record is not removed** while durability is unconfirmed; a later stage adds a flush-only operation (flush the file and its directory, no rewrite) that clears the state, retried with the existing backoff; the record is removed when it succeeds, and kept when it does not.
   - **Uncertain** — the replacement call returned an error and the state could not be proven either way. Nothing is deleted or retried automatically; `recovery_paths` lists the temporary file, which may hold the only copy of a revision. The note stays dirty and the recovery record stays. Before any further write the caller **inspects**: if the target equals the attempted content, treat it as committed; if it equals the previous content and the temporary file is gone from the destination, it was not committed and a retry is safe; anything else is an external change and is reported as a conflict, not overwritten.
   - After *any* error from the rename itself the writer inspects file identities before classifying; a post-rename error is never assumed to mean the original is intact.
8. **Temporary files.** The writer removes only a temporary file it created and never installed; one it cannot remove is reported (`leftovers`), not hidden. A temporary file left by a crash may hold a complete newer revision and is **never** deleted merely because the destination exists, and never by another write. The writer holds an exclusive `flock` on its temporary file until it finishes, so a later sweep can tell a live writer from a dead one; that sweep (take the lock, then surface or move aside, never silently delete) is a later stage. Until then abandoned temporaries accumulate (and, in a cloud-synced folder, would sync, which is one reason those are not supported).
9. **Crash recovery is unchanged in this stage.** ADR-062's rules stand: a recovery record is removed only when the note has nothing unsaved. The only new requirement is the one above for *durability unconfirmed*. A failed or uncertain save never causes the only valid copy of the user's content to be discarded.
10. **Failure injection is test-only.** The step-by-step fault seam (fail a step, make a rename take effect then report an error, run a side effect at an exact step) is compiled only for tests, so production carries no injection code.

11. **Create and replace are different intents, and the intent travels with the request.** The native request carries `Intent::{Create, Replace, ReplaceIfContent(bytes), Upsert}`; it is never inferred from whether the file happens to exist, so it survives a failure and a retry.
    - `Create`: the destination must not exist, at validation (`DestinationExists`) **or** at the rename (`RENAME_EXCL`, `DestinationAppeared`). A retried create is still a create: it can never become permission to replace a file another process made in the meantime. A caller that gets `DestinationExists` chooses another name or fails visibly.
    - `Replace`: the destination must exist (`TargetMissing` otherwise): a save never re-creates a deleted note (today's in-place write silently does). `ReplaceIfContent`: as `Replace`, and the file must hold exactly the expected bytes (`StaleExpected` otherwise). `Upsert`: replace or create, last writer wins; **only** for application state and `.folder.md` where either is correct (see the table), never for user notes.
    - Every replacing intent also refuses (`TargetChanged`, retryable, or `StaleExpected` for the conditional one) if the file at the path is not the file it validated.
    - **The smallest API change** to preserve this on the TypeScript side (not implemented here): `VaultFileSystem.writeFile(path, contents, intent?)` where `intent` is `'create' | 'replace' | 'upsert' | { replaceIf: string }`; absent means today's behaviour for test doubles and the in-memory provider, and the production `LocalFileSystem` requires it. Each call site in the table above passes the intent it has there; nothing is inferred by an `exists()` call (a check-then-write is exactly the race this removes).
12. **Two read-only-for-the-file companion operations are part of the writer** (`confirm_durability`, `inspect`; both take the per-path lock and apply the same scope, symlink and volume policies):
    - `confirm_durability(path, expected)` flushes the file and its directory **without rewriting anything**, only while the file still holds `expected`. `expected` is the identity of the revision: if a newer revision is on disk the answer is `Superseded` and nothing is flushed on its behalf, so confirming N can never stand in for N+1. Flush failures are reported (`Unconfirmed` with the gaps), not hidden; a refused or unreadable file is `Refused` / `Failed`.
    - `inspect(path, attempted, previous, temp_paths)` answers, after an `Uncertain` write, whether the destination holds the attempted content (`HoldsAttempted`), the previous content (`HoldsPrevious`), nothing (`Missing`) or something else (`HoldsOther`: an unresolved third state), plus what each listed temporary file holds. It reads only this writer's own temporary files in the destination's directory and refuses any other path. When previous and attempted are identical it reports `HoldsAttempted`: the file is what the caller wanted whichever way the write went. Operations are associated with the caller's intended destination and content, which is also how a revision is identified: the native layer has no notion of revision numbers and must not.
13. **How the application handles each outcome.** The page's state is `dirty` (unsaved in memory), `saved(N)`, or failed (`SaveError`, still dirty). A revision is identified by its content (and the editor's revision number, which stays in TypeScript).
    - **Not committed.** The page stays dirty and shows the existing failure notice. Automatic retries (existing backoff) run only for reasons that can change; manual Retry is always allowed. Every retry runs the *same intent* and the *current* revision (a retry never writes an older revision than the newest edit, as today). The recovery record stays. A second save is serialised behind the first by the per-page queue. `TargetMissing` / `StaleExpected` are never retried: the file was deleted or changed behind the app, Sync reconciles, and the unsaved text is recoverable through ADR-062's `missing-note` / `conflict` paths. Shutdown with the note still dirty goes through the existing "Close anyway" flow; startup offers the record as today.
    - **Committed, durability confirmed.** `saved(N)`; the recovery record is removed if (and only if) the note has nothing unsaved at that moment, so a newer edit N+1 keeps its record.
    - **Committed, durability unconfirmed.** `saved(N)`: the content is installed and visible, the Vault model takes it, no failure is shown. **It is never retried by rewriting.** The application records a durability-pending entry keyed by *(page, revision N, content)*. While that entry exists the recovery record that protects N is kept even though the note is clean. The application asks `confirm_durability(path, content N)` with the existing backoff (2, 4, 8, 16, 30 s): `Confirmed` clears the entry (and then the normal removal rule runs against the *current* state, so N+1's record is untouched); `Superseded` also clears it (the file now holds something else, whose own result governs); `Unconfirmed` / `Failed` keep it and retry; after the budget the record is simply kept. A newer edit N+1 does not wait for N: it is saved normally, by replacement of a file that already holds N. **Shutdown** makes one bounded confirm attempt and then leaves the records. **Startup**: if the vault holds the text, the record is classified `already-saved` and removed: the content survived a restart, which is the evidence that matters; if the vault lacks it, the record is offered as usual.
    - **Uncertain.** The page stays dirty and failed; `saved(N)` is **not** recorded; nothing is retried automatically and nothing is repeated blindly. The next attempt of any kind first calls `inspect(path, attempted, previous, recovery_paths)`: `HoldsAttempted` → treat as *committed* (then durability as above); `HoldsPrevious` → *not committed*: a normal retry is safe (the listed temporary file stays until a sweep); `HoldsOther` → someone else changed the file: **do not write**, keep the page dirty and the record, report that the note changed on disk, and let Sync reconcile (what the user then does with their text is the existing conflict handling, not a new overwrite); `Missing` → as `TargetMissing`; an inspection that is itself refused or fails leaves the state uncertain. **A second save while the first is uncertain** (revision N+1) is held by the per-page queue until the inspection resolves; then it proceeds (`HoldsAttempted`: replace the file that holds N; `HoldsPrevious`: replace the previous file, superseding N; `HoldsOther`: blocked). The recovery record is kept throughout. A create uses `previous = None`: `Missing` means not committed, `HoldsOther` means someone else created the file.
14. **Corrupt JSON in `.clutter/workspace.json` is quarantined, never silently reset.** Atomic writes alone do not fix `workspaceStateFile.ts`: it parses the file, treats a parse failure (or a non-object) as `{}`, merges one patch and writes the result, so one unreadable file becomes a file holding only the latest patch. The policy (the one `TagMetadataStore` already follows) is: read the raw text; if it does not parse as an object, **first** copy the raw bytes aside with `Create` to `workspace.json.corrupt-<timestamp>` (on `DestinationExists` retry with a new timestamp), log once per distinct corrupt content, and only after that copy exists use `{}` as the base; if the copy cannot be made, **do not write** (workspace state is read-only for the session, with a warning). The write itself is `ReplaceIfContent(raw)` (or `Create` when the file was missing); `StaleExpected` means another writer got in: re-read once and redo the merge. Nothing else about `workspace.json`, its queue or its merge semantics changes. The same read-modify-write shape applies to `ResourceArchiveMetadataStore` (which also needs a queue) and to `tags.json` (already tolerant).

## Known limitations

- **Ownership.** The replacement is created by the current user. If the destination is owned by someone else (a shared folder), metadata verification refuses the write (`MetadataPreservationFailed`) although an in-place write to a file the user may write would have succeeded. There is no fallback.
- **Directory permissions.** Replacement needs write permission on the *directory* (to create the temporary file and rename); an in-place write needs it only on the file. A vault folder that is read-only while its files are writable can no longer be saved to (`PermissionDenied`).
- **Space.** A save transiently needs room for a complete second copy of the file.
- **Large notes** are written whole each time, as today.
- **Whole-document regeneration** (frontmatter is rebuilt from the in-memory page on every save) is unchanged. A Gate save is no longer unconditional: it is refused as "changed on disk" when the file is not what the session last read or wrote, and Sync repairs are expected-content protected (see "Editor versus disk"). The one remaining unprotected window is an external edit made between that final check and the rename (microseconds; see Lock identity below).
- Power-loss durability is requested, not proven (decision 3); ordinary local APFS is the only supported location, and cloud-managed folders are unverified even though they are APFS (decision 4).
- **Lock identity** is case-folded but not normalisation-folded (decision 6). **External applications** do not take Clutter's lock: the final check narrows the window to microseconds and cannot close it; an in-place external edit that keeps the same inode is caught only by `ReplaceIfContent` (content), not by the identity check.
- The hand-written native declarations are checked against the SDK headers on the build machine (arm64); the x86_64 `fstatfs$INODE64` path has not been exercised.
- Replacement changes the inode: tools that track a note by inode see a new file.

## Scope of migration (later stages; not done here)

- **Stage 2a — the commands and the contract, unwired to callers (done; see the section below).**
- **Stage 2b — wire it.** Route `LocalFileSystem.writeFile` through the command; convert every caller in the table to its intent (not only notes); implement the outcome handling of decision 13, including the durability-pending entry and the uncertain-inspect gate in the Gate/`SaveCoordinator` path, and the recovery journal's removal rule; handle the watcher (ignore `.clutter-tmp.*` names so the temporary half never enters rename pairing, and make sure the destination of a temp-to-note rename is always notified, with self-write suppression still consuming it); give Sync repairs `ReplaceIfContent` (plumbing the raw text the scan read); apply decision 14 to `workspace.json` and give `ResourceArchiveMetadataStore` a queue; replace `writeFileAtomic` for `tags.json`.
- **Required coverage for every caller of the shared writer**, not only notes, including: a retried create stays a create; `TargetMissing` does not resurrect a deleted note; an unparsable `workspace.json` is quarantined and not reset; `StaleExpected` on a Sync repair reconciles instead of overwriting; a newer revision's recovery record survives confirmation of an older one; an uncertain save is inspected before any retry.
- **Stage 3 — temporaries and unsupported volumes.** The sweep policy (decision 8) and the user-facing message for an unsupported or unverified location.
- Later: asset writes and `copyFile`; any widening of the supported list; any recognition of File Provider locations.

## Stage 2a: the integration boundary (implemented, not activated)

**Production is unchanged.** `LocalFileSystem.writeFile` still calls the plugin's `writeTextFile`; no caller constructs `NativeAtomicVaultWriter`; a test fails if any non-test source outside `atomicWrite/` imports the contract, or if `LocalFileSystem.ts` mentions the commands. The contract is a *separate* interface (`AtomicVaultWriter`), not an extension of `VaultFileSystem`, so a `Promise<void>` from `writeFile` can never be read as an outcome, and a writer states its `kind` (`native-atomic` or `in-memory-simulation`).

- **Commands** (`atomic_write_file`, `atomic_inspect_write`, `atomic_confirm_durability`, macOS only, registered in `lib.rs`): serialisable requests (`deny_unknown_fields`, so a forged field such as a filesystem list is a request error) and tagged, camel-cased results. They run off the main thread.
- **Trust boundary.** The backend holds no registry of open vaults: the Space registry lives in the webview, and the existing `allow_vault_asset_scope` and `start_vault_watcher` already take frontend-supplied roots. A vault root from the frontend is therefore **not authorization** here. Authorization is the approved filesystem scope (the *runtime* fs scope, `app.fs_scope()`: folders chosen in the native picker, which JS cannot grant itself; the static `$HOME/**` capability is a different scope and is not in it, see Stage 2b-ii). Each command: (1) the root must be absolute, exist, be a directory and be inside that scope; (2) the root must contain a real `.clutter` directory (an integrity check that catches a wrong root *inside* the scope; it is not an extra authority, since anything that can write inside the scope can create one); (3) the target must be absolute and inside the scope (the plugin's own test); (4) the target's canonical parent must lie inside the canonical root, resolved once (this refuses `..` and symlinked folders that point elsewhere, which Tauri's string match accepts for a path that does not exist yet). Inspection and durability confirmation apply the same four rules, and inspection additionally requires each listed temporary file to be inside the scope and to be one of this writer's own (name shape and directory). **The root only narrows**: a root broader than the real vault is still inside the scope, so these commands give the webview no more than the plugin already does. Closing that remaining gap needs a backend-held list of the vaults the user opened, which does not exist; it is reported, not invented.
- **Tests at the real boundary.** The commands are invoked through Tauri's mock runtime with real IPC dispatch and the real fs-plugin scope (`tauri` `test` feature, dev-dependency only, no new crate): registration, the documented JSON, a forged root, a root with a vault marker that is not itself approved, a target outside the scope, a symlinked parent, inspection and durability confirmation of out-of-scope targets, and invalid or missing root information, each asserted as *rejected* with the target untouched. Removing the containment, the root-scope check or the marker check makes tests fail. The wire format is held to one text on both sides (the same documents are asserted in Rust and parsed in TypeScript).
- **Recovery invariants, as pure code with tests** (`uncertainWritePolicy.ts`, `durabilityLedger.ts`; nothing wired):
  - After an uncertain write the destination is inspected first, for every retry, manual or automatic alike. Attempted content on disk is *visible* and durability is not claimed (it stays unconfirmed until `confirmDurability` says otherwise). Previous content on disk allows a retry that preserves the intent, with a replace becoming a conditional replace against the observed content, so an intervening change makes the retry fail (`staleExpected`) rather than overwrite. Different content is a conflict: no write, recovery record kept. A missing destination is `target-missing` for a replace (never re-created); a create stays a create. An inspection that itself fails leaves the write uncertain. The unavoidable race between the final comparison and the rename remains for applications that do not take Clutter's lock.
  - The durability ledger is keyed by page **and content**. Confirming N clears N; `superseded` for N retires N only and implies nothing about N+1 (a newer version being visible is not a confirmation of it); a recovery record may be removed only when the note has nothing unsaved **and** no pending entry exists for that record's own content.
  - **Revised in 2b-i: the ledger tracks save attempts, not content.** Content alone is not an identity (A -> B -> A writes the same bytes twice), so each `add` returns an `attemptId` and `confirmed`/`superseded` retire that attempt only; an older attempt's answer can never clear a newer attempt with identical bytes. Record removal is blocked while *any* attempt holding the record's content is pending.
  - **Smallest changes still required before activation** (not made): the Gate/`SaveCoordinator` path must call the policy after an `uncertain` outcome and hold a second save behind the inspection; it must add to the ledger on `committed` + `unconfirmed` and drive `confirmDurability` on the existing backoff; and `RecoveryJournal`'s removal rule must consult `mayRemoveRecoveryRecord` with the record's content. Each needs its own tests where it lands.
- **Folder duplication corrupted binary files — fixed in Stage 2b-i.** `VaultEntryDuplicator.copyContents` used to read every file with `readFile` (`readTextFile`, UTF-8 decode with replacement) and write it with `writeFile`, so invalid bytes in a PNG or PDF became U+FFFD. It now copies each file with `copyFile` (bytes, never text), as `duplicate(file)` always did. Regression tests (`VaultEntryDuplicator.binary.test.ts`) run the real plugin JavaScript against a fake IPC and assert byte-for-byte equality, including nested folders; they fail against the old text path.
- **`ResourceArchiveMetadataStore` lost logical updates under concurrency — fixed in Stage 2b-i.** Even with every write atomic, two concurrent `record` calls left one record and an archive racing a restore could resurrect or drop one: the loss was in the read-modify-write, which atomic replacement cannot fix. All store operations now run through a failure-tolerant per-store promise queue (as in `TagMetadataStore`). It serialises within one process only; another process is covered, if at all, by `ReplaceIfContent`. Regression tests (`ResourceArchiveMetadataStore.concurrency.test.ts`) are ordinary passing tests, including that a failed operation does not wedge the queue.

## Activation boundary and Stage 2b sequence

- **Registered is not inactive.** Any Tauri command registered in `lib.rs` is callable by every webview, including one that has loaded unexpected content; "no caller constructs the writer" says nothing about who can invoke `atomic_write_file`. The commands' only defences are the fs-plugin scope and the vault-root narrowing described above, and a `.clutter` marker is not proof that a vault was opened by the user. Before activation the commands should be feature-gated (not registered in production builds until 2b-iii) and, ideally, authorise against a **backend-held registry of opened vault roots** rather than a frontend-supplied one.
- **No partial production rollout.** A Gate-only atomic rollout must not ship: Sync still writes through the plugin's truncating writer, and a Rust per-path lock cannot serialise writers that do not go through it. Gate-only use is acceptable in a disposable test vault.
- **Sequence.** 2b-i: fix folder duplication and archive-metadata lost updates (done; separate small changes, regression tests passing). 2b-ii: test the registered Rust commands in a real, isolated Tauri app, including denied paths and unexpected response states. 2b-iii: integrate atomic saves across Gate **and** Sync together with the watcher and recovery handling, tested as a whole before anything is enabled. `atomic_replace.rs` is not to be expanded again.

## Stage 2b-ii: the commands in a real Tauri application

`apps/native-verify` is an isolated Tauri app (its own crate, not part of Clutter) that compiles `atomic_replace.rs` and `atomic_commands.rs` unchanged and registers them as `lib.rs` does. A scenario runner hands every call to a real WebView, whose JavaScript performs it through the real IPC bridge; the runner then inspects the actual disk. 84 checks pass: create, replace, replaceIfContent, upsert, inspect and flush-only confirm; birth time, mode, extended attributes, file flags and owner preserved (and the documented inode change and broken hard link); a real full APFS volume (temporary file refused, and a write that runs out of space mid-file, both not committed with nothing left behind); an ACL that denies the final rename (not committed, the leftover temporary file reported in `leftovers`); read-only, immutable, unwritable-directory, directory, symlink and FIFO targets; HFS+, MS-DOS and exFAT volumes refused as `unsupportedFilesystem` with nothing written, case-sensitive APFS accepted; forged roots, `..`, symlinked directories, another vault, malformed requests; and 16 racing conditional replaces (exactly one wins), 12 racing creates (exactly one wins), 24 racing replaces against a concurrent reader (never a torn file).

Findings, and what was done about them:

1. **Authorization scope (fixed, with a real-app test).** The commands authorise against the runtime scope, not the capability's `$HOME/**`. `app.fs_scope()` starts empty and holds only what is granted at runtime. Tested in the **real Clutter binary**, in a throw-away `HOME`: a folder made as `createSpaceFolder` used to make a Space (a plugin `mkdir` in Documents) was reachable by the fs plugin, but `atomic_write_file`, and the existing production commands `rename_space_folder` and `move_file_no_clobber`, all refused it (`outOfScope`, `forbidden path`). So a Space made with "Create" had no runtime grant; only a picked Space did (the dialog plugin calls `fs_scope().allow_directory(path, recursive)`). That was a defect in Space creation independent of atomic saves. Fix, reusing the existing persisted-scope plugin (it saves every change to the fs scope, so no second persistence system was added):
   - **Create is one backend operation.** `create_space_folder(name)` (`space_folder.rs`) validates the name again, makes the folder non-recursively and exclusively in Documents, and grants exactly that folder; if the grant fails the folder it just made is removed. `createSpaceFolder` in TypeScript now calls it instead of a plugin `mkdir`; the Space is registered only after it returns, as before.
   - **Existing created Spaces** are restored when they are opened: `ensure_space_access(path)` grants only a real (not symlinked) direct child of Documents that already holds a real `.clutter` directory, and only that folder; a picked Space, an unmarked folder, a nested folder, a link, a Space elsewhere, Documents and the home directory are all left alone. It is honest to say this does not *prove* Clutter created the folder: the `.clutter` marker is Clutter's own artifact, and the grant adds no reach the webview lacked, since the fs plugin's static `$HOME/**` already covers every folder it can name; it makes the native commands agree with the plugin for those folders. Nothing broader than the specific Space is ever granted.
   - **Real-app results** (two launches sharing one app-data directory): a created Space can immediately be written, moved within and renamed, and the new name works; after a restart both the created, renamed Space and the restored legacy Space are still writable (restored from `.persisted-scope`, which lists only those exact folders); a name with `..` is refused and creates nothing; a duplicate name is refused; a legacy Space is refused before `ensure_space_access` and accepted after it; an unmarked folder, a Space under `~/Projects`, the home directory and Documents are refused before and after a restart; one Space cannot write into another, nor into an ungranted folder. Known small leftover: renaming a Space leaves its old path in the runtime scope (pre-existing behaviour of `rename_space_folder`).
2. **Caller gating (fixed).** Application commands are callable from every window by default, and the obvious fix, listing the three commands in Tauri's app manifest, was tried and rejected: once any app manifest exists, every other app command (`frontend_ready` included) needs a permission grant too. The commands therefore check their caller: only the `main` webview is accepted (`unauthorizedWindow`), covered by a mock-runtime test and by the verify app (an unauthorised window is refused for all three commands even inside a granted vault, while `main` still writes). They are also compiled in only with the off-by-default Cargo feature `atomic-writes`, so an ordinary build registers none of them. Migrating every command to the permission system is a separate, larger change.
3. **A rename failure can leave a temporary file the writer cannot remove** (an ACL that denies delete is copied to the temporary file with the other metadata). The writer reports it in `leftovers`; callers must surface or clean leftovers rather than assume none. To be handled with recovery lifecycle work in Stage 2b-iii, since such files may hold a complete copy of a private note.

Not covered here, by design: power-loss durability, SMB/NFS/cloud-synced folders, x86_64, and the native folder picker itself (it cannot be driven by automation; the verify app and the real-app test use `allow_directory`, the call the dialog plugin makes). Before releasing with atomic writes enabled, also move every application command under Tauri's permission system (`AppManifest::commands`, with a grant for each existing command) and keep the `main`-window check as defence in depth.

## Stage 2b-iii: integration (implemented; was off by default, now the only writer — see "The only saving system")

**Switch** *(historical: there is no switch now; see "The only saving system")*. `VITE_ATOMIC_WRITES=true` at build time (`featureFlags.atomicWrites`) together with the `atomic-writes` Cargo feature. Both off in every ordinary build, which is unchanged: the plugin's in-place `writeTextFile`, no native command registered. It is **one switch for every writer**: `Application.bootstrap` puts `AtomicWriteFileSystem` under the self-write wrapper, so the Persistence Gate, Sync's repairs and the `.clutter` state files all follow it at once; no writer keeps the truncating path while another replaces. `rawFileSystem` stays the plain provider (seal, Duplicate's byte copy), and the seal is honoured before the native writer.

**What was done, by decision.**
- *Intent (11).* `VaultFileSystem.writeFile(path, contents, intent?)`; every call site states `create`, `replace`, `upsert` or `{ replaceIf }`, enforced by a source-level test. A provider that cannot honour an intent ignores it.
- *Outcomes (7, 13).* `AtomicWriteFileSystem` maps them: committed is a successful write (a partly-flushed one is handed to `DurabilityTracker` and never rewritten); not committed throws `AtomicNotCommittedError`; a write in doubt is inspected immediately and again before any later write to the same path (`AtomicUncertainError`, or `AtomicExternalChangeError` when the file holds something else, reported once so a later explicit save is not blocked for ever). The pure policy gained one rule: the writer's own temporary file still holding the attempted content proves the rename never happened.
- *Retry.* `PageOperations` puts a failed save on the backoff only when `isRetryableSaveFailure` (a permanent refusal, a doubtful save and a changed file wait as `needs-action`, dirty and recoverable; every other error, including any non-atomic provider's, is retried as before).
- *Recovery.* A clean note whose last save is installed but not confirmed durable keeps its record (`RecoveryJournal` `holdRecord`/`recheck`); the tracker confirms on the existing backoff, shutdown makes one bounded attempt, and the next launch's `already-saved` classification is unchanged.
- *Watcher.* Measured on macOS: a rename of `.clutter-tmp.*` onto a note gives name events for both paths. The temporary path is now dropped before rename pairing (like `.DS_Store`); the note's events still arrive and Sync re-derives from disk.
- *State files.* Under the atomic provider `workspace.json` is quarantined when unreadable and written with `replaceIf`/`create` (decision 14); `writeFileAtomic` writes the target directly. `ResourceArchiveMetadataStore` keeps its queue and `upsert`.
- *Tests.* End to end over the in-memory simulation (`PageOperations.atomicSave.test.ts`: edit, Gate, provider, tracker, journal) for a normal save, a save with a flush gap, a newer edit while an older one awaits confirmation, a permanent refusal then a manual Retry, a doubtful save that provably did not happen, one that cannot be inspected, and a note deleted behind the app; the native writer itself is covered by the 84 real-WebView checks above.

**Not done, and why (each is a release blocker unless it says otherwise; the four-way build matrix has been run as real builds, see the next section).**
1. **Sync repairs are tied to the content they were derived from (done under the atomic provider).** Atomic replacement does not make a stale write correct, and a modification time is only supporting evidence, so a note repair is bound to the exact text its page was built from: `Page.sourceFingerprint` (`fingerprint` of that text, set by the scan, Sync's reconcile and the Gate's own writes, never written to frontmatter). `persistSyncedPageDocument` reads the file (or takes the text its caller already read), proceeds only if that text is the one the page identifies (a page without an identity falls back to its recorded modification time), then replaces the file only while it still holds exactly that text (`replaceIf`). The `.folder.md` repairs go through one shared `persistSyncedFolderDocument` with the same rule, expressed semantically because folders carry no identity: every metadata field the repair does not change must still equal what the file holds. A refused repair writes nothing, installs nothing in the Vault (the caller keeps the page it had) and calls `onStale`, and Sync then reconciles that path from disk itself on the page's own lane, bounded to three times per 30 seconds per path (startup repairs are reconciled as soon as Sync exists); it does not wait for an event that may already have come and gone. Gate saves are conditional too, see *Editor versus disk* below. The provider also refuses to write at all, from its first write, if the native writer is proven absent, whichever path constructed it.
2. **The notice tells four situations apart (done; deliberately small).** `PageOperations.saveFailureKind` classifies the failure (`classifySaveFailure`): `failed` ("Couldn’t save changes", Retry, as before; also a read-only file or no room), `unverified` ("Couldn’t verify the save", Retry, which inspects before it writes), `changed-on-disk` ("This note changed on disk", **no Retry**, because writing again would overwrite what is there; the one action is "Save as new note", which keeps the unsaved text as a new note beside the original and overwrites nothing), and `unsupported-location` ("Can’t save safely to this location", nothing to press). A save installed with only a flush gap is not shown as failed at all. The conflict itself is detected and resolved as described under *Editor versus disk*.
3. **Real-UI tests exist now, in an isolated build (`packages/automation/atomic-test`).** The first attempt (a throw-away `HOME`) leaked the developer's own Space registry: an unbundled binary's WebKit storage is keyed by its executable name, not by `HOME`. The harness builds a separate binary (`clutter-atomictest`, identifier `com.clutter.atomictest`, its own frontend build, port and cargo target), wipes that binary's own WebKit store at the start of each run, and every spec begins with `assertIsolatedProfile`, which throws before anything is written if the app-data directory is not the isolated one or any known Space lies outside the disposable root (tested against a seeded foreign registry). Results so far, in the real app on disposable Spaces: **(a)** an edit autosaves by replacement (new inode, birth time kept, frontmatter intact, no temporary file); **(b)** with the Space on a full 2 MB APFS volume the save is refused, the original note is byte-identical, no temporary file is left, the editor keeps the text, a recovery record exists, the UI shows "Couldn't save changes" with Retry, and once room is freed the bounded automatic retry saves the complete note. Running them found two defects that no simulation could: a Space the registry names but nothing granted was refused before its first write, and every dotfile of a granted Space (`.folder.md`, `.clutter/*.json`, the writer's temporary files) was refused because the runtime fs scope hides dotfiles; both fixed. More real-app results: **(c)** restart: two launches of one profile, the Space reopens by itself, the native writer still has access (grant restored, hidden files included) and a second edit is again a replacement; **(d)** `kill -9` with unsaved work (the recovery snapshot already written, the autosave not yet run): the note is byte-identical afterwards with no temporary file, the relaunch offers Restore, the restored text is saved and the snapshot cleared, and a third launch has nothing to ask; **(e)** an external atomic replace, an in-place edit and a writer-shaped rename over the open note all converge in the editor with the note neither deleted nor duplicated. In the native verification app, 110 `SIGKILL`s at random moments of back-to-back replacements of a 1 MB file left the destination a whole generation every time (12 landed with a replacement in flight and left only a hidden `.clutter-tmp.*` file). Found on the way: a vault under a **symlinked path** (`/tmp/...`) receives no watcher events at all (the events carry the resolved path), so the harness uses canonical paths; this is existing behaviour, not caused by the writer, and a Space reached through a symlink is unsupported until the watcher canonicalises. Not run in the real app, and why: a directory-flush failure and a rejected `F_FULLFSYNC` cannot be injected there (they are covered by the Rust fault-injection tests and the durability integration test); an external edit landing inside a Sync repair and rapid typing during a repair cannot be timed from outside (covered by the stale-repair tests, including one driving a real `VaultSyncService`).
4. **`.clutter-tmp.*` sweep and the unsupported-volume message** (Stage 3).
5. **Stale runtime grants.** Renaming a Space leaves its old path in the runtime fs scope, which has no revoke (only `forbid_*`, which would also forbid the name for ever). Policy to implement before release: keep the native commands' authorisation as *scope AND a backend-held registry of the Spaces opened or created in this session and the paths they currently occupy*, removed on rename and close, filled by `create_space_folder`, `ensure_space_access` and the picker's grant; the scope then only widens what the registry already allows. Persisted grants are left alone (they are the user's picks), and a registry entry never grants anything the scope did not.
6. **App commands under Tauri's permission system (done).** `build.rs` lists every application command (`APP_COMMANDS`) and `capabilities/default.json` grants each to the `main` window only (no remote origin). Tauri's application-command permissions are all or nothing: once one command is listed, every command a window calls must be listed and granted or it is refused, `frontend_ready` included, so `tests/command_permissions.rs` fails if `lib.rs`, `build.rs` and the capability ever disagree. The `main`-window check inside the atomic commands stays as a second layer. Verified in the real app: the whole real-app suite and all four cells of the build matrix pass with the permissions in place, the plain (no feature) build included.
7. **Picker regression.** The folder picker cannot be driven by automation. `ensure_space_access` only ever adds a grant for a marked direct child of Documents and never touches a picked Space's grant (unit-tested, and observed in the real app: a Space under `~/Projects` is neither granted by it nor affected after a restart). A manual check (pick a vault under `~/Projects`, relaunch, rename and move inside it) is still owed.

## Editor versus disk (done under the atomic provider)

A Gate save used to be unconditional: it serialized the Vault's page and replaced the file, so an autosave of a stale editor silently destroyed an edit made in another application, even one Sync had already seen. Now each `DocumentSession` carries `diskFingerprint`, the identity of the file text its saved revision corresponds to. It is set when the session opens (from the page) and after every successful save, and it moves otherwise only when Sync applies an external revision to a **clean** session; a dirty session keeps the version it started from. A Gate save (`writeParseRebuildReplace`, via `replaceFileGuarded`) reads the file, refuses with `AtomicExternalChangeError` ("changed on disk") unless it still has that identity, and replaces it only while it still holds exactly the text read (`replaceIf`), so a change in the read-to-rename gap is the same conflict. A save with no session (a metadata patch) is held to the Vault's own `sourceFingerprint`. Because the expectation is the session's base and not the Vault's latest, nothing needs remembering to keep a conflict alive: every later autosave, Retry, navigation-and-back and close-time flush re-reads the disk, finds the same difference and refuses, leaving the editor dirty and the recovery record in place. **Save as new note** creates `<name> (my changes)` with the unsaved text, then brings the original session in line with the disk (Sync reconciles the path first) and clears the failure; no step writes the file that was changed elsewhere. Tests: the full sequence in `PageOperations.atomicSave.test.ts` (external edit, autosave, more typing, autosave, Retry, close flush, navigation, Save as new note; with Sync's view of the page both stale and current; removing the check fails three of them), and the same scenario in the real isolated app. Any other provider is unchanged: the plugin writer still saves last-writer-wins.

Edges, each with a test: **(1)** every Gate write of a page goes through `PageOperations.enqueueGate`, which holds a guarded save that carries no expectation of its own (a metadata patch) to the session's base, and moves the base to the text Clutter itself just wrote (a metadata edit, a rename, an archive) when the session was in step with the Vault; so Clutter's own edits are never false conflicts, a dirty editor's text is never overwritten by them, and a session that had really diverged keeps its conflict. **(2)** A body save moves the base to the document it wrote, not to editor text typed since: when the follow-up save of the newer revision begins, the base equals what is on disk. **(3)** *Save as new note* creates a new page (own id, `create`-only, so it cannot replace a note), and only after that succeeds does the original follow the disk; if the copy cannot be made (disk full, name taken, write refused) the session stays dirty with the same text and conflict, the recovery record stays, nothing on disk changes, the error reaches the caller and the UI says "Couldn’t save as a new note". **(4)** The content identity is the 106-bit fingerprint plus the text's UTF-16 and UTF-8 lengths (`contentIdentity`); it is not a security hash, and it is never the only protection, since the replacement is conditional on the exact bytes read.

## The App Sandbox: every packaged build (verified in a sandbox-enabled build)

Every packaged Clutter runs in the App Sandbox, whether it was built locally (`npm run tauri build`) or comes from the Mac App Store; the entitlements are in `tauri.conf.json`, not in a distribution overlay, and nothing below depends on a distribution flag. Measured in a genuinely sandboxed, ad-hoc-signed build of the real app (separate identity, container, disposable folders), three things differed from an ordinary build:

1. **Create Space landed in the app's container.** `$HOME` and `Documents` resolve to `~/Library/Containers/<id>/Data`, and the real `~/Documents` is refused. Now (`space_access.rs`, `spaceFolders.ts`): inside the sandbox the real Documents is named by its real path, and the first Create opens the system picker on it; the user chooses it once. Cancelling, or choosing another folder, creates nothing, not even in the container (`create_space_folder` answers `documentsAccessNeeded`). Later creations ask nothing. The Create Space screen is unchanged.
2. **A picked folder was lost at restart.** Tauri's persisted scope remembers the *path*; the OS needs a **security-scoped bookmark**. A folder is bookmarked when the picker's result is accepted (a failure refuses the folder), every bookmark is resolved and its access started at launch before any Space is probed, and a folder whose access cannot be restored is presented as the Space whose folder has to be selected again, never opened from another place. Bookmarks live in `space-access.json` in the app data folder; entries that fail to restore are kept.
3. **The second save of a note failed.** The OS stamps every file a sandboxed process creates with a fresh `com.apple.quarantine` value (it embeds a timestamp), so the replacement file could never carry the original's. The writer's metadata check now requires the system-stamped attributes `com.apple.quarantine` and `com.apple.provenance` to be *present* on the replacement, not equal; every other attribute is still compared exactly, and a missing one still refuses the write.

**Dot entries without a broad scope.** The fs plugin builds its runtime scope with defaults, so a folder granted at runtime hides dot entries (`.clutter`, `.folder.md`) whatever `requireLiteralLeadingDot` says; only entries that come from a *capability* honor that setting, and inside the sandbox `$HOME/**` is the container. A first version added `/Users/**` and `/Volumes/**` to a static capability, only for the App Store build; that was replaced because it dropped Tauri's own restriction for everything under those paths and still left a Space picked elsewhere (for example `/opt`) without its dot entries. Now every folder the user authorizes (Documents, a restored bookmark, a picked folder) gets **one runtime capability of its own** (`space_access::grant_static_scope`, `Manager::add_capability`): `fs:scope` for exactly that folder and its contents, for the main window. Nothing else becomes reachable, wherever the folder is. A capability cannot be removed once added, so it lasts for the run; a folder name with pattern characters is escaped so it matches only itself.  The grant is the same for every authorized folder, sandboxed or not (it also fixes a Space picked outside `$HOME` in an unsandboxed development run, which used to hide its dot entries). Tested against the app's real permission tables (a runtime grant alone hides `.clutter`; the capability shows it for that folder only, never a sibling or anything outside) and in the real app.

Verified in the real sandboxed app (`packages/automation/sandbox-test`, local only: it names this machine's paths): sandbox and real-path reporting; nothing created before authorization or on cancel; Create at `~/Documents/<name>` after one grant, with no container copy; four atomic saves of one note, each a whole-file replacement; an external atomic replace shown in the open editor; rename and delete; image and PDF import through the system file picker; quit and relaunch with Documents restored without a prompt and the Space reopening; a picked folder outside Documents bookmarked, reopened after relaunch and saved to; a Space picked outside `/Users` and `/Volumes`, opened, saved and reopened after relaunch; Tauri's scope still refusing an unauthorized path (`~/Desktop`, `forbidden path`); a corrupted bookmark for each presented as needing selection, with access denied by the OS and nothing created elsewhere, and re-selecting restoring access. Not verified: a properly signed (Developer ID or App Store) build, TestFlight, iCloud or external volumes, and any App Review outcome.

Entitlements (`src-tauri/Entitlements.plist`, the one file every packaged build is signed with): `app-sandbox`, `files.user-selected.read-write`, `files.bookmarks.app-scope`, `network.client`.

## The only saving system (decided; supersedes "off by default" above)

Atomic saves are **on by default and the only way Clutter saves**, in development and in every packaged build (local `.dmg` and Mac App Store alike). Reason: a different writer in development than in production hides exactly the bugs real users would hit.

- **No switch.** The native writer is a *default* Cargo feature (`atomic-writes`) and `featureFlags.atomicWrites` is `true` with no environment variable that turns it off. `VITE_ATOMIC_WRITES` no longer exists. The one remaining build-time variable is whether the native writer is compiled in at all (`--no-default-features`), and a build without it refuses to open a Space with a clear error instead of saving some other way (`AtomicWritesMisconfiguredError`; tested as a real build in the matrix).
- **No fallback.** A failed atomic save (`notCommitted`, `uncertain`, an external change) is reported and the text is kept; it never reaches the plugin's truncating write. `AtomicWriteFileSystem` has no code path to the inner provider's `writeFile`, and a regression test asserts it for every outcome. A conflict, a full disk or a refused write ends in the recovery and Retry UX, not in a second writer.
- **Packaging fails closed, inside the build.** A release (packaged) compile fails in `build.rs` unless the atomic writer is compiled in and `tauri.conf.json` points at an `Entitlements.plist` that holds every required sandbox entitlement and none of the forbidden ones; `beforeBuildCommand` runs `npm run check:atomic` (the interface half). After bundling, `apps/app/scripts/verify-bundle.sh` (run by `build:share` and `build:appstore`, and available as `npm run verify:bundle`) fails unless the executable contains the atomic commands and the sandbox access commands, the sandbox entitlements are present, no forbidden entitlement (temporary exceptions, all-files access, debugging, `network.server`) is, and the WebDriver automation plugin is not compiled in. Distribution differs only in signing and packaging: `build:share` (Developer ID, notarization) and `build:appstore` (distribution identity, provisioning profile, installer package) need Apple credentials; `npm run tauri build` does not.
- **The old writer is kept, unused.** `LocalVaultProvider.writeFile` (the fs plugin's `writeTextFile`) stays in the repository, as the inner provider of the atomic stack (reads, moves, binary writes and the seal use it) and as the stand-in the contract tests compare against. No vault *text* write reaches it (`vaultTextWriteAudit.test.ts`, `writeIntentCoverage.test.ts`).

**Removal criteria for the legacy text writer** (delete `LocalVaultProvider.writeFile`'s text path, the `isAtomicWritesEnabled()` branches that choose between the providers, and `featureFlags.atomicWrites`, in one change), when all of these hold:

1. A properly signed Mac App Store build has been submitted and has shipped to real users with atomic saves, with no data-loss report attributable to the writer.
2. The packaged-app regression (the real-app suites in `packages/automation/atomic-test` and the sandbox suite) has passed against that signed build, including iCloud and an external volume (APFS only; any other volume is refused by design, see Known limitations).
3. The `--no-default-features` cell and the "never falls back" tests still pass, so the change cannot remove a safety by accident.

Until then the code stays, and nothing in normal operation calls it. The commands, how to test the sandbox locally, and the open release work are in [`docs/building-and-distribution.md`](../building-and-distribution.md).

## Alternatives considered

- **The existing `writeFileAtomic.ts` (temp file in TypeScript, then `moveFile`).** Visible `.tmp` next to the note, no flush, no metadata or birth-time handling (it would reset Created), and not conditional. Fine for a small JSON file, wrong for notes.
- **`RENAME_SWAP` compare-and-swap for the conditional write.** Exchanges the new and old files, compares the displaced file with the expectation, and swaps back on a mismatch. Rejected: it briefly exposes the new (wrong) content at the path, doubles the rename events the watcher sees, adds its own uncertain failure (a swap-back that fails), and still leaves a window in which an external write lands in the wrong file. A comparison made immediately before the rename, under the lock, is simpler and no weaker.
- **Keep writing in place but `fsync`.** Adds durability, not atomicity: the truncate-then-write window remains.
- **Fall back to an in-place write where replacement is unsupported.** Rejected outright: it reintroduces exactly the corruption this ADR removes, silently.
- **A hard-link claim for creation (as `move_no_clobber.rs` does for moves).** `RENAME_EXCL` claims the name in one step and is already used here; the move path is unchanged.
- **Rely on the Persistence Gate's serialisation instead of a native lock.** Rejected: it does not cover every physical-path writer (decision 6).

## Verification

Verified at module level only, in a scratch harness that compiles the file from its repository path without registering it (55 tests pass, 3 are manual or child-process helpers): successful replacement and creation without overwrite; a retried create stays a create; a replace never creates; failure before replacement leaves the original; a write that fails part-way (some bytes written, then an error) leaves the original complete and unchanged; rename failure before and after taking effect; directory-sync failure after replacement; uncertain outcomes; flush-only (no rewrite, no temporary file, `Superseded` for a newer revision, explicit failures and refusals, waits for the lock); inspection (previous, attempted, missing, third state, temporary files, refusals); concurrent writers to one path, including two spellings that differ in case; expected-content mismatch, including an external change between the early and the final comparison, equal bytes in a different file, and a deleted target; metadata and birth-time preservation; temporary-file removal failure; a read-only file and a read-only directory; the volume policy; the hand-written structure layouts; and that no descriptor leaks on any exit path (a mutation that leaks one, and one that un-folds the lock key, both make their tests fail). Not verifiable in that harness: power-loss durability, SMB/NFS/cloud and File Provider locations, x86_64, a destination owned by another user, and behaviour inside the running application (nothing is wired). The two volume tests that need a disk image remain manual.
