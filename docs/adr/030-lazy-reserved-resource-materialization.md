# ADR-030: Reserved/System Resources Are Lazily Materialized — Generalizing ADR-019 Beyond Daily Notes

**Status:** Accepted

## Context

`RESERVED_RESOURCES`/`RESERVED_FOLDER_IDS` (`vault/initialize/ReservedResources.ts`) declare five reserved folders (`.clutter`, `Daily Notes`, `Archive`, `Inbox`, `Templates`) and two reserved files (`.clutter/workspace.json`, `.clutter/tags.json`). [ADR-019](./019-retire-boot-time-daily-note-scaffolding.md) already established, for Daily Notes specifically, that a reserved resource's *definition* does not imply its *existence*: it retired `ensureDirectoryForToday()`'s boot-time scaffolding in favor of materializing the Daily Notes folder chain only at first-save time, via `DailyNoteService.ensureFolderChain()` calling `FolderOperations.ensureReservedFolder('daily-notes')`. That primitive — `FolderOperations.ensureReservedFolder()` / `PagePersistenceCoordinator.runEnsureReservedFolder` — is idempotent, Gate-serialized per reserved-folder id, and correctly positioned (Application-layer entry point, Persistence-Gate-layer mutation), and `Application.bootstrap()` already carries an explicit doc comment stating no reserved folder/file is eagerly materialized at boot.

Two problems, found by a full audit of every reserved-resource consumer (not limited to Daily Notes):

1. **The principle was never generalized into a standing rule, and two consumers never adopted it.** `NavigationRouter.openReservedFolder` (backing `openArchive()`/`openInbox()`/`openTemplates()`) read `vault.getReservedFolder(id)` directly and threw `Reserved ${id} folder not found in vault` when absent, instead of calling the existing `ensureReservedFolder()` primitive. `ensureReservedFolder('inbox')` and `ensureReservedFolder('templates')` had zero production call sites anywhere in the codebase — only `daily-notes` (via `DailyNoteService`) and `archive` (via the Gate's own `runArchive`/`runArchiveFolder`) were ever actually ensured. A fresh vault, or a vault where Inbox/Templates was deleted externally and reconciled away by `VaultSyncService`, made opening Inbox or Templates from the sidebar throw — the exact bug class ADR-019 already fixed once, recurring because the fix was applied to one consumer (Daily Notes) rather than encoded as a rule every reserved-resource consumer is checked against.

2. **`docs/architecture-specification.md`'s own Startup sequence still describes eager reserved-folder creation.** Line 707 reads `→ Platform: VaultInitializer.initialize(rootPath)   [ensure reserved folders]`. No file named `VaultInitializer` exists anywhere in the repository, and `Application.bootstrap()`'s shipped code does the opposite by design (see its own doc comment, `Application.ts:113-121`). This line predates ADR-019 and was never struck when the lazy design was implemented — ADR-019's own amendment only removed the Daily-Notes-specific `ensureDirectoryForToday` step from this sequence, leaving the separate, more general `VaultInitializer` line for the other four resources unaddressed. Per `implementation-rules.md` §4's divergence process, this is a case where the *implementation is correct and the specification is wrong*: the code already implements the target lazy-materialization architecture; the spec text simply drifted from it, undocumented, exactly the kind of silent drift `implementation-rules.md` §5 and §6 exist to catch.

## Decision

1. **`docs/architecture-specification.md`'s Startup sequence is corrected.** The `VaultInitializer.initialize(rootPath) [ensure reserved folders]` line is struck. In its place, the sequence states plainly that no reserved resource (folder or file, per `RESERVED_RESOURCES`) is materialized during `bootstrap()` — a missing reserved resource is scan-discovered as absent, the same as any other empty vault region — matching `Application.bootstrap()`'s own shipped behavior and doc comment.

2. **The lazy-materialization principle is stated as a standing rule, not a Daily-Notes-specific fix.** Generalizing ADR-019's finding: *a reserved resource being defined in `RESERVED_RESOURCES` never implies it is materialized on disk or in `Vault`*. It is materialized only at the point some feature actually requires it, through the one sanctioned mechanism for its resource type:
   - Vault-domain reserved folders (`daily-notes`, `archive`, `inbox`, `templates`) → `FolderOperations.ensureReservedFolder(id)`, backed by `PagePersistenceCoordinator.runEnsureReservedFolder` — idempotent, Gate-serialized per id.
   - `.clutter` (filesystem-only; never a Vault `Folder` — excluded from every scan by `isClutterInternalPath`) → `ensureClutterDirectory(fileSystem, vaultRoot)`, a deliberately separate, bare filesystem check-then-create primitive, since there is no `Vault` entity to register it as.

   No third primitive, and no per-resource wrapper (`ensureInbox()`, `ensureTemplates()`, etc.), is introduced or permitted by this ADR — every reserved-folder consumer calls one of the two primitives above, never a new one.

3. **`NavigationRouter.openReservedFolder` is corrected to follow the rule it was already supposed to follow.** It now calls `await this.folderOperations.ensureReservedFolder(id)` before `this.folderOperations.open(folder.id)`, for all three reserved-folder navigation intents (`openArchive`/`openInbox`/`openTemplates` — Archive included, since its unguarded read had the identical latent shape even though an archive operation usually ensures it as a side effect first). This is the one production code change this ADR's decision requires; it is a call-site correction to an existing method, not a new abstraction — `NavigationRouter`'s spec contract ("if an intent needs to mutate a page/folder, it delegates to `PageOperations`/`FolderOperations`") already permitted this, since `ensureReservedFolder` is exactly such a delegated facade call, not a reimplementation.

4. **No public API signature changes.** `Application.bootstrap()`/`attachVault()`/`open()` are unchanged — this ADR corrects the spec's *description* of already-correct behavior, plus the one consumer that hadn't yet adopted the already-correct primitive. `NavigationRouter.openArchive()`/`openInbox()`/`openTemplates()` keep their `(): void` signatures (fire-and-forget, matching the existing pattern in `commit()`'s `void this.pageOperations.open(...)`), even though their private implementation is now `async`.

## Alternatives Considered

- **Reintroduce an eager `VaultInitializer`-style creation step to make the spec's existing text true.** Rejected outright — this is the exact architecture the bug report identifies as wrong: it would make every reserved folder's existence depend on "the application started" rather than "a feature required it," reintroducing the class of coupling ADR-019 already spent one ADR removing for Daily Notes.
- **Fix only `openInbox()`/`openTemplates()`, leave `openArchive()`'s identical unguarded read alone since Archive "usually" already exists.** Rejected — "usually exists because something else happened to ensure it first" is caller-discipline, not a structural guarantee, and is the same latent shape already flagged (non-fatally) in `MoveService.resolveArchiveDestination`/`FolderPathResolver.resolveArchiveDestination`. Fixing all three call sites in `openReservedFolder` with one shared code path costs nothing extra and closes the latent case too.
- **Leave the spec's stale `VaultInitializer` line in place as a harmless historical artifact.** Rejected per `implementation-rules.md` §4's divergence-handling process: a specification that describes different behavior than the shipped code is exactly the drift the architecture-governance process exists to prevent, independent of whether the drift is currently causing a visible bug.

## Consequences

- `docs/architecture-specification.md` §"Sequence Specifications → Startup" is amended to remove the stale `VaultInitializer.initialize` line and state the lazy-materialization rule generally, in the same place ADR-014/ADR-017/ADR-019's prior amendments to this exact sequence already live.
- `NavigationRouter.openReservedFolder` (`core/application/navigation/NavigationRouter.ts`) now ensures before opening, for `archive`/`inbox`/`templates` uniformly, via the existing `FolderOperations.ensureReservedFolder()` — no new primitive, no new file.
- `NavigationRouter.test.ts`'s two `throws when missing` tests for `openArchive`/`openInbox` (previously asserting the bug as intended behavior) are replaced with tests proving the ensure-then-open lifecycle for all three reserved folders: missing → recreate + open, already-present → open without a duplicate create, repeated opens stay idempotent, and an externally-deleted-then-reopened folder is recreated correctly.
- No change to `ensureReservedFolder`, `runEnsureReservedFolder`, `ensureClutterDirectory`, `DailyNoteService`, or the Archive Gate methods (`runArchive`/`runArchiveFolder`) — they were already correct and remain the reference implementation this ADR generalizes to the remaining consumer.
- `ARCHITECTURE_RULES.md` rule 2's scope note and `docs/architecture-compliance-checklist.md`'s Persistence Rules item both still reference `VaultInitializer` as an illustrative example name for "directory-only scaffolding that isn't a Gate bypass." Neither asserts a file by that name currently exists, and the underlying point (directory-only writes to reserved paths are not Vault-domain-content writes and so aren't Gate-governed) remains correct regardless of what the code that performs them is called — left unchanged by this ADR as out of its narrow scope, flagged here so a future pass doesn't mistake the naming mismatch for a new finding.

## Why This Approach Is Preferred

It closes the exact gap the audit found — two of five reserved folders never adopted the lazy-materialization primitive ADR-019 already built and proved correct for a third — using only that existing primitive, with one corrected call site. It also converts a fix that was previously scoped to "Daily Notes" into a standing, citable rule (`defined ≠ materialized`, plus the two-primitives-only rule for how materialization happens) that a future sixth reserved resource is checked against by name, rather than requiring this exact investigation to repeat itself the next time a new reserved folder is added and one of its consumers forgets to ensure it.
