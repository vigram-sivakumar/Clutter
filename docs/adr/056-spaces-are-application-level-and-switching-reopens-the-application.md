# ADR-056: Spaces are application-level; switching a Space closes the Application and bootstraps a new one

**Status:** Accepted (approved for implementation, 2026-10-15). Adds no subsystem, write path or Gate operation. `Application` stays one-per-vault-root; the Space registry lives above it, in the UI shell where the Composition Root is already created and closed (ADR-014).

## Context

Until now the vault root was one hard-coded path in `AppShell` (marked TODO "replace with the folder picker"). Product wants several Spaces — a Space is an existing folder on disk, named after that folder — with "New space" opening the native directory picker, and the active Space restored on restart.

Investigation found the lifecycle already supports this:

- `Application.bootstrap(rootPath)` builds the whole runtime graph for one root, and `Application.close()` is its orderly, idempotent teardown (flush every dirty page and folder, flush the workspace session, stop the filesystem watcher, dispose sync, cancel timers, dispose projections, clear sessions). Its own doc comment names "an eventual vault-switch flow" as an intended caller.
- `AppShell` already creates and closes an `Application` in an effect keyed on `vaultPath`.
- The Rust watcher is token-owned (`should_stop`), so a belated `stop` from the old watcher cannot tear down the new one.
- Every per-root store (`.clutter/workspace.json` keys, parsed-note cache keyed by root) is loaded inside `bootstrap`, so nothing from a previous Space survives in the new `Application`.

No ADR defines multiple Spaces or a registry. Nothing app-level (outside a vault's `.clutter`) is persisted today except the parsed-note cache.

## Decision

1. **The registry is application-level and lives outside every Space**: `{ paths, activePath }` under one key (`clutter.spaces.v1`) in the webview's `localStorage`, read tolerantly (anything malformed yields the default registry) and written best-effort. It is deliberately not in a Space's `.clutter` (a Space cannot know about its siblings, and an unreadable Space would hide the list that leads out of it).
2. **A Space is identified by its normalized path**; its display name is the folder's name. Registering a folder already in the registry only activates it. No separate display-name field.
3. **Switching = prepare, then commit.** Changing `activePath` makes `AppShell` `bootstrap()` the next `Application` (filesystem, scan, stores, services) *while the current one stays mounted and usable*; `bootstrap()` starts no watcher and shows nothing. Only once it is built does a short commit run, serialized with any other: close the current `Application` (its orderly `close()`), `open()` the new one, and swap the UI in one render. The watcher is a single native slot with one global event name, which is why the old Application must close before the new one opens. At most one `Application` is ever *open*; a prepared one that was superseded or cancelled is closed unused. The "Opening Clutter…" frame is the first-open path only. `AppLayout` is keyed by the vault root so state it reads once at mount is rebuilt per Space.
4. **Safe failure.** A folder is probed read-only (`probeSpaceFolder`: exists, is a directory, readable, inside the filesystem scope) before any switch; `bootstrap` would otherwise create a missing root. If preparation fails, nothing changes but the registry, which returns to the last Space that opened; if the new one fails during `open()` after the old one closed, the old one is rebuilt and reopened. The registry is persisted only after a Space has opened, so a bad folder is never what the next launch tries first. At startup the stored active Space is probed and nothing else: see the amendment below.
5. **No import step.** Existing Markdown, PDFs, images and subfolders are indexed by the normal scan. Opening a Space writes only what a normal open already writes (see Consequences).

## Alternatives considered

- *Registry in each Space's `.clutter`* — rejected (decision 1).
- *Native store via a Rust command or `plugin-store`* — more durable than `localStorage` (which a browser-data clear would wipe) but adds Rust/dependency surface for a small list. The registry is behind `loadSpaceRegistry`/`saveSpaceRegistry`, so this is a contained later swap.
- *Open two `Application`s at once for a seamless swap* — rejected: the Rust watcher is a singleton and both would hear its global events. Only *preparation* overlaps.
- *Reload the window on switch* — rejected: loses the orderly `close()` flush guarantee.

## Consequences

- During preparation the current Space stays fully usable. Between closing it and the swap (its final flush plus the new one's `open()`) the old screen is briefly inert; edits made in that window are not possible to flush.
- `bootstrap` can already write to a vault on open (duplicate-ID repair, archive/template reconciliation). A folder with existing notes may therefore receive those repairs on first open. This is existing behaviour, not new to Spaces.
- The filesystem scope is `$HOME/**`; folders outside the home directory are refused by the probe.
- The registry is per webview profile, not synced across devices.
- Not covered here: renaming or removing a Space, a Settings view. (Avatar and identity: see the Space profile amendment below.)

## Amendment (startup fallback removed; vault roots are never recreated)

- **Fallback to the next available Space (supersedes an earlier "no fallback" amendment).** When the active Space is lost — its folder is confirmed missing at startup, or disappears while the app runs — the shell tries the other registered Spaces in registry order, starting after the lost one and wrapping (`fallbackCandidates`: only folders that probe as `available` right now; confirmed-missing and inaccessible folders are never offered). Each is opened through the same validated flow as the Welcome dialog (`selectSpace` → bootstrap → open): the active path changes in memory for the attempt, is persisted only if it opens, and is put back if it does not, then the next candidate is tried. The Welcome dialog shows only when no registered Space can be opened (or none is configured). While this runs the shell shows the opening frame, never the Welcome dialog or the lost workspace. Every registry entry, the lost one included, stays as stored; permission and scope failures are not "missing" and keep the existing error screen at startup.
- **A vault root is never recreated.** `Application.bootstrap` no longer creates a missing root (it throws `VaultRootMissingError`), and `LocalVaultProvider` refuses every recursive `createDirectory` (including `.clutter`, `Assets`, reserved/Daily Note folders, moves and duplicates) when the root no longer exists, so a background write can't turn a deleted or moved vault into an empty replacement. Creating a new Space's own folder is a separate, explicit operation (`createSpaceFolder`, non-recursive).
- **A vault that disappears while open is detected, discarded and replaced by Welcome.** `Application.verifyRoot()` runs one `stat` of the root (`isFolderConfirmedMissing`; only the OS's "no such file" counts — permission, scope and other I/O errors do not) and, on a confirmed loss, `handleRootLost()` seals the local filesystem (`LocalVaultProvider.seal()`: every later mutation is refused, so queued, in-flight or debounced writes cannot land, even if the folder reappears), stops the session store, autosave timers, sync service and cache write, and only then notifies `onRootLost` subscribers. `close()` on a lost Application skips every flush. `AppShell` checks on window focus / visibility (no polling) and treats any watcher `deleted`/`moved` event as a hint to run the same check — the watcher is not trusted to report loss of its own root (notify/FSEvents watches the root recursively but has no root-change flag, and `start_vault_watcher` drops watcher errors). On loss the shell drops the Application and runs the fallback above; only if no registered Space opens does it show the Welcome dialog over the startup frame. The registry, including the missing path, is never edited by this. Additive to the Composition Root (`Application`): three methods (`verifyRoot`, `onRootLost`, `isRootLost`), no new subsystem, write path or Gate operation.
- **Known and accepted:** the sync service still reconciles a vanished root as an emptied subtree if an event reaches it before the check completes (its tests assert this). That in-memory vault is never persisted (sealed) and never shown (the Application is discarded). Unsaved edits in the lost vault cannot be saved anywhere and are dropped.

## Amendment (Spaces may live anywhere the user can pick)

- **No location rule beyond "not too broad".** A Space may be any folder the user can choose in the native directory picker — Documents, a projects folder, an external drive. The only refusals are the disk root, the user's home folder itself, and a folder containing it (`isTooBroadForSpace`): opening one would scan, and write `.clutter` into, everything beneath it. This replaces the earlier rule that a Space must be inside the home directory (the statement above that folders outside the home directory are refused no longer holds).
- **Access outside `$HOME/**` persists through `tauri-plugin-persisted-scope`.** The static capability scope is unchanged (still `$HOME/**`; nothing was broadened). The native picker grants the chosen folder to the fs scope at runtime (`recursive: true`), and the new plugin, registered after `fs`, saves that scope to `.persisted-scope` in the app data directory and restores it at launch. Only folders chosen in the native dialog are ever added to the runtime scope — webview JavaScript cannot grant itself access — so only those are persisted. There is no UI to revoke a grant yet. macOS may separately prompt once for protected locations (Documents, Desktop, Downloads, removable volumes); those grants persist per app signature.
- **Unchanged:** a folder that is later missing (an unplugged drive) is a confirmed-missing Space and takes the fallback path; a folder that is merely inaccessible is not "missing".

## Amendment (a Space's identity and avatar live in the Space; the registry stays paths only)

- **Decision.** The registry (`clutter.spaces.v1`) remains exactly `{ paths, activePath }`: which folders Clutter remembers, and which was last active. It is not a source of truth for anything about a Space, and it never stores a Space's ID, name or avatar. Everything Space-specific lives inside the Space and travels with the folder: the `space` key of `.clutter/workspace.json`, `{ version, id, avatar? }`, owned end to end by `SpaceProfileStore` — a sibling store in the extension pattern ADR-033 and ADR-035 set out (a new top-level key, one reader, one writer, the shared serialized merge-write helper). Not Gate-backed, for the same reason as every other `.clutter/*` file (ARCHITECTURE_RULES.md rule 2's scope clause).
- **Identity.** `space.id` is a UUID issued once and never changed. Nothing reads it to find or reconnect a Space; it exists so a Space carries a stable identity of its own for what comes later (sync, sharing). A Space with no `space` key (every Space that predates this) is migrated lazily: it is given an ID the first time Clutter opens it — a deliberate, backward-compatible write that sits alongside the repairs `bootstrap` can already make on open. Selecting a folder, or opening the settings dialog, writes nothing.
- **Avatar.** An emoji is stored as is. An uploaded image is copied into the Space's `Assets/` with the existing cover-asset convention (`Application.importCoverAsset`, a non-Gate write like every asset import) and stored as the vault-relative reference, so nothing depends on the original file. The avatar is written only after the user confirms the settings dialog *and* the Space has opened (`Application.applySpaceProfile`), never before. Removing an avatar removes it from the file; the image copy stays in `Assets/` like any other user file.
- **No relocation detection.** A Space is a folder that Clutter opens; its path is its only handle in the registry. If a folder is moved or renamed outside Clutter its registered path simply stops being available, and the existing behaviour applies unchanged: fallback to the next available registered Space, or the Welcome dialog if none opens. If the user later selects the moved or renamed folder it opens like any other folder — a new registry entry, with its identity and avatar read from inside it — and the old path stays registered as unavailable, as before. Nothing searches the filesystem, matches folder names, matches IDs across paths, or re-points an old entry.
- **Display.** The Space selector and its menu show each registered Space's own avatar, read from that Space's own file (a read-only look; an unreadable or never-opened Space shows its initial). The settings dialog for a selected folder is prefilled from the folder itself: its name (the folder's name — there is still no separate display-name field, decision 2 stands) and any avatar it carries. The display name is not stored in the Space.
- **Consequences / limits.** A copy of a Space folder carries a copy of its ID; this is unproblematic while nothing keys on it. Avatar images live in the user-visible `Assets/` of their Space. `.clutter/workspace.json` is the user's to delete: a Space without it simply loses its avatar and gets a new ID on its next open. Not verified in a packaged build: that the asset protocol serves an avatar in a Space outside `$HOME` after a restart (it relies on the folder's persisted-scope grant, as every cover image in that Space does).

## Amendment (renaming a Space's folder from the settings dialog, anywhere it lives)

- **Scope of this amendment.** It closes the "Not covered here: renaming a Space" gap for exactly one entry point: the Space settings dialog opened from "New space" on an *existing* folder. The Name field there is editable; on Create, a changed name renames the folder itself, and the Space is then registered and opened at its new path. Nothing else about Spaces changes: still no relocation detection (a folder renamed *outside* Clutter is never re-pointed), no display name separate from the folder name (decision 2 stands), no new registry fields.
- **Owner and write path.** Renaming a Space root cannot go through `FolderOperations.rename` or the Persistence Gate: those rename a folder *inside* an open vault, and a Space being set up is not open (there is no vault, no Gate). It is the same kind of operation as `createSpaceFolder` — a deliberate, user-initiated, pre-vault operation on the Space's own root folder — and lives beside it: `renameSpaceFolder(path, newName)` in `core/vault/providers/spaceFolders.ts`, the only place a Space folder is created *or renamed*. Not Gate-backed, for the reason `createSpaceFolder` is not (ARCHITECTURE_RULES.md rule 2's scope clause: the Gate owns vault content, not the Space root's own existence).
- **Location never restricts it.** The folder's own access is the authority, not where it sits. The webview's `plugin-fs` `rename` is not enough: it checks *both* paths against the fs scope, and outside `$HOME/**` the scope holds only the folder the user picked (the native dialog's runtime grant, persisted by `tauri-plugin-persisted-scope`), not the destination name or its parent, so it would be refused for every Space outside the home directory. A single Rust command, `rename_space_folder`, therefore does the rename for every location, following the precedent of `allow_vault_asset_scope` (a Rust command that adjusts a runtime scope for a user-chosen folder):
  1. **Authorization comes from the existing grant.** The command renames only a path that the fs scope already allows (`$HOME/**`, or the folder's own picker grant). A path with no grant is refused with the same "forbidden path" outcome the plugin would give. The webview cannot name a folder it has no access to.
  2. **The destination is derived, never supplied.** It is `<parent of the old path>/<new name>` — the same parent, a single validated component (the rules of `isValidSpaceFolderName`, re-checked in Rust) — so the command can only rename a folder in place, never move it.
  3. **It never overwrites.** The destination is claimed with a non-recursive `create_dir` (exclusive: an existing file or folder of that name is refused, with no check-then-act race) and the old folder is then renamed over that empty directory; if the rename fails the claimed directory is removed.
  4. **The grant follows the folder.** On success the new path is added to the fs scope (and the asset-protocol scope) as a directory, recursively — exactly what the picker had granted for the old path — and `tauri-plugin-persisted-scope` saves it as for any other scope change. No access is added beyond the renamed folder itself.
  5. **No parent permission is needed beyond what the OS enforces.** Renaming a directory needs write access to its parent; that is the operating system's decision (including macOS's per-location privacy prompts). When it refuses, the real OS error is returned and shown as is (permission, read-only volume, in use). The command never retries with elevated or broadened access.
- **Registry consistency.** The registry is changed only through its owner (`useSpaceRegistry`), and only once the Space has opened, as before. After a successful rename the dialog opens the folder at its new path with `switchSpace(newPath, oldPath)`, the existing "replace this entry" form, so an inactive registered Space keeps its place in the list under its new path and an unregistered folder is just added. A rename that fails changes nothing: the folder, the registry and the active Space are untouched. If the rename succeeds but the folder is then refused at confirm (the probe: unreadable, outside the scope), the dialog stays, now on the renamed folder, so a retry opens it and never renames twice. If it is accepted and the open then fails, it fails as any failed open does: the registry returns to its last opened Space and keeps the old entry, the dialog closes and the reason is shown. The folder is then at a path the registry does not know, and the old entry reads as "folder not found" with its existing recovery (the missing-Space dialog's Change location). The rename is never undone: nothing renames a folder back on a failed open. Cancelling the dialog, or choosing a different folder with Change, renames nothing: the rename happens only on Create.
- **The open Space is read-only.** The currently active Space's Name stays read-only: its folder is held open by the running Application (watcher, flush, session), and renaming it underneath would break it. Registered but inactive Spaces, and unregistered folders, can be renamed.
- **What survives a rename.** The folder's contents and `.clutter/workspace.json` move with it, so the Space profile's stable `id` and avatar are preserved (the avatar is kept as stored; the dialog does not treat an unchanged avatar as a change). The one known cost is ADR-053: a renamed Space gets a new parsed-note-cache id, so its first open rebuilds that cache.
- **Not changed.** No Gate operation, no new subsystem, no registry field, no change to the static capability scope (`$HOME/**`); `fs:allow-rename` is not used by this path.

## Amendment (renaming the open Space's folder; removing the open Space)

- **Status.** In place: orchestration, registry, reconciliation, state migration, lifecycle guard, and the entry point — the open Space's page in Settings (its name field is editable and, after a confirmation, calls `renameActiveSpaceFolder`; a taken or invalid name is refused with the Space still open). Other Spaces' names stay read-only there, and the "New space" dialog still cannot rename the open Space. This supersedes the "the open Space's folder can't be renamed" limit above for the operation itself.
- **One name.** A Space's name is still its folder's name. No display-name field was added; renaming the Space renames the folder.
- **Lifecycle boundary.** `Application.quiesceForRename()` stops admitting write-producing work (imports, archive cleanup), drains and flushes everything (pages, folders, the session store, the workspace-state queue, the Gate), and — only when a **synchronous** check finds nothing left — seals the filesystem **in the same tick**, so no write can begin between "verified clean" and "sealed". `flushAll` alone cannot give that (it only flushes what was dirty when called, swallows failures and gives up silently at its timeout). If it cannot get clean in time, is cancelled, or throws, admission is restored and the Application is untouched. A sealed Application is permanently non-resumable and is only closed. `LocalVaultProvider.duplicate` of a file did not check the seal; it does now.
- **Orchestration (`renameActiveSpaceFolder`).** Validate and confirm the Space id is saved in the folder → record `pendingRename` in the registry (written synchronously; if it can't be, nothing starts) → quiesce → close → the existing Rust `rename_space_folder` (collision detection stays authoritative there) → verify the Space id at the new path → carry saved state over → move the registry to the new path and clear the record in **one mutation and one write** → the open effect opens the new path. If the rename fails, the old path is verified to still hold the original Space before a fresh Application is opened there; otherwise nothing is opened and the existing recovery runs. The folder is never renamed back. A shared `SpaceLifecycleGuard` keeps switching, removing and renaming from overlapping, and is released on every path.
- **Registry and recovery.** The registry blob gains an optional `pendingRename: { from, to, spaceId }`. It is a best-effort recovery HINT, not a transaction: it lives in `localStorage`, whose write the browser may flush lazily, so after a hard crash it can be missing, in which case the Space falls back to the missing-Space flow with no data lost (everything is inside the folder). Every registry helper preserves it unless it intentionally settles it. Old blobs load without it. Startup settles an unfinished rename **before anything opens** (`reconcilePendingRename`): the Space id recorded at the start is compared at both paths — a consistency check, not proof, because a copied Space shares its id. A path that is unavailable or unreadable is never read as missing and decides nothing (the record is kept); two paths that both carry the id are ambiguous: neither is opened or touched, the record is kept and the active Space is held back like a lost one, so the existing recovery runs; an old path that was read and is not the recorded Space is not opened. Nothing is ever deleted, moved or overwritten by recovery.
- **Path-derived ids.** A page or folder with no persisted id has its absolute path as its id, and an asset always does, so a root rename changes them. `migrateRenamedRootState` rewrites exactly those ids (an id is path-derived only if it starts with `<oldRoot>/`) in the places each store keeps one — the session's open view and collapsed folders, collection view keys and manual order, fold and embed-collapse state, references display, template usage, preferred templates, the default daily-note template and the Space's default note folder — one handler per store key. It is not a search-and-replace: stable ids, the Space's own id, names, tags and relative paths are never touched. Undo history and open editor sessions are reset, as on any Space switch. The migration is idempotent (an id already moved no longer starts with the old root) and is written as one merged write, so it either lands whole or not at all. Startup recovery **retries it before completing the registry transition**: verify the destination's id → migrate → persist the new path and clear the record together → only then open; if the migration fails the record is kept and the Space is not opened with half-migrated state.
- **Removing the open Space.** Allowed: another registered Space is switched to through the normal switch first and the old entry is forgotten only once that Space has opened (`confirmOpened`); with none available the Application is closed (flushing) and the entry removed, leaving the remaining entries with no active Space — `{ paths, activePath: null }` is now a valid stored registry, and the app starts at Welcome. Never touches the folder.
- **Not changed.** Relocation detection (a folder renamed outside Clutter is still not re-pointed), the avatar, and the Gate's frozen contracts.
