# File 06.1 — Caret Intervention Boundaries

**Status**: 🔒 LOCKED  
**Scope**: When (and only when) the editor is allowed to set browser caret  
**Version**: 1.0  
**Locked Date**: 2026-02-06

---

## Purpose of This Document

This document exists to prevent over-control of the caret.

It answers definitively:

- When the editor may set the caret
- When the editor must never set the caret
- Which keyboard actions are browser-owned vs editor-owned
- How caret placement must be implemented (mechanically)

If implementation violates File 06.1, it is incorrect by definition — even if it "works".

---

## 0. Canonical Rule (Absolute)

**Caret placement is allowed only after structural mutations.**  
**Caret placement is forbidden during navigational or typing actions.**

If text content was not structurally changed,
the editor must not touch the caret.

---

## 1. Definitions (Precise)

### 1.1 Structural Mutation (Editor-Owned)

A structural mutation is an operation that:

- Creates a node
- Deletes a node
- Merges nodes
- Splits a node
- Changes node hierarchy
- Changes node variant

These operations invalidate the browser's caret, therefore require editor intervention.

---

### 1.2 Non-Structural Interaction (Browser-Owned)

A non-structural interaction:

- Does not change document structure
- Does not invalidate DOM continuity
- Can be handled natively by the browser

These must never trigger caret placement.

---

## 2. Authoritative Caret Control Table (LOCKED)

### 2.1 Editor MAY Set Caret (Allowed)

| Action                            | Reason                         |
| --------------------------------- | ------------------------------ |
| Enter                             | Creates / splits node          |
| Backspace (merge/delete)          | Removes node boundary          |
| Delete (merge)                    | Removes node boundary          |
| Tab                               | Changes hierarchy              |
| Shift+Tab                         | Changes hierarchy              |
| ArrowUp                           | Cross-node vertical navigation |
| ArrowDown                         | Cross-node vertical navigation |
| Markdown conversion ([]␣, -␣, #␣) | Variant change                 |
| Undo                              | Structural rollback            |
| Redo                              | Structural reapply             |

➡️ Caret placement REQUIRED after these actions.

---

### 2.2 Editor MUST NEVER Set Caret (Forbidden)

| Action                | Owner   |
| --------------------- | ------- |
| Character typing      | Browser |
| ArrowLeft             | Browser |
| ArrowRight            | Browser |
| Shift+ArrowLeft       | Browser |
| Shift+ArrowRight      | Browser |
| Mouse click           | Browser |
| Mouse drag            | Browser |
| Double / triple click | Browser |
| Selectionchange       | Browser |
| IME composition       | Browser |
| Home / End            | Browser |

➡️ Any caret placement here is a violation.

---

## 3. Arrow Key Authority (Critical Section)

### 3.1 Horizontal Arrows (LOCKED)

**ArrowLeft / ArrowRight are 100% browser-owned.**

Rules:

- ❌ Editor must NOT call `preventDefault()`
- ❌ Editor must NOT update offset
- ❌ Editor must NOT place caret
- ❌ Editor must NOT "correct" browser position

**Only exception (boundary-only)**:

```
offset === 0        (ArrowLeft)
offset === textEnd (ArrowRight)
```

At boundaries, editor may:

- Collapse selection
- Move focus to adjacent node
- Then place caret ONCE

No other interception is allowed.

---

### 3.2 Vertical Arrows

**ArrowUp / ArrowDown are editor-owned** because:

- DOM layout does not encode logical node order
- Browser cannot infer cross-node intent reliably

Editor:

- Prevents default
- Computes target node
- Places caret explicitly

---

## 4. Caret Placement Mechanism (MANDATORY)

### 4.1 Implementation Pattern (Immutable)

Caret placement must be:

- Deferred
- Single-shot
- Non-reactive

**REQUIRED mechanism**:

```typescript
const needsCaretPlacementRef = useRef(false);

function requestCaretPlacement() {
  needsCaretPlacementRef.current = true;
}
```

**Caret placement effect**:

```typescript
useEffect(() => {
  if (!needsCaretPlacementRef.current) return;

  placeCaretAt(activeNodeId, offset);

  needsCaretPlacementRef.current = false;
}, [activeNodeId, offset]);
```

---

### 4.2 Forbidden Mechanisms

Caret placement must NOT use:

- ❌ React state (`useState`) as a trigger
- ❌ Placement inside event handlers
- ❌ Placement during `selectionchange`
- ❌ Placement during render
- ❌ Repeated placement for same action

**Exactly one placement per structural mutation.**

---

## 5. Typing Semantics (Reinforced)

During normal typing:

- ❌ `preventDefault()` is forbidden
- ❌ Manual text insertion is forbidden
- ❌ `commit()` per character is forbidden
- ❌ Caret placement is forbidden

**Flow must be**:

```
Browser inserts text
        ↓
Editor observes via input / selectionchange
        ↓
Editor updates state AFTER
```

Caret remains fully browser-owned.

File 06.1 is satisfied only if ALL are true:

**Navigation**

- ✅ ArrowLeft/Right feel native
- ✅ No horizontal caret snapping
- ✅ Shift+Arrow selection works natively

**Structural Ops**

- ✅ Enter moves caret correctly
- ✅ Backspace merge places caret correctly
- ✅ Tab/Shift+Tab preserve offset

**Control Discipline**

- ✅ Caret placement happens < 10 times total in codebase
- ✅ No caret logic in selection observer
- ✅ No caret logic during typing
