# Autosave Strategy — Architecture & Product Analysis

**Status:** Research only. No code changes. This document is the pre-implementation deliverable for the Autosave milestone — product research, architecture analysis, impact analysis, risks, trade-offs, and a recommendation. Implementation does not start until this is reviewed and accepted; if accepted, follow-on work proceeds under `docs/implementation-rules.md` (pre-implementation checklist, ADR if the recommendation requires a specification amendment, post-implementation verification).

This document uses the vocabulary defined in [`docs/durability-model.md`](./durability-model.md) (Committed / Durable / Reconciled) throughout — read that first if the stage names are unfamiliar.

---

## 0. Where Clutter stands today (baseline, verified against source)

Before designing anything, the actual current behavior, read directly from the code:

- **The only save trigger today is the editor `contentEditable` div's native `onBlur` event.** [`MarkdownEditor.tsx:54-75`](apps/app/src/features/markdown/editor/MarkdownEditor.tsx). There is no `onInput`/keystroke handler — nothing observes typing as it happens.
- **Commit and disk-write are coupled, not staged.** `PageOperations.save()` calls `session.commit(...)` and enqueues the Gate write in the same synchronous call, both gated by the same blur event ([`PageOperations.ts:281-331`](apps/app/src/core/application/page/PageOperations.ts)). There is no "commit locally, sync to disk later" split today — Committed and the start of the Durable transition happen at the same instant.
- **No debounce/throttle utility exists anywhere in the codebase.** A future design starts from zero on this primitive.
- **No window-blur, app-quit, or navigation-triggered save exists.** Switching the active page in `Workspace` (`openPage`/`closePage`) does not save. The only thing that currently causes a save on "switching notes" is that switching *usually* also blurs the editor DOM node, which is incidental, not designed — a focus change that doesn't blur the contentEditable (e.g., a programmatic navigation that doesn't move focus) would switch pages with the previous page's edits uncommitted to disk, silently.
- **`SaveCoordinator` already documents "Coordinate autosave" as a stated responsibility** in its own header comment ([`SaveCoordinator.ts:6-11`](apps/app/src/core/engine/SaveCoordinator.ts)), never implemented — this is the one line of prior intent in the codebase pointing at this milestone.
- **Draft lifecycle (ADR-017) already established the precedent this design must extend, not duplicate:** the first `save()` for an unpersisted id promotes a draft to a real page through the same Gate `create` path a persisted page's `save()` uses for ordinary saves. Any autosave trigger model change flows through this same `save()` entry point — it does not bypass it.
- **The Persistence Gate's per-page queue is the only serialization primitive that exists.** Nothing upstream of it (editor, `PageOperations`) does its own request coalescing today.

This baseline matters because it bounds the design space: today, "autosave" doesn't exist as a distinct concept from "save" — there is one save path, triggered by one DOM event. The question this milestone answers is not "how do we add autosave to a rich save pipeline" but "how do we introduce a *trigger model* upstream of a save path that is otherwise already correct and doesn't need to change."

## 1. Autosave trigger model — comparative analysis

Each model evaluated on: UX, durability, performance, complexity, failure modes. All models are evaluated as *candidates to trigger `PageOperations.save()`*, not as replacements for it — per §0, the Gate/Vault/DocumentSession machinery downstream of `save()` is already correct and out of scope for redesign.

### Every keystroke

- **UX:** Maximum perceived safety — nothing is ever "unsaved." But at typing latency, this either forces every keystroke through an async write pipeline (introducing input lag if not carefully decoupled from the render path) or requires the save to be fire-and-forget from the keystroke's perspective, which reintroduces exactly the ordering problem `SaveCoordinator` exists to solve, at far higher frequency.
- **Durability:** Best-in-class *if* durable writes could actually keep up — they can't. A write to disk (even Clutter's non-atomic, non-fsync'd write per `durability-model.md` Stage 2) is orders of magnitude slower than a keystroke's ~50-200ms cadence. In practice "every keystroke" always means "every keystroke reaches Committed, not every keystroke reaches Durable" — conflating the two is the most common design mistake in this space.
- **Performance:** Unacceptable if interpreted literally as "one disk write per keystroke." A 2,000-word session would generate on the order of 10,000 write calls. Even with the Gate's per-page queue serializing them safely, `writeParseRebuildReplace`'s write-then-reread-to-verify pattern (`durability-model.md` Stage 2) makes each one relatively expensive; queuing 10,000 of them would starve the queue and make the *n*th keystroke's durable write land arbitrarily far behind the *n*th keystroke's on-screen appearance.
- **Complexity:** Low to state, high to implement correctly — requires either an extremely cheap in-memory commit path decoupled from an independently-paced disk-flush path (i.e., this model *only* makes sense paired with debounce/idle underneath it), or accepting the performance failure above.
- **Failure modes:** Queue starvation under fast typists; battery/CPU cost on mobile from constant I/O; makes every individual write's failure narrower in scope but far more numerous, which is not actually good — more failure surface area, not less.
- **Verdict:** Not a standalone trigger model. Valid only as the *Committed*-stage trigger (i.e., "commit on every keystroke to update in-memory state," which costs nothing since it's not I/O) paired with a *different, coarser* trigger for the Durable-stage write. This is the standard "keystroke commits in-memory, something else flushes to disk" split every serious editor uses, per §2 below.

### Debounce

- **UX:** Good — the user's mental model ("it saves shortly after I stop typing") matches what most competitors already train users to expect. A well-tuned debounce (typically 500ms-2s) is invisible during active typing and fires quickly enough after a pause that a mid-thought interruption (Slack notification, phone call) is very unlikely to lose more than the debounce window's worth of text.
- **Durability:** Strong for the common case (continuous typing with natural pauses); weak for the "typed for 10 minutes straight with zero pause long enough to trigger the debounce, then the app crashes" case — a pure debounce with no upper bound can, in principle, never fire during a very long unbroken typing burst. This is why production debounce implementations are almost always paired with a **max-wait ceiling** (a hybrid, not a pure debounce — see below).
- **Performance:** Good — write frequency scales with pause frequency, not keystroke frequency, typically producing one write every few seconds during active editing rather than one per keystroke.
- **Complexity:** Low — one timer, reset on each commit, fires the trigger on timeout. No new dependency needed; a bounded number of lines of code, not a library.
- **Failure modes:** The "never fires during one long unbroken burst" gap above. A debounce timer that isn't cancelled on session teardown (component unmount, page switch) can fire against a stale/closed session unless explicitly guarded — a real implementation bug class, not theoretical (this is exactly the kind of stale-completion problem `SaveCoordinator` already guards against for save *completions*; a debounce timer needs the equivalent guard for save *initiations*).
- **Verdict:** The right default trigger for "user is actively typing," but incomplete alone — needs a ceiling (hybrid) and needs to be paired with non-debounce triggers for the events debounce structurally cannot see (blur, navigation, close).

### Idle timer

- Functionally a variant of debounce (fire after N seconds of no activity) rather than a distinct model — the distinction usually drawn in practice is "debounce resets on every keystroke and fires shortly after typing stops" (short window, ~0.5-2s) vs. "idle timer fires after a longer period of no *interaction at all*, including no scrolling/clicking" (longer window, ~30s-several minutes, sometimes tied to marking the document/app as idle for other purposes like session timeouts). For autosave specifically, these collapse into the same trigger shape (a timer reset by activity, firing on expiry) — treated as one mechanism in this analysis (§4 uses "debounce" to mean this whole family, with the specific interval a tuning question, not an architectural one).

### Blur

- **UX:** Matches Clutter's current (accidental) behavior almost exactly, so a design keeping blur as *one of several* triggers has zero UX regression risk for existing behavior — it's a strict addition, not a change, to keep it.
- **Durability:** Blur is a real, meaningful commit boundary a user actually experiences ("I clicked away") — reliable *for the interactions it covers*, but blur does not fire for every path work is lost through: an app crash, force-quit, or OS kill happens with no blur event at all.
- **Performance:** Cheap — fires rarely relative to keystrokes (once per focus change), so this is a near-free addition regardless of what else triggers saving.
- **Complexity:** Trivial — already implemented.
- **Failure modes:** None new; blur is a strict subset of what a combined trigger model already needs to cover, and it's the one trigger Clutter has already validated in production use (today, effectively as the *only* trigger).
- **Verdict:** Keep. It is not sufficient alone (as §0 establishes — anything that changes focus without a true DOM blur, or a crash before any blur, loses data today), but it's free, already correct, and should remain one input into the hybrid trigger, not be replaced.

### Navigation (switching documents within the app)

- **UX:** Users expect "switching to another note" to implicitly save the one they were on — this is one of the most consistently-implemented behaviors across every competitor in §2. A user who doesn't get this and later finds their edit missing perceives it as a bug, not a documented trade-off.
- **Durability:** Explicit and reliable — unlike blur (which can be triggered by many things, or fail to fire for a programmatic focus change), a navigation-triggered save can be placed deliberately in the one chokepoint that already exists for "switching the active page" (`Workspace.openPage`/`closePage`, or more precisely the call site in `PageOperations`/`NavigationRouter` that leads to it), guaranteeing it fires for every way of switching pages, not just the ones that happen to also blur a DOM node.
- **Performance:** Cheap — fires once per navigation, not per keystroke.
- **Complexity:** Low, but real: today `Workspace.openPage`/`closePage` are pure, synchronous, no-I/O methods (§0; `Workspace.ts`'s own spec section states "Synchronous, single-threaded — no async operations, no races possible"). Making navigation trigger an async save means either (a) the caller *above* `Workspace` (i.e., wherever navigation is actually initiated — `PageOperations`, `NavigationRouter`, or the UI action handler) is responsible for flushing the outgoing session's pending changes before calling into `Workspace`, or (b) `Workspace` itself gains an awareness of pending saves it explicitly doesn't have today. Option (a) is the only one consistent with `ARCHITECTURE_RULES.md` rule 5 (never move a responsibility across a subsystem boundary as a side effect) and Workspace's own explicit "must never own persisted product data or write logic" (spec §10) — this is a real, load-bearing architectural constraint on the design, detailed in §4.
- **Failure modes:** If the flush-before-navigate step is fire-and-forget (not awaited), a slow save racing a fast navigation could still lose the tail of an edit if the app is also closed in the same moment; if it's awaited, navigation now has save latency in its critical path, which needs to be invisible to the user (optimistic UI: switch the view immediately, let the flush happen in the background against the *closing* session, not the newly-opened one).
- **Verdict:** Should trigger a save (of the outgoing session), implemented as a caller-side flush above `Workspace`, not inside it. This is the single most product-expected trigger missing from Clutter today.

### Window focus loss (OS-level, not editor blur)

- **UX:** Covers the case editor-blur misses within the app: user alt-tabs to Slack, or the window loses OS focus entirely, without necessarily blurring the specific contentEditable node first (in practice these often coincide, but not guaranteed across all browsers/webview embeddings — Tauri's webview is Chromium/WebKit-based, and focus semantics between the OS window and a DOM element inside it are two distinct event streams).
- **Durability:** Meaningfully stronger than editor-blur alone in the cases they diverge, but the difference is narrow given editor-blur already covers most real focus-loss scenarios; the marginal safety gained is real but not large.
- **Performance:** Free — fires rarely.
- **Complexity:** Requires a Tauri-level window-focus event listener wired somewhere in the Composition Root or a UI-layer hook, and a way to reach "flush every session with pending changes," not just the currently active one (a user could plausibly have more than one page open even without a multi-window feature, if Clutter's `Workspace.isPageOpen` tracks more than one open page at a time — worth confirming against actual `Workspace` usage before deciding whether this needs to flush one session or several).
- **Failure modes:** None distinct from blur's, just a wider net.
- **Verdict:** Worth adding as a second net alongside editor-blur, low cost, meaningfully closes a real (if narrow) gap. Not a *replacement* for blur or navigation-triggered saves — an addition.

### Application close

- **UX:** Users strongly expect "quitting the app never loses my last few seconds of typing," and this is the single trigger where getting it wrong causes the most visible, trust-damaging failure (see §2 — every competitor researched treats this as non-negotiable).
- **Durability:** This is where the durability model matters most directly: an application-close handler needs to *complete* a Durable-stage write (or at least hand it irrevocably to the OS) before the process actually exits, which is a genuinely different problem than "trigger a save" — it's "block exit until the save's disk write (Stage 2 per `durability-model.md`) has returned, or accept the OS's kill signal mid-write and risk the torn-write gap `durability-model.md` already documents as an existing, accepted limitation of Durable's guarantee (§Stage 2, 'Explicitly does not guarantee: Atomicity of the write itself')." This isn't a new gap this milestone introduces — it's the *same* gap, just now reachable through a new, more frequently-hit path (deliberate app close, not just a crash).
- **Performance:** Irrelevant at this point (app is exiting) except for how long the user has to wait for exit to actually happen — a slow flush-and-wait-for-write-confirmation on close needs a bound (with what UX on timeout — force quit anyway and accept the loss, or block the user with a spinner?), and Tauri's own before-close event model needs to actually support blocking exit (needs verification during implementation, not assumed here).
- **Complexity:** Moderate — needs a Tauri `tauri://close-requested` (or equivalent) handler, needs to enumerate every session with pending changes (not just the active one), needs to actually await their flushes before allowing the close event to proceed, and needs a decision for what happens if a write is slow or fails at exactly this moment.
- **Failure modes:** A close-handler that isn't correctly wired to *block* exit (vs. just being *notified* of it) provides zero benefit — this is a real implementation trap, since "listen for close" and "delay close until an async operation finishes" are different capabilities and not every desktop framework's close event supports the second by default.
- **Verdict:** Required. This is not optional the way window-focus-loss is a nice-to-have — every reference product in §2 treats "don't lose data on quit" as table stakes, and Clutter's own Committed-stage documentation (`durability-model.md` §Stage 1) already states plainly that content sitting in Committed has "no guarantee whatsoever" against a crash — an intentional, accepted gap for *crashes*, but application *close* is not a crash, it's an orderly, catchable event the app has the opportunity to act on, and failing to act on it is a design defect, not an accepted trade-off.

### Hybrid (the actual answer)

Every credible product researched in §2 uses a hybrid, not a single trigger — because each pure model above solves a different failure mode and none of them, alone, covers "continuous typing," "user pauses," "user switches focus," "user switches documents," and "user quits," simultaneously. The hybrid this analysis recommends (detailed as the actual recommendation in §7) is:

1. **Commit (Committed stage) on every keystroke or every N ms of active typing** — cheap, in-memory only, no I/O. This is the "every keystroke" model's only valid role.
2. **Debounced flush to disk (Durable stage) after a short pause in typing**, with a max-wait ceiling so a long unbroken typing burst still flushes periodically.
3. **Immediate flush on blur, window-focus-loss, and navigation-away** — these are cheap, rare, and each closes a gap the debounce alone can't (a debounce mid-window is still pending when the user switches away).
4. **Blocking flush-and-await on application close** — the one trigger that must complete before the process is allowed to exit.

This isn't a fifth model bolted onto the other four — it's the recognition that "trigger model" was never actually a single choice; it's a *set* of triggers converging on the same underlying `save()` call, which Clutter's architecture already supports as a single entry point (§0).

## 2. Industry research

Conducted as a dedicated web-research pass (packet-capture writeups, official engineering blogs, official docs, and forum/community evidence where nothing more authoritative exists). Every claim below is tagged **VERIFIED** (a specific, checkable source exists — cited inline) or **INFERRED** (directionally reliable, standard-for-the-category behavior, but no pinpoint citation found). No source used the Committed/Durable/Reconciled vocabulary itself — that mapping is this document's own synthesis, applied in §3, not lifted from any vendor.

### Obsidian (local markdown, plugin ecosystem)

CodeMirror buffer commits on keystroke (**INFERRED** — standard editor behavior). Disk writes happen on a recurring **~2 second** interval while the buffer is dirty, continuing throughout a long typing session, not just at the end — **VERIFIED**, corroborated across multiple independent forum sources ([Autosave Control plugin thread](https://forum.obsidian.md/t/plugin-autosave-control-delay-automatic-saves-keep-manual-saves-immediate/104651); [plugin README](https://github.com/mihasm/obsidian-autosave-control); [file-system write-frequency thread](https://forum.obsidian.md/t/change-how-often-obsidian-writes-to-the-file-system/34340)). One user in the last thread reported that after an OS crash mid-editing, Obsidian "had saved all but the last couple of keystrokes" — a real, first-hand data point on the ~2s cadence's actual loss window (**VERIFIED**). Switching files and app close are presumed to flush the pending write (**INFERRED** — no direct source, but the aggressive default interval makes this low-stakes either way). Because storage is one plain local file per note, only the current note's debounce window is ever at risk — other notes are structurally unaffected, which is a direct, load-bearing parallel to Clutter's own one-file-per-page model (§3).

### Bear (Mac/iOS)

No explicit "Save" action, consistent with the category norm. Sync is via **CloudKit**, chosen specifically over Dropbox/iCloud-Drive-style file sync for speed (**VERIFIED** — [Bear Syncing & Privacy FAQ](https://bear.app/faq/syncing-privacy/)). Bear's sidebar surfaces live sync status and a "last sync" time in Preferences, implying sync runs as an async background process decoupled from app lifecycle events (**VERIFIED (partial)** — [Bear backup blog post](https://blog.bear.app/2018/11/how-to-back-up-your-bear-notes/)). Local write timing, switch-note behavior, and crash behavior are not documented anywhere found — **INFERRED** throughout, on the general Core-Data-app pattern.

### Apple Notes

Community/technical sources state edits are written to local disk **immediately** — no discrete interval, closer to continuous persistence than periodic saves (**VERIFIED (community source)** — [Apple Community thread](https://discussions.apple.com/thread/6862710)). Notes uses CloudKit directly for sync (not `NSPersistentCloudKitContainer`, which Photos/Notes both bypass — **VERIFIED**, [developer.apple.com forum](https://developer.apple.com/forums/thread/811294)). Real, documented failure modes exist at the sync layer specifically: users report notes disappearing locally after a crash until iCloud sync is toggled off/on to force a resync (**VERIFIED** — [Apple Community crash thread](https://discussions.apple.com/thread/254592023)), and a general (not Notes-specific) `NSPersistentCloudKitContainer` caveat exists where disabling iCloud during a throttled sync can wipe the *local* store even though changes were already saved locally (**VERIFIED, general CloudKit stack risk** — [developer forum](https://developer.apple.com/forums/thread/811294)). The clearest cross-product lesson here: **local durability and sync durability are genuinely different guarantees, and conflating them is a real, documented failure mode**, not a theoretical one — directly reinforcing why `durability-model.md` keeps Durable and Reconciled/cloud-sync as separate stages rather than one.

### Craft (block-based, sync)

Edits persist into a local **Realm database** as the underlying data model (**VERIFIED** — [Craft's sync-protocol blog post](https://www.craft.do/blog/in-house-sync-protocol)). "All your edits are saved locally" automatically, including fully offline (**VERIFIED** — [Craft Offline Mode docs](https://craft-support.mintlify.app/en/introduction/offline)). Server sync runs over **socket.io**, continuously reacting to local DB changes or incoming remote changes (**VERIFIED (mechanism)** / interval not disclosed, **INFERRED**). Notably, **switching-document behavior differs by platform** — Mac/iOS sync the entire "space" in the background regardless of which document is open; Web/Windows/Android sync per-document and only refresh on open, so closed documents don't sync in the background (**VERIFIED** — same Offline Mode docs). Unsynced changes on app close are safely retained locally and sync automatically on next launch with connectivity (**VERIFIED**, same source). One documented multi-device caveat: two devices editing the same doc fully offline "won't see the other's changes until both are online and you reopen the document" — no live merge outside the real-time-connected mode (**VERIFIED**, same source).

### Notion (cloud-first, block-based)

The most precisely documented pipeline in this survey, from Notion's own engineering blog: edits apply as a **transaction** to local state immediately (optimistic apply, in-memory + a local `RecordCache` in SQLite/IndexedDB), then the transaction is placed into a durable local `TransactionQueue` (persisted in IndexedDB/SQLite) *before* any server round-trip — this queue is itself a genuine local-durability layer, independent of network state (**VERIFIED** — [Notion's data-model blog post](https://www.notion.com/blog/data-model-behind-notion)). The queue is sent to the server (`/saveTransactions`), which loads a before-snapshot, applies and validates the operations, and commits — only then does the client advance the queue (**VERIFIED**, same source). Under load, Notion explicitly **buffers** transactions rather than sending strictly per-keystroke: "sending transactions immediately when the queue is empty, but buffering them when needed" (**VERIFIED (qualitative)**, same source). For page-switching: Notion's offline-mode design deliberately refuses to show a page offline until it is **fully downloaded** — explicitly because partial state makes conflict resolution unpredictable (**VERIFIED** — [How we made Notion available offline](https://www.notion.com/blog/how-we-made-notion-available-offline)); real-time updates propagate per-page via pub/sub, and offline-enabled pages use a **CRDT** model specifically for conflict resolution (**VERIFIED**, same source). This is the clearest real-world illustration in the whole survey of "commit granularity determines crash blast radius" — because Notion's local queue is durable *before* the network round-trip, a crash risks at most whatever hasn't reached the local queue yet, not whatever hasn't reached the server yet.

### Google Docs (cloud-first, OT-based)

The best independently-sourced product in the set: an outside developer's packet-capture reverse-engineering of Docs' keystroke-playback feature shows a `/save` request is issued **per atomic edit** — typing a single period produced its own individual save operation with its own operation ID (**VERIFIED**, primary technical source — [James Somers, "How I Reverse-Engineered Google Docs"](https://features.jsomers.net/how-i-reverse-engineered-google-docs/)). This per-operation granularity is inherent to **Operational Transformation**, the collaboration technique Docs adopted starting 2009 — each op must be transformed against concurrent ops in near-real-time for OT correctness (**VERIFIED** — [Wikipedia: Operational Transformation](https://en.wikipedia.org/wiki/Operational_transformation), corroborated by the packet capture). This means Docs cannot and does not batch/debounce the way local-first apps do — continuous per-op persistence is a *requirement* of its collaboration model, not a UX choice. Revision history stores **deltas between revisions**, not full snapshots (~1000x storage reduction cited by Somers), visually grouped into ~1-2 minute "sessions" in the version-history UI (**VERIFIED**, same source). An offline mode exists (Docs Offline extension / mobile caching) that queues edits locally and syncs on reconnect (**VERIFIED (general/secondary sourcing)**). Google Docs is the clearest existence proof that commit-and-durable-write can collapse into the *same* event — but only because the durable-write target is a low-latency, always-available server, a precondition Clutter's local-file architecture does not have and, per `durability-model.md`'s explicit local-disk-only scoping for Durable, is not adopting.

### Ulysses (Mac/iOS writing app)

The single cleanest documented example of "switch triggers save" in the whole survey: Ulysses syncs all sheets to an iCloud-backed store **every 60 seconds, or immediately on switching to a different sheet — whichever comes first** (**VERIFIED**, official Ulysses documentation/blog). This cap holds even during continuous, uninterrupted typing on one sheet — sync to iCloud never waits longer than 60s regardless of activity (**VERIFIED**, same source). Ulysses is explicit that it **cannot force iCloud to sync** — sync completion on app close is not guaranteed (**VERIFIED (qualitative constraint)** — [Ulysses sync-issues FAQ](https://help.ulysses.app/en_US/subscription-synchronization/synchronization-issues)). Separately, and independently of iCloud sync entirely, Ulysses maintains an automatic **local backup ladder** — hourly backups for the last 12 hours, daily for the last 7 days, weekly for the last 6 months, no user action required (**VERIFIED** — [Ulysses backup blog post](https://blog.ulysses.app/backup/)). This is a second, explicit, well-documented product precedent (alongside VS Code's Hot Exit, below) for treating "ordinary sync/autosave" and "crash/version protection" as two structurally separate mechanisms — directly relevant to `durability-model.md`'s already-named "Recoverable" gap (§Named gaps).

### Drafts (Mac/iOS quick capture)

The weakest-sourced product in the survey — official docs describe *what* technology is used but not *when* commits/syncs happen at a technical level. What is confirmed: Drafts stores locally first; sync (auto-enabled at install when an iCloud account is present) runs via **CloudKit**, not file-based sync (**VERIFIED** — [Drafts iCloud Sync docs](https://docs.getdrafts.com/docs/settings/sync)). No sync data is stored on the vendor's own servers — it lives in the user's private iCloud database, with Advanced Data Protection enabling end-to-end encryption of draft content specifically (**VERIFIED** — [Drafts Privacy page](https://getdrafts.com/support/privacy)). Local commit cadence, switch-behavior, and crash behavior are **INFERRED** by analogy to Bear/Notes, which share the same CloudKit substrate and the same lack of published low-level timing.

### VS Code (editor)

The only product in the survey with an **official, explicitly documented, separately-named crash-durability mechanism**, decoupled from ordinary autosave. `files.autoSave` (default `off`) governs disk writes: `afterDelay` (debounce, default **1000ms**, via `files.autoSaveDelay`), `onFocusChange` (save when focus leaves the dirty editor), or `onWindowChange` (save when focus leaves the window) (**VERIFIED** — [VS Code Basic Editing docs](https://code.visualstudio.com/docs/editing/codebasics)). Independent of that setting entirely, **Hot Exit** (`files.hotExit`: `off` / `onExit` / `onExitAndWindowClose`) preserves unsaved buffer state to a platform-specific local backup path on quit or crash, restoring it on next launch — this works even with `files.autoSave` set to `off`, i.e., even when the user has explicitly opted out of writing the real file, their unsaved content still survives a crash via this separate store (**VERIFIED**, same source). This is VS Code's single most transferable precedent for Clutter: it demonstrates a three-tier model in practice — **Committed** (in-memory dirty buffer) → a **crash-durable local buffer** (Hot Exit's backup store) → **Durable** (the actual file write, gated by `files.autoSave`) — where the middle tier exists specifically because `durability-model.md`'s own stated gap ("no intermediate stage exists today; the only transition out of Committed is directly to Durable, with nothing in between," §Stage 1) is a real product liability serious enough that a major, widely-used editor built a dedicated mechanism to close it.

### Cross-cutting patterns

1. **Committed vs. Durable is a near-universal architectural split, even where invisible to the user.** Every product with an official/technical description (Notion, Google Docs, VS Code, Craft) documents an explicit two-stage model: instantaneous local/in-memory commit, then a separate, later durability step. Products with only marketing-level docs (Bear, Drafts, Apple Notes, Ulysses) don't describe this explicitly, but nothing suggests they differ structurally — the pattern likely holds universally, just undocumented for those.
2. **Local-first apps converge on short, sub-few-second debounce windows for disk writes — never true per-keystroke local writes.** Obsidian: ~2s. VS Code `afterDelay`: 1000ms default. This directly supports debounce+ceiling as Clutter's own Durable-stage trigger (§1), arrived at independently, not copied from a single competitor. **Google Docs is the sole, explained exception** — its near-per-operation persistence is a requirement of OT-based real-time collaboration, not a general local-editor pattern, and doesn't apply to Clutter's local-file, single-writer architecture.
3. **"Switch away" is a recurring, explicit, independently-documented save trigger, not just an incidental side effect of a blur event.** Ulysses' documented "sync every 60s **or on sheet switch, whichever comes first**" and VS Code's dedicated `onFocusChange`/`onWindowChange` autosave modes are direct, first-party confirmations that mature products treat document/focus switching as a deliberate flush point. This is the single most consistent, best-evidenced finding in the survey, and it's also the largest gap in Clutter's *current* behavior (§0) — Clutter has no navigation-triggered save today, only an incidental blur.
4. **Crash-durability is consistently treated as a separate mechanism from ordinary autosave/sync, not folded into it, when a product bothers to document it at all.** VS Code's Hot Exit and Ulysses' hourly/daily/weekly local backup ladder are the two clearest, best-documented examples — both exist precisely because their normal durable-write path (disk autosave / iCloud sync) wasn't judged sufficient insurance against crashes or sync failures, and both are local-only, independent of any network layer.
5. **Local durability and cloud/sync durability are documented, in practice, as genuinely different guarantees that can fail independently** — Apple Notes' real, reported failure mode (notes vanishing locally after a crash until an iCloud resync is forced) is concrete evidence, not a hypothetical, for why `durability-model.md` is correct to keep Durable (local disk) and Reconciled/future-cloud-sync as separate, non-conflatable stages.
6. **Version history / backup ladders (Ulysses, Google Docs' delta-based revision history, Notion implicitly via its transaction log) are consistently a separate mechanism from autosave**, never conflated with it — directly consistent with `durability-model.md`'s own framing of "Recoverable" as an independent, currently-absent stage that autosave itself is not expected to provide.
7. **Platform-dependent sync scope is a real, shipped pattern (Craft), not a hypothetical edge case** — the same product legitimately makes different Committed/Durable/Reconciled trade-offs on different platforms. Worth remembering if Clutter ever targets a second platform (§6, Mobile) — nothing here demands it now, but it establishes that platform-specific trigger tuning is normal, not a design smell.

## 3. Clutter durability model — where autosave fits

Mapping this milestone onto `docs/durability-model.md`'s three stages directly, per that document's own stated usage instructions ("a future ADR proposing a change to persistence, editing, or sync behavior should state which stage(s) it affects... and whether it changes that stage's guarantee or adds a new one"):

- **Which stage does autosave operate on?** Both, by construction, but as two distinct sub-decisions:
  - The **trigger for `DocumentSession.commit()`** (keystroke-level, or coalesced at a short interval) operates entirely within **Committed**. This is free — no I/O, no Gate involvement, and per `durability-model.md` §Stage 1, committing more frequently doesn't strengthen Committed's guarantee (it never had crash-survival to begin with) — it just makes the in-memory `currentRevision` more up-to-date more often, which mainly matters for UI (dirty-state indicators) and for shrinking the gap between "what the user typed" and "what the next Durable-stage write will contain."
  - The **trigger for enqueuing a Gate `save`/`create` operation** (debounce+ceiling, blur, navigation, window-focus-loss, close) operates on the **Committed → Durable transition**. This is the actual "autosave" decision in the product sense — it does not change Durable's own guarantee (still non-atomic, non-fsync'd, exactly as documented today) — it changes *how often* content reaches that existing guarantee, not what the guarantee is.
- **Which stage should the UI communicate as "saved"?** Durable, not Committed — consistent with how `DocumentSession.isDirty`/`state` already work today (`Clean` only after `markSaved`, i.e., after a Durable-stage write actually succeeds). This is not a new decision this milestone introduces; it's confirming the existing state machine's meaning stays correct once the *frequency* of transitions into it changes. A UI indicator showing "saved" the instant a debounce timer merely *starts* (rather than when the write actually completes) would misrepresent Committed as Durable — an explicit anti-goal.
- **Which stage defines "saved" for the user's own mental model?** Durable — same answer, for the same reason; this is also consistent with every product in §2 (all of them represent "saved" to the user only once a local write, or in cloud-first products' case an acknowledged send, has actually happened, not merely queued).
- **Which stage does crash recovery guarantee today, and does this milestone change that?** Crash recovery today guarantees only what already reached Durable before the crash (`durability-model.md` §Stage 1's explicit statement that Committed has "no guarantee whatsoever" against a crash). **A pure trigger-model change (debounce/blur/navigation/close) does not add crash recovery for content that never reached Durable — it only shrinks the *window* of at-risk content by writing more often.** This is an important, precise distinction: tightening the debounce interval reduces how much unsaved work a crash can destroy, but doesn't change the *kind* of guarantee — Committed is still exactly as fragile as it always was, just for a shorter average stretch of unwritten content. Closing that gap structurally (not just narrowing it statistically) would require the new intermediate stage named in §7 (a crash-durable local buffer, VS Code's Hot Exit precedent) — which this document recommends naming explicitly as a *candidate* future addition to the durability model, not something to build as part of this milestone's trigger-model work, and not something to leave conflated with it.

**Summary table, stated in the model's own vocabulary:**

| Question | Answer |
|---|---|
| Stage `DocumentSession.commit()` frequency affects | Committed (unchanged guarantee, just updated more often) |
| Stage the autosave trigger (debounce/blur/nav/close) affects | The Committed→Durable transition frequency (unchanged Durable guarantee, reached sooner/more often) |
| Stage the UI's "Saved"/dirty indicator should reflect | Durable (`DocumentSession.state === Clean`, post-`markSaved`) |
| Stage crash recovery guarantees, before and after this milestone | Durable only — unchanged in kind, narrower in the average-loss-window sense only |
| Stage a future "don't lose typed-but-uncommitted-to-disk content on crash" feature would add | A new stage between Committed and Durable — not proposed here, named as a gap consistent with `durability-model.md`'s own "Future capabilities that belong outside this stage" framing for Stage 1 |

## 4. Full architecture impact sweep

Evaluated against every subsystem named in the specification, per `implementation-rules.md`'s pre-implementation checklist item "Which subsystems are affected?"

| Subsystem | Impact | Detail |
|---|---|---|
| **`DocumentEditing` (`DocumentSession`/`DocumentRegistry`/`SaveCoordinator`)** | **Direct, primary** | `commit()` called more often (on a keystroke/coalesced-keystroke cadence instead of only on blur) — no signature change. `SaveCoordinator` gains an actual autosave-scheduling responsibility it already claims in its own doc comment but has never implemented — this is a natural extension of an existing collaborator, not a new subsystem, and stays within `PageOperations`'s internal collaborator boundary (spec §9 — `DocumentEditing` is not exported outside `application/`). A debounce/timer mechanism is new *code* here, not a new *subsystem* — it's exactly the kind of thing `SaveCoordinator`'s stated-but-unbuilt "Coordinate autosave" responsibility already anticipated. |
| **`PageOperations`** | **Direct, primary** | `save()` remains the single entry point every trigger converges on — per §0/§1, this design adds *callers* of `save()`, not new methods on the facade, which is exactly the "new verb on an existing aggregate" vs. "no new capability" distinction the spec's own closing section (§"Why This Stays Coherent") anticipates as the common case. The draft-promotion branch (ADR-017) is unaffected in its logic — it still only cares about "does `vault.getPage(pageId)` resolve," regardless of what triggered the call. One new consideration: if the *first* autosave trigger for a still-unpersisted draft fires from a debounce timer rather than a user-initiated blur, draft promotion now happens without an explicit "the user left the field" moment — worth a product decision (see §6, Risks) about whether autosave should promote drafts identically to blur-triggered saves, or whether draft promotion specifically should stay blur/navigation/close-gated even if body saves for *already-real* pages autosave more eagerly. This is a product-policy question belonging inside `PageOperations` (ARCHITECTURE_RULES.md rule 5 — business policy lives in the facade), not an infrastructure one. |
| **Persistence Gate (`PagePersistenceCoordinator`)** | **None required** | The Gate's contract is trigger-agnostic by design — it only knows "enqueue this operation for this page id" (spec §5). More frequent `save`/`create` enqueues from a tighter trigger model are exactly the kind of load its per-page queue already exists to serialize correctly, per spec §5's own concurrency model. No new `PersistenceOperation` kind needed. The one thing worth verifying (not designing pre-emptively) during implementation: whether a much higher enqueue frequency changes anything about queue *depth* under pathological cases (see §5, Back-pressure) — a verification concern, not an architecture change. |
| **`Vault`** | **None** | Unaffected — `Vault`'s mutation methods are called by the Gate exactly as often as the Gate is asked to write, and `Vault`'s own invariants (spec §3) don't depend on write frequency. |
| **`Workspace`** | **Indirect, real** | Per §1's Navigation analysis: a navigation-triggered flush must be implemented as a caller-side responsibility *above* `Workspace`, never inside it — `Workspace.openPage`/`closePage` stay exactly as synchronous and I/O-free as spec §10 requires. This means the actual "flush the outgoing session before switching" logic lives in whatever already calls into `Workspace` for navigation (most likely `PageOperations`/`NavigationRouter`'s call sites, or a thin coordination point the UI layer already goes through) — not a new `Workspace` responsibility. Naming this precisely is one of the more consequential design decisions of this milestone, flagged explicitly rather than assumed (see §7, Recommendation, and the open question in §6). |
| **`Sync`/`VaultSyncService`** | **None** | Sync only reacts to *external* filesystem changes (spec §4) — the app's own more-frequent autosave writes are exactly the kind of self-write the existing `SelfWriteAwareWatcher`/`SelfWriteRegistry` machinery (Platform §1) already suppresses correctly, regardless of how often they happen. Worth a verification step (not a design change) confirming the self-write suppression window comfortably covers a tighter autosave cadence — see §5. |
| **`FileSystem`/Platform** | **None** | `VaultFileSystem.writeFile` is called more often, but its contract (spec §1) doesn't change. This is the layer §2's cross-product research shows is the actual cost center (a real disk write per Durable-stage flush) — the trigger model's whole purpose is managing *how often* this layer is invoked, not changing what it does. |
| **Editor (`MarkdownEditor.tsx`)** | **Direct, but bounded** | Needs an `onInput`/keystroke (or coalesced-keystroke) handler feeding `commit()`, in addition to (not instead of) the existing `onBlur`. This is UI-layer work, not an architecture change, provided it stays within the existing prop-callback pattern (`onCommit`) already wired through `PageHost`/`toResourcePageModel` (§0) — no new facade import, no new application-layer construction inside the component (`ARCHITECTURE_RULES.md` rule 6 stays satisfied as long as this is implemented as "call the same `onCommit` callback more often," not "the editor reaches for `PageOperations` directly"). |
| **Draft lifecycle (ADR-017)** | **Interacts, needs an explicit decision** | Covered under `PageOperations` above — the specific open question is whether autosave-triggered promotion (as opposed to blur/navigation/close-triggered promotion) is desired product behavior. Flagged, not resolved, in this document (§6). |
| **Revisions / `DocumentRevision`** | **None structurally, more instances created** | `DocumentRevision` objects are created on every `commit()` regardless of trigger source (already true today) — a tighter commit cadence just creates more of them per editing session. Since only `currentRevision` and `savedRevision` are retained (`durability-model.md` §Stage 1, "no history of prior revisions retained past the current and last-saved pointers"), this has no accumulation cost — old revisions are simply not referenced after a new commit and become garbage. No change needed here; confirms `durability-model.md`'s existing framing was already accurate. |
| **Future undo/history** | **Positive interaction, no redesign forced** | `DocumentTransaction`'s existing shape is already "a discrete, replayable unit," per ADR-010, specifically anticipating this. A finer-grained commit cadence (keystroke or short-coalesced-interval, rather than only blur-sized commits) actually makes a *future* undo stack more useful (finer-grained undo steps) rather than less — this milestone is a strict improvement for that future capability, not a complication of it. Recorded here as a positive side-finding, not a requirement of this milestone. |
| **Future cloud sync** | **No forced redesign, one thing worth naming** | `durability-model.md` already scopes cloud sync as "a separate, later stage this one would eventually feed into" (§Stage 2). A more frequent local Durable-stage write is, if anything, a *better* upstream feed for a future cloud-sync stage than today's blur-only cadence — less latency between "user typed something" and "there's a local durable copy a sync layer could pick up." No architecture change required now; worth noting as a reason *not* to delay this milestone waiting for cloud sync to be designed first — the two are compatible, in the helpful direction. |
| **Future collaboration** | **Out of scope, no conflict** | Real-time collaboration (per §2's Notion/Google Docs research) requires an operation-transform/CRDT layer that doesn't exist in Clutter today and isn't implied by this milestone — this milestone's local-only, single-writer trigger-model design doesn't foreclose that future architecture (it would layer on top of/replace the Committed-stage commit mechanism, not the trigger-model decisions made here), but also doesn't build toward it. Explicitly out of scope, consistent with `implementation-rules.md` §5's instruction not to invent architecture the task doesn't require. |
| **Composition Root** | **Minor** | If a debounce/scheduling utility needs to be a shared, constructed-once collaborator (rather than purely local `useEffect`/component state), it's wired in `Application.ts` per rule 10 (`ARCHITECTURE_RULES.md`) — worth deciding explicitly during implementation planning whether the autosave scheduler is UI-layer (React hook state, per-editor-instance) or application-layer (a `SaveCoordinator`-owned, session-keyed timer). This document recommends application-layer (§7) specifically because navigation/close/window-focus-loss triggers need to reach *every* open session, not just the currently-focused component's local state — a purely component-local debounce can't see "the user switched away from this tab entirely," which is one of the triggers this design needs. |
| **UI/Features generally** | **Indirect** | Any component reading `DocumentSession.state`/`isDirty` for a "saving.../saved" indicator continues to work unchanged in meaning (§3) — just updates more frequently, which is a UX improvement (more accurate real-time feedback), not a contract change. |

**Net finding:** this milestone's blast radius is almost identical in shape to ADR-017's own "the blast radius is `PageOperations` + `DocumentEditing`" conclusion (§4 of that ADR) — the trigger model is additive to the entry points into an already-correct `save()` pipeline, not a redesign of anything downstream of it. The one genuinely new architectural question (not just an extension of existing collaborators) is **where the navigation-triggered flush-before-switch logic lives**, because it's the one trigger that structurally cannot live inside `Workspace` per its own frozen contract — this is called out explicitly in §7 as the recommendation's one design decision requiring a stated placement, not left implicit.

## 5. Concurrency analysis

All of the following are evaluated against the Persistence Gate's existing, already-correct concurrency model (spec §5) — the question in every case is "does a tighter/multi-trigger autosave model create new concurrency surface, or just exercise the existing guarantees more often."

- **Multiple rapid saves (same page, different triggers firing close together — e.g., debounce fires, then blur fires half a second later before the first write completed):** Already handled. The Gate's per-page queue (spec §5) guarantees strict enqueue-order execution regardless of *why* each `save()` call was made. `SaveCoordinator`'s stale-completion guard (spec §9's invariant, already implemented in `SaveCoordinator.completeSave`/`failSave`) already discards a late-arriving completion for a superseded save. **No new guard needed** — this is exactly the scenario these two existing mechanisms were built for; a hybrid trigger model just makes this scenario common instead of rare, which is a reason to be confident in this existing machinery, not a reason to add more.
- **Save already running when another trigger fires:** Same answer — the Gate queue serializes; a second `save()` call while the first is still enqueued/executing simply enqueues behind it. Worth one implementation-time check (not a design change): confirm the debounce/scheduling layer in `DocumentEditing` doesn't need its own "is a save already in flight" guard *before* enqueueing, or whether it's acceptable/correct to always call `PageOperations.save()` and let the Gate's queue absorb the ordering (this document recommends the latter — adding a second, UI/application-layer-side "is it safe to save right now" check would duplicate the Gate's own job, contrary to Rule 5's placement principle: the Gate already owns *how* a write happens safely).
- **Navigation during save:** The one case needing genuine design attention (§4). Recommendation: the flush-before-navigate call **awaits** the outgoing session's save before actually switching `Workspace`'s active page, but the *UI* doesn't block on it — optimistically render the new page immediately (per §1's navigation analysis) while the flush completes against the *closing* session in the background. This requires the flush to be initiated and tracked independently of whether the user has already moved on, which `SaveCoordinator`'s existing per-session `activeSaves` map (keyed by session id, not by "currently active/focused" status) already supports without modification — a save in flight for a session that's no longer the active `Workspace` page still completes and calls `markSaved`/`markSaveFailed` correctly, because nothing in `DocumentSession`/`SaveCoordinator` today assumes the session it's tracking is the *focused* one.
- **Window close during save:** This is the one case where "await, but don't block the UI" (navigation's answer) is wrong — on close, the app **must** block exit until pending saves resolve (§1, Application close). This is a different concurrency shape than navigation: not "let it finish in the background," but "prevent the process from exiting until it finishes," which needs to enumerate *every* session with `isDirty === true` (not just the last-active one) and await all of their flushes, with a bounded timeout and an explicit decision for the timeout-exceeded case (force-close and accept the loss, vs. block indefinitely — recommend a bounded wait with a generous but finite timeout, consistent with how VS Code's Hot Exit precedent in §2 avoids ever blocking exit indefinitely, instead relying on its separate buffer-preservation mechanism for the case a write genuinely can't complete in time).
- **Save failures:** Already correctly isolated per-page and per-operation by the Gate (spec §5's invariant: "On any step failure... the queue for that page rejects the current operation and continues processing subsequent ones"). A more frequent autosave cadence means failures (if they happen — e.g., disk full, permissions revoked mid-session) surface more often but each one is exactly as contained as today's single blur-triggered failure already is. `DocumentSession.markSaveFailed()` already preserves the current (unsaved) revision for retry (per its own doc comment) — this existing behavior is sufficient and needs no change; a subsequent autosave trigger (the next debounce firing, or the next blur) naturally becomes the retry, with no new retry machinery required.
- **Recovery after failure:** Same point — because every trigger converges on the same `save()` call (§0), "recovery" is just "the next trigger fires and tries again," which falls out of the hybrid model for free rather than needing dedicated retry logic. Worth a UX decision (not an architecture one) about whether a failed autosave should surface an explicit error state to the user (it already can, via `DocumentSession.state === SaveError`) rather than failing silently and only retrying on the next debounce — recommend surfacing it, consistent with `durability-model.md`'s general ethos of being precise about what's actually guaranteed rather than implying success.
- **Duplicate save requests (e.g., blur and a debounce ceiling firing in the same tick):** Not a new problem — `DocumentSession.commit()` already no-ops if the incoming transaction's markdown matches the current revision exactly (`DocumentSession.ts:76-78`, "Ignore no-op transactions to preserve a meaningful revision history"), and if two triggers both call `save()` with the same already-committed revision, the Gate enqueues two operations but the second is writing identical content — wasteful but not unsafe (the existing write-parse-rebuild-replace cycle is idempotent for identical content). Worth a light guard in the scheduling layer to skip a redundant enqueue when nothing changed since the last successful save (comparing `session.currentRevision` against `session.savedRevision`, i.e., `session.isDirty`, already a public getter) — cheap, and avoids unnecessary disk I/O rather than avoiding a correctness problem.
- **Back-pressure / queue depth:** The Gate's per-page queue has no explicit depth limit today because nothing has ever generated enough concurrent operations for one page to matter (`PagePersistenceCoordinator`'s queues are described as "plain promise chains," spec §5). A hybrid trigger model, especially with a debounce ceiling firing during long sessions, keeps per-page enqueue frequency in the range of "a handful of operations per minute at most" — nowhere near a volume that stresses an unbounded promise chain. **No back-pressure mechanism is needed for this milestone** — flagged only because the question was asked; the answer is that the trigger model, correctly debounced, structurally avoids ever generating queue depth beyond 1-2 pending operations per page in normal use. A keystroke-frequency trigger *without* debouncing (the rejected pure "every keystroke" model from §1) is the only scenario that would actually threaten this, which is one more reason that model is rejected outright rather than tuned.
- **Queue behavior across multiple open pages:** Unaffected — the Gate already serializes per-page-id, and different pages' queues already run independently (spec §5's concurrency model). A hybrid trigger model firing independently for several open sessions simultaneously (e.g., window-focus-loss flushing every dirty session at once) is exactly the "operations for different `pageId`s execute concurrently" case the Gate's design already covers without modification.

**Net finding:** the concurrency story for this milestone is almost entirely "the existing Gate/`SaveCoordinator` machinery already covers this, because it was designed against an already-async, already-multi-trigger-capable `save()` entry point, even though only one trigger has used it until now." The one genuinely new concurrency *shape* (not just new frequency) is close-time blocking-flush-of-all-dirty-sessions, which has no precedent in the current codebase and needs to be built, but is a bounded, well-understood pattern (VS Code, and every other product in §2, already solve it) rather than a novel design problem.

## 6. Future scalability — stress test

| Future feature | Does this trigger-model design require rework later? | Reasoning |
|---|---|---|
| **Undo/Redo** | No — net positive | Finer-grained `commit()` cadence (§1, §4) produces more, smaller `DocumentRevision`s, which is exactly what a future undo stack over `DocumentTransaction`'s already-replayable shape (ADR-010) would want. No redesign; an improvement to the substrate undo would consume. |
| **Version History** | No | Per §2/§3, version history/Snapshots are consistently a *separate* mechanism from autosave in every researched product, and `durability-model.md` already frames "Recoverable" as an independent, currently-absent stage rather than something autosave provides. This design doesn't need to anticipate version history's shape — it just needs to not conflate "saved" with "recoverable," which §3's stage mapping already keeps distinct. |
| **Plugins** | No | A plugin calling `PageOperations.save()` programmatically (an eager, non-interactive caller, per ADR-017 §6's explicit scope note that programmatic callers should use eager `create()`/direct `save()`, not draft/autosave machinery) is unaffected by anything in the trigger model, which only concerns *interactive* editing triggers. |
| **AI editing** | Minor consideration, no rework | If AI-generated edits are inserted into the same `DocumentSession` (as a `DocumentTransaction`, consistent with the existing shape), they'd flow through the same commit/autosave pipeline automatically. Worth a future product decision about whether AI-authored content should trigger the *same* draft-promotion policy as user typing (§4's flagged open question about autosave-triggered promotion applies equally here) — not a new architectural question, the same one, just another instance of the caller needing a policy answer. |
| **Templates** | No | Templates are a content-source concern (what initial markdown seeds a new/draft session), orthogonal to when that session's edits get saved. No interaction. |
| **Attachments** | No | Per ADR-017's amendment (draft-promotion trigger generalization to any committed, persistent, user-owned change including metadata), a future attachments feature modeled as page metadata already has a defined promotion/save path; the trigger-model design doesn't need to special-case it — it's exactly the kind of future `EditablePageMetadata` field ADR-017's amendment already verified needs zero changes to the promotion mechanism. |
| **Rename** | No | Title changes already go through the same `persistDraft`/promotion path (ADR-017's amendment) — an autosave trigger for title edits (e.g., debounce on a title input, analogous to body debounce) is a natural, independent extension of the same pattern, not a new mechanism. |
| **Large documents** | Worth flagging, not a redesign | `writeParseRebuildReplace`'s write-then-reread-to-verify cost (durability-model.md §Stage 2) scales with document size — a very large document autosaving on a tight debounce could make each Durable-stage flush noticeably more expensive. This doesn't change the *trigger model*, but is a reason the debounce ceiling/interval should probably not be a single hardcoded global constant if Clutter ever supports very large documents — a tuning parameter, not an architecture change, and explicitly not solved by this document (flagged as a future tuning concern, per this milestone's scope of trigger model, not write-cost optimization). |
| **External file edits** | No new interaction beyond what Sync already handles | A tighter autosave cadence increases how often Clutter's own writes need to be correctly suppressed by `SelfWriteAwareWatcher` (§4) — already the existing mechanism's job, just exercised more often. If an external edit and an autosave-triggered internal write raced at exactly the same moment, that's the same unresolved "two writers, different content" gap `durability-model.md` already names as out of scope for Reconciled (§Stage 3, "Explicitly does not guarantee: Resolution of a genuine write race") — this milestone doesn't make that gap worse or better, it's orthogonal to trigger frequency. |
| **Multiple windows** | Needs naming, not solved here | If Clutter ever supports multiple windows/views onto the same vault, the close-triggered "flush every dirty session" step (§5) needs to be scoped per-window or per-process correctly — today's single-window assumption in `Application.close()` (spec §11) would need revisiting, but that's a multi-window feature's own architectural question, not something this trigger-model design should attempt to solve pre-emptively (`implementation-rules.md` §2 rule 13 — don't build for a hypothetical future). Flagged as a dependency to check *if/when* multi-window is ever scoped, not a gap in this design today. |
| **Mobile** | Adds one new consideration, doesn't invalidate the design | Mobile platforms (if ever targeted) have OS-level app-suspension semantics stricter than desktop close (an app can be suspended/killed by the OS with very little warning, not just user-initiated quit) — the "application close" trigger's implementation would need a platform-appropriate equivalent (e.g., `applicationWillResignActive`-style hooks), but the *trigger model itself* (commit continuously, debounce-flush, flush-on-backgrounding) is the same shape mobile apps already use (per §2's Bear/Apple Notes/Drafts research, all of which are primarily mobile-native apps already solving exactly this). No redesign — a platform-specific implementation of an already-generalized trigger. |
| **Cloud sync** | No rework, positive interaction | Already covered in §4 — a more frequent local Durable-stage write is a better upstream feed for a future sync stage, not a complication of one. |
| **Collaboration** | Explicitly out of scope, no conflict | Already covered in §4 — real-time collaboration needs an operation-transform/CRDT layer this milestone doesn't build and doesn't foreclose. |

**Net finding:** no future feature in the stress-test list forces a redesign of the trigger model recommended in §7. The recurring pattern is that this design's choices (converge everything on the existing `save()` entry point; keep Committed/Durable staged distinctly; keep version-history-shaped concerns explicitly separate from autosave) are exactly the choices that keep future work additive rather than corrective — consistent with the specification's own stated design philosophy (§"Why This Stays Coherent After 300 More Features").

## 7. Risks, trade-offs, and recommendation

### Risks

1. **Draft-promotion-on-autosave is a real product-policy question this document does not resolve.** If a debounce timer alone (with no blur/navigation/close involved) can promote a draft to a real, on-disk page, then simply pausing while typing a first sentence — before the user has any intention of keeping the note — writes a real file. This is close to the exact "abandoned Untitled.md" problem ADR-017 was written to solve, reintroduced through a different door. **Recommendation within the recommendation:** debounced *body* autosave should still be gated by the same "has the user produced a committed, persistent, user-owned change" test ADR-017's amendment already defines generically — which it already is, structurally, since the debounce trigger still calls the same `save()` entrypoint. The open question is narrower than it first appears: it's not "should autosave promote drafts" (yes, unavoidably, since `save()` is the one promotion mechanism) but "should the debounce interval for a still-unpersisted draft be longer/more conservative than for an already-real page," to avoid persisting a two-word false start. Worth a product decision, not an architecture decision — flagged for the next conversation, not resolved here.
2. **The close-time blocking flush needs a concrete answer for "what if the write doesn't finish in time."** A generous but finite timeout is recommended (§5), but the specific number, and what happens to a user's in-progress content if it's exceeded, is a product/UX decision, not something this document should assert as settled.
3. **Debounce interval tuning is a real, non-trivial product decision** with real trade-offs between "aggressive (more disk writes, smaller loss window)" and "conservative (fewer writes, larger loss window, better for large documents per §6)" — this document recommends treating it as a tunable constant, not hardwiring a specific number into the architecture, but does not itself pick the number.
4. **The navigation-flush placement (§4) is the one piece of new architecture, not just new usage of existing architecture**, and needs to be scoped precisely during implementation planning against `implementation-rules.md`'s pre-implementation checklist — specifically "which existing implementation is being replaced" and "which existing implementation must remain untouched" (`Workspace` itself, explicitly).
5. **This document's §2 industry research mixes VERIFIED and INFERRED claims per-product**, as marked. Where a specific number (e.g., an exact debounce interval) is INFERRED, it should not be treated as a target to match precisely — Clutter's own tuning should be decided on Clutter's own constraints (document size, write cost, `writeParseRebuildReplace`'s verify-by-reread pattern), not by copying an unverified competitor number.

### Trade-offs

- **Committing on every keystroke (Committed stage) vs. a lighter coalesced-interval commit:** true zero-latency commit is nearly free (no I/O) and gives the most accurate `isDirty`/revision state, but even in-memory work has some cost at extreme typing speed if every single keystroke triggers a full transaction/notify cycle (`DocumentSession.commit()` calls `notify()` synchronously, per `DocumentSession.ts:85`, which re-renders every subscriber). A very short coalescing window (tens of milliseconds, not seconds) for the *commit* trigger specifically may be worth considering purely as a rendering-performance optimization, separate from the Durable-stage debounce — flagged as an implementation-time tuning question, not a stage-model change (still squarely within Committed either way).
- **Whole-document save vs. finer-grained (block/operation-level) persistence:** §2's research (Notion, Google Docs) shows finer-grained persistence shrinks the crash-loss window further than whole-document debouncing ever can. Clutter's current architecture is whole-document (`writeParseRebuildReplace` writes and re-verifies the entire file each time, spec §5) — adopting block-level persistence would be a materially larger architecture change (a new `PersistenceOperation` shape, a different Gate model, likely a different `Vault`/`Page` internal representation) than this milestone's scope, and is explicitly **not recommended** as part of this work — named here only so the trade-off is visible, not because this document proposes taking it.
- **A crash-durable local buffer (VS Code Hot Exit precedent) vs. relying solely on tighter Durable-stage cadence:** the former structurally closes the Committed-stage crash gap; the latter only narrows it statistically. Building the former is a bigger, separate piece of work (a new stage in the durability model, new local storage, its own recovery-on-launch logic) that this document recommends naming as a *future candidate*, explicitly not part of this milestone's recommendation, to avoid scope creep into `implementation-rules.md` §5's "implementing the requested feature would require inventing a new architecture" failure condition.

### Recommendation

Adopt the **hybrid trigger model from §1**, staged per §3's durability-model mapping, as the target design for the Autosave milestone:

1. **Commit-stage trigger:** every keystroke (or a very short, purely-rendering-motivated coalescing window, tens of ms) commits into `DocumentSession` via the existing `commit()` API — no signature change, no new subsystem, wired through the existing `onCommit` prop callback already in place, just called more often than only-on-blur.
2. **Durable-stage trigger, the actual "autosave":**
   - Debounced flush after a pause in typing, with a max-wait ceiling for long unbroken sessions (both values to be tuned, not fixed by this document).
   - Immediate flush on editor blur (already correct, keep as-is).
   - Immediate flush on window/app focus loss (new, low-cost addition).
   - Immediate flush of the outgoing session on navigation-away, implemented as a caller-side responsibility above `Workspace` — never inside it (§4's explicit architectural constraint).
   - Blocking flush-and-await of every dirty session on application close, with a bounded timeout (§5).
3. **`SaveCoordinator` is the right home for the scheduling logic** (debounce timers, ceiling tracking, "which sessions are currently dirty" enumeration for the close-time flush) — it already claims this responsibility in its own documentation and already has the per-session bookkeeping (`activeSaves`) this design needs to extend, not replace.
4. **Every trigger continues to converge on `PageOperations.save()`** — this design adds callers, not new facade methods, new Gate operation kinds, or new `Vault` mutation paths, keeping the milestone within existing architectural contracts per `ARCHITECTURE_RULES.md` rules 1, 2, and 12.
5. **Explicitly deferred, not rejected:** a crash-durable Committed-stage buffer (VS Code Hot Exit-style) is named as a strong future candidate for extending `durability-model.md` with a new named stage, but is out of scope for this milestone — recommend revisiting it as its own, later, explicitly-scoped ADR if/when the product decides narrowing-by-frequency isn't a strong enough guarantee.
6. **Two product-policy questions are surfaced for explicit decision before implementation, not resolved by this document:** (a) whether debounce-only-triggered draft promotion should behave identically to blur/navigation/close-triggered promotion, or use a more conservative interval (Risk 1); (b) the specific debounce interval, ceiling, and close-timeout values (Risk 3).

This recommendation requires **no specification amendment and no new ADR to begin scoping implementation** — every subsystem touched (`DocumentEditing`, `PageOperations`, the editor UI layer) is extended within its existing contract, per §4's sweep, with the one placement decision (navigation-flush ownership) resolvable as an implementation detail within `PageOperations`/`NavigationRouter`'s existing scope rather than as new architecture. If, during implementation, the navigation-flush placement or the draft-promotion policy question turns out to need a contract change the spec doesn't currently express, that is exactly the trigger `implementation-rules.md` §4's "Handling divergence from the specification" process exists for — surface it then, not pre-emptively here.
