# Editor Architecture Decisions

## Purpose and scope

This is **not** an ADR and not a research document. It is a concise lookup layer over the Markdown editor's architecture Q&A — the semantic-inline construct thread specifically (parser design, grammar, resolution semantics, the shared interaction contract). Its only job is to let a reader, including a cold-start Claude session, answer *"is X already decided, and under what conditions?"* in under a minute, without reading the full research archive.

The full reasoning, worked examples, counter-examples, and scenario walkthroughs behind every entry below live in [`docs/editor-research/`](./editor-research/README.md) — **that is the evidence layer; this is not.** Entries here are deliberately terse. When an entry's "why" isn't enough to settle a disagreement, follow its link rather than re-deriving the reasoning from scratch.

**Relationship to ADRs**: none of this is an ADR yet, by design (per the working decision on how to document this phase of work). Once this architecture stabilizes, the small number of genuinely foundational, durable commitments here (candidates: CodeMirror 6 as the engine, Markdown as sole canonical source with no second document model, one shared interaction mechanism for semantic inline constructs) should graduate into real ADRs in `docs/adr/`, matching the scale of `ADR-017`/`ADR-020`. The much larger volume of fine-grained grammar/precedence/interaction decisions below is not expected to ever need that treatment individually.

**Earlier, separate phase of work not covered here**: the Markdown editor behavioral specification (`clutter-editor-interaction-spec-v0.2.md`), the three architecture-blocking-decision resolutions, the architecture proposal, and the bounded implementation plan are prior, self-contained deliverables with their own internal decision/open-item summaries. This log does not re-capture them — it picks up from the semantic-inline construct Q&A that followed.

## Status key

- **Locked** — settled; treat as a fixed constraint for any further work in this area.
- **Recommended, not locked** — a considered, evidenced recommendation, but not yet a product/architecture commitment. Do not build against it as if it were Locked without checking whether it's since been promoted.
- **Superseded** — an earlier position that was explicitly reversed. Kept visible on purpose so nobody re-discovers the same dead end.
- **Open** — a genuine, named unresolved question. Not silently decided by omission.

- **GFM's `Autolink` inline parser is registered under the literal name `"Autolink"`, with no `before`/`after` of its own** — confirmed by reading `@lezer/markdown`'s own source. - **GFM's `Strikethrough` parser is registered `after: "Emphasis"`** — confirmed real (not just inferred precedent) evidence that delimiter-based custom inline constructs are already proven to compose correctly with `Emphasis` in the shipped grammar.

- **`Decoration.replace`, `Decoration.widget`, `WidgetType`, and `EditorView.atomicRanges` all confirmed to exist with the assumed shapes.** One precision worth recording: `atomicRanges` affects cursor-motion and deletion commands, but does **not** prevent programmatic selection changes — doesn't contradict anything locked, just a detail worth knowing before relying on it for anything beyond keyboard interaction.
- **`atomicRanges` should be applied to tokens at rest, but deliberately *not* to ordinary Live-Preview-hidden inline marks (bold/italic/etc.).** This wasn't previously stated as sharply: at-rest atomic whole-token deletion is the *desired* behavior for semantic tokens (already Locked), but the same combination on an ordinary hidden formatting marker would reintroduce the "whole range deletes in one step" problem the original audit already flagged as a bug pattern to avoid. Both use `Decoration.replace`/`WidgetType`; only tokens additionally register in `atomicRanges`.
- **Decoration position stability via `RangeSet.map(changeDesc)` confirmed real** — not an assumed mechanism.

## Reference vocabulary

Concepts reused across many entries below; defined once here rather than re-explained per entry.

- **Reveal-on-engagement**: the shared lifecycle for every semantic inline construct. *At rest*: rendered as a collapsed/atomic widget. *Engaged*: raw Markdown revealed, ordinary character-level editing applies. Engagement is **derived**, not stored — see next entry.
- **Engagement is derived from selection**: a construct is engaged if and only if the current CM6 selection (including a zero-width caret) lies strictly within its syntax range. There is no engagement flag anywhere. This is why undo/clipboard/accessibility all "just work" for these constructs without bespoke code — anything defined purely in terms of selection inherits CM6's already-correct handling for free.
- **The one-way pipeline**: Stored Markdown → Parsed syntax → Semantic resolution → Display label → User activation. One direction only — there is no arrow from display back to stored. **Serialization** is the one exception, and it only ever fires once, at insertion time (e.g. autocomplete acceptance) — never as an ongoing re-derivation of already-existing text.
- **The shared semantic descriptor**: `{ kind, resolve, displayLabel, activate, validate, serialize }`, supplied per construct kind. `resolve`, `validate`, and `activate` are each **optional per kind** — not every kind needs all three meaningfully (e.g. a tag leans on `resolve`, `@due` leans on `validate`, neither needs both). `resolve()` returns **resolved / unresolved / ambiguous**, never a bare boolean — silently picking a candidate on ambiguity is never acceptable.
- **Lenient reader, strict writer**: Clutter's parser tolerates non-canonical-but-valid existing text (extra whitespace, `.`/`..` in paths, unnecessary-but-valid escapes) and never rewrites it just because it was read. Clutter's own writer always produces normalized, canonical text. Applied repeatedly across path normalization, alias trimming, and WikiLink escaping.

## Foundational principles (Locked)

All originate in the earlier architecture-proposal phase; restated here because every later document in this archive depends on them.

- **Markdown remains the sole canonical source of truth at all times.** No second/parallel rich-document model is ever introduced as a competing source of truth.
- **No second, independent parser.** Clutter-specific syntax is recognized through the exact same parse as CommonMark/GFM — never a regex/scanner pass running alongside it.
- **Clutter syntax extends `@lezer/markdown`'s public `MarkdownConfig` mechanism** (`parseBlock`/`parseInline`/`defineNodes`/`props`) — the same mechanism GFM's own Table/TaskList/Strikethrough/Autolink extensions are built on, confirmed against the library's own documentation, not assumed. See [parser-architecture.md](./editor-research/clutter-editor-parser-architecture.md).
- **Distinct Lezer node types per semantic kind** (`WikiLink`, `Tag`, `Mention`, `PropertyToken`, …) — not one generic `SemanticInline(kind=...)` node. A shared node-group/prop tags the family for the interaction layer's generic queries; grammar stays per-kind. See [shared-semantic-inline-model.md](./editor-research/clutter-editor-shared-semantic-inline-model.md).
- **One shared interaction mechanism for every inline semantic construct** — rendering, engagement, selection, deletion, clipboard, undo/redo, IME, and accessibility are shared infrastructure; only resolution, display label, activation, validation, and serialization are type-specific. Explicitly scoped to **inline** constructs — a future block-shaped construct (e.g. a full transclusion) is not assumed to fit this mechanism. See [shared-token-interaction-contract.md](./editor-research/clutter-editor-shared-token-interaction-contract.md).
- **Native CommonMark/GFM meaning must never be compromised.** A Clutter extension may only claim text that would otherwise remain literal — amended below with a precision the original one-line rule was missing.
- **Plain Markdown links (`[text](url)`) remain ordinary Live Preview marks**, not semantic tokens — validated, not assumed: link display text is exactly the content users routinely edit character-by-character, which atomic treatment would actively harm.
- **Images participate in the semantic-token/reveal-on-engagement family**, unlike plain links — validated for a different, firmer reason: an image's at-rest form is an actually-rendered widget, not styled text with hidden markers, which is structurally a token-family concern regardless of how often alt-text gets edited.

## Parser precedence & grammar

- **CommonMark/GFM-always-wins needs one addition, not just "ordering."** *Locked.* Where a Clutter trigger is a strict prefix of a built-in trigger (`[[` vs `[`, `![[` vs `![`), `before`-ordering (e.g. `before: "Link"`) is necessary but **not sufficient** — the extension's own matcher must also verify no valid built-in continuation (`(` or `[`) follows its closer, or a genuine CommonMark link like `[[Project A]](url)` would be silently misinterpreted. Where trigger characters share a start character but not a start *position* (`@mention` vs. GFM email autolink, whose match begins before the `@`), ordering alone (`after: Autolink`) is sufficient. See [precedence-validation.md](./editor-research/clutter-editor-precedence-validation.md).
- **`#tag` vs. ATX heading resolves automatically**, no extension logic needed — CommonMark's own space-required rule already prevents collision; block- and inline-level parsing are separate phases, so they never compete for the same dispatch point.
- **WikiLink requires `before: "Link"` plus the continuation-lookahead check above.** *Locked.* The same pattern applies identically to a future `![[embed]]` vs. `Image`.
- **WikiLink grammar and escaping — full formal rules.** *Locked.* Summary: backslash escapes exactly one following character, reusing CommonMark's own escapable-punctuation set (**semantic-rule reuse, not delegation** — the WikiLink parser's own scan must implement escape recognition itself; the generic `Escape` node never gets an independent turn inside an already-claimed WikiLink range — this was an imprecision in the first pass, corrected explicitly). First unescaped `|` is the separator, and only the first — further unescaped pipes are just alias text. First unescaped `]]` always terminates (lazy match, not greedy). No WikiLink nesting — an inner `[[` is never treated as a nested start. The parser never produces a partial node: either a complete, validly-closed structure is found, or the whole span falls through to ordinary text. See [wikilink-grammar.md](./editor-research/clutter-editor-wikilink-grammar.md).
- **Canonical serialization escapes every literal `]`, not only `]]`-forming pairs.** *Locked, corrected from an ambiguous first phrasing.* A naive "only escape adjacent `]]` found in the data" rule is unsafe, not merely non-minimal — a lone trailing `]` (e.g. `path = "A]"`) can silently combine with the closer written immediately after it (`[[A]]]` mis-parses), a boundary case invisible to a scan of the data alone. Escaping every `]` unconditionally is both simpler (context-free) and actually correct. See [wikilink-grammar-corrections.md](./editor-research/clutter-editor-wikilink-grammar-corrections.md).
- **Round-trip invariant, precisely stated.** *Locked, corrected from an overstated first version.* `parse(serialize(v)) == normalize(v)` — **not** `== v` for arbitrary unnormalized input. The writer trims whitespace as part of serialization, so exact equality only holds when `v` was already normalized. Canonical-serialization stability (repeated serialization doesn't drift) still holds, since `serialize()` is a pure function of the decoded value alone, never of prior raw text.

- **Highlight delimiter length — widened to any run `>= 2`, opening/closing lengths need not match (2026-08-27).** *Locked.* Supersedes the construct's original `~~`-mirroring "exactly 2, triple-run rejects" guard: `highlightSyntax.ts`'s `Highlight` parser now scans the full contiguous `=` run at each candidate position (the same primitive `@lezer/markdown`'s own built-in `Emphasis` scanner uses — confirmed against the installed `@lezer/markdown@1.7.2` source), gated at `>= 2` rather than a fixed width of exactly 2. `===text===`, `====text====`, and mismatched pairs like `==text===`/`===text==` all produce one flat `Highlight` node whose two `HighlightMark`s are exactly whatever run was actually matched on each side — never a fixed 2, never a swallowed/stray leftover character. **Deliberately not full `Emphasis`-style asymmetric-length *peeling* into nested sub-nodes**: that peeling lives in `@lezer/markdown`'s internal `resolveMarkers`, hard-gated behind an identity check against the library's own two singleton `Emphasis` delimiter objects — there is no public extension point that applies it to a custom `DelimiterType`. It's also not the same kind of ambiguity to begin with: `Emphasis`/`StrongEmphasis` are two distinct node types to peel into by length parity; `Highlight` has exactly one node type regardless of run length, so mismatched-length pairs are already fully and consistently handled by the generic (non-`Emphasis`) path in `resolveMarkers` with zero further change — it wraps the full open range and full close range as-is, requiring only that both delimiters share the same `type`, which every `Highlight` delimiter does. No renderer, decoration, marker-DOM, engagement, or CM6 navigation change was needed: both `delimitedInlineRenderer` (at rest) and `revealedMarkerRanges` (engaged) already resolve marker ranges from the actual parsed node, never a hardcoded 2-character assumption — confirmed by mounting a real `EditorView` before writing any code. See `inlineLivePreviewRegion.test.ts`'s `==text== (Highlight)` describe block for the regression coverage (symmetric runs of every length, asymmetric pairs, single-`=`/unflanked-run rejection, and independent-region composition).

- **Concealed marker inflated `.cm-line` to 30px at rest (24px once engaged) — fixed via `line-height: 1` (2026-08-27).** *Superseded 2026-08-27 (same day) — see the selection-geometry entry below.* The `line-height: 1` fix itself was correct and is preserved in spirit (concealed markers must not inflate the line box), but the near-zero-`font-size` technique it was patching a side effect of was replaced later the same day by an atomic-box-plus-`transform` technique, which does not have an inherited-line-height mismatch to begin with (`line-height: inherit` is safe once `font-size` is also `inherit`). Kept below, unedited, as the historical record of that investigation. **This is a general CSS box-model finding, not a WebKit/Tauri-specific one** — deliberately not recorded in `docs/tauri-webkit-editor-issues.md`, which is scoped to behavior proven to differ from Chromium; this bug was never shown to be engine-specific (Chromium could not be verified this session — see below), and its mechanism (an inline box's inherited `line-height` contributing "half-leading" space around its own near-zero-font-size content, independent of glyph size) is standard CSS2.1 inline-formatting-context behavior, not a browser quirk. Measured in real Safari: a formatted line's own `.cm-line.getBoundingClientRect().height` was `30px` at rest and `24px` once engaged, against an intended `24px` (`--lh-body`) in both states; a plain line with no marker spans measured `24px` throughout. **Root cause, proven by direct measurement:** `.cm-marker--concealed` overrides `font-size` down to a near-zero value but never declared its own `line-height`, so it inherited `.cm-content`'s absolute `line-height: 24px` unchanged — diffing every child of the line between at-rest and engaged states showed the concealed marker's `font-size` as the *only* difference, and it's the only thing that correlates with the 30px/24px split. **Proven to predate the `font-size: 0.05px` WebKit navigation fix**: reproduced identically at `font-size: 0` (the original pre-fix value) and `font-size: 1px`, via temporary injected overrides, never touching the production file until the actual fix was confirmed — this bug has nothing to do with which tiny font-size value the WebKit navigation fix (above, and `docs/tauri-webkit-editor-issues.md`) happens to use. **Isolating the exact contributor:** adding `line-height: 1` while leaving `font-size: 0.05px` completely unchanged restored `24px` on every construct tested (`==`, `**`, `~~`, `*`, nested `===**bold**===`), with the marker's own rect measured unchanged (still `0` height, still a fraction-of-a-pixel wide) — `line-height: 1` touches only the inherited-line-height mismatch, never concealment. **Fix**: `.cm-marker--concealed { font-size: 0.05px; line-height: 1; }` — one additional declaration on the existing rule, `font-size` untouched. **Verified in real Safari after the fix** (production CSS, no injected overrides): every construct measures `24px` at rest, engaged, and after; the full 13-line ArrowDown/ArrowUp regression corpus (`docs/tauri-webkit-editor-issues.md`) still sweeps with zero skips in both directions, including the previously fragile `***~~Italic bold strikethrough~~***` transition; all 8 variable-length Highlight cases measure `24px` and navigate cleanly; marker concealment (invisible at rest, reveals on engage, re-conceals on leaving) is unaffected. **Chromium was not verified with real confidence this session** — the real Chrome extension wasn't connected, and the available sandboxed Chromium automation pane could not reliably build a multi-line test document (a previously-noted limitation of that pane); only the built CSS asset's `line-height: 1` declaration was confirmed to parse correctly there, which is not a geometry or behavioral check. Given the standard-CSS nature of the mechanism, there is no specific reason to expect this differs in Chromium, but that expectation is not yet independently confirmed. Regression coverage: `apps/app/src/features/markdown/editor/markerConcealedLineHeight.test.ts` (a source-level assertion that the rule declares both properties — jsdom cannot compute real layout, so this is a tripwire against reverting the fix, not a layout-correctness test).

- **Concealed marker's near-zero `getClientRects()` height zeroed out `drawSelection()`'s selection-background rectangle for the whole line — fixed by switching to an atomic-box `transform` technique (2026-08-27).** *Superseded 2026-08-27 (same day, next entry below) — the `transform: scaleX()` fix here correctly solved the vertical-geometry bug it targeted, but `transform` never changes an element's *layout* box, only its painted one (confirmed at the CSS-spec level), so the marker still reserved its full original glyph width in the line's horizontal layout — every concealed marker on a line pushed later content right by its own (invisible but still-reserved) width, compounding with each additional marker. Reproduced directly: a document with `*x*`/`**x**`/`***x***`/`****x****` on consecutive lines rendered each line's visible content at a progressively larger left offset. Kept below, unedited, as the historical record of that investigation — its vertical-geometry fix and measurements are still accurate; only the technique as a whole is superseded.* **Bug**: Cmd+A (`selectAll` — a plain `{from: 0, to: doc.length}` selection; CM6 selection semantics themselves are not in scope here and were not touched) on a document whose first line starts with a concealed marker painted no selection-background rectangle at all for that line, even though the line was genuinely selected — reproduced and measured in this session's Chromium-based browser pane, no WebKit-specific dependency assumed or required. Markers were confirmed to stay concealed throughout (`.cm-marker--concealed` count unchanged, `.cm-marker`/`.cm-marker--concealed` counts equal before/during/after Cmd+A) — the earlier appearance of "raw Markdown becomes visible under Ctrl+A" (screenshot-driven starting hypothesis) is **not** a decoration-class change; `isTokenEngaged` (`codemirror/semanticToken/tokenEngagement.ts`) only reveals a construct when the selection is strictly *contained inside* that construct's own node range, which a document-spanning selection never is for an ordinary inline construct. That appearance was this same rendering bug in disguise. **Root cause**: CM6's `drawSelection()` does not use native `::selection` painting — it computes its own `.cm-selectionBackground` rectangles in JS (`rectanglesForRange` in `@codemirror/view`) by querying `coordsAtPos`/DOM `Range.getClientRects()` at selection boundaries and deriving each rectangle's `top`/`bottom` from those boundary rects. The prior concealment technique (`font-size: 0.05px; line-height: 1`, previous entry) left the marker's own `getBoundingClientRect().height` measured at `0` (confirmed directly: `.cm-marker--concealed` elements' `getClientRects()` returned `height: 0` uniformly). When a selection boundary landed on/inside such a marker, that `0`-height rect fed directly into the line's selection-rectangle height — measured directly: the selection layer's first box (`.cm-selectionLayer .cm-selectionBackground`) had `height: "0px"` for exactly the line starting with a concealed marker, while an ordinary line in the same selection measured its correct `72px`(3-line block)/`19px` height. **Fix**: give the marker a normal, non-degenerate content-box height instead of trying to suppress both dimensions via `font-size`. `.cm-marker--concealed` is now `display: inline-block; font-size: inherit; line-height: inherit; transform: scaleX(0.001); transform-origin: left center;` — the box lays out at the run's real size (so its content-box height always matches its context, header or body text alike, with nothing further needed for `line-height` correctness) and is squashed to near-zero *width* only, only visually, after layout, via `transform`. `transform` was confirmed load-bearing specifically because of `display: inline-block`: a plain `inline` element ignores `transform` entirely per spec (verified directly — identical rule with `display` left at its default measured an *unscaled* `getBoundingClientRect().width`, close to the marker's natural glyph width). Measured after the fix: marker `getBoundingClientRect()` is `{height: 24, width: ≈0.0145}` for a 2-character marker at a 24px line-height context (down from the predecessor's `0.05px`-ish width, and no longer `height: 0`); every `.cm-line` in a 4-line test document measures the correct `24px`, matching the previous entry's fix (no reintroduced inflation). A `width: 0; overflow: hidden` alternative was tried and rejected: forcing `width: 0` on the atomic box makes the browser wrap the marker's own multi-character text one glyph per internal line, which *doubled* the box's own height (measured `48px` instead of `24px` for `**`) — the same inflation failure mode this whole investigation started from, just triggered by width instead of font-size. **Verified in the real Clutter webapp** (not just an isolated harness, per this repo's standing testing rule) in the browser pane's Chromium engine: Cmd+A on a 4-line document (`**Bold**` / `*Italic*` / `***Italic bold***` / `**bold `` `code` `` _italic_ ~~strike~~**`) paints a selection-background rectangle for every line including the one starting with a marker, with zero `height: "0px"` boxes in `.cm-selectionLayer` (down from 2 of 3 boxes at `0px` before the fix); ArrowUp/ArrowDown single-steps through all 4 lines with zero skips in either direction (this fix does not rely on any near-zero `font-size` value, so it does not merely avoid the WebKit vertical-motion bug the predecessor's `0.05px` was tuned against — it structurally cannot trigger it, since `font-size` is never shrunk at all); ArrowRight single-steps character-by-character through a concealed marker's own text (DOM Range offsets identical to the predecessor technique at each step — `display: inline-block` does not turn the marker into an atomic caret-motion unit); Cmd+A followed by typing replaces the full document correctly (selection-state semantics are a CM6 `EditorState` concern entirely orthogonal to this CSS-only fix — nothing here can affect `selection.main.from`/`.to`); normal (unselected) at-rest and engaged rendering is visually unchanged from before the fix. Chromium-verified this session (browser pane); not independently re-verified in Safari/WebKit, though the fix's mechanism (an atomic box's own content-box height, plus a spec-standard `transform`) is not WebKit-specific and the change is, if anything, less exposed to the WebKit near-zero-`font-size` navigation bug than its predecessor, not more. Regression coverage: `apps/app/src/features/markdown/editor/markerConcealedLineHeight.test.ts` was rewritten (source-level tripwire only, same jsdom limitation as before) to assert the new technique's declarations (`display: inline-block`, `font-size`/`line-height: inherit`, `transform: scaleX(...)`) and to guard against reverting to either rejected alternative (a shrunk `font-size` or a `width: 0` box).

- **Concealed markers switched from `Decoration.mark` + CSS metric-hacking to `Decoration.replace()` + a dedicated widget (`ConcealedMarkerWidget`) — the CM6-native mechanism for concealment (2026-08-27, later same day).** *Locked.* **Why the entire `Decoration.mark`-based line of fixes above was replaced, not just further tuned:** both prior CSS techniques failed for the same underlying, structural reason — a *mark* decoration can only ever style the marker's own real glyphs, never replace or resize them, and a real multi-character text run's width and height are governed by the same font metrics. Shrinking `font-size` fixed width but broke height (`getClientRects()` → `0`, breaking `drawSelection()`'s selection-rectangle math — the previous-previous entry). Keeping `font-size` normal and using `transform: scaleX()` fixed height but broke width, because CSS transforms never change an element's layout box, only its painted one — the marker still reserved its full glyph width in the line's horizontal layout, so lines with more/longer concealed markers rendered progressively more indented (the previous entry, and the bug the user's screenshot in this session named directly: `*Italic*`/`**Bold**`/`***Italic bold***`/`****Bold****` each pushed further right than the last). No CSS declaration on a *mark* decoration can fix both axes at once, because both are contending for control of the same real text run.

  **Fix**: `inlineLivePreviewParticipants.ts`'s `delimitedInlineRenderer` now emits `Decoration.replace({widget: new ConcealedMarkerWidget(markerClass)})` for each marker range (open and close) instead of `Decoration.mark({class: ...})`, for the same five constructs as before (Emphasis, StrongEmphasis, Strikethrough, Highlight, InlineCode). This is CM6's own documented mechanism for this exact job — the `Decoration.replace()` JSDoc states it "replaces the given range with a widget, or simply hides it," and the official examples page names concealment as its paradigm use case, in contrast to `Decoration.mark`'s own documented purpose (styling, e.g. syntax highlighting) — this migration was, in that sense, moving *onto* the primitive CM6 designed for concealment, off one that was never intended for it. `ConcealedMarkerWidget` (`apps/app/src/features/markdown/editor/codemirror/highlight/ConcealedMarkerWidget.ts`) renders an **empty** `<span>` — no marker text at all, unlike the retired techniques — carrying `cm-marker cm-{construct}-marker cm-marker--concealed` for continuity with existing per-construct concealed-marker queries. Because the widget is a *new*, independently-styled element rather than the marker's own glyphs, its box is authored independently of any font metric: `.cm-marker--concealed` is now simply `display: inline-block; width: 0; height: 1em;` — two previously-irreconcilable declarations (a real, uncontested `width: 0` and a normal, non-degenerate `height`) that no longer compete, because there is no glyph run underneath either of them to reserve space for.

  **How the widget gets correct vertical metrics in every context (body, headings, nested content):** `height: 1em` is deliberately relative, not a pixel value, and `font-size` is left unset on the rule entirely — the widget inherits whatever `font-size` its actual rendering context provides (16px body text, or a heading's own larger `tok-heading1`-`tok-heading6` font-size when a marker is nested inside one), so `1em` scales correctly with zero per-context CSS. This does not need to equal the *line's* full `line-height` exactly: `drawSelection()` takes the min/max across every rect it queries on a line, so as long as this box's height is non-zero and roughly glyph-sized (not wildly larger, which would risk the same inflation the `line-height: 1` fix above exists to prevent), the line's neighboring real text already establishes the correct bounding rectangle. `display: inline-block` is required for `height` to apply at all — a plain `inline` element's box height is derived from its content and `line-height`, not a settable property, and this element deliberately has no content to derive one from (an empty `inline-block` left at `height: auto` collapses to `0` per CSS2.1 §10.6.7 — "no in-flow content" — which is exactly why `height: 1em` is load-bearing, not decorative).

  **How marker hit-testing works, and why this does not repeat the reason Clutter originally moved *away* from `Decoration.replace()` for this family** (`docs/markdown-dom-structure-agreement.md` §5.5/§7.1, `inlineLivePreviewParticipants.ts`'s own prior doc comment): that original concern was about a **bare** `Decoration.replace({})` — no widget, no DOM node at all, nothing to click. `ConcealedMarkerWidget` is a real, positioned, zero-width DOM element, not an absence — and `WidgetType`'s default `ignoreEvent()` returns `true`, meaning **by default a widget's events, including `mousedown`, never reach CM6's own click-to-position handling at all** (confirmed by reading `@codemirror/view` source directly — the same fact `WikiLinkWidget.ignoreEvent`'s own doc comment already established for a different reason). `ConcealedMarkerWidget.ignoreEvent()` overrides this to unconditionally return `false`, letting `mousedown` reach CM6's built-in handling. Verified directly, not assumed: a real click at the widget's own on-screen coordinate (in the real Clutter webapp, not just the sandbox) resolved to the correct document position and engaged the construct, every time tried, across five different construct kinds and multiple nesting depths.

  **`EditorView.atomicRanges` is not, and was not made, applicable to this family — confirmed directly, not merely carried over by assumption.** Unlike the genuinely-atomic widget family (`WikiLink`/`Tag`/`Date`, `widgetReplaceRenderer`), `delimitedInlineRenderer`'s `ParticipantDecoration` return value has no `atomic` field for the marker ranges — the same participant-owned-fact mechanism that already governed this before the migration (`inlineLivePreviewRegion.ts`'s `buildDecorations`) is unchanged, so there was no new call site that could have silently added atomicity. Regression coverage added (`inlineLivePreviewRegion.test.ts`, "every `ConcealedMarkerWidget`-backed participant never registers as atomic, at rest") and Backspace/Delete were independently re-verified against real CM6 commands and, separately, live in the real webapp (`Delete` at a concealed marker's own boundary removed exactly one character — `**bold**` → `*bold**` — not the whole marker).

  **Reconciles `docs/obsidian-vs-clutter-editor-audit.md`'s prior "do not migrate markers to widgets" recommendation (§1, §24(G))** — that pass's PROVEN source facts (`moveByChar` is decoration-blind; `WidgetTile.coordsIn` collapses interior widget positions to one of two edge rects) are unchanged and correct, but its *inference* from those facts to a predicted user-visible degradation was never checked against reveal-on-engagement, and does not hold once it is: **any** position inside a concealed construct's range satisfies `isTokenEngaged`'s containment check, which reveals the *entire* construct as real text on the very same render — so which collapsed sub-position a vertical-motion landing resolves to inside an about-to-be-revealed marker is not a user-observable outcome. ## WikiLink resolution, aliases, and display

- **Display-label precedence, corrected from the originally proposed ordering.** *Locked.* **Local alias > target's primary frontmatter alias > filename** — not "filename > target aliases" as first proposed. Putting filename above target aliases would mean a page's alias never actually changes how it displays anywhere unless every reference is hand-edited, defeating much of the point of having page-level aliases. This does **not** conflict with "editing frontmatter never rewrites references" — that guarantee is about the stored buffer; display is a pure, always-re-derived render, the same "derived data is disposable" pattern already governing every decoration in this architecture. See [semantic-resolution-model.md](./editor-research/clutter-editor-semantic-resolution-model.md).
- **Bare-reference display is live and dynamic, never written back.** *Locked.* Renaming a target's primary alias changes what every bare (no-local-alias) reference to it shows, with zero buffer mutation anywhere. A reference carrying an explicit local alias is completely unaffected, forever, unless a user edits it directly.
- **Alias-based resolution (`[[Alpha]]`) is supported as a fallback**, tried only after a literal path match fails. *Locked.* The Markdown is never auto-rewritten to the canonical path on resolution — resolution never causes a write, without exception.
- **Ambiguous alias/mention matches must produce an explicit ambiguous resolve state, never a silent pick.** *Locked.* Silently choosing a candidate risks opening or editing the wrong entity without the user realizing — a materially worse failure mode than an honest "please disambiguate."
- **Path normalization**: vault-relative, `/`-separated, no `.`/`..`, no extension, in Clutter's own canonical writer — but the parser remains tolerant of reading non-canonical-but-valid variants without ever rewriting them. *Locked.*
- **Autocomplete acceptance is insertion-only, never navigation.** *Locked.* Accepting a WikiLink completion — the `+ Create "X"` option, an existing-page option, via click, Enter, or the `|` alias-boundary key — only inserts (and, for `+ Create`, creates) the reference; it must never make the newly-referenced/created page the active view, and the editor keeps focus. The only thing that opens/navigates to a WikiLink is an explicit `activate()` on an already-rendered token (a genuine click on the token itself, or the keyboard adjacent-activation path) — never a side effect of the insertion mechanism that produced it.

## `@Today` / relative dates — reversal, capture explicitly

- **`@Today`/`@Tomorrow` are insertion-time shorthand only, never persistent syntax.** *Locked.* **This reverses an earlier working assumption**, carried through the shared-token-interaction-contract and semantic-resolution-model documents, that `@Today` was a fifth persistent token kind exactly like `WikiLink`/`Tag`/`Mention`/`@due`, with its own `DateToken` node. That assumption is superseded — accepting "Today" immediately writes the concrete literal date; nothing named `@Today` ever reaches the buffer. Reasoned from two angles that converged: (1) a persistent-but-frozen reading is architecturally impossible without hidden state, which is explicitly forbidden; (2) a persistent-and-dynamic reading fails both worked scenarios (a daily note's own `@Today` drifting off its dated identity; a recorded "launch date" silently changing every day). See [relative-date-semantics.md](./editor-research/clutter-editor-relative-date-semantics.md).
- **Consequence**: the `@`-family parser's disambiguation simplifies from three branches (Mention/DateToken/PropertyToken) to two (Mention/PropertyToken) — less parser complexity than previously planned, a direct benefit of the reversal, not a cost.
- **`@due:@Today` needs no recursion.** *Locked.* Nothing persistent exists to nest; malformed input is handled exactly like any other invalid property value.
- **A non-recursive path for a future relative due-date exists** (`@due:today` as a literal keyword inside `PropertyToken`'s own value grammar) but is **not decided to be built** — see Open items below.

## Live-preview rendering architecture (research, 2026-08-23) — Recommended, not locked

*Recommended, not locked.* Full research: [cm6-live-preview-rendering-architecture.md](./editor-research/cm6-live-preview-rendering-architecture.md).

- **Root cause of the previous breakage, confirmed forensically**: 100% a keyboard/command-layer problem (hand-rolled Arrow-key cursor hops, a drag-selection "atomic sweep" corrector, and Backspace/Enter/Tab keymaps racing `@codemirror/lang-markdown`'s own defaults at `Prec.high`), never a decoration/widget problem — the dormant `*Decoration.ts` files were audited and found to have no keymap/`atomicRanges`/`transactionFilter` coupling. Reframes the task: decorations are the low-risk part; hand-rolled commands are the part to avoid rebuilding.
- **Recommended split per construct**: `Decoration.mark()` for content that stays character-editable (bold/italic inner text, heading text), `Decoration.replace()` for marker concealment (`**`, `##`, `[[`/`]]`) and for the already-Locked semantic-token family at rest — not one uniform strategy.
- **`EditorView.atomicRanges` should stay scoped to the semantic-token family only** (WikiLink/Tag/Date/Task, already Locked) — never applied to ordinary Live-Preview-hidden marks — confirmed both by this repo's prior finding and by a real-world documented bug (`discuss.codemirror.net/t/hide-markdown-syntax/7602`) where broad `atomicRanges` use turned ordinary character deletion into whole-span jumps.
- **Engagement (reveal-on-cursor-enter) should stay selection-derived, computed fresh per decoration rebuild** — matches the already-Locked semantic-token model and independently confirmed by every real-world implementation surveyed (Obsidian's plugin ecosystem, `atomic-editor`, `codemirror-live-markdown`) — never stored engagement state.
- **`ViewPlugin`, not `transactionFilter`/`changeFilter`, is the correct home for this rendering** — confirmed at the CM6 API-contract level: neither filter has any path into the `EditorView.decorations` facet, and `transactionFilter` is explicitly documented as unsuitable for this ("likely to break something or degrade the user experience").
- **CM6's clipboard already copies underlying `state.doc` text by default, regardless of decorations** — no custom clipboard handling needed for ordinary copy/paste.
- **IME safety is not resolved by research alone** — CM6 has strong internal composition-safety machinery but no public contract covering concealed markers adjacent to an active composition range; flagged as needing direct manual testing (Hindi, Japanese, Korean, Chinese, dead keys) before shipping.
- **Tables are explicitly out of scope for the shared inline mechanism** and need their own design pass — the one construct every real-world implementation surveyed found genuinely hard.

- **Bold and Italic are one emphasis family, not two independent constructs.** They are implemented by a single `emphasisLivePreview()` `ViewPlugin` performing one `syntaxTree` traversal that visits both `Emphasis` and `StrongEmphasis` nodes — not two separately-mounted plugins. The earlier `boldLivePreview.ts`/`italicLivePreview.ts` vertical slices (and their test files) were retired in the same commit that introduced the merge.
- **Nested/combined emphasis is made atomic by traversal order, not by a shared range resolver.** `Emphasis`/`StrongEmphasis` always nest with the inner node as the outer's sole non-mark child and zero character gap between them. The traversal's `enter` callback returns `false` when the outer node is engaged, which stops `syntaxTree.iterate` from descending into the inner node at all — so the inner node is never independently visited or evaluated. No coordinator plugin, shared "combined region" computation, or cross-node state was needed for this; it falls out of visiting outer-before-inner and conditionally not descending.
- **`isTokenEngaged` (`semanticToken/tokenEngagement.ts`) was reused unchanged.** Only the range passed to it changed during earlier iteration of this slice (see the file's own doc comment for why full node-range containment, not inner-content-range, was the final choice) — the function itself needed no modification.
- **Implementation finding, specific to this slice — not a general CodeMirror rule:** a 4+-delimiter run (e.g. `****text****`) is valid CommonMark and parses as `StrongEmphasis` nested inside `StrongEmphasis`. Building the decoration set with `RangeSetBuilder` throws, because outer-before-inner tree visitation produces ranges out of the strictly-non-decreasing order `RangeSetBuilder.add` requires. `emphasisLivePreview.ts` instead collects ranges into an array and calls `Decoration.set(ranges, true)`, which sorts internally and tolerates the resulting overlap — the same pattern `liveMarkDecoration.ts` already used for its own nested-construct case. Treat this as evidence to check for when any *other* construct's decorations can nest same-kind (not as a rule that applies universally).
- **Known, deliberately deferred limitation, unchanged from the bold-only slice:** a document whose content is (or ends with) exactly one emphasis construct loads with the caret at `doc.length` (per `createEditorView.ts`'s seeding), which sits on the construct's boundary and is treated as engaged — so that construct stays permanently revealed on load until the user moves the caret. No rule that's a pure function of `(tree, selection)` can distinguish this from "just typed, stay revealed," which is the far more common case and the one the current behavior optimizes for. See `emphasisLivePreview.test.ts` for the pinned regression test documenting this as a known limitation, not silently untested.

**Heading content classing moved into the shared decoration source (2026-08-25) — correction to the entry below.** *Locked.* `headingHighlighting()`'s own safety claim — "headings have no equivalent competing content-mark source" — was **false**: it checked only `headingMarkerDecoration.ts` (a `Decoration.replace`, no conflict possible) and missed that heading content is ordinary inline content, fully able to contain any `inlineLivePreviewRegion` participant (Highlight, Emphasis, Strong, Strikethrough, Link, ...). Confirmed empirically (mounted `EditorView`, real DOM): `# ==Heading==` produced `<span class="tok-highlight"><span class="tok-heading1">Heading</span></span>` — two *independent* decoration sources (CM6's own `syntaxHighlighting()`/`TreeHighlighter` for `headingHighlighting()`, and `inlineLivePreviewRegion`'s shared `Decoration.set()` for Highlight) splitting/nesting by registration precedence rather than composing correctly, exactly the same failure class this document's own "Shared `DecorationSet` vs. independent CM6 extensions" section already named — just not recognized as applying to headings at the time. The same failure reproduced for `# **Bold** heading` (untested by `headingHighlighting.test.ts`'s existing duplicate-only assertion, which is why it went unnoticed).

**Fix**: `headingHighlighting()` is retired. Heading content classing (`tok-heading1`-`tok-heading6`) is now emitted directly inside `inlineLivePreviewRegion.ts`'s own `buildDecorations`, as a small unconditional branch feeding the *same* `ranges` array every participant already contributes to — not as a `participants` map entry. That distinction matters: the `participants` contract's engagement short-circuit (`isTokenEngaged` on the node's own range → stop descending, nothing inside decorates) is for reveal-on-engage marker-hiding constructs; heading content is never concealed, only the marker is (via `headingMarkerDecoration.ts`'s own independent, `'physical-line'`-scoped mechanism, left unchanged). Registering headings as ordinary participants was prototyped and rejected: it would make the entire heading — including any nested Highlight/Bold/Link — stop decorating and stop independently engaging whenever the cursor is anywhere on that line, which is nearly always while editing a heading. The unconditional branch always emits the class and always keeps descending, so nested participants engage exactly as before.

Range covers the full node (marker included, matching prior `TreeHighlighter` behavior exactly — including the pre-existing "revealed marker renders at heading size" artifact, deliberately not fixed in this pass) with `inclusiveStart`/`inclusiveEnd: true`, required for the exact-range-coincidence case (`# [[Page]]`, `# ==Heading==` alone) — same reasoning as every other wrapping participant in this file. Verified via a real mounted `EditorView` across ATX H1-H6, Setext H1/H2, and every participant kind (Highlight, Bold, Italic, Strikethrough, Link, WikiLink, and Bold-wrapping-WikiLink) nested inside a heading: single correctly-nested span per range, no duplicate wrapper, no sibling-split, nested constructs' own reveal-on-engage behavior fully independent of heading state, marker reveal parity unchanged. `headingMarkerDecoration.ts` and `liveMarkDecoration.ts` were not touched. See `headingContentClassing.test.ts` (replaces the retired `headingHighlighting.test.ts`).

**`headingHighlighting()` added and wired (2026-08-25) — a new, narrower export, not the full `markdownHighlighting()`. Superseded by the correction above — kept for historical context, not current behavior.** Headings now render at their `tok-heading1`-`tok-heading6` font-size/weight in the live app, reusing the exact same tag→class pairs `markdownHighlightStyle.ts` already defined (no new CSS, no new classes — the array of heading tag/class pairs is now a single shared constant both `markdownHighlightStyle` and `headingHighlighting()` consume). **Why not just enable the pre-existing, still-commented-out `markdownHighlighting()`**: confirmed empirically, via a mounted `EditorView`, that doing so produces real DOM duplication for Emphasis/StrongEmphasis/Strikethrough/InlineCode at rest — `inlineLivePreviewParticipants.ts`'s `delimitedInlineRenderer` already wraps each of those constructs' at-rest content in its own same-named `Decoration.mark` (`tok-strong`, etc.), independently of this file; `markdownHighlighting()`'s own `tags.strong`→`tok-strong` rule (etc.) targets the identical range from a second, independent decoration source, and CM6 nests same-range marks from two different extensions rather than merging them (per the "Shared DecorationSet vs independent CM6 extensions" section above) — confirmed as `<span class="tok-strong"><span class="tok-strong">Bold</span></span>` in `view.dom.innerHTML`. ## Duplicate decoration ownership cleanup — Locked (2026-08-25)

Follow-up to the heading composition fix above, prompted by a full source-level audit of every Markdown construct's decoration ownership (requirement: no two independent decoration sources may own the same semantic range with competing `Decoration.mark`s; legitimate nested/different ranges still compose via ordinary CM6 nesting — this was never about flattening `heading → strike → highlight`-style legitimate nesting). The audit found the heading fix closed one *active* collision, not the underlying bug class: several dormant files still carried the same risk, reachable the moment they were wired.

**`markdownHighlighting()`/`markdownHighlightStyle` retired outright (deleted, not left dormant).** Every tag it mapped collided with an already-wired dedicated decoration owner: `heading1`-`6` (the exact bug just fixed for headings — the earlier fix only retired the narrower `headingHighlighting()` export, not the heading tags still spread into the full style via `headingStyleSpecs`), `emphasis`/`strong`/`strikethrough`/`monospace` (already documented), and — previously unnamed — `highlightContentTag` (`Highlight`'s content, attached at parse time by `highlightSyntax.ts`'s own `defineNodes`, mapped to `tok-highlight` here, colliding with `delimitedInlineRenderer('HighlightMark','tok-highlight')` in the already-wired shared set). With every entry independently known to collide, there was no safe remaining ownership to prune down to — retiring the whole file was the smaller, more honest fix than leaving a style definition whose only remaining rule (`tags.processingInstruction`→`tok-mark`) has never been verified safe against the heading/blockquote-marker boundary-coincidence case either. `highlightContentTag`'s `defineNodes` attachment in `highlightSyntax.ts` itself was left in place (now-inert parser metadata, harmless unconsumed, out of scope for this narrowly-scoped cleanup) — a candidate for a later, separate simplification, not a live risk.

**`emphasisMarkerDecoration.ts`/`strikethroughMarkerDecoration.ts` retired outright (deleted, not left dormant).** Their sole job — marker concealment for `Emphasis`/`StrongEmphasis`/`Strikethrough` — is fully subsumed by `inlineLivePreviewRegion`'s shared set (`delimitedInlineRenderer` already emits both the marker-concealing `Decoration.replace` and the content `Decoration.mark` from the one source). Enabling either dormant file alongside the already-wired shared mechanism would have been a redundant `Decoration.replace`-vs-`Decoration.replace` duplicate owner over the identical marker range — harmless in isolation (both just hide the same text) but a genuine double-owner, and an easy trap for a future contributor who reads the dormant file's own doc comment (which describes it as *the* marker-hiding mechanism for that construct, no longer true) and re-enables it thinking it's needed. No coverage was lost: `inlineLivePreviewRegion.test.ts` already independently covers the identical marker-reveal-on-engagement behavior for Emphasis/StrongEmphasis/Strikethrough (it already superseded the equivalent `emphasisLivePreview.test.ts`/`strikethroughLivePreview.test.ts` once before, per the file's own header comment). `liveMarkSelectionSnap.test.ts` — which used `emphasisMarkerDecoration()` as one of two vehicles to exercise the still-real, still-needed `liveMarkSelectionSnap.ts` mechanism — was rewritten to exercise it via heading alone; `liveMarkDecoration.ts`/`liveMarkSelectionSnap.ts` themselves are unchanged and still genuinely needed (heading, and dormant blockquote/list).

**Lists (`listMarkerDecoration.ts`'s plain bullet/ordered `ListMark`) — ownership question resolved as a side effect, no code change needed.** The audit's own finding was `ListMark`'s `Decoration.mark` (`cm-list-marker ...`) colliding with `markdownHighlighting()`'s `tags.processingInstruction`→`tok-mark` (also a `Decoration.mark`, not `replace`, over the identical range — the unsafe mark-vs-mark pattern, unlike every other dormant marker file which uses `replace`). With `markdownHighlighting()` retired, this collision no longer exists — confirmed by construction, not by re-testing an extension that no longer exists to collide. `listMarkerDecoration.ts` itself is unchanged and remains dormant; Lists are still not wired.

**Tables (`tableDecoration.ts`'s `TableCell`) — fixed, still not wired.** `TableCell`'s `Decoration.mark` (`cm-table-cell ...`) is an independent source from `inlineLivePreviewRegion`'s shared set and from `wikiLinkLivePreview` (`Prec.high`). Confirmed empirically, before any fix, mounting `tableDecoration()` + `inlineLivePreviewRegion()` + `wikiLinkLivePreview()` together: `| **Bold** |` produced `<span class="tok-strong"><span class="cm-table-cell">Bold</span></span>` (inverted nesting — `cm-table-cell` lost its own outer wrapper) and `| [[Page]] |` dropped `cm-table-cell` entirely. Fix: `inclusiveStart`/`inclusiveEnd: true` on the `TableCell` mark (same reasoning as every other wrapping participant), plus wrapping the whole `tableDecoration()` extension in `Prec.lowest` — confirmed empirically which precedence direction is actually correct, since it's the *reverse* of the intuitive reading: CM6 nests the *lower*-precedence source as the outer wrapper and the *higher*-precedence source inner (this is exactly why `**[[Page]]**` already nests as `tok-strong > tok-wikilink`: `inlineLivePreviewRegion`, default precedence, is outer; `wikiLinkLivePreview`, `Prec.high`, is inner). `Prec.lowest` (not merely omitting `Prec`) so `TableCell` reliably stays outer regardless of registration order relative to both `inlineLivePreviewRegion` and `wikiLinkLivePreview`, matching the same self-contained-precedence reasoning `wikiLinkLivePreview.ts` already documents for itself. Verified via a real mounted `EditorView` for `| **Bold** |`, `| ==highlight== |`, and `| [[Page]] |` (all three exact-range-coincidence cases named in the audit) plus the full pre-existing `tableDecoration.test.ts` suite (26 tests, all still passing). New containment regression tests added under `tableDecoration.test.ts`'s "cm-table-cell correctly wraps a nested construct" describe block. `tableDecoration()` itself remains commented out in `MarkdownEditor.tsx` — this fixes its decoration definition ahead of ever being wired, it does not wire it.

**Net result — every active semantic range has exactly one decoration owner.** No same-range duplicate-mark collision is reachable in the currently-wired editor. The eliminated dormant sources (`markdownHighlighting()`, `emphasisMarkerDecoration`, `strikethroughMarkerDecoration`) can no longer be accidentally re-wired to reintroduce one, since they no longer exist. The remaining still-dormant constructs (`listMarkerDecoration`/`listLineDecoration`/`listIndentWhitespaceDecoration`, `blockquoteMarkerDecoration`, `tableDecoration`) were individually re-audited against this requirement — List's only identified risk was resolved by `markdownHighlighting()`'s removal; Table's `TableCell` risk was fixed directly; Blockquote has no content-classing mechanism of its own to collide with anything (only its own `QuoteMark`, replace-vs-mark against `tok-mark`, already safe by the same reasoning as heading's own marker).

**No order for re-enabling the rest is currently decided.** The emphasis family was the first slice re-enabled; nothing in this repository commits to which construct comes next, or to re-enabling them in any particular sequence at all. Do not assume WikiLink/Tag/Date/Task/List/Blockquote/Table decorations are live in the running app on the strength of their source code existing, and do not infer a forward implementation order from the fact that emphasis went first — that fact records what happened, not a plan for what happens next. See `docs/editor-feature-matrix.md` for the per-feature current-wiring status.

## Standalone-renderer extraction — lessons from the WikiLink split — Locked (2026-08-25)

WikiLink's engaged-state UX (compact alias/filename at rest; raw `[[`/filename/`|alias`/`]]` when engaged, folder prefix always concealed) does not fit `inlineLivePreviewRegion.ts`'s shared reveal-on-engage contract, so it was pulled out into its own standalone extension, [`wikiLinkLivePreview.ts`](../apps/app/src/features/markdown/editor/codemirror/wikilink/wikiLinkLivePreview.ts). Two real regressions surfaced during that extraction, both found by real-DOM investigation after the split shipped, neither anticipated in advance. This section generalizes both as reusable rules for **any future construct that needs standalone rendering outside the shared mechanism** — not a WikiLink-specific bug note.

### Shared `DecorationSet` vs. independent CM6 extensions

- **Decorations produced in one shared `Decoration.set()` compose differently from decorations produced by independent facet/`ViewPlugin` contributions, even with identical ranges.** Range containment alone does not determine DOM nesting — this is not an implementation detail, it's a documented CM6 contract: `Decoration.mark`'s own doc comment (`@codemirror/view`) states nesting order is "determined by precedence of the facet," and elements are "split on... the boundaries of lower-precedence decorations." A mark whose content range exactly coincides with a *lower-precedence* widget's range gets split at that widget's boundary and never wraps it — confirmed empirically: swapping only extension registration order (nothing else) turned a bare `<span class="tok-wikilink">` sibling into the correct `tok-strong > tok-wikilink` nesting.
- **`inclusiveStart`/`inclusiveEnd` and decoration precedence are two separate mechanisms, not one.** The inclusivity flags govern whether a mark's boundary extends to absorb a decoration sitting exactly at that boundary; precedence governs whether the mark survives *unsplit* across a decoration from another source in the first place. Inside the shared traversal (one decoration source, no precedence conflict), the flags alone were sufficient. The moment the widget moved to an independently-registered extension, the flags stayed correct and unchanged — the fix that was actually needed was precedence, not inclusivity. Treat these as independently-verifiable facts about any given composition, never assume one implies the other holds.
- **Default extension precedence is registration order (earlier = higher).** An extraction that must nest inside/around an existing extension should not depend on where `MarkdownEditor.tsx` happens to list it — wrap the extraction itself in `Prec.high`/`Prec.low` so correctness is self-contained in the extension, not an artifact of call-site ordering someone could innocently reorder later.
- **Any future extraction of a renderer into an independent extension must include a real mounted-`EditorView` DOM composition check** (`view.dom.innerHTML` / `.closest()` assertions against the expected nested classes) before being declared correct. A decoration-shape or `Range` unit test cannot see this failure mode — the emitted ranges are byte-identical between the working and broken versions; only the CM6-composed DOM differs.

### Independent engagement semantics

- **Moving a construct outside `inlineLivePreviewRegion` means it no longer automatically participates in the shared engagement decision.** Inside the shared traversal, "region root" (the widest engaged ancestor-or-self) falls out for free from top-down short-circuit: an engaged ancestor's `enter` callback returns `false` before `syntaxTree.iterate` ever descends into a nested participant, so that participant's own engagement is never independently asked while its ancestor is engaged. A standalone extension has no such short-circuit handed to it — it must compute the equivalent boundary itself, deliberately, or it silently reverts to "my own node range only," which is a strictly narrower (and wrong) definition.
- **A child syntax node's range is narrower than its enclosing live-preview region**, by exactly the width of the enclosing construct's own delimiters (e.g. WikiLink's range starts two characters after its enclosing StrongEmphasis's own `**`). This is the ordinary shape of *every* nested construct, not an edge case — it produces a real, reachable caret-position gap (confirmed via a full-position DOM sweep, not a timing/flicker artifact) wherever two independently-computed engagement checks disagree about a position strictly between the two node boundaries.
- **Future standalone renderers must explicitly verify cursor positions at every child boundary, and at "inside enclosing construct but outside child" positions specifically** — not just "cursor inside the child" and "cursor outside everything," which is the pair of cases that looks complete but misses exactly the gap that caused this regression.
- **Widening the engagement boundary must stay generic, never construct-paired.** The correct shape walks the ancestor chain structurally, checking each ancestor's own `firstChild`/`lastChild` for the "two identically-named delimiter children" shape every `delimitedInlineRenderer` participant already shares (`wikiLinkLivePreview.ts`'s `widenToEnclosingLivePreviewRegion`) — never a check that names StrongEmphasis/Strikethrough/etc. by identity. This composes automatically with any current or future delimited construct, with zero new knowledge added to the standalone renderer about what that construct is.

### WikiLink-specific rationale (why the extraction, not a precedent for others)

- WikiLink was extracted because its engaged-state contract is **intentionally different** from the shared marker-hiding contract, not because standalone extensions are generally preferred. At rest: a compact widget (alias, or filename — never the folder-qualified path). Engaged: raw WikiLink syntax (`[[`, filename, optional `|alias`, `]]`) with **only** the folder-prefix concealed — neither the shared contract's "engaged region → fully raw source" nor a second engaged-state hook bolted onto the shared `ParticipantRenderer` contract (explicitly rejected during Phase 3 review of `inlineLivePreviewRegion.ts`).
- **This does not reopen or generalize the shared traversal.** Tag and Date keep the ordinary reveal-on-engage contract unchanged and stay inside `inlineLivePreviewRegion.ts`/`inlineLivePreviewParticipants.ts` for exactly that reason — they still implement the shared contract WikiLink no longer does. A construct extracted for its own genuinely different contract is the narrow exception this section documents, not a precedent for preemptively moving other participants out.

### Standalone-renderer verification checklist

Before declaring any standalone (outside `inlineLivePreviewRegion.ts`) inline-construct renderer correct, verify each item against a real mounted `EditorView` with real dispatched transactions — not unit-level assumptions about decoration shape:

1. **Decoration precedence** — is the extension's precedence (explicit `Prec.high`/`Prec.low`, self-contained in the extension) correct relative to every other extension it must nest inside or around?
2. **DOM nesting** — `view.dom.innerHTML` / `.closest()` checks that the actual composed DOM nests as required, for every enclosing construct and at least one 2+-level nested combination.
3. **Inclusive boundaries** — where a mark from another source must visually wrap this renderer's decoration, confirm `inclusiveStart`/`inclusiveEnd` are set — verified separately from precedence, since one never substitutes for the other.
4. **Nested Markdown** — the renderer's output composes correctly under every enclosing construct it can realistically appear inside, not just the single-level case.
5. **Cursor at construct boundaries** — both boundaries of the renderer's own node, and both boundaries of every enclosing construct it can appear inside.
6. **Cursor inside child** — the renderer's own node's interior.
7. **Cursor inside enclosing construct but outside child** — the specific gap this document exists to name: a real, reachable caret position within an ancestor's range but outside the renderer's own node's range.
8. **Exit behavior** — moving the caret back out returns to the exact at-rest state, with no intermediate/stuck state.
9. **Atomic ranges** — correct at rest, correctly absent while engaged, and — if the renderer computes its own widened engagement boundary — absent across the *entire* widened range, not just the renderer's own node.
10. **Selection** — drag/programmatic selections spanning the construct behave as intended, with no reliance on any removed cursor-interception mechanism (see "CodeMirror owns cursor and selection behavior," above).
11. **Autocomplete** (or any other raw-text-driven mechanism) — confirm it still operates against `EditorState`'s raw document text, unaffected by the renderer's decorations, for both a fresh/in-progress construct and an already-closed one.
12. **Document immutability** — the stored document text never changes as the construct's rendering state changes, across every state transition exercised above.

### Regressions actually encountered

Recorded as the concrete evidence behind the checklist above.

- **Cross-source mark/widget composition regression.** *Symptom*: `**[[Page]]**` rendered the WikiLink widget as a bare DOM sibling with no `tok-strong` wrapper — `inclusiveStart`/`inclusiveEnd` unchanged and still correctly set. *Root cause*: the mark and the widget moved from one shared `Decoration.set()` to two independently-registered extensions; the mark's default (registration-order) precedence was lower than the widget's, so CM6 split the mark at the widget's boundary instead of wrapping it. *Fix*: `Prec.high` wrapping the standalone extension's own returned `Extension`, verified against a test helper that deliberately matches production's registration order (not the test's own, possibly-accidentally-favorable order) — proven necessary by reverting it and observing 8 nesting assertions fail.
- **Independent-engagement boundary-gap regression.** *Symptom*: with the cursor positioned inside the enclosing `**` but not yet inside the WikiLink's own node, `**[[Display text]]**` showed `**Display text**` — an impossible third state, neither at rest nor fully engaged. *Root cause*: the standalone renderer's engagement check used the WikiLink node's own (narrower) range, independently of the enclosing StrongEmphasis's separately-computed engagement — the two-character gap described in "Independent engagement semantics," above. *Fix*: `widenToEnclosingLivePreviewRegion`'s generic ancestor walk, proven necessary by reverting it and observing a full caret-position DOM sweep fail at exactly the predicted gap positions (also surfaced a second latent test bug: the sweep's own "at rest" baseline was itself silently sitting on the pre-existing default-`(0,0)`-selection edge case documented earlier in this file, producing a false pass until corrected).

### A live, already-shipped side effect discovered while investigating `Link` (not yet fixed)

`widenToEnclosingLivePreviewRegion`'s ancestor check (`isDelimitedMarkConstruct`: "two identically-named children whose name ends in `Mark`") assumed each delimited-inline participant has its own **uniquely**-named mark type (`EmphasisMark`/`StrikethroughMark`/`HighlightMark`/`CodeMark` — true for all five current shared participants). `@lezer/markdown`'s `Link`, `Image`, and `Autolink` violate that assumption: all three share one generic `LinkMark` node name for their opening/closing marks, and `Link`'s own first/last child both happen to be named `LinkMark` — satisfying the check even though `Link` is not a registered shared-mechanism participant at all. **Confirmed live today, independent of any `Link` renderer existing yet**: mounting `wikiLinkLivePreview.ts` alone against `[See [[Page]]](https://example.com)` and placing the caret at the `Link`'s own opening `[` (nowhere near the WikiLink) already incorrectly reveals the nested WikiLink's raw `[[Page]]`. Recorded here as a known, named gap in the "generic, no construct names" rule above — the rule needs "and this ancestor is actually a registered delimited-inline participant," not just "structurally resembles one," to be fully correct. Not yet fixed; will become far more commonly triggered once `Link` rendering exists (`[text [[Page]]](url)` is an ordinary, encouraged pattern), so it should be addressed alongside or immediately after `Link` ships, not left as a silent surprise.

## Shared live-preview participant contract — confirmed via `Link` (2026-08-25)

Investigated (read-only) and then implemented: `[Display name](https://example.com)` joining `inlineLivePreviewParticipants.ts` as an ordinary shared participant — the deliberately opposite case from WikiLink's extraction, and useful precisely because it confirms the shared mechanism's contract still holds without modification. Implementation: [`linkLivePreview.ts`](../apps/app/src/features/markdown/editor/codemirror/link/linkLivePreview.ts) (or wherever the renderer function lives inside `inlineLivePreviewParticipants.ts` — see that file for the actual registration).

### CM6/Lezer facts this rests on — confirmed empirically, not assumed

- **`@lezer/markdown` provides the parse tree; CM6 itself renders nothing for Markdown links on its own.** `Link`, `Autolink`, and bare `URL` are native Lezer node types (`@lezer/markdown`'s `Type` enum), always present in the parse regardless of Clutter's own grammar extensions — but `@codemirror/lang-markdown`/`@codemirror/view` supply zero decoration, widget, or styling for any of them out of the box. Rendering is entirely the consuming application's responsibility, same as every other construct already in this codebase.
- **`ParticipantRenderer`/`inlineLivePreviewRegion.ts` support `Link` with no contract or traversal change, because the renderer receives the complete `SyntaxNode`.** The shared traversal's only obligation to a participant is `participants.get(node.name)` → call it with the full node; nothing about the traversal or the `ParticipantDecoration`/`ParticipantRenderer` types assumes a particular internal child shape. That assumption lived entirely inside `delimitedInlineRenderer`'s own implementation (a 2-same-named-child precondition), never in the shared contract itself — confirmed by writing `Link`'s renderer as a new, `Link`-specific function that walks its own known shape (first two `LinkMark` children specifically, not `firstChild`/`lastChild`) and registering it exactly like any other map entry.
- **`Decoration.mark` is correct for the label, `Decoration.replace` is correct for the concealed syntax — and `Link` must not be atomic.** The label stays ordinary, character-editable text (a `Decoration.mark` classing it, not replacing it) because `Link`'s contract is "hide Markdown syntax while keeping the user-visible label editable" — this is the same, already-Locked distinction as "plain Markdown links remain ordinary Live Preview marks, not semantic tokens." `Decoration.replace({})` conceals the opening `[` and, as one combined range, everything from the label-closing `]` through the node's end (`](url "title")`, regardless of internal shape — `URL`/`LinkTitle` are swallowed together, never independently rendered). No `atomic` field is returned from `Link`'s renderer, and no `EditorView.atomicRanges` contribution exists for it — confirmed by a negative test. This is the clearest structural difference from WikiLink/Tag/Date, which are atomic at rest by contract; `Link` never is, in any state.
- **Because `Link` stays inside the shared `Decoration.set()`, it does not have WikiLink's independent-extension precedence problem.** `Link`'s content-mark decoration is produced by the same `inlineLivePreviewRegion` traversal, in the same array, as StrongEmphasis/Strikethrough/etc.'s own decorations — there is no second facet/`ViewPlugin` contribution to conflict with, so the precedence-driven mark-splitting failure mode documented above for WikiLink (independent sources, lower-precedence mark split at a higher-precedence widget's boundary) is structurally inapplicable here. This was the central reason to keep `Link` shared rather than extracting it, not merely a convenience.
- **`inclusiveStart`/`inclusiveEnd` on the label's content mark, justified and tested specifically for the nested-widget case.** A WikiLink can legally appear inside a `Link` label (`[See [[Page]]](url)`, confirmed by direct parse) and must visually inherit the label's styling exactly as it already does inside StrongEmphasis/Strikethrough/etc. — same mechanism, same flags, same reasoning as the original WikiLink-inheritance fix, verified again here via a real mounted-DOM nesting check rather than assumed to transfer from the emphasis case.
- **The general CM6 lesson from the WikiLink split, reconfirmed by contrast**: independent decoration sources (separate facet/`ViewPlugin` contributions) can split each other's marks depending on facet precedence — nesting is not guaranteed by range containment alone. Decorations produced by the *same* shared `DecorationSet` never have that cross-extension precedence conflict in the first place, because there's only one source to order. `Link` staying shared is the positive-control confirmation of the rule the WikiLink regressions established.
- **Verified empirically with a real mounted `EditorView`, not source-level reasoning alone**: at-rest concealment (label only visible), engaged reveal (full raw source, from any caret position inside the node — label or URL portion, no distinction needed), exit re-collapse, nested-formatting composition, WikiLink-in-label composition, `Link`-inside-StrongEmphasis DOM nesting, `atomicRanges` absence, and document-text immutability across every transition — all checked against actual `view.dom`/`view.state`, matching the standalone-renderer checklist's own instruction to prefer mounted-DOM evidence over decoration-shape assumptions, even though `Link` is a shared (not standalone) participant.
- **Selection/caret behavior is left entirely to CM6.** No `Link`-specific keymap, no cursor repositioning, no custom selection handling — engagement is purely the existing, unmodified `isTokenEngaged` containment check against `Link`'s own node range, exactly as every other shared participant already works.

### The architectural boundary this confirms

**A construct is a *shared* `inlineLivePreviewRegion` participant when its contract is "hide Markdown syntax while keeping the user-visible content editable, and reveal everything when engaged" — the ordinary reveal-on-engage contract every marker-hiding participant (Emphasis/Strong/Strikethrough/Highlight/InlineCode) already implements, and `Link` now joins.** A construct is *standalone* only when its contract is genuinely different from that — WikiLink's reason for extraction was specifically that it must conceal part of its canonical content (the folder path) even *while engaged*, which the shared "engaged region → fully raw source" contract cannot express at all. `Link` has no such requirement — engaging it correctly reveals everything, with nothing permanently hidden — so it belongs in the shared mechanism by the same test that put WikiLink outside it. This is the concrete, reusable form of "is this construct's contract the same as the shared one, or genuinely different" for deciding where the *next* Markdown construct's renderer belongs — check the contract before checking whether the existing helper functions happen to fit its grammar shape.

Bare `URL`/`Autolink`/`www.` rendering remains a separate, unresolved product/architecture decision (§ above) — nothing in this section decides it, implicitly or otherwise.

## `syncMarkdownIntoView` excluded from CM6 undo history (2026-08-27)

**Bug (confirmed, not theoretical):** `syncMarkdownIntoView` (`createEditorView.ts`) — dispatched by `MarkdownEditor.tsx`'s own effect whenever the `markdown` prop changes while the CM6 view is unfocused — was a plain, undo-eligible transaction. Its real callers are external, same-page mutations that don't go through this editor's own `onDocChange` at all: `PageOperations.mutateBody()` (task-checkbox toggles from a different UI surface, template insertion, any future bulk/AI-assisted edit per its own doc comment) commits directly into the page's open `DocumentSession`, which round-trips back into `MarkdownEditor` as a changed `markdown` prop. If the editor is unfocused when that happens, `syncMarkdownIntoView` applies the change to keep the document in sync — correctly — but until this fix, that transaction was indistinguishable from a real user edit to CM6's `history()` extension.

**Reproduced directly against CM6's own `undo`/`redo`/`undoDepth` commands** (`createEditorView.test.ts`'s new `syncMarkdownIntoView — external syncs must not corrupt undo history` suite) — no UI or real browser needed, since this is a CM6 history-mechanics question, not a rendering one; `createEditorView()`/`syncMarkdownIntoView()` used unmodified, real production code, not a reimplementation. Two distinct, independently-confirmed failure modes:
- **Unannotated (the pre-fix state):** dispatching an external sync immediately after one real user edit did not create a *second* undo-able step — CM6's default history grouping silently merged it into the *same* group as the preceding user edit (`undoDepth` stayed at `1`, not `2`). A single subsequent `undo()` reverted the user's own edit *and* the unrelated external change together, in one step the user never asked for.
- **`Transaction.addToHistory.of(false)` alone, keeping the previous full-document-replace change shape** (`{from: 0, to: currentDoc.length, insert: markdown}`): excluding a transaction from history does not exempt it from history's change-*mapping* — a still-open undo entry from *before* it has its recorded positions mapped through it regardless. A full-document replace maps every prior position through "the entire document was deleted and something new inserted," which degenerates the mapped entry into an empty/meaningless change: `undoDepth` dropped to `0` immediately after the sync, permanently losing the user's own unsaved edit from undo, with no way to recover it.

**Fix — two changes together, each addressing one of the two failure modes above, not applied as an unexamined pair:**
1. `Transaction.addToHistory.of(false)` on the dispatch, alongside the pre-existing `externalSync` annotation (which serves a completely different, unrelated purpose — telling the update listener not to re-fire `onDocChange` for this transaction, preventing a feedback loop; a transaction can need either annotation, or — as here — both, for independent reasons).
2. The change shape itself switched from a full-document replace to a minimal common-prefix/common-suffix diff (`minimalReplaceChange`) — deliberately not a general (multi-hunk) diff algorithm, since every real caller of this function makes one small, localized edit to an otherwise-unchanged document (a task-checkbox toggle is the concrete case), which a prefix/suffix diff finds exactly and cheaply. This is what lets CM6's `ChangeSet.map` carry a prior, unrelated user edit's positions through the sync intact, confirmed directly: `undoDepth` stays at `1` through the sync, `undo()` reverts only the user's own edit (leaving the externally-synced content in place), and `redo()` correctly restores it afterward. Repeated localized syncs (several task toggles in a row) do not accumulate separate history entries either, confirmed the same way.

**History is per-note by construction, already, unrelated to this fix — verified, not inferred.** `PageHost.tsx` renders `<MarkdownEditor key={activePageId} ...>` — React's `key` forces a full unmount/remount of `MarkdownEditor` (and therefore a `view.destroy()` + brand-new `createEditorView()` call, per that component's own mount-effect cleanup) on every page switch. `syncMarkdownIntoView` can only ever run against the currently-mounted view for the currently-active page — there is no code path where it (or anything else) could carry one note's CM6 `historyField` state into a different note's `EditorState`, since each note's `EditorState` (and the `history()` extension's data living inside it) is destroyed and freshly recreated on every switch. This fix does not change that property — it was already true before it, confirmed by testing the pre-fix `syncMarkdownIntoView` the same way — and does not introduce any note-switching-specific isolation logic, because none was needed. Verified live in the real Clutter webapp (browser pane) as well as in the source-level test: edit note A, switch to note B (note A's edit persisted correctly in the sidebar), edit note B, switch back to note A (note A showed exactly its own prior content, not note B's and not empty), edit note A again, undo (reverted only the post-switch edit, landing on the pre-switch content), redo (restored it) — all correct.

**Explicitly not investigated further, out of scope for this fix:** a separate, still-unexplained anomaly where `Cmd+Shift+Z` (redo) after a `Cmd+A`-select-all-then-retype-then-`Cmd+Z` sequence produced an empty document in this session's browser-pane testing — confirmed *not* caused by `syncMarkdownIntoView` (the view never lost focus during that reproduction, so the sync path this fix addresses was never invoked) and confirmed still present after this fix (retested live, same result). Not chased further per explicit instruction; flagged here only so a future investigation doesn't assume this fix was expected to resolve it.

**Files changed:** `createEditorView.ts` (`minimalReplaceChange`, `syncMarkdownIntoView`'s annotations); `createEditorView.test.ts` (new `syncMarkdownIntoView` suite — 8 tests: user edit enters history/undo/redo; sync alone never undo-able; undo-after-sync reverts the user's edit not the sync; redo-after-that-undo; repeated syncs don't accumulate; a normal edit after a sync still enters history; a no-op sync (matching content) dispatches nothing; note-switching isolation). No other files touched — concealment decorations, engagement/reveal logic, Markdown parsing, and selection behavior are all unrelated to this fix and were not modified.

## Per-document CM6 undo/redo history preservation (2026-08-27, later same day)

**What was true before this entry, confirmed by source reading, not assumption:** `PageHost.tsx` renders `<MarkdownEditor key={activePageId} ...>`. React's `key` forces a full unmount/remount on every page switch, which runs `MarkdownEditor`'s own mount-effect cleanup (`view.destroy()`) followed by a fresh `createEditorView()` call for the new page — a brand-new `EditorState`, and therefore a brand-new (empty) `history()` `StateField`, every single time. This is *why* undo/redo "disappears" on a page switch — not a bug in the previous entry's fix, not history being incorrectly cleared, just nothing anywhere preserving the `EditorState` (and the `historyField` data living inside it) across the destroy.

**CM6's own, official mechanism for exactly this, verified end-to-end before writing any production code (a throwaway jsdom test against the real installed `@codemirror/state`/`commands`/`view`, deleted after use):** `historyField`'s own doc comment (`@codemirror/commands`) states it should be used "when you want to serialize or deserialize state objects in a way that preserves history." `EditorState.toJSON({history: historyField})` / `EditorState.fromJSON(json, config, {history: historyField})` round-tripped a document's full undo/redo stack (and its selection — already core `EditorState`, included automatically) with zero cross-document leakage between two unrelated documents' snapshots, confirmed directly by asserting on `undoDepth`/`undo()`'s actual resulting document text, not just that serialization succeeded.

**Implementation — the smallest change consistent with the existing architecture, per explicit instruction: keep the existing one-`EditorView`-per-mount, remount-per-`key` model; no persistent-view/`EditorView.setState()` architecture (a documented, viable alternative — CM6's own doc comment: "use it when the new state isn't derived from the old state" — but a larger, separate change not made here).**
- `editorHistoryCache.ts` (new): a plain `pageId -> unknown` (serialized `EditorState`) `Map`, module-level, in-memory/session-lifetime only — not a persistence mechanism, `durability-model.md`'s stages are untouched. Deliberately no eviction/LRU: a stale entry for a page that's gone is inert (nothing will ever look it up by that id again), and wiring `PageOperations.delete()` to invalidate it would need this feature-layer module reachable from `core/application`, the wrong dependency direction for this codebase — noted as a known, accepted limitation, not solved here.
- `createEditorView.ts`: new `restoreHistoryJSON?: unknown` option. When supplied, `EditorState.fromJSON` is used instead of `EditorState.create` — **but only if the snapshot's own embedded document text still matches the `doc` being opened with** (`docTextMatches`); otherwise silently falls back to a fresh state, exactly like any ordinary cache miss. New `serializeEditorHistory(view)` export — the write side, `view.state.toJSON({history: historyField})`.
- `MarkdownEditor.tsx`: the mount effect now passes `restoreHistoryJSON: getCachedEditorHistory(pageId)` into `createEditorView`; the unmount cleanup calls `setCachedEditorHistory(pageId, serializeEditorHistory(view))` immediately before `view.destroy()`. `MarkdownEditorProps` gained a required `pageId: string`, read explicitly from `PageHost.tsx`'s own `activePageId` (the same value already used for React's `key`) at both call sites — deliberately not inferred from the `key` prop itself (a private React implementation detail) or from `markdown` content (not a stable identity — two pages can share text, and a page's own text changes on every edit).

**How external-sync-vs-restored-session safety is guaranteed — the `docTextMatches` check above is the entire mechanism, not a separate one.** The risk named before implementing: a page's persisted content can legitimately change while it's closed (`PageOperations.mutateBody()` — a task toggle from a different UI surface, acting on a page whose `DocumentSession` stays open even though its editor isn't mounted). If that happens, the cached snapshot's embedded document (from when the page was last open) no longer matches the fresh `markdown` prop on reopen. `docTextMatches` catches this by construction: a mismatched snapshot is never handed to `EditorState.fromJSON` at all, so there is no path where a restored (stale) document could be silently shown, and no path where a subsequent `syncMarkdownIntoView` correction (unfocused-prop-sync effect) could run against an already-restored-but-now-wrong history and corrupt it — the mismatch is caught *before* any restoration is attempted, not patched up after. Confirmed directly (test F below): a mismatched cache entry produces exactly the same outcome as no cache entry at all — current, correct content, clean empty history.

**Regression coverage** (`createEditorView.test.ts`'s new "Per-document undo/redo history preservation" suite, 6 tests, scenarios A–F as specified): history survives a page switch and only the leaving page's own edit undoes on return (A); histories are independent in both directions (B); multiple undo/redo steps survive a round trip through another page, using explicit `Transaction.time` annotations to force separate history groups since same-tick test dispatches otherwise merge under CM6's default `newGroupDelay` (C); a page with no cached entry starts clean (D); selection/caret is restored alongside history (E); a cache entry whose document no longer matches the incoming prop is never used (F, the external-sync-safety case above).

**A real bug this test suite itself caught, before it ever reached the app — worth recording as a specific, cautionary data point, not just "tests passed":** the first version of `docTextMatches` assumed `EditorState.toJSON()`'s `doc` field was an array of lines (`Text.toJSON()`'s own, different shape), and joined it with `\n` before comparing. It's actually a plain string — `doc: this.sliceDoc()`, confirmed directly in `@codemirror/state`'s source, which also confirms `EditorState.fromJSON` itself validates `typeof json.doc === "string"` and throws otherwise. The array-shaped check silently returned `false` on every call, meaning `restoreHistoryJSON` was *always* rejected — no restoration ever happened, in either direction, on any page. Every one of the new "Per-document" tests failed identically (`undoDepth` stuck at 0, selection stuck at the fresh-state default) until this was caught and fixed. Flagged here specifically because it's exactly the kind of bug that a design review or a "does the API shape look right" read would not have caught — it required running the actual restore path against a real `EditorState` to surface.

**Verified live in the real Clutter webapp** (browser pane): edited today's daily note (page A) across three separately-typed edits, switched to tomorrow's daily note (page B, confirmed via sidebar that A's edit persisted correctly), edited B, switched back to A (content exactly A's own — never B's, never empty), undid twice (each step removed exactly one of A's own edits, landing on the correct intermediate content each time), switched to B and undid there (removed exactly B's own edit, independently of anything done to A). Selection/caret restoration was not independently re-verified pixel-visually in this browser session (clicking to focus the editor for keyboard commands necessarily moves the caret, confounding a purely visual check) — relied on jsdom test E for that specific claim, which asserts on `EditorState.selection` directly rather than rendered caret position, and is unaffected by that confound.

**Redo (`Cmd+Shift+Z`) was not used to verify this feature**, per explicit instruction — a separate, still-unexplained, environment-specific anomaly (this browser pane specifically; flagged in the previous entry, confirmed pre-existing and unrelated to `syncMarkdownIntoView`) reproduced again during this session's testing, on *both* pages, confirming it's a general quirk of this testing environment and not something newly introduced by (or specific to) history preservation. ## Per-page editor session model completed: scroll restoration, deletion invalidation, cache policy (2026-08-28)

Closes out the remaining items from the previous entry. Renamed `editorHistoryCache.ts`'s cache value from a bare history blob to `CachedEditorSession { historyJSON, scrollEffect, domScrollTop }` — same module, same `pageId -> Map` shape, extended rather than replaced.

**`EditorView.scrollSnapshot()` does not work for scroll restoration in Clutter's actual layout — confirmed by direct measurement, not assumed from the API shape.** `scrollSnapshot()`/`EditorViewConfig.scrollTo` operate exclusively on `view.scrollDOM` (CM6's own `.cm-scroller`; its doc comment says as much: "only affects the editor's own scrollable element, not parents"). But Clutter's editor uses `EditorView.lineWrapping`, so `.cm-scroller` renders at full content height and is never itself the scrolling element — the *page shell's* container (`Page.tsx`'s `.page__content`, `overflow-y: auto`) is what actually scrolls. Measured directly in the real app: scrolling a 40-line document left `.cm-scroller.scrollTop` at `0` throughout, while `.page__content.scrollTop` moved to `409.5`. `scrollSnapshot()`/`restoreScrollEffect` were kept in `createEditorView.ts` anyway (harmless, correct per documented contract, gated behind the same `docTextMatches` staleness check as history — "restored as one unit or not at all") but a second, working mechanism was required to deliver actual scroll restoration.

**`domScrollTop` — the second, working mechanism.** `MarkdownEditor.tsx` adds a generic `findScrollableAncestor(el)` helper (walks up from the mount container checking computed `overflow-y` for `auto`/`scroll` — not hardcoded to `.page__content`'s class name, to avoid coupling this feature module to `Page.tsx`'s DOM structure) resolved once at mount into a ref. On unmount, the resolved ancestor's `scrollTop` is captured into the cache alongside `historyJSON`; on mount, if `domScrollTop !== undefined` and `docTextMatches` passes, it's applied directly (`ancestor.scrollTop = cached.domScrollTop`).

**Why capture is polling-based (`setInterval`, 300ms), not a `scroll` event listener — a debugging finding, not a stylistic choice.** A listener-based "last known scrollTop" was tried first and rejected: React's commit phase mutates the DOM (removing the outgoing page's content, inserting the incoming page's, typically much shorter) *before* running the outgoing component's unmount cleanup. The browser auto-clamps the ancestor's `scrollTop` to the new, shorter `scrollHeight` as part of that same synchronous mutation — so by the time cleanup runs, a plain "read `scrollTop` now" is already reading the post-clamp value, and a `scroll`-event-driven "last known" ref is exactly as vulnerable, since the clamp itself fires a `scroll` event that a listener would dutifully record, overwriting the real pre-switch value, before cleanup ever gets to read it. Polling avoids this structurally: the interval is cleared as the *first* line of cleanup, so no poll can ever observe a post-clamp value — polling stops before the clamp-inducing mutation for that page's unmount has a chance to be sampled again. (A synthetic-dispatch differential test in this session's browser tooling also found that JS-driven `scrollTop =` assignment doesn't reliably fire native `scroll` events in that specific tool/environment, which independently ruled out verifying a listener-based approach here — but the structural race above is the real reason for polling, not a workaround for that tooling gap.)

**Deletion cache invalidation — `PageHost.tsx`'s `onDelete`, not `PageOperations.delete()`.** `clearCachedEditorSession(pageId)` is called directly in `onDelete` before `application.pageOperations.delete(activePageId)`. This feature-layer cache module cannot be imported from `core/application` without inverting the enforced dependency direction; `PageHost.tsx` (app layer) already legitimately depends on both `core` (via `application.pageOperations`) and this feature's `MarkdownEditor`, so it's the natural existing bridge — no new event/subscription mechanism added. Deliberately *not* wired into `onArchive`/`onRestore`: those are reversible, and an archived page's prior editing session is still meaningful if it comes back. Known, accepted race, not solved: `pageOperations.delete()` is async and typically triggers navigation away, which unmounts the deleted page's `MarkdownEditor` — whose own cleanup calls `setCachedEditorSession` again, *after* this clear. If that unmount lands after the clear, the entry is silently repopulated — judged harmless, since a deleted page's id is never looked up again through normal navigation, so the race can only ever make this best-effort cleanup a no-op, never cause incorrect behavior.

**Cache memory policy: still a plain `Map`, no eviction — a confirmed decision, not a deferred one.** Assessed directly rather than left as a stale TODO: a real editing session opens at most a handful to a few dozen distinct pages, and each entry's dominant cost (the `historyJSON` blob) is proportional to how much edit history *that page* accumulated this session, not document size. `clearCachedEditorSession` on deletion is judged sufficient eviction for today's usage; an LRU would be speculative complexity against a scenario (thousands of pages touched in one never-reloaded session) that hasn't been observed.

**Regression coverage added** (`createEditorView.test.ts`, tests G–J, alongside the existing A–F): `domScrollTop` round-trips through the cache unchanged (G); a stale doc-mismatched entry discards `domScrollTop` alongside history — no partial restore (H); `clearCachedEditorSession` (mirroring `PageHost.tsx`'s `onDelete`) actually clears an entry, and a reopen under the same id starts fully fresh (I); rapid A→B→A→B switching produces no cross-contamination, confirming React's synchronous unmount-before-mount ordering holds regardless of switch speed (J). All 22 tests in the "Per-document" suite pass. Polling/DOM-ancestor logic in `MarkdownEditor.tsx` itself is not separately unit-tested — inherently DOM-layout/timing-dependent in a way jsdom doesn't reproduce (no real scroll/layout) — verified instead in the real browser, per project convention for editor/UI behavior.

**Verified live in the real Clutter webapp:** placed the caret mid-word on a specific line of a multi-line document, switched to the next day's note and back — `window.getSelection()` confirmed the DOM caret landed at the exact same character offset in the same line afterward, and a screenshot confirmed it visually. Set `.page__content.scrollTop` to a specific value on a 40-line document, switched away and back — `scrollTop` read back the same value afterward. Concealed-widget rebuild after restoration was visually confirmed correct throughout (no stale/duplicated decorations on remount). React StrictMode double-invoke and rapid page-switching races are covered by jsdom test J; no additional real-browser-specific race was found.

**Redo (`Cmd+Shift+Z`) anomaly:** not investigated in this pass either, per standing instruction; not encountered this session (no redo testing was performed).

**Remaining limitations, stated explicitly:**
- The cache is still in-memory/session-only — an app reload loses all preserved sessions (history, scroll, selection), matching baseline behavior, never regressing it.
- `domScrollTop` restore does not itself re-scroll to keep the restored caret in view if the two conflict (e.g., a very different-length document reopened with a stale caret position) — not a scenario this pass needed to handle, since both are gated by the same `docTextMatches` document-identity check and so only ever restore together, for the same document text.
- No eviction beyond deletion, by design (see above) — worth revisiting only if a real long session demonstrates unbounded growth actually matters.

## Focus restoration — Superseded (2026-08-28, later same day)

**Superseded by "Note-open focus policy" below, same day.** `wasFocused`-gated restoration (preserve whatever focus state a page had when last closed) was replaced with a different, product-directed rule: an *established* editing session (real prior engagement, not just "was focused") always focuses on reopen regardless of prior focus state, and a fresh/no-session page defers to the same open-time "empty title → title focus" policy `Page.tsx` already applies. `wasFocused` was removed from `CachedEditorSession` entirely — kept here, not deleted, per this doc's own "Superseded" convention (Status key above): so nobody re-discovers the same dead end. The investigation and verification methodology below are still accurate and still relevant background; only the specific gating rule they led to was replaced.

**Investigated first, per instruction, before writing any code — the question was genuinely open, not assumed.** Traced the full open-note lifecycle (sidebar click → `activePageId` change → `PageHost` remount → `MarkdownEditor` mount → `createEditorView` → `EditorState.fromJSON`) and grepped the entire app for every `.focus()`/`autoFocus` call. Finding: **no code path anywhere in the app ever focused the editor on note-open, before or after the per-document session work** — the only existing focus-transfer is `Page.tsx`'s `PageTitle.onSubmit` (Enter in the title advances focus into the body), a distinct, deliberate interaction unrelated to opening/reopening a note. Confirmed live in the browser across single-hop (A→B→A) and multi-hop (A→B→A→C→A) switching: `EditorState`'s restored selection was always correct internally (confirmed via `window.getSelection()` after programmatically focusing), but DOM/`EditorView` focus never returned on its own — `document.activeElement` stayed on whatever sidebar control was last clicked, consistently, not intermittently. **Conclusion at that point: expected/pre-existing behavior (not a regression the per-document work introduced), but a genuine product-behavior gap** — restoring a caret that isn't visibly active is confusing in a way "no caret at all" never was. Presented both options; product direction confirmed: implement `wasFocused`-gated restoration.

**Implementation — extends the existing session cache and polling mechanism rather than adding new machinery.** `CachedEditorSession` (`editorHistoryCache.ts`) gains `wasFocused: boolean`. `MarkdownEditor.tsx`'s mount effect calls `view.focus()` immediately after the scroll restore, gated on `cachedSession?.wasFocused && docTextMatches(cachedSession.historyJSON, markdown)` — the identical staleness gate already used for history/scroll ("restored as one unit or not at all"); a fresh page (no cache entry) or a stale one never autofocuses.

**Why focus capture reuses `scrollPollInterval` rather than a `focus`/`blur` listener pair — the same class of race as `domScrollTop`, confirmed by reasoning through the actual click sequence, not assumed by analogy.** The click that switches pages (e.g. a sidebar item) synchronously blurs the outgoing editor as a *native* side effect of that click — before React's own state update, before the remount, before this component's unmount cleanup ever runs. A live `view.hasFocus` read at unmount, or a `blur` listener that sets a ref to `false`, would therefore always read `false` at exactly the moment that matters, regardless of whether the user was genuinely typing in the editor a second earlier — the blur is inherent to the switching gesture itself, not a symptom of anything. The fix is the same one already proven for scroll: sample `view.hasFocus` on the existing 300ms poll into `lastKnownFocusRef`, and read that *last-known* value (not a live one) at unmount, after the interval is cleared. This also correctly handles the secondary case of the user blurring the editor *without* switching pages (e.g. clicking into the page title) and then switching later — the poll has time to catch that intermediate blur before the eventual switch, so `wasFocused` still reflects "was the editor the last thing focused right before leaving," not just "was it ever focused during this mount." A pathologically fast blur-then-switch (under one 300ms tick) could theoretically still read stale — accepted, same documented tolerance already recorded for scroll's own polling.

**Regression coverage** (`createEditorView.test.ts`, tests K–O, alongside the existing A–J): a focused editor regains focus and its selection on return (K); an unfocused editor stays unfocused, proving selection restoration and focus restoration are independent (L); a page with no cached session never autofocuses (M); focus state doesn't leak between pages in either direction (N); a stale (doc-mismatched) cache entry's `wasFocused` is never honored, following the same all-or-nothing gate as history/scroll (O). Both `openPage`/`closePage` test helpers were updated to mirror the real mount/unmount code exactly (`openPage` now conditionally calls `view.focus()`, matching `MarkdownEditor.tsx`'s own gate). 32 tests total in the "Per-document" suite pass.

**Verified live in the real Clutter webapp:** typed a multi-line note, clicked mid-word into "Charlie," confirmed focused (`cm-focused` class, `document.activeElement` on `.cm-content`), switched to the next day's note and back — **without any click**, `document.activeElement`/`cm-focused` confirmed the editor regained real DOM focus on its own, `window.getSelection()` confirmed the caret at the exact same offset, and a screenshot confirmed a visible blinking caret rendered after "Charlie." Verified the negative case symmetrically: a page that was opened but never clicked into stayed unfocused (`activeElement` remained the sidebar control) after being switched away from and back. Verified isolation across a longer hop sequence (A focused → B never-focused → C → B → A) — A's focus and B's non-focus each held independently at every step, no leakage in either direction.

**A render-timing detail worth recording, not a bug:** immediately after `view.focus()` is called in the mount effect, `document.activeElement`/the `cm-focused` class are correct right away, but the actual `.cm-cursor-primary` blink-layer DOM node takes one additional CM6 measure/layout pass (a `requestAnimationFrame` tick) to appear — confirmed directly (present after a ~1s wait, absent immediately before it). Not a defect: `EditorView.focus()`'s own contract is about DOM/model focus, not a synchronous guarantee that every visual layer has repainted, and a real browser's own paint cadence means a user never perceives this gap. Not worth engineering around for a sub-frame timing detail.

**Remaining focus edge cases, stated explicitly (historical — see the entry below for what actually shipped):**
- The sub-300ms blur-then-switch race described above (accepted, matching scroll's own documented tolerance).
- Focus restoration is strictly binary (`wasFocused`) — it does not also restore *which* of several possible in-page focus targets was active (there is only one: the editor's `contentDOM`; a future page type with multiple focusable regions would need a richer model, not needed today).
- Archived/restored pages: `wasFocused` is captured and read exactly like history/scroll (i.e., it survives archive/restore, since nothing clears it there — consistent with the existing "archived pages keep their editing session" decision above).

## Note-open focus policy (2026-08-28, later same day)

**Product direction, stated explicitly, that motivated replacing the entry above:** when a user explicitly opens a note, they should be able to start editing immediately. `wasFocused`-gated restoration didn't deliver that for the common case of an existing, previously-edited note that simply wasn't focused the instant it was last closed (e.g. the user scrolled it via the sidebar, or blurred it before navigating away) — reopening it left the editor unfocused even though the note plainly has an established body worth continuing to edit. The fix is a priority rule, not a bigger cache:

1. **A restorable cached session with real, established prior engagement always focuses the editor** — regardless of `wasFocused`'s old per-close snapshot (that field is gone; this is a stronger, simpler replacement, not an addition to it).
2. **Otherwise, `focusOnOpen`** — a flag `PageHost.tsx` computes at the moment it renders `<MarkdownEditor>`, mirroring the exact same "empty title → title gets focus" emptiness check `Page.tsx`'s own `shouldAutoFocusTitle` already applies to the *same* `title` value (`focusEditorOnOpen(title) = title !== ''`, `PageHost.tsx`) — decides: a non-empty title means the user is opening an already-named note to keep working in its body, so the editor is ready to type into immediately; an empty title (a brand-new, just-created note) leaves the title as the first editing target, unchanged from today.

**How `PageHost` knows a page was "explicitly opened"** — investigated before writing anything, per instruction: it doesn't need to, because it doesn't need to distinguish. `<MarkdownEditor key={activePageId}>` already forces a full remount for exactly one reason — a distinct `activePageId` — so "this component mounted" and "this page was opened" are already the same event; no new plumbing (an explicit `onNoteClick` signal, a "just navigated" ref, etc.) was needed to tell them apart.

**What "restorable... with real, established prior engagement" means, precisely, and why "a cache entry exists" alone is not enough — a real bug this investigation caught, not a hypothetical.** `editorHistoryCache.ts`'s `setCachedEditorSession` runs unconditionally on *every* unmount — including a page opened and closed without the user ever touching it, and (dev-only) React StrictMode's own mount→unmount→remount cycle. Confirmed directly: a brand-new, empty-title draft's *second* StrictMode mount found a cache entry written by its own *first* mount's cleanup moments earlier — a component-lifecycle artifact, not anything the user did — and the naive "any matching cache entry → focus" rule very nearly stole focus from the title on every single brand-new note, defeating priority (2) above entirely. Fixed by adding `createEditorView.ts`'s `hasEstablishedEditingPosition(view)`: true when the restored selection's head is anywhere other than the two positions a truly untouched session can have (`0`, or `doc.length` — `EditorState.create`'s own default "cursor at end" placement), *or* `undoDepth(view.state) > 0`. A session only counts as restorable when `docTextMatches` passes (the existing staleness gate) **and** `hasEstablishedEditingPosition` is true — an untouched page, or a StrictMode double-mount, correctly falls through to `focusOnOpen` instead.

**Regression coverage** (`createEditorView.test.ts`, tests K–Q, replacing the old K–O): a non-empty-title page with no session focuses via `focusOnOpen` (K); `focusOnOpen=false` never autofocuses (L); no session and no `focusOnOpen` never autofocuses (M); a genuinely established session (real selection movement or an edit) always focuses and restores its selection, *even overriding* `focusOnOpen=false` — an established position always wins (N); focus decisions are isolated per page, unaffected by another page's state (O); a stale (doc-mismatched) entry never grants focus on its own — `focusOnOpen` decides instead (P); **a cache entry with no real engagement — default caret, no edits — never forces focus on its own (Q)**, the direct regression test for the StrictMode/untouched-page bug above. `openPage`'s test helper was updated to mirror `MarkdownEditor.tsx`'s exact gate, including the `hasEstablishedEditingPosition` check. All 33 tests in the "Per-document" suite pass.

**A second, real bug this pass caught along the way, unrelated to the focus logic itself but exposed by it:** `MarkdownEditor.test.tsx` reuses the same `pageId="test-page"` (often with the same markdown text, e.g. `"Hello"`) across many independent `it()` blocks, with no cache-clearing between them. Once *any* cache entry could unconditionally trigger `view.focus()`, this cross-test cache pollution became an observable failure (`syncs an external markdown prop change into the DOM while unfocused` started failing, because an earlier test's leftover session auto-focused its editor). Fixed with a `beforeEach(() => __clearAllCachedEditorHistoryForTests())` at the top of that file, mirroring the pattern `createEditorView.test.ts` already used.

**Verified live in the real Clutter webapp**, each independently:
- *Existing note, non-empty title, no session (A/K):* opened today's daily note fresh, typed immediately with no click — text landed directly in the body.
- *Brand-new note, empty title (B/L):* clicked "New" in the sidebar — `document.activeElement` was the title's `editable-text` element, not the editor; typed immediately — text landed in the title, not the body. (This is the exact case the StrictMode bug above broke before the `hasEstablishedEditingPosition` fix; confirmed fixed by re-running this same check.)
- *Cached, established session (C/N):* typed real content into a note, switched away and back — typed immediately with no click, text landed correctly appended to the prior content, proving both the caret position and focus were restored together.
- *Switching between already-open notes, no leakage (E):* an established note (A) and an untouched-but-non-empty-title note (B) — A→B→A — each behaved independently and consistently across the round trip, matching K/N/O's jsdom coverage.
- *Click note → type immediately, no editor click first (F):* the decisive end-to-end check, folded into A/K and C/N above — passed in both the "no session" and "established session" cases.

**Remaining focus edge cases, stated explicitly:**
- The `head === 0` / `head === doc.length` heuristic in `hasEstablishedEditingPosition` has one known false-negative: a user who moves the caret (no edit) to exactly the start or end of the document, then leaves, won't have that movement alone count as "established" on return (an edit, or a mid-document caret position, always does). Accepted as a narrow, low-stakes trade-off rather than tracking a separate explicit "was genuinely engaged" flag, which would reintroduce the same kind of extra state this redesign specifically removed (`wasFocused`).
- `PageTitle`'s own Enter-to-advance-into-body behavior (`Page.tsx`'s `onSubmit` → `bodyFocusRef.current.focus()`) was observed, during this verification, to not reliably move focus into the body in one specific manual sequence (typed a title, pressed Enter, kept typing — text kept appending to the title instead of moving to the body). Not investigated further and not fixed here: this component/wiring was not touched by this change, `Page.tsx`'s `onSubmit` prop and `EditableText.tsx`'s key handling are exactly as they were before this session, and the task was scoped to note-open focus policy, not title-to-body Enter handling. Flagged here as a real, observed, separate issue worth a dedicated look.
- Archived/restored pages: a cached session's establishedness is evaluated the same way regardless of archive state — consistent with the existing "archived pages keep their editing session" decision (no new interaction with archive/restore introduced here).
