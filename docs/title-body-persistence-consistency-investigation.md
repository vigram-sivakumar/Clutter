# Investigation: Should Title Editing Share the Body's Editing/Persistence Model?

**Status:** Research only, no code changes. Written in response to a direct question, not as part of a migration phase. Follows the same research-before-design discipline `autosave-strategy-analysis.md`/`autosave-ownership.md`/`autosave-execution-model.md` used for the body — this document is best read as their unfinished thread: `autosave-execution-model.md` §9's "Rename" row already flagged this exact question in one sentence ("a debounced title-autosave would be a second `SaveCoordinator`-managed timer of the same kind... not a new state, not a new coalescing rule") without working it through. This document works it through.

---

## 1. How the body edit lifecycle actually works today

Two events, deliberately decoupled (`autosave-execution-model.md` §0, §3.1):

1. **Commit (cheap, in-memory, every keystroke).** `MarkdownEditor.onEdit` → `PageHost.onUpdateMarkdown` → `PageOperations.commitEdit(pageId, markdown)` → `DocumentSession.commit(new DocumentTransaction(markdown))`. This produces a new immutable `DocumentRevision`, updates `currentRevision`, and notifies subscribers — no Gate call, no disk I/O. `SaveCoordinator.scheduleSave()` is also called here, arming/resetting a 2-second debounce timer and (on the first commit of a dirty streak) a 30-second ceiling timer, both keyed by session id.
2. **Persist (debounced, coalesced, eventually reaches disk).** When a timer fires, or blur/navigation/shutdown/manual-save calls `PageOperations.requestSave(pageId)`, `SaveCoordinator.evaluate(session)` decides `execute`/`suppress` from exactly two facts: `session.state` (a `DocumentState`: `Clean`/`Saving`/`SaveError`/etc.) and `session.isDirty` (`currentRevision !== savedRevision`). Only on `execute` does `PageOperations.save()` run, enqueueing `{kind: 'save', content}` through the Persistence Gate's per-page queue, ending in `Vault.replacePage()`.

The result: five triggers (type, blur, debounce, navigate, close) reliably collapse into exactly as many disk writes as there is genuinely distinct content to persist — never more, never fewer (`autosave-execution-model.md` §4.2's worked example). Failure is uniform (`SaveError`, content never discarded, next trigger retries). This machinery — `DocumentSession`'s state machine, `SaveCoordinator`'s timers/coalescing, `PageOperations.requestSave()` as the one entry point — is genuinely general-purpose: it has no markdown-specific logic anywhere in it. `DocumentRevision` happens to hold a `markdown: string` field, but nothing in `DocumentState`, `SaveCoordinator.evaluate()`, or the timer model inspects that field's contents.

## 2. How the title edit lifecycle differs today

Title editing (`EditableText` → `PageTitle` → `PageHost.onTitleCommit`) has **no commit/persist split at all**:

1. The browser's `contentEditable` div holds the in-progress text. Nothing above it — not React state, not `DocumentSession`, not any Clutter-owned structure — sees a keystroke while the user is still typing the title.
2. On blur (or Enter), `EditableText.handleBlur` compares the final `textContent` against the last-committed `value` prop and, if different, fires `onCommit(committedValue)` **exactly once, synchronously with the browser focus-loss event.**
3. For a persisted page, `onCommit` now goes straight to `PageOperations.rename(pageId, title)` — which immediately enqueues `{kind: 'rename', title}` through the Gate, ending in an actual `fileSystem.moveFile()` and `Vault.updatePagePath()`. There is no in-memory "typed but not yet persisted" title state anywhere: the moment between "user stopped typing" and "file renamed on disk" is a single synchronous call chain with no debounce, no `DocumentState` awareness, no `SaveError` path, and no coalescing if the user blurs and refocuses the title field multiple times in a row.

Concretely: three body keystrokes followed by a pause produce one commit-then-debounced-save sequence with full retry/failure semantics. Three title edits each ended by a blur produce **three independent, un-coalesced Gate `rename` operations**, each a real disk rename, each with no shared failure-handling story beyond "the returned promise rejects and `PageHost.onRenamePage` currently does nothing with that rejection" (worth noting as a smaller, related gap: `onRenamePage` fires `void application.pageOperations.rename(...)`, discarding a thrown `Page not found` the same way `onRenameFolder` already does — consistent with today's code, but neither surfaces a failure to the user).

`updateDraftTitle()` (a still-unpersisted draft's title) is architecturally closer to a commit — it's an in-memory descriptor mutation with no Gate call *until* it's the first committed change that promotes the draft — but it's still blur-triggered only, with no debounce concept, because a draft's title commit is a rare, one-shot "does this promote the draft" event, not a repeatable autosave target the way a persisted page's title now is.

## 3. What's shared vs. what's genuinely different

| | Body | Title (persisted page) |
|---|---|---|
| In-progress state while typing | `DocumentSession.currentRevision`, updated on every keystroke | Browser DOM only — invisible to Clutter until blur |
| Commit trigger | Every keystroke (`onEdit`) | Blur/Enter only |
| Persist trigger | Debounce (2s) / ceiling (30s) / blur / navigation / shutdown, coalesced | Same event as commit — blur *is* persist |
| Failure handling | `SaveError` state, preserved content, retried by next trigger | None — a thrown rename error is silently discarded by the current UI wiring |
| Gate operation | `'save'` — rewrite content at the *same* path | `'rename'` — *move* the file to a new path |
| Concurrency safety | Per-page Gate queue + per-session `SaveCoordinator` state | Per-page Gate queue only (no `SaveCoordinator` involvement at all today) |

The infrastructure that's genuinely reusable: `DocumentState`, `SaveCoordinator`'s per-session timer pair, and `PageOperations.requestSave()`'s coalescing algorithm are all **field-agnostic already** — none of them know they're managing markdown specifically. `autosave-execution-model.md` §9 said as much in one line; this investigation confirms it by inspection, not just by design intent.

What's missing structurally: `DocumentSession`/`DocumentRevision` today model *only* `markdown`. There is no in-memory slot for "the title as currently being edited, not yet persisted." That's the one real gap — not a redesign, an absence.

## 4. Filesystem implications of frequent (debounced) renames

This is the one place title and body genuinely diverge even *after* fixing the missing-debounce gap, because the underlying Gate operations are different in kind, not just cadence:

- **A body autosave rewrites the same path repeatedly** — cheap, and invisible outside the app (no directory entry changes, nothing for a file watcher, git, or another open tool to react to beyond "this file's mtime/content changed").
- **A title autosave, even debounced to the same 2s/30s cadence, is an actual OS-level rename each time it fires.** If a user pauses mid-title (e.g., typing "Meeting No—" then a pause, then continuing to "Meeting Notes"), debouncing at the *same* cadence as body saves means at most one rename per pause-or-ceiling, not one per keystroke — so the existing coalescing model already prevents the worst case (a rename per character) automatically, with no new mechanism required. But it does mean a title composed over a long pause-filled session could rename the file several times before settling, each one:
  - Re-running the collision-free-name resolver against the vault's *current* state (already correct — `resolveRenameDestination` excludes the page's own id — but a title that transiently collides with an existing sibling mid-composition would get a real, transient " 2" suffix that then disappears once the user keeps typing past the collision).
  - Firing a real filesystem rename event, which `SelfWriteRegistry`/`SelfWriteAwareFileSystem`/`SelfWriteAwareWatcher` already exist specifically to suppress as an echo — this path is already proven safe for exactly this kind of self-initiated rename (it's the same mechanism every already-shipped app-initiated move/rename relies on), so debounced title renames don't introduce a new race, they just increase how often an already-handled one occurs.
  - Being visible, as file history noise, to anything watching the vault directory outside the app (a git-tracked vault, an external sync tool, a Finder/Explorer window left open) — a body edit never produces this kind of externally-visible churn; a rename always does, regardless of cadence.
- **Backlinks resolve by path/filename against the live vault state, not by a cached id** (`LinkResolver.resolve()`, checked directly: it looks up `link.target` — the raw text inside `[[...]]` — via `pageIndex.findByPath`/`findByFileName` on every rebuild, never a stored `targetPageId`). This means a `[[Old Title]]`-style link elsewhere in the vault genuinely goes from `resolved` to `missing` the instant this page is renamed away from "Old Title" — already true today, with blur-only rename. Making renames continuous/debounced during typing would make this flip happen more often and more transiently (a link could resolve, go missing, then resolve again to a different-looking title, all while one person is mid-composition) — a real, visible product effect worth surfacing explicitly if title autosave is pursued, though not a correctness bug: `LinkResolver`'s output is a disposable, fully-rebuilt projection (rule 8), so nothing is ever left permanently wrong, only transiently stale until the next rebuild.

Net: debouncing title renames at the *same* cadence as body saves is safe and doesn't introduce a new class of problem, because the coalescing model that already prevents "one write per keystroke" for the body applies identically here. The remaining cost is `Archive/`-adjacent: purely more renames of a *directory entry* than a body edit ever produces, which is externally visible in a way a body write isn't — a real but bounded cost, not a correctness risk.

## 5. Smallest architectural change to make title consistent with body

Given §3's finding that the coalescing/timer/state infrastructure is already field-agnostic, the smallest change is extending it to a second field, not building a parallel mechanism:

1. **Give the session a place to hold an in-progress title**, alongside `currentRevision`/`savedRevision`. The narrowest version: `DocumentSession` gains a `currentTitle`/`savedTitle` pair (or a small sibling object it holds), mirroring `DocumentRevision`'s shape exactly — this is the one genuinely new piece of state; everything else below reuses existing collaborators.
2. **`PageOperations` gains a commit-only method for titles** (`commitTitle(pageId, title)`), mirroring `commitEdit()`'s existing contract exactly (§3.1's "commit without persisting" shape): updates the session's in-progress title, calls the same `SaveCoordinator.scheduleSave()` the body already uses — the *same* per-session timer pair, not a second one, since both fields belong to the same document and there's no product reason to persist them on different cadences.
3. **`SaveCoordinator.evaluate()`'s dirty check generalizes from one boolean to "any tracked field is dirty"** — still `(DocumentState, dirty) → decision`, no new state, no new row in the coalescing table, exactly as `autosave-execution-model.md` §9 predicted. `session.isDirty` becomes an OR across body-dirty and title-dirty rather than a single comparison.
4. **`PageOperations.requestSave()`'s `execute` branch fans out to whichever Gate operations are actually pending** — a dirty body enqueues `'save'`, a dirty title enqueues `'rename'`, both dirty enqueues both (order doesn't matter; they're different Gate operation kinds against the same per-page queue, already serialized). This stays "one entry point, one write path per capability" (rule 12) — `requestSave()` doesn't gain a new capability, it just now recognizes two kinds of pending work instead of one.
5. **`EditableText`'s title usage moves from blur-only commit to continuous commit**, mirroring `MarkdownEditor`'s `onEdit`/`onFlush` split: an `onEdit`-equivalent fires `commitTitle()` on every input event (or on a lighter debounce inside the component, matching how body edits already commit per-keystroke rather than per-blur), and blur becomes just another trigger for `requestSave()` — not the *only* trigger, and not fused with commit anymore. This is the one real UI-facing behavior change: today's blur-only model reads as intentional ("commit when you're done"); the body's model reads as continuous ("save while you work, coalesced"). Adopting the latter for titles means a title starts renaming the file while the user is still in the field, on the same debounce boundary the body already uses — not only when they click away.

**What this explicitly does not require:** a new `DocumentState` value, a new `PersistenceOperation` Gate kind (`'rename'` already exists), a new subsystem, or a new facade. It does require a real (if small) structural addition to `DocumentSession` — today it is genuinely markdown-only, and giving it a second tracked field is the one piece of this that isn't already sitting there waiting to be wired, unlike everything in `SaveCoordinator`/`PageOperations.requestSave()`, which already generalizes for free.

**What's deliberately not resolved here:** whether continuous title-renaming during typing is the *product* behavior wanted, given §4's filesystem-churn cost — that's a product call, not an architectural one, and this document's job was to answer whether the architecture supports it cleanly (it does, with the one addition above) and what it would cost (bounded, but real and externally visible in a way body autosave isn't). No code changes were made as part of this investigation.
