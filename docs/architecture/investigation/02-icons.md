# 02 — Icons Audit

Scope: `apps/app/src/shared/icon/` (`AppIcon.tsx`, `iconRegistry.ts`, `types.ts`, `AppIcon.css`, `index.ts`, `svg/`), `core/presentation/getPageIcon.ts`, and every consumer of icon/emoji rendering across `apps/app/src/features/` and `apps/app/src/app/`.

## Summary

Icons are cleanly owned: one registry file (`iconRegistry.ts`) is the sole importer of SVG assets, one component (`AppIcon`) is the sole renderer, and one pure function (`getPageIcon`) is the sole source of truth for "what icon does this page/folder type get by default." This is a genuinely well-factored slice of the codebase relative to the rest of the audit. The weaknesses are elsewhere: roughly 40% of the 57 registered icons (23 of 57, by direct usage-string search) have zero consumers anywhere in the app, there is no icon picker UI despite a fully round-tripped per-page/folder `metadata.icon` emoji field, and the "icon" concept quietly splits into two unrelated systems — a fixed enum of 57 SVG `SystemIcon`s and a completely freeform `emoji: string | null` field — with no validation, no picker, and no product-visible way for a user to actually choose a custom icon today.

## Current Architecture

- **Registry** (`iconRegistry.ts:1-124`): a single object literal mapping ~57 camelCase keys to imported SVG React components (via `vite-plugin-svgr`'s `?react` suffix, confirmed at `vite.config.ts:3,7`) or, in one case, a hand-written React component (`calendar-today.tsx`, mapped at `iconRegistry.ts:76`). The file's own header comment (`iconRegistry.ts:1-5`) states it is "the ONLY file that imports SVGs" — verified true; no other `.svg?react` import exists outside this file.
- **Type derivation** (`types.ts:1-8`): `SystemIcon = keyof typeof iconRegistry` — the icon name type is derived from the registry object, not maintained as a separate union, so adding/removing a registry entry can't silently desync from the type.
- **Renderer** (`AppIcon.tsx:1-35`): a single component accepting `icon?: SystemIcon`, `emoji?: string | null`, `size`, and `slotSize`. Precedence is emoji-first: if `emoji` is truthy, it renders `<span className="emoji-icon">{emoji}</span>` regardless of whether `icon` is also passed (`AppIcon.tsx:28-32`); `icon` is only rendered when `emoji` is falsy. `slotSize` becomes a per-instance CSS custom property (`--app-icon-size`, `AppIcon.tsx:22-24`) consumed by `AppIcon.css:9-10`.
- **Default-icon-by-type policy** (`getPageIcon.ts:1-22`): a pure switch mapping `'note' | 'daily-note' | 'folder' | 'tag'` to a fixed `SystemIcon` (`squiggleLine`, `calendar`, `folder`, `tag` respectively). Its doc comment (`getPageIcon.ts:6-9`) explicitly states it's meant to be the single reused source for this mapping across "sidebars, page headers, search results, folder children."
- **Emoji override field**: `PageMetadata.icon: string | null` (`core/vault/models/PageMetadata.ts:4`) and `FolderMetadata.icon: string | null` (`FolderMetadata.ts:2`) — a raw, unvalidated string, round-tripped through YAML frontmatter as the `icon` key (`FrontmatterSerializer.ts:56`). This is the *only* per-instance icon customization mechanism found; there is no separate "reserved icon" or non-emoji custom-icon concept anywhere in the codebase.
- **Consumption pattern**: every consumer found calls `getPageIcon(<fixed literal type>)` for the `icon` prop and passes the entity's `metadata.icon` (or a mapped `emoji` field) for the `emoji` prop, letting `AppIcon`'s internal precedence decide which actually renders. Confirmed consumers: `Note.tsx:30`, `Folder.tsx:49`, `toCollectionPageModel.ts:5,38`, `buildBreadcrumbs.ts` (imports `getPageIcon`, per grep), `FolderTree.tsx:97,114,148` (passes `metadata.icon` as `emoji` directly to `Folder`/`Note`, which then call `getPageIcon` internally with their own hardcoded type literal).

## Evidence

- **Single-importer claim verified**: `grep -rn "\.svg?react" apps/app/src` (via `iconRegistry.ts` imports, lines 7-64) shows all SVG imports confined to this one file; no `.svg?react` import exists in any feature or component file.
- **Type safety verified**: `types.ts:8` (`export type SystemIcon = keyof typeof iconRegistry;`) — confirmed no parallel/duplicate `SystemIcon`-shaped union exists elsewhere.
- **Dead icons — verified via exhaustive per-key grep** (pattern `icon={'X'}|icon="X"|icon:.*'X'|iconRegistry\.X` across all `.ts`/`.tsx`): the following 23 of 57 registry keys returned zero matches outside their own registry declaration: `keyEsc`, `folderAdd`, `notePencil`, `favouriteFilled`, `settings`, `squareExpand`, `squareFill`, `squareHug`, `tabsFlat`, `widthHug`, `chevronDown`, `chevronLeft`, `chevronRight`, `chevronUp`, `chevronSquareRight`, `chevronSquareRightLight`, `circleDashed`, `arrowDownRight`, `arrowLeftSmallHead`, `arrowRightSmallHead`, `bookshelfBox`, `caretLeft`, `caretUp`, `squareDashed`. **Verified** for these exact search patterns; a small number of false negatives are possible if an icon name is referenced through further indirection this audit didn't trace (e.g., a lookup table keyed by something other than a literal string) — flagged as **Strong Evidence** rather than absolute certainty for the full count, but the pattern (a large minority of the registry is unused) is unambiguous.
- **`calendarToday` used exactly once outside its registry mapping**, at `app/layouts/sidebar/Sidebar.tsx:42` (`icon: 'calendarToday'`) — confirming the registry's one hand-written (non-SVG-file) icon is live.
- **Emoji precedence, not fallback-chaining**: `AppIcon.tsx:28-32` — `emoji ? <emoji-span> : Icon ? <Icon .../> : null`. There is no combined rendering (e.g., a small SVG badge overlaid on a custom emoji) and no explicit handling for an invalid/non-emoji string in `emoji` (e.g., `"hello"` would render literally as text inside `.emoji-icon`, styled with `font-size: var(--text-body)` — `AppIcon.css:2` — with no length/content guard).
- **`getPageIcon` called with a hardcoded literal, not a dynamic `entry.type`, in `Note.tsx:30` and `Folder.tsx:49`** — i.e. `getPageIcon('note')` and `getPageIcon('folder')` are always called with a constant argument at these two call sites, since a `Note` component only ever renders notes and a `Folder` component only ever renders folders. This makes the switch-based design of `getPageIcon` (which handles four cases) partially over-general relative to how two of its current call sites use it — those two call sites could hardcode `'squiggleLine'`/`'folder'` directly with identical runtime behavior, though routing through `getPageIcon` does still correctly centralize the *mapping itself* for the sites that vary by actual type (`toCollectionPageModel.ts:38`, which computes the type dynamically from `isFolder(entry)`).
- **No emoji picker UI found**: exhaustive search for `EmojiPicker`, `emoji-picker`, `setIcon`, `updateIcon`, `onIconChange` across `apps/app/src` returned zero matches. `metadata.icon` is fully round-tripped (parsed from frontmatter, serialized back, covered by tests — `DocumentRoundTrip.test.ts:75`, `FrontmatterSerializer.test.ts:54`, `VaultBuilder.test.ts:35`, `VaultSyncService.test.ts:242,691`, `PageOperations.archiveRestore.test.ts:277,308,529`, `PageOperations.test.ts:298,359`) but no UI control to set it was found — a user can only get a custom page/folder emoji today by hand-editing the markdown file's frontmatter outside the app, or via whatever created the fixture data in tests. **Verified absent from `apps/app/src`**; **Unknown** whether this is planned/upcoming or an intentional out-of-scope gap — see Next Investigation Areas.
- **No "reserved icon" concept exists.** The task brief hypothesized a "reserved icon" concept; none was found. The only two icon-selection axes in the whole codebase are (a) the fixed `getPageIcon`-driven default per entity type, and (b) the freeform per-instance `metadata.icon` emoji override. There is no concept of a curated subset of `SystemIcon`s being user-choosable, no icon-name storage on `Page`/`Folder` beyond the emoji string, and no "default icon differs from reserved/system icon" distinction anywhere.

## Strengths

1. **Textbook single-owner pattern.** The registry-import / type-derivation / single-renderer-component triad (`iconRegistry.ts` → `types.ts` → `AppIcon.tsx`) is close to a model example of the architecture's own stated philosophy (`ARCHITECTURE_RULES.md` rule 1, "every capability has exactly one owning facade") applied to a UI concern the governance docs don't actually cover — the icon subsystem independently arrived at the same shape.
2. **`getPageIcon` is genuinely the single source of truth it claims to be.** Every consumer found routes through it rather than hardcoding an icon name inline for a page/folder/tag context — the one theoretical drive-by risk (a component hardcoding `'squiggleLine'` directly) was not found anywhere.
3. **Type derivation prevents drift.** `SystemIcon = keyof typeof iconRegistry` means the type can never list an icon that doesn't exist in the registry, and TypeScript enforces that any `icon` prop value is a real registry key at compile time — a meaningfully better guarantee than a hand-maintained parallel enum.
4. **Clean separation of "system icon" vs. "emoji"** as two distinct, differently-typed props on `AppIcon` (`icon?: SystemIcon` vs `emoji?: string | null`) rather than one polymorphic "icon" prop that has to be sniffed at runtime — the precedence rule is simple and centralized in one component.

## Weaknesses

1. **~40% of the icon registry is dead.** 23 of 57 icons have no consumer. This is a meaningfully large fraction of a small, hand-authored asset set — each entry is a real SVG file plus a registry line plus (implicitly) prior design/import work, all currently unused.
2. **No product-facing way to set a custom icon.** The data model, persistence, and round-trip logic for `metadata.icon` are fully built and tested, but the UI half doesn't exist — this is exactly the kind of "half-built capability" the codebase's own `ARCHITECTURE_RULES.md`/`implementation-rules.md` philosophy would flag if it were an architectural capability (it isn't formally one of the twelve subsystems, so it isn't literally in scope of those rules, but the *pattern* — data support without a consuming UI — is the same shape those rules exist to prevent at the persistence layer).
3. **No validation on the emoji field.** `metadata.icon: string | null` accepts any string; `AppIcon` renders it verbatim as text (`AppIcon.tsx:29`). A non-emoji string (e.g., a stray word from a bad frontmatter edit) degrades silently to rendering as small text rather than failing visibly or falling back to the type default — there's no length cap, emoji-pattern check, or fallback-on-invalid-input.
4. **The `note`/`daily-note`/`folder`/`tag` union in `getPageIcon` mixes vault-model page types with two structurally different concepts (`'folder'` isn't a `PageType`, it's a sibling aggregate; `'tag'` may not correspond to a persisted entity at all)** — `getPageIcon.ts:11` types its parameter as `PageType | 'folder' | 'tag'`, meaning the function's signature is already an ad hoc union rather than a single closed domain type, which will need extending by hand for every future page-like entity (templates, attachments — both plausible future aggregates per `ARCHITECTURE_RULES.md`'s "Templates, Attachments" example, rule 6/implementation-rules §6) rather than being naturally exhaustive over a real domain type.

## Hidden Assumptions

- **`AppIcon`'s emoji-wins-over-icon precedence is implicit, undocumented behavior every caller silently depends on.** No consumer was found passing both `icon` and `emoji` expecting `icon` to win — but nothing prevents a future caller from doing so and being surprised. The precedence rule lives only in `AppIcon.tsx:28-32`'s control flow, not in a comment or the prop types (`emoji?` and `icon?` are both simply optional, with no type-level expression of "at most one should be provided" or "emoji takes precedence").
- **Every consumer assumes `metadata.icon` is either `null` or a valid single-glyph emoji** — an assumption the type system does not enforce and no runtime validation checks (see Weaknesses #3).
- **The registry assumes SVGR's `?react` transform is stable infrastructure.** All 57(-1 hand-written) icons depend on `vite-plugin-svgr` (`vite.config.ts:3,7`) continuing to support the `?react` query suffix; there's no abstraction layer between the registry and this specific build-tool feature, so a Vite/SVGR major-version change would require touching all 56 import lines directly (a `Unknown`/low-severity risk, noted for completeness).

## Hidden Coupling

- **`Folder.tsx` and `Note.tsx` each independently hardcode which `getPageIcon` argument applies to them** (`'folder'` at `Folder.tsx:49`, `'note'` at `Note.tsx:30`) rather than receiving an `icon` prop from a caller that already knows the entity's type. This means the *type-to-icon* mapping is centralized (`getPageIcon`), but the *decision of which type this component represents* is duplicated across every type-specific leaf component (`Folder`, `Note`, and presumably `Task`/`Tag` sidebar components per `features/tasks/sidebar/Task.tsx`, `features/tags/sidebar/Tag.tsx` found in the initial grep but not read in this pass — see Next Investigation Areas). Adding a new page type requires adding both a `getPageIcon` case *and* a new leaf component that hardcodes the corresponding literal — two places to touch for one new type, which is a mild echo of the exact "one capability, one owner" concern the codebase's governance docs care about elsewhere, just at the UI-leaf-component level rather than the application-facade level those docs formally cover.
- **`toCollectionPageModel.ts` re-derives `type` from `Folder | Page` union discrimination (`isFolder`, `toCollectionPageModel.ts:14-16`) independently of however the sidebar tree does the same discrimination** (not directly traced in this pass) — a plausible second implementation of "is this a folder or a page" logic; worth the data-model investigator confirming whether `isFolder` here and any equivalent check elsewhere are the same shape or subtly different (e.g., structural check `!('type' in entry)` vs. a tagged-union check elsewhere).

## Behavior Analysis

- Icon resolution is fully synchronous and pure (no async loading, no lazy import per icon — SVGR bakes all 57 into the bundle at build time via static imports in `iconRegistry.ts`), so there's no runtime "icon not found" flash — an unknown `SystemIcon` value is actually impossible to construct given the type derivation, and a missing SVG file would fail at build time, not runtime.
- `AppIcon` renders `null` for its `<span className="app-icon">` content when both `icon` and `emoji` are falsy (`AppIcon.tsx:26-34`) — an empty-but-present sized slot, not an absent element. This is a considered, correct choice for layout stability (avoids reflow when an icon is conditionally absent).

## UX Analysis

- The emoji-precedence-over-system-icon design matches the Notion/Tana-style product category the app appears to target (per report 01's Product Analysis) — letting a user's custom emoji always override the type default is the expected UX for this genre of app, even though the *mechanism* to set that emoji doesn't currently exist in the UI (see Weaknesses #2).
- With no validation, a corrupted or manually-mistyped `icon` frontmatter value degrades ungracefully in the UI (renders as literal text in an icon-sized slot) rather than falling back to the type default — a minor but real UX rough edge for anyone hand-editing files outside the app (a stated, apparently-expected workflow given the app is file/markdown-based).

## Product Analysis

- The gap between "fully built and tested persistence for custom icons" and "no way to actually set one" strongly suggests either (a) an icon/emoji picker is a known, upcoming feature that just hasn't landed yet, or (b) the only supported way to set a custom icon is external file editing, which would be a deliberate (if unusual) product stance for a markdown-native app. This is the single most product-relevant open question this audit surfaced — worth explicit confirmation from whoever owns the roadmap rather than treating either possibility as default-true.
- 40% dead-icon inventory is mild but real technical debt/signal: it suggests either rapid early UI iteration (icons added speculatively for features that changed direction) or a design handoff (Figma) that over-provisioned relative to what shipped — consistent with report 01's observation that individual components cite specific Figma node IDs (`Badge.css:1`, `calendar-today.tsx:10`), implying a design-first workflow where assets get imported ahead of their consuming feature.

## Performance Analysis

- All icons are statically bundled (no lazy-loading), so the ~40% dead-icon fraction has a real (if almost certainly small, since these are simple line-art SVGs) bundle-size cost with zero product benefit today — a legitimate, low-urgency cleanup target rather than a performance emergency.
- No dynamic icon lookup/indirection beyond a single object-property access (`iconRegistry[icon]`, `AppIcon.tsx:21`) — this is as cheap as icon resolution gets; no performance concern in the render path itself.

## Scalability Analysis

- The registry pattern scales linearly and safely: adding an icon is "add an SVG file, add one import line, add one registry entry," with the type system automatically picking up the new `SystemIcon` value everywhere — this is a good shape for a growing icon set.
- The `getPageIcon` ad hoc union (`PageType | 'folder' | 'tag'`) will need manual extension for every new page-like aggregate (Templates, Attachments per `ARCHITECTURE_RULES.md`'s own example of legitimate future aggregates) — not a blocker, but each addition requires touching this function plus (per Hidden Coupling above) a new leaf component that hardcodes the corresponding call, so the "cost per new page type" for icons specifically is two coordinated edits, not one.
- If a real icon picker ships, the current `SystemIcon` type (all 57 keys, including currently-dead ones) is already shaped correctly to back a picker UI (it's just an enum) — no rearchitecture would be needed to add that feature, only new UI code plus (per Weaknesses #4) probably some input validation on the emoji path.

## Alternative Designs

- **A curated "pickable icon" subset type** (e.g., `PickableSystemIcon` as a narrower union of `SystemIcon`) separate from the full registry would let internal/utility icons (chevrons, arrows used only for navigation chrome) stay out of any future picker's list without needing to delete them from the registry — worth considering once/if a picker is built, rather than exposing all 57 keys as equally "choosable."
- **Emoji validation via a lightweight regex or a small allow-listed grapheme check** at the point `metadata.icon` is set (likely in `PageOperations`/`FolderOperations` per the app's own architecture, or in a future picker component) would close the unvalidated-string gap without needing a heavyweight emoji library.
- **Deleting the 23 unused icons** (or, more conservatively, moving them to a clearly-labeled "reserve" section of the registry with a comment) would make the registry's actual live surface area legible at a glance — currently a reader has to cross-reference usage to know which of the 57 entries matter.

## Trade-offs

- Keeping unused icons around costs little (small bundle size, some reading overhead) and preserves optionality for near-future features that might reuse them (e.g., `settings`, `keyboard` are very plausibly slated for a preferences/shortcuts UI that just hasn't shipped) — deleting eagerly risks re-adding the same assets shortly after. This makes "leave them, but audit periodically" a defensible trade-off rather than a clear mistake, unlike the `01-design-tokens.md` dead-token findings which have no equivalent "obviously coming soon" justification.
- The `Folder`/`Note` components hardcoding their own `getPageIcon` argument trades a small amount of duplication for simplicity (no prop threading needed for something that's always constant per component) — a reasonable trade-off at the current scale, worth revisiting only if a third or fourth type-specific leaf component pattern emerges with the same shape.

## Recommendations

1. **Confirm the product status of custom icon/emoji setting** — determine definitively whether a picker UI is planned, and if not, decide whether `metadata.icon`'s only intended entry point is external file editing (and document that explicitly, since it's surprising for a fully-round-tripped, fully-tested data field to have no in-app UI).
2. **Add basic validation to `metadata.icon`** at whichever layer ends up setting it (a future picker, or a defensive check in `PageOperations`/`FolderOperations` per the architecture's ownership rules) to avoid the silent-degrade-to-text-rendering failure mode.
3. **Prune or clearly quarantine the 23 unused icons** — a short pass deleting genuinely-unneeded assets, or moving speculative-but-likely-needed ones (settings, keyboard, notePencil) into a commented "reserved for upcoming X" section of `iconRegistry.ts`, would make the registry's live surface legible.
4. **Consider narrowing `getPageIcon`'s parameter type** as new aggregates (Templates, Attachments) get added, to avoid the ad hoc union growing indefinitely — a small `PageIconSubject` type alias would at least name the concept explicitly rather than leaving it as an inline union.
5. **Document `AppIcon`'s emoji-precedence rule** in a short comment on the component itself (it currently has none beyond the code's own control flow) — a one-line addition that removes the "hidden assumption" flagged above.

## Confidence Level

- **Verified**: registry single-ownership, type derivation, `AppIcon`'s precedence logic, `getPageIcon`'s exhaustive switch and its consumers, the emoji data model and its round-trip test coverage, the absence of any emoji-picker UI code.
- **Strong Evidence**: the exact 23-icon dead list (grep-based, high confidence but not a full static-analysis/tree-shaking report).
- **Unknown**: whether an icon/emoji picker is planned; whether `editor.css`'s dead-token issue (report 01) has any bearing on icon rendering inside the document editor specifically (not traced in this pass).
