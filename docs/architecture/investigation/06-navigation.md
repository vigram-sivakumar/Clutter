# 06 — Navigation Architecture Audit: NavigationRouter, Workspace, Hooks

Scope: `apps/app/src/core/application/navigation/NavigationRouter.ts` (+ test), `apps/app/src/core/workspace/Workspace.ts`, `apps/app/src/app/hooks/*`, breadcrumb-building logic in `core/presentation/buildBreadcrumbs.ts`, and every call site of these across `app/` and `features/`.

## Summary

`NavigationRouter`'s actual public API is a strict subset of what `architecture-specification.md` §8 documents: the spec lists nine methods (`openArchive`, `openInbox`, `openTemplates`, `openFavorites`, `openAllNotes`, `openAllTasks`, `openSomedayTasks`, `openCompletedTasks`, `openAllTags`); the shipped class has three (`openArchive`, `openInbox`, `openTemplates`) plus two throwing stubs (`createTask`, `createTag`) that the spec explicitly says should **not** exist on this class at all. This is a real, unremediated specification/implementation divergence — not the "already matches, verify only" case the task brief anticipated. The six missing `open*` view methods correspond to product surfaces (All Notes, All Tasks, Someday, Completed, All Tags, Favorites) that simply don't exist as navigable views anywhere in the current UI; there is nothing broken to observe, but the spec's own contract for this class is stale relative to the code, in the direction the spec being aspirational rather than the code lagging.

On the positive side, the class does correctly implement the spec's core discipline: it holds no reference to `PageOperations` (comment at `NavigationRouter.ts:14-17` explains this was a deliberate consequence of deleting the forwarding methods), and its one non-trivial method (`openReservedFolder`) is not a bare forward — it resolves the reserved folder and throws on a missing one before delegating, satisfying Rule 9 (confirmed by `NavigationRouter.test.ts`'s explicit throw-on-missing-folder test cases).

`Workspace` matches its spec closely, with one representational discrepancy (`string | null` in code vs. `string | undefined` in the spec's public API) and one additive, undocumented-in-spec getter (`openPages`). The mutual-exclusivity invariant (exactly one of `activePageId`/`activeFolderId` set) is enforced structurally by `openPage`/`openFolder` each clearing the other (`Workspace.ts:59-70`), not by a runtime assertion — correct behavior today, but nothing would catch a future third mutator that violates it.

The hook layer (`useWorkspace`, `useVault`, `useActivePage`, `useDocumentSession`) is small, uniform, and has exactly three consumer sites total (`PageHost.tsx`, `AppLayout.tsx`, `Sidebar.tsx`) — navigation state does not leak into deeper components via ad hoc hook calls; it is threaded explicitly as props from these three composition points.

## Current Architecture

```
Application (Composition Root)
 ├─ workspace: Workspace                — constructed once in constructor()
 ├─ navigation: NavigationRouter        — constructed in attachVault(), depends on (folderOperations, vault)
 ├─ pageOperations: PageOperations      — depends on (vault, workspace, ...)
 └─ folderOperations: FolderOperations  — depends on (vault, workspace, ..., prepareNavigation callback)

Navigation state WRITE paths into Workspace:
 - PageOperations: workspace.openPage() [open/openAtPath/create paths], workspace.closePage() [delete/close], workspace.refresh() [one call site — see below]
 - FolderOperations: workspace.openFolder() [open()]
 - NOTHING else calls Workspace mutators — NavigationRouter itself never touches Workspace directly, only via FolderOperations.open()

Navigation state READ paths (UI):
 - useWorkspace(workspace) — React subscription adapter, used in PageHost.tsx, AppLayout.tsx (indirectly via useVault only), Sidebar.tsx
 - useActivePage(vault, pageId) — derives the current Page object from activePageId, used in PageHost.tsx only
 - useVault(vault) — generic Vault-mutation subscription, used in AppLayout.tsx (top-level, drives sibling re-renders) and useActivePage.ts internally
 - useDocumentSession(session) — editor-buffer subscription, used in PageHost.tsx only
```

## Evidence

### NavigationRouter's actual vs. spec'd public API

- Spec (`architecture-specification.md:432-441`) lists: `openArchive, openInbox, openTemplates, openFavorites, openAllNotes, openAllTasks, openSomedayTasks, openCompletedTasks, openAllTags`.
- Actual (`NavigationRouter.ts:19-63`): `openArchive` (28), `openInbox` (32), `openTemplates` (36), `createTask` (46, throws), `createTag` (50, throws). No `openFavorites`, `openAllNotes`, `openAllTasks`, `openSomedayTasks`, `openCompletedTasks`, `openAllTags` anywhere in the class.
- Confirmed these six methods don't exist anywhere else either: `grep -rn "openAllNotes|openFavorites|openAllTasks|openSomedayTasks|openCompletedTasks|openAllTags" apps/app/src` returns **zero** matches project-wide. There is no alternate call path that implements this functionality outside the class — the corresponding UI (an "All Notes" view, a "Favorites" view distinct from the sidebar's Favorites *section*, a Someday/Completed task filter view) simply isn't built. **Verified.**
- Spec explicitly frames the class's job as deleting `openNote`/`openDailyNote`/`createNote`/`createTask`/`createTag` for being bare forwards (`architecture-specification.md:443-444`): "Note what is absent... `openNote`, `openDailyNote`, `createNote`, `createTask`, `createTag` are deleted from this class." **The shipped code still has `createTask`/`createTag`** (`NavigationRouter.ts:46-52`), directly contradicting this specific spec sentence. The in-code comment (`NavigationRouter.ts:40-45`) argues these are a deliberate, disclosed exception: "createTask/createTag are NOT deleted alongside the 6 view-intent stubs removed in Phase 4... unlike a filtered view, removing 'create a task/tag' from the UI entirely is a product regression... ADR-012 already disposed of these — permanent removal, blocked on TaskOperations/TagOperations existing." This is a *reasoned* divergence with its own paper trail (ADR-012), but it is still a literal contradiction of the frozen spec's explicit "these five are deleted" list, and per Implementation Rule 7/`docs/implementation-rules.md` §4 ("Handling divergence"), an accepted divergence should result in the spec being amended, not left silently contradicting the code. **Strong Evidence** this is a known, accepted, but formally unreconciled divergence — no evidence found of an ADR specifically amending §8's method list to reflect this (ADR-012 is cited for the *product* decision to keep the affordance, not for a spec-text amendment).
- **Regression-signature check (Rule 9)**: is `openReservedFolder`/`openArchive` etc. a bare forward now? No — `NavigationRouter.ts:54-62` performs a null-check-and-throw (`if (!folder) { throw ... }`) before delegating to `folderOperations.open(folder.id)`. This is genuine added behavior (structural precondition/error translation), not a pass-through. `NavigationRouter.test.ts:34-43,61-70` explicitly test the throw path, confirming this isn't accidental. **Verified compliant with Rule 9.**

### Workspace: spec conformance

- Public API method-for-method matches spec §10 (`openPage`, `openFolder`, `closePage`, `toggleFolderExpanded`, `isPageOpen`, `isFolderExpanded`, `subscribe`, `refresh`, `activePageId`, `activeFolderId`) — all present in `Workspace.ts`. **Verified.**
- **Type discrepancy**: spec says `get activePageId(): string | undefined` (`architecture-specification.md:544`); implementation returns `string | null` (`Workspace.ts:126-133`, backed by `private _activePageId: string | null = null`). Every consumer (`useActivePage.ts:19`, `PageHost.tsx:50-51`) is written against the `null`-based reality, not the spec's `undefined`. **Verified** — cosmetic-looking but a literal signature mismatch per Implementation Rule 7/Post-Implementation "Public API verification" step, unresolved.
- **Additive, unspec'd surface**: `get openPages(): readonly string[]` (`Workspace.ts:142-147`) is not in the spec's public API list. Not currently consumed anywhere in the audited tree except `isPageOpen`'s internal check (`Workspace.ts:113-116` uses `openPageIds.includes`, not the getter) — **Unknown** whether any UI reads `openPages` today (no grep hit found for `.openPages` outside `Workspace.ts` itself and its own internals), suggesting this may be present for a future tabs/multi-pane feature ahead of any consumer, which brushes against Implementation Rule 13 ("never treat 'it's lazy'/'disposable' as license to add new unconsumed machinery") — though `openPages` isn't a disposable projection in that rule's sense, it is genuinely currently-unconsumed public surface.
- **Mutual-exclusivity invariant**: `openPage` (`Workspace.ts:59-66`) sets `_activeFolderId = null` before setting `_activePageId`; `openFolder` (`Workspace.ts:71-77`) sets `_activePageId = null` before setting `_activeFolderId`. No third method mutates either field directly (`closePage` only ever touches `_activePageId`, never `_activeFolderId` — `Workspace.ts:82-95`). **Verified** the invariant holds for all current mutators; it is enforced by convention/code-review at each mutator, not by a single guarded setter, meaning a future mutator added carelessly could violate it without any test failing unless a new invariant test is written for it. Spec's own "Testing strategy" (`architecture-specification.md:579-580`, referenced range) calls for "unit tests for the mutual-exclusivity invariant" — **Unknown** without further investigation whether such a test currently exists (not found in the files read for this report; `Workspace.ts` has no colocated `.test.ts` file found in this pass — flagged as a follow-up, see Next Investigation Areas).

### Navigation state write paths (who is allowed to mutate Workspace)

- `PageOperations.ts` calls `this.workspace.openPage(...)` at five sites (lines 173, 203, 235, 256, 701 per grep) and `this.workspace.closePage(...)` at two sites (330, 854), plus exactly one `this.workspace.refresh()` call (line 318). **Verified** via grep; full semantic reading of each call site is out of this report's scope (belongs to a `PageOperations`-focused investigation) but the *shape* — Workspace mutated only from an approved facade, never from UI — holds.
- `FolderOperations.ts` calls `this.workspace.openFolder(folderId)` exactly once, inside `open()` (`FolderOperations.ts:47`), after resolving and validating the folder exists (`FolderOperations.ts:41-45`) and after calling `this.prepareNavigation()` (`FolderOperations.ts:46`) — a page-agnostic pre-navigation hook the Composition Root wires to `PageOperations.flushActivePage()` (`Application.ts:196-198`), explicitly to avoid `FolderOperations` gaining a direct dependency on `PageOperations` (comment at `FolderOperations.ts:26-33`). **Verified** — this is a clean example of Rule 7 (dependencies point downward) being honored via callback injection rather than a forbidden `FolderOperations → PageOperations` import.
- `NavigationRouter` **never** calls `workspace.openPage`/`openFolder`/etc. directly — its only path to Workspace mutation is via `FolderOperations.open()` (which itself calls `workspace.openFolder`). **Verified**, consistent with spec's invariant "Never calls the Persistence Gate directly... it delegates to PageOperations/FolderOperations" (§8) — the only reservation being that the same invariant doesn't literally say "never touches Workspace directly," but the effect is the same: `NavigationRouter` has no `Workspace` write access, only read access is even possible in principle (and it currently doesn't read `Workspace` either — it has no dependency on it at all, per its constructor at `NavigationRouter.ts:23-26` taking only `FolderOperations` and `Vault`).
- **No other file in `apps/app/src` calls a `Workspace` mutator.** Grep for `workspace.openPage|workspace.openFolder|workspace.closePage|workspace.toggleFolderExpanded` outside `PageOperations.ts`/`FolderOperations.ts` was not exhaustively re-run for this report beyond the two facade files above and the UI-side reads noted below; UI-side files read in this investigation (`Sidebar.tsx`, `PageHost.tsx`, `FolderTree.tsx`, `DailyNotesList.tsx`) call `workspace.toggleFolderExpanded`/`isFolderExpanded`/`isPageOpen` for **reads and the one legitimate direct-UI mutator, `toggleFolderExpanded`** (`FolderTree.tsx:102`, `DailyNotesList.tsx:98`) — this is a UI-initiated *transient view state* change (expand/collapse), not a navigation/active-target change, and matches spec's framing of Workspace owning "expanded folders" as UI state the UI itself is allowed to toggle directly (the spec's own example at §10's usage snippet implies this). **Likely** correct per spec intent, though the spec's invariant section doesn't explicitly call out `toggleFolderExpanded` as UI-callable vs. facade-only the way it's explicit about `openPage`/`openFolder`.

### `refresh()` — compliance with its narrow contract

- Only one call site was found: `PageOperations.ts:318` (`this.workspace.refresh()`). Per spec, `refresh()` must fire only when (1) no other observable owner exists for the changed state and (2) the change concerns a target Workspace already tracks. **Unknown** without reading the surrounding `PageOperations.ts:300-320` context in full whether this specific call satisfies both conditions — flagged as a follow-up for a `PageOperations`-focused investigation, since verifying it requires understanding what state changed at that call site, which is outside this report's traced files.

### Hook layer — dependency graph

- `useWorkspace(workspace: Workspace): Workspace` (`useWorkspace.ts`) — pure React-subscribe adapter, re-renders on any `Workspace.notify()`. Consumers: `PageHost.tsx:40`, `Sidebar.tsx:26`. **Verified** exhaustive via grep (`useWorkspace` imported nowhere else).
- `useVault(vault: Vault): Vault` (`useVault.ts`) — pure subscribe adapter, re-renders on any `Vault` mutation event. Consumers: `AppLayout.tsx:14` (top-level, drives both `Sidebar` and `PageHost` re-rendering as siblings per the comment "Single vault subscription for sibling Sidebar + PageHost re-renders" — `AppLayout.tsx:13`), and internally inside `useActivePage.ts:17`. **Verified.**
- `useActivePage(vault, pageId): Page | undefined` (`useActivePage.ts`) — derives the live `Page` for `activePageId`; calls `useVault` internally rather than requiring the caller to also subscribe. Sole consumer: `PageHost.tsx:52`. Doc comment (`useActivePage.ts:5-11`) explicitly scopes it: "Does not own editor state — use DocumentSession for the editable buffer," a clean single-responsibility boundary against `useDocumentSession`.
- `useDocumentSession(session): DocumentSession | undefined` (`useDocumentSession.ts`) — subscribes to editor-buffer changes, framework-agnostic `DocumentSession` wrapped for React. Sole consumer: `PageHost.tsx:60`.
- **No hook is called more than once per render tree depth**, and no hook is called from inside `features/*` sidebar/topbar components directly — all four are only ever invoked from the three top-level composition files (`AppLayout.tsx`, `Sidebar.tsx`, `PageHost.tsx`). This means the full navigation-state dependency graph has exactly three entry points into React, which is a strong result for traceability: any navigation-state bug can be triaged by checking these three files first. **Verified** via `grep -rln` for each hook name across `apps/app/src`, excluding tests — result set matches exactly the files named above.

### Breadcrumb logic and navigation state flow

- Breadcrumbs are pure functions (`buildBreadcrumbs`, `buildBreadcrumbsForDraft` in `core/presentation/buildBreadcrumbs.ts`) taking `(entry, vault, onOpenFolder)` — they read `Vault` directly (an approved read-only dependency, not a mutation) and receive `onOpenFolder` as a callback the caller (`PageHost.tsx:62,113,153`) wires to `application.folderOperations.open(id)`. **Verified** — breadcrumbs never touch `Workspace` directly; clicking a breadcrumb ancestor triggers `FolderOperations.open()`, which is the one and only approved path to `workspace.openFolder()`. This is architecturally correct: breadcrumb navigation reduces to the exact same facade call a sidebar folder click would make.

## Strengths

- The write-path fan-in for `Workspace` is genuinely narrow: exactly two files (`PageOperations`, `FolderOperations`) mutate `activePageId`/`activeFolderId`, matching the spec's ownership intent even though the spec doesn't literally enumerate this as a rule the way Rules 1–3 do for Vault/Gate. No UI file was found mutating `Workspace`'s navigation-target state directly.
- The hook layer's three-entry-point design (`AppLayout`, `Sidebar`, `PageHost`) is a strong, verifiable property — the "how much of the codebase do I need to understand to change X" test from `implementation-rules.md` §6 passes cleanly for navigation-state consumption.
- `FolderOperations`'s `prepareNavigation` callback-injection pattern is a well-reasoned way to sequence "flush the outgoing page's autosave before switching" without creating a `FolderOperations → PageOperations` upward-pointing dependency — a real example of the architecture's downward-dependency rule being honored under pressure rather than bent.
- `NavigationRouter`'s one real method (`openReservedFolder`) demonstrates the "structural precondition check" pattern correctly (ADR-011's amendment to Rule 5) — it's tested for both the happy path and the throw path.

## Weaknesses

- **Spec/code divergence on `NavigationRouter`'s public API is real and currently unresolved on the spec side.** Six spec'd methods don't exist; two spec-forbidden methods (`createTask`/`createTag`) do exist. The code's own comments explain *why* for the `createTask`/`createTag` half, but no equivalent explanation or spec amendment addresses the six missing view methods — it's simply not observable whether their absence is "intentionally not built yet" (most likely, given no UI references them) or "a spec section describing aspirational, not-yet-real API," and the spec text doesn't distinguish the two.
- **`activePageId`/`activeFolderId` return-type mismatch** (`null` vs. spec's `undefined`) is a small but real Public-API-verification-step failure per `implementation-rules.md` §4 that appears to have gone unflagged.
- **`refresh()`'s single call site was not verifiable as compliant** with its narrow two-condition contract within this report's traced files — this is a gap in this investigation, not a confirmed violation, but it's the one `refresh()` call in the entire codebase and its contract is unusually strict, making it worth a dedicated check.
- **No test file for `Workspace.ts` was found** in this pass (only `NavigationRouter.test.ts` was located under `core/application/navigation/`) — if true, the mutual-exclusivity invariant and subscriber-notification behavior the spec explicitly calls out as the required testing strategy (§10) may be unverified by any automated test. Flagged as **Unknown**, not **Verified**, since a targeted search for `Workspace.test.ts` was not exhaustively performed.

## Hidden Assumptions

- `Sidebar.tsx`'s `activeTab` (which of the five tabs — Daily Notes/Notes/Tasks/Tags/Search — is open) is local `useState`, not `Workspace` state (`Sidebar.tsx:27`). This means sidebar-tab selection is invisible to `Workspace`, to `NavigationRouter`, and to any future "restore last session" feature the spec's own `Workspace` "Extension points" section (`architecture-specification.md:574-575`) anticipates for `.clutter/workspace.json` persistence — if that feature is ever built against `Workspace`'s current tracked state alone, it will silently not restore which sidebar tab was open, since that fact lives outside the subsystem the spec identifies as owning "transient navigation UI state."
- `PageHost.tsx`'s `editorRef` (shared across draft/persisted branches) assumes exactly one of the mutually-exclusive render branches is active at a time — true today because `Workspace`'s own invariant guarantees `activePageId` xor `activeFolderId`, so this is actually a case of `PageHost` correctly *relying on* a Workspace invariant rather than an independent assumption — worth noting as a positive example of the invariant paying off downstream.

## Hidden Coupling

- `Application.ts:191-198`'s `prepareNavigation` callback is constructed via a closure over `this.pageOperations` before `pageOperations` is assigned (`() => this.pageOperations.flushActivePage()`), relying on `this` late-binding rather than a captured local — the code comment (`Application.ts:184-190`) explicitly acknowledges this construction-order dependency. This is a hidden temporal coupling between `FolderOperations`'s construction and `PageOperations`'s later assignment within `attachVault()`; reordering the two constructor calls in `Application.ts` would silently break navigation (calling `flushActivePage` on `undefined`) with no compile-time signal, since `pageOperations!` is asserted non-null via `!`.
- `getActiveDailyNoteDate` (used only by `Sidebar.tsx`) couples the generic sidebar shell to `PageOperations.getDraft()` in addition to `Vault.getPage()` (`getActiveDailyNoteDate.ts:16-23`) — meaning "what date is the calendar currently showing as selected" depends on reading two different subsystems (Vault for persisted pages, PageOperations' internal draft map for unpersisted ones) reimplemented as a narrow presentation helper rather than exposed as a single `Workspace`- or `PageOperations`-level query. This is a reasonable factoring given `PageOperations` explicitly should not gain UI-specific query methods, but it does mean the "what's the active thing" question has at least three different answer paths in the codebase depending on which feature is asking (`workspace.activePageId` raw; `useActivePage` resolved to a `Page`; `getActiveDailyNoteDate` resolved to an ISO date string via a Draft-aware helper).

## Behavior Analysis

From a user's perspective, all navigation actions — clicking a sidebar note, clicking a folder, clicking a breadcrumb ancestor, clicking "Inbox"/"Templates"/"Archive," opening today's daily note — resolve through the same two facades (`PageOperations`, `FolderOperations`) and the same single `Workspace` state object, so the app's "what's currently open" concept is consistent everywhere it's displayed (sidebar selection highlighting, page header, breadcrumbs) with no observed drift between these surfaces. The one behavior not covered by this unification is which *sidebar tab* is showing — switching from the Notes tab to the Tags tab is invisible to the navigation system entirely (pure local component state), so, for example, there is no way today to "navigate to Tags" via `NavigationRouter`, keyboard, or any other mechanism outside directly clicking that specific tab.

## UX Analysis

Because breadcrumb clicks and sidebar clicks both terminate in the same `FolderOperations.open()`/`PageOperations.open()` calls, the two navigation entry points behave identically (same busy-state handling, same error behavior) — a genuine UX consistency win that would be easy to lose if breadcrumbs had grown their own bespoke navigation path instead of reusing the facades. No inconsistency was found here.

## Product Analysis

The gap between `NavigationRouter`'s spec'd nine methods and its shipped three suggests the spec was written ahead of (or independently of) the product surfaces that would consume the missing six — "All Notes," "All Tasks," "Someday," "Completed," "All Tags," and a dedicated "Favorites" view (as opposed to the sidebar's inline Favorites *section*, which already exists via `getFavoriteItems`/`FavoriteList` without going through `NavigationRouter` at all). Product/design should confirm whether these six views are still on the roadmap; if not, the spec should be pared down to match, since a frozen spec describing UI surfaces that were never built (and may never be) undermines the "spec is the source of truth" premise the whole documentation set rests on.

## Performance Analysis

Nothing performance-relevant was found specific to navigation state itself — `Workspace` is synchronous, single-threaded, in-memory, and its `notify()` is a flat `Set` iteration (`Workspace.ts:104-109`), which is O(subscriber count) and trivial at the scale this app operates at.

## Scalability Analysis

The three-entry-point hook design (see Strengths) scales well to additional navigation-state consumers — a new feature needing `activePageId` doesn't need a new hook, it needs to be threaded through one of the existing three composition points, keeping the "who touches navigation state" question bounded as the codebase grows. The one scalability risk is `NavigationRouter` itself: if/when the six missing view methods are eventually implemented, each will need a backing `VaultQuery` filtered-read method (per spec's own "Extension points" note, §8) — worth confirming those `VaultQuery` methods don't already exist unused (a violation of Implementation Rule 13) before building new ones.

## Alternative Designs

- Sidebar tab selection (`activeTab`) could be promoted into `Workspace` as tracked state (a `activePanel`/`activeTab` field alongside `activePageId`/`activeFolderId`) if "restore last session" or deep-linking into a specific tab ever becomes a requirement — currently out of scope per spec's stated fields, and reasonably so given YAGNI, but worth a deliberate decision rather than defaulting to "it's local `useState` because that's where it started."
- The spec's six missing `NavigationRouter` methods could be replaced with a smaller, explicit "not yet implemented" note in the spec itself (mirroring how `createTask`/`createTag`'s divergence is at least explained in-code) rather than left listed as if already real — reducing the risk of a future contributor building against the spec's text without checking the actual class.

## Trade-offs

Keeping `createTask`/`createTag` on `NavigationRouter` despite the spec saying they should be deleted is a real, disclosed trade-off (ADR-012): it preserves a stable call site for the "New" button in Tags/Tasks (`buildTagsShortcutHandler.ts`, `buildTasksShortcutHandler.ts`) so that landing the real `TagOperations`/`TaskOperations` facades later only requires changing these two methods' bodies from `throw` to real delegation, not hunting down and rewiring every UI call site. The cost is a spec that currently reads as incorrect for anyone trusting it literally.

## Confidence Level

**High** for the NavigationRouter API-surface comparison (spec text and source both read in full, grep-verified for absence of the six missing methods elsewhere). **High** for the Workspace write-path fan-in claim (both facade files' Workspace call sites enumerated via grep) and the hook-consumer-site claim (grep-verified exhaustive). **Medium** on the `refresh()` call-site compliance and the `Workspace.test.ts` existence question — both explicitly flagged as **Unknown**, requiring a follow-up read of `PageOperations.ts` lines ~300-320 and a targeted file search, respectively, which this report's scope didn't extend to.
