# Investigation: Should `DocumentSession` Own Title, and Should Title Reuse the Body's Persistence Policy?

**Status:** Research only, no code changes. Direct follow-up to `title-body-persistence-consistency-investigation.md`, narrowing its §5 proposal against two specific questions before any implementation is attempted.

---

## 1. Should `DocumentSession` become the editable representation of the whole document (title + markdown)?

**No — and this isn't a fresh judgment call, it's already a settled, written decision.** [ADR-018](./adr/018-document-editing-identity-decoupling.md) — "Decouple `DocumentEditing` from `Page` — Identity-Free Editing Sessions" — evaluated exactly this class of question and adopted "Design B": `DocumentSession` knows only an opaque `id: string` and markdown content, with **domain identity (title, path, type, persisted-or-not) resolved by callers, not by this class** (ADR-018's own words, Decision item 4). Title is domain identity — it's a `Page`/`Folder`-level concept (today literally derived from the filesystem path via `VaultPath.pageName()`), not a property of an edit buffer. Folding it into `DocumentSession` would directly reverse ADR-018, not extend it:

- ADR-018's whole rationale was that `DocumentEditing` should own only what spec §9 says it owns — "a buffer, revision tracking, save-lifecycle state" — and nothing that requires knowing whether the id is backed by a real `Vault` page. Title genuinely does require that: a draft's title lives in `PageOperations`'s own `DraftDescriptor` map, with no `DocumentSession` involvement at all, precisely because a draft has no `Vault` identity yet. A persisted page's title lives in `Page.name`, resolved from `Vault`. There is no single "the title" `DocumentSession` could hold consistently across both lifecycle stages — `PageOperations` already has to look in two different places today, and that's a real, load-bearing fact about where identity lives, not an oversight to paper over.
- Rejected Design C in ADR-018 (`Page | Draft` union inside `DocumentSession`) was rejected for exactly this shape of problem — "domain knowledge leaks into engine," "doesn't stop growing." Adding a title field to `DocumentSession` is a smaller instance of the identical mistake: it would make `DocumentEditing` need to know, per session, whether this id is a draft or a real page in order to know where title truly lives — reintroducing the coupling ADR-018 spent its entire text removing.
- Practically: `DocumentRevision` (what `DocumentSession` actually manages) is a single immutable snapshot of one field, produced by one kind of `DocumentTransaction`, persisted through one kind of Gate operation (`'save'`). Folding title in would mean a single "revision" spans two fields with two different Gate operations (`'save'` vs `'rename'`), two different collision/validation rules (a body write never collides with anything; a rename can), and two different failure semantics — which breaks the clean 1:1 "one revision, one write path" shape the whole engine is built around, not just a naming inconvenience.

**Conclusion: `DocumentSession` stays markdown-only.** The higher-level owner coordinating title and body is `PageOperations` — which is not a new responsibility for it; it is already the one place both live today (`DraftDescriptor.title` pre-persistence, `PageOperations.rename()`/`updateDraftTitle()` post- and pre-persistence respectively). What's missing isn't a coordinator — `PageOperations` already is one — it's a small, title-specific piece of *in-flight* state for the persisted-page case, analogous in spirit to `DraftDescriptor` but for "a title edit that's been committed but not yet persisted," which doesn't exist anywhere today because title currently has no commit/persist split at all (per the prior investigation, §2).

## 2. Should title reuse the same engine but a different persistence policy?

**Yes, and the prior investigation's proposed design (§5, point 3: a single shared `isDirty` that ORs body and title) doesn't actually achieve this — it needs correcting before implementation, not just tuning constants.**

### The problem with one shared dirty flag / one shared timer

If title and body shared `SaveCoordinator`'s *single* debounce/ceiling timer pair and a single OR'd `isDirty`, they would necessarily also share cadence — the moment either field's timer fires, `evaluate()` would see the union `isDirty` as true and execute *whatever's* dirty, including a title that's still well within its own, deliberately longer, debounce window. A shared timer structurally cannot give two fields independent cadences; the timer itself is the cadence. Achieving "reuse the engine, not necessarily the cadence" requires the timer/dirty-tracking to be **per-field ("channel"), not per-session** — a materially different (if still small) design than the prior document's §5 sketch, and worth naming as a correction now rather than discovering it mid-implementation.

There's a second, sharper correctness issue in naively sharing `DocumentState` itself: `DocumentSession.markSaved()` unconditionally sets state to `Clean`. If body and title were two independent, differently-timed async Gate operations both driving the *same* `DocumentState`, a body save completing while a title-rename is still in flight would incorrectly flip the session to `Clean` — losing the "something is still being persisted" signal for the still-in-flight title. `SaveCoordinator`'s existing `activeSaves` stale-guard (comparing a completing revision against the tracked in-flight one) prevents *stale* completions from corrupting state, but says nothing about *concurrent, different-field* completions stepping on each other — that guard was built for one field, and doesn't generalize for free.

### What does generalize almost for free

Everything else in `SaveCoordinator` is already parameterized by nothing more than a `string` key and a caller-supplied `onFire` closure:

- `scheduleSave`/`cancelTimers`'s `debounceTimers`/`ceilingTimers` maps are keyed by a plain string (`session.id` today). Keying by a **channel-qualified key** (e.g. `${session.id}:title` vs `${session.id}` for body, or an explicit `channel` parameter) costs nothing structurally — the maps, the arm/reset/cancel logic, and the debounce-vs-non-resetting-ceiling distinction are already channel-agnostic.
- `scheduleSave`'s `AUTOSAVE_DEBOUNCE_MS`/`AUTOSAVE_CEILING_MS` are already named as "placeholder, not tuned... exported so changing them later is a one-line edit" (`SaveCoordinator.ts`'s own doc comment) — accepting them as parameters (with today's constants as the body channel's defaults) rather than hardcoded module constants is a mechanical change, not a design change, and is exactly the seam needed for title to get its own, longer values without touching body's.
- `PageOperations.requestSave()` staying the single externally-visible entry point is unaffected — it can still be the one method every trigger (blur, navigation, shutdown, a debounce firing) calls; what changes is that its internal evaluation becomes per-channel rather than per-session, and its `execute` branch fires the Gate operation belonging to whichever channel(s) were actually found due (`'save'` for body, `'rename'` for title, potentially both).

What needs new (small) machinery, not just parameterization:

- A **per-channel `activeSaves`-equivalent** for title, since today's is typed `Map<string, DocumentRevision>` — title has no `DocumentRevision`; it needs its own tiny "current/pending title value" tracked wherever `PageOperations` keeps its title-in-flight state (§1's conclusion — not `DocumentSession`). A plain string comparison is an adequate stale-guard for this (unlike a `DocumentRevision`'s object-identity comparison, two *equal-content* title states compared by string equality would be treated as interchangeable — harmless, since the outcome is identical either way, but worth naming as a minor semantic difference from the body's guard, not a bug).
- **Trigger routing that distinguishes "flush this one channel" from "flush everything."** A channel's own debounce/ceiling timer firing should only evaluate and, if due, execute *that* channel — otherwise a body-cadence timer firing would force-flush a still-debouncing title (or vice versa), defeating the entire point of giving title its own, longer policy. Blur, navigation-away, and shutdown, by contrast, should keep today's behavior generalized to *both* channels — those are genuine "nothing dirty may survive this moment" boundaries for the whole document, not just the body, so an uncommitted title-rename should not be silently dropped on navigation any more than an uncommitted body edit is today.

### Conclusion

Reuse is real and substantial — the timer model, the coalescing algorithm's *shape* (`(state, dirty) → execute/suppress`), the single-entry-point discipline, and the Gate as the sole write path all carry over unchanged in spirit. But "reuse the engine" concretely means **generalizing `SaveCoordinator` from session-keyed to channel-keyed** (timers, stale-guards, and tunable debounce/ceiling values all becoming per-channel), not sharing one timer pair and one dirty flag across two fields with different cost profiles. That generalization is what actually delivers "different persistence policy, same architecture" — a shared flag delivers neither independence nor architectural cleanliness, just a subtler bug.

No `DocumentState` enum change, no new Gate kind, and no new subsystem are required by either conclusion above — `DocumentState` stays a per-session, body-scoped concept exactly as it is today (title's own in-flight/error signal lives in `PageOperations`'s new small title-state structure, independently of `DocumentState`, since — per §1 — title isn't `DocumentSession`'s concern to represent in the first place). This is a smaller, more surgical change than "unify title into the document model" would have been, and it's smaller specifically *because* §1's answer keeps `DocumentSession` out of it.
