# 03 — Design System (Component Primitives) Audit

Scope: `apps/app/src/components/` — `button`, `entry`, `checkbox`, `badge`, `count-badge`, `date-label`, `editable-text`, `menu`, `overlay`, `tabs`, `caret`, `tauri-drag-strip` (12 primitives).

## Summary

The primitive layer is stylistically consistent (BEM-ish class naming, CSS-module-free plain CSS files scoped by convention, token-only styling — no hardcoded colors anywhere) and several primitives (`Overlay`, `EditableText`, `Entry`, `Menu`) show real design care: hook-decomposed concerns, explicit ownership comments, and correct ARIA patterns. But the layer also contains two build-breaking import-casing bugs, a CSS selector typo that silently kills a documented variant, debug `console.log` statements left in shipped keyboard-handling code, inconsistent accessibility coverage (some primitives are fully ARIA-correct, others — `Checkbox`, `Tabs`, `Caret` — have no ARIA semantics at all for their obviously interactive/toggle nature), and no shared foundation (no `Primitive`/`Slot`-style base, no shared prop-composition helper) despite highly repeated patterns (class-list building, `forwardRef`, boolean-prop-to-modifier-class mapping) copy-pasted near-identically across all 12 files.

## Current Architecture

Each primitive is a self-contained folder: `ComponentName/ComponentName.tsx` + `ComponentName.css` (+ occasionally `.types.ts`, `.test.tsx`, or a `hooks/` subfolder for the more complex ones — `overlay/` and `menu/`). There is no shared base component, no `cva`/`clsx`-style variant utility, and no shared style-composition helper — every component hand-rolls its own `[...].filter(Boolean).join(' ')` class-list pattern independently:

- `Button.tsx:39-51`, `Entry.tsx:69-78`, `Badge.tsx:26-28`, `Checkbox.tsx:15-21`, `CountBadge.tsx:42`, `DateLabel.tsx:12-14`, `Tabs.tsx:31,54-56`, `Overlay.tsx:58-59,75-81` — eight independent, structurally identical implementations of the same "array of conditional class names, filter falsy, join with space" idiom.

Composition model is prop-driven slots (`leading`/`trailing`/`actions` on `Entry`, `leading`/`trailing` on `Button`) rather than compound-component/children-based composition, except for `Menu`/`MenuItem` (context-based) and `Tabs`/`Tab` (context-based) — meaning the codebase actually has *two different composition idioms* live at once: slot-props (`Button`, `Entry`) and context-provider-plus-children (`Menu`, `Tabs`), with no stated rule for which a new primitive should follow.

### Verified bugs

1. **Two build-breaking import-casing mismatches.** `Badge.tsx:2` imports `./badge.css`; the actual file on disk is `Badge.css` (confirmed via `ls`: only `Badge.css` exists, `badge.css` does not — `os.path.exists('badge.css')` returns `False` from within the component's own directory). Identically, `Checkbox.tsx:2` imports `./checkbox.css`; the actual file is `Checkbox.css`. On a case-sensitive filesystem (Linux, most CI containers, most production Docker builds) these imports fail to resolve. **Verified** as a real filesystem mismatch; whether it currently breaks CI could not be confirmed in this sandbox (no `node_modules` installed to run an actual Vite build), but the on-disk case mismatch is unambiguous and would resolve identically under Vite's/Node's default (OS-native) module resolution. This likely "works" only on case-insensitive developer filesystems (macOS default, Windows) and either silently fails or has already failed on Linux CI — worth an urgent, cheap fix (rename the import to match the file, or vice versa) regardless of current CI status.
2. **CSS selector typo disables a documented variant.** `Badge.css:91` defines `.adge--outlined` (missing the `b`) instead of `.badge--outlined`. `Badge.tsx:7-8` explicitly types and documents `'outlined'` as a valid `badgeColor` ("the border-only outlined variant from Figma"), and `Badge.tsx:26` generates the class `badge--outlined` for it — which never matches the misspelled selector. Any consumer passing `color="outlined"` gets an unstyled (transparent, borderless, default-text-color) badge instead of the documented outlined treatment. **Verified**; no current consumer of `color="outlined"` was found in this pass, so the bug is latent rather than currently visibly broken, but it will silently misbehave the moment someone uses the documented variant.
3. **Debug logging left in shipped keyboard-navigation code.** `useMenuKeyboard.ts` contains `console.log` calls on every arrow-key press and every `Enter`/`Space` activation (lines 70, 78-82, 94, 102-106, 143) — these fire on every menu interaction in production, not gated behind a dev-only flag. **Verified.**
4. **A CSS rule with no reachable class.** `Button.css:80-83` styles `.button--muted .button__content`, but `Button`'s `variant` type (`Button.tsx:8`) is `'filled' | 'outlined' | 'ghost' | 'outline-fill'` — `'muted'` is not a valid variant and the component's class-list builder (`Button.tsx:39-51`) has no code path that emits `button--muted`. The only place `button--muted` is applied is `features/daily-notes/shortcuts/DailyNotesShortcuts.tsx:57`, which passes it as a **raw `className` override**, bypassing the `variant` prop system entirely rather than extending it. **Verified** — this is a real, working style, but it proves a consumer reached around the component's own variant API rather than through it, which is exactly the kind of "second path to the same outcome" the codebase's broader architectural philosophy (one owner per capability) explicitly warns against, applied here at the styling-API level rather than the data layer.

### Consistency findings

- **Boolean-to-modifier-class mapping is reinvented per component** with no shared helper — eight near-identical `[cond && 'x'].filter(Boolean).join(' ')` blocks (see Current Architecture). A shared `cx()`/`clsx`-equivalent utility (there is no dependency on the `clsx` package anywhere in the primitives — confirmed by the manual reimplementation in every file) would remove this duplication; instead each is authored independently, with correspondingly ad hoc quality (some use array literals, `Entry.tsx:69-78`; some inline the join, `DateLabel.tsx:12-14`).
- **`forwardRef` usage is inconsistent without an obvious rule**: `Button`, `Entry`, `EditableText` use `forwardRef`; `Checkbox`, `Badge`, `CountBadge`, `DateLabel`, `Caret`, `Tabs`/`Tab` do not. Some of the non-ref components (`Checkbox`) are genuinely simple enough that a ref may never be needed, but `Badge`/`CountBadge` are exactly the kind of small display primitive a consumer might reasonably want to measure or animate via ref, and there's no stated convention for when a primitive should support one.
- **Prop-naming conventions are inconsistent across primitives**: `Button` uses `isActive`/`isIconOnly`; `Checkbox` uses `isChecked`; `Entry` uses `selected`/`active`/`disabled` (no `is` prefix); `Caret`/`Overlay` mix both styles within the same file (`isPlaceholder`, `isExpanded` vs. `disabled`, `open`). There's no `is`-prefix rule applied consistently — a genuinely minor but real API-surface inconsistency across the primitive set.
- **Type naming casing is inconsistent**: `Badge.tsx` exports `badgeColor`, `badgeSize`, `badgeProps` (lowercase-leading, non-standard for TypeScript type/interface naming), while every other primitive (`ButtonProps`, `EntryProps`, `OverlayProps`, `CheckboxProps`) uses standard PascalCase. `Badge` is the sole outlier in the whole set.

## Strengths

1. **Zero hardcoded colors, tokens-only styling, confirmed across all 12 primitives** (see report 01's cross-check) — a genuinely strong, consistently-applied invariant.
2. **`Overlay` and `EditableText` are exemplary.** Both decompose cleanly into single-purpose hooks/functions with explicit doc comments stating ownership boundaries (`EditableText.tsx:36-42` is a model example: "It owns only the browser editing experience... It does not own document state, persistence, validation, or business rules... The parent decides whether to accept, reject, or persist the change" — this is the component-level equivalent of the app's own architectural philosophy of single, explicit ownership, self-applied without any governance document requiring it).
3. **`Entry`'s nested-interactive-element click handling** (`Entry.tsx:46-56`) is a real, correct solution to a genuinely tricky problem (a clickable row containing clickable buttons) that a naive implementation gets wrong — worth calling out as evidence of real engineering care in at least this primitive.
4. **`Menu`'s `aria-activedescendant` roving-focus pattern is implemented correctly** (`Menu.tsx`, `useMenuKeyboard.ts`, `MenuItem.tsx`) — full keyboard nav (arrow up/down, Home/End, Enter/Space, disabled-item skipping) is present and follows the standard WAI-ARIA menu pattern, which is more accessibility investment than most of the other primitives received.
5. **`CountBadge`'s explicit null-rendering for zero/invalid state** (`CountBadge.tsx:34-36`) is a small but correct product decision — avoids a meaningless empty badge — implemented with a clear, separately-testable `normalizeCount`/`formatCount` pair.

## Weaknesses

1. **The two case-mismatched CSS imports are the single most concrete, highest-severity finding across this entire audit** — a plausible build break, not a hypothetical one, in two of twelve primitives.
2. **Accessibility coverage is bimodal, not systematic**: `Overlay`, `Menu`, `EditableText`, `Entry`, `Checkbox`, `CountBadge` have deliberate, mostly-correct ARIA; `Tabs`, `Caret`, `DateLabel`, `Badge` have none at all despite `Tabs` and `Caret` both being genuinely interactive, stateful controls (tab switching; expand/collapse) that are exactly the category of component ARIA guidance exists for. There's no accessibility checklist or shared pattern being applied uniformly — it appears to track individual component authorship rather than a system-wide standard.
3. **`Checkbox` cannot be labeled.** `CheckboxProps` (`Checkbox.tsx:4-8`) has no `HTMLAttributes` spread and no explicit `aria-label`/`aria-labelledby`/`id` support — a consumer has no mechanism to give the checkbox an accessible name at all, which is a real WCAG-level defect (a checkbox with `role="checkbox"` but no accessible name), not just a missing nicety. Its one current consumer (`Task.tsx:37`) doesn't provide one, so this is live, not latent.
4. **No shared variant/class-composition utility**, leading to eight independent reimplementations of the same class-list idiom, and consequently no single place to fix or extend that pattern (e.g., adding conditional-object support à la `clsx`) system-wide.
5. **Two live composition idioms with no documented rule for which to use**: slot-props (`Button`, `Entry`) vs. context+children (`Menu`, `Tabs`). Both are legitimate patterns individually, but a new contributor building the 13th primitive has no stated guidance for which to reach for.
6. **`className="button--muted"` as a raw override** (Weaknesses/Evidence #4 above) demonstrates the variant system doesn't yet cover every real product need, and the gap is being closed by bypassing the component's typed API rather than extending it — a smell that the `variant` union may be incomplete relative to actual usage.

## Hidden Assumptions

- **`AppIcon`, `getPageIcon`, and `TagPaletteId` (from the design-system/icon audits) are assumed stable dependencies of this primitive layer** — `Checkbox`, `Caret`, `Note`/`Folder` (feature-layer, not primitive, but consuming `Entry`) all import `AppIcon` directly; `Badge` imports `TagPaletteId`. This is architecturally fine (icons/tokens are lower-layer, per the app's dependency-direction philosophy) but means any of report 01/02's findings (undefined tokens, dead icons) can silently propagate into primitive rendering with no primitive-level test catching it.
- **`Overlay`'s `useOverlayFocus` assumes exactly one focusable root inside the overlay content** (`useOverlayFocus.ts:22-24`: `overlayRef.current?.firstElementChild?.firstElementChild` — a hardcoded two-levels-deep DOM traversal to find the focus target). Any consumer whose content structure doesn't match this exact shape (e.g., a menu with a search input as the true first focusable, nested one level differently) silently gets no initial focus, with no runtime warning.
- **`Entry`'s interactive-element-detection assumes a fixed CSS selector list** (`'button, a, input, select, textarea, [role="button"]'`, `Entry.tsx:49`) — any future interactive element type added inside an `Entry` (e.g., a custom combobox with `role="combobox"` but no native tag) would not be recognized, silently reintroducing the double-click-handling bug this code was written to prevent.

## Hidden Coupling

- **`MenuItem` is coupled to `Entry`'s exact prop shape** (`MenuItem.tsx:5`, `export interface MenuItemProps extends EntryProps {}`) and to `Entry`'s DOM structure implicitly, since `Menu`'s keyboard navigation selects `[role="menuitem"]` elements (`useMenuKeyboard.ts:4`) and calls `.click()` on them directly (`useMenuKeyboard.ts:144`) — meaning `MenuItem`'s rendered root must remain a real, clickable DOM element for keyboard activation to keep working; this constraint exists only implicitly in the interaction between three files (`Menu.tsx`, `MenuItem.tsx`, `useMenuKeyboard.ts`), not documented anywhere.
- **`Caret`'s hardcoded `icon="caretRight"` plus CSS-driven rotation** (`Caret.tsx:32`, rotation applied via `.caret-icon--expanded`/`.caret-icon--collapsed` classes per `Caret.css`, not read in full in this pass but referenced via `Caret.tsx:30`) couples the caret's visual "up/down/left/right" appearance entirely to CSS `transform: rotate(...)` rather than swapping the underlying icon — meaning the `chevronUp`/`chevronDown`/`caretUp`/`caretLeft` icons flagged as dead in report 02 are dead *specifically because* `Caret` doesn't use them, having chosen a rotate-one-icon strategy instead. This is a real, useful cross-reference between the icon and component audits: those "dead" icons may be dead by design, not by omission, at least for the caret-rotation use case.
- **`Note.tsx`/`Folder.tsx` both import `Entry` and independently re-derive nearly identical `leading`/`actions` slot structures** (compare `Note.tsx:24-46` to `Folder.tsx:28-62`) — both wrap an `AppIcon`, both add a `moreHorizontal`-icon ghost button in `actions`. This is feature-layer code (outside this report's direct primitive scope) but is worth flagging: the *pattern* is copy-pasted at the feature layer rather than factored into a shared "entry with icon and overflow menu" primitive, which — if this pattern repeats for `Task`/`Tag` (per report 02's Next Investigation Areas) — would be a good candidate for a new shared primitive rather than continued per-feature duplication.

## Behavior Analysis

- `Entry`'s hover/active/selected state CSS (`Entry.css:23-34,102-105`) layers three mutually-exclusive-by-specificity states (`hover`, `active`/pressed, `selected`) with `:not()` chains to prevent, e.g., a selected row also showing hover background — a correct, deliberate interaction design, consistently applied.
- `Overlay`'s position/animation logic is fully hook-driven and recalculated per render while `open`, with no memoization guard visible in the files read — a plausible minor performance point (see Performance Analysis) but not a correctness issue given `useOverlayPosition` presumably only runs meaningful work when open (not fully traced — see Next Investigation Areas).

## UX Analysis

- The bimodal accessibility coverage (Weaknesses #2) means keyboard/screen-reader users get a genuinely good experience in menus and overlays but a broken or absent one in tabs, checkboxes' labeling, and folder/tree expand-collapse controls (`Caret`) — an inconsistent product experience for assistive-technology users depending on which part of the UI they're in, which is a worse experience than uniformly-mediocre coverage would be, because it's unpredictable.
- `DateLabel`'s empty `<span>` for "today" (`DateLabel.tsx:16`) relies entirely on a visual dot with no text alternative — a screen reader announces nothing distinguishing "today" from any other date cell.

## Product Analysis

- The primitive set is scoped tightly to what the current sidebar/tree/editor UI actually needs (12 primitives, no speculative extras) — consistent with report 01/02's finding that the design-token and icon systems are similarly proportionate rather than over-built, suggesting a consistent, deliberate "build what's needed" discipline at the product level even where per-file execution quality varies.
- The `Badge` component's Figma-node-ID comment (`Badge.css:1`) and the `outlined` variant's dead CSS selector together suggest a Figma-to-code handoff process that isn't fully verified end-to-end (a visual QA pass against the Figma source would have caught the `.adge--outlined` typo immediately, since the variant would visibly fail to render).

## Performance Analysis

- No primitive in this set does anything performance-notable on its own (no virtualization, no expensive computation) — the entry/tree components (`Entry`) are the ones most likely to render at scale (long note/folder lists), and `Entry`'s implementation is a plain, unmemoized functional component; whether the *feature* layer (`FolderTree`, sidebar) wraps these in `React.memo` or virtualization was not traced in this pass and would be the right place to look for actual large-list performance behavior (see Next Investigation Areas — this is more a data-model/feature-layer question than a primitive-layer one).
- `Overlay`'s `useOverlayPosition` recalculating on every render while open (not confirmed memoized) is a plausible, minor concern for overlays that reposition frequently (e.g., anchored to a moving/scrolling target) but was not measured.

## Scalability Analysis

- The lack of a shared class-composition utility and the two competing composition idioms (slot-props vs. context+children) are the main scalability risks: as more primitives are added, both patterns will keep being copy-pasted independently rather than converging, and a 13th contributor has no rule to follow — this is a "will get more expensive to fix, not less, over time" issue, the same shape report 01 flagged for token-system enforcement.
- Accessibility inconsistency will compound as more features build on the currently-unaccessible primitives (`Tabs`, `Caret`) — every new consumer of `Tabs` inherits its missing ARIA rather than the gap being fixed once at the source.

## Alternative Designs

- **Adopting a small `clsx`-equivalent utility** (or writing one shared 5-line helper in this codebase) would remove the eight duplicated class-list implementations with minimal risk and effort — the lowest-cost, highest-value structural fix available in this audit.
- **A shared base for interactive-toggle primitives** (`Checkbox`, `Caret`, `Tab`) — e.g., a `useToggleButton`-style hook providing consistent `role`, `aria-pressed`/`aria-expanded`/`aria-selected`, and keyboard handling — would close the accessibility gap once, systematically, rather than requiring each primitive to be fixed individually. Given `EditableText`/`Overlay` already demonstrate this codebase's authors are capable of exactly this kind of hook-decomposition, this seems like a natural, in-house-style fix rather than an externally-sourced pattern.
- **Explicit accessibility acceptance criteria per primitive** (a short checklist analogous to `docs/architecture-compliance-checklist.md`, but for UI primitives — keyboard support, ARIA role, accessible-name mechanism) would give this layer the same "enforced, not aspirational" treatment the rest of the codebase's governance explicitly values, currently absent for this layer entirely.

## Trade-offs

- Per-component class-list reimplementation is cheap to write and avoids taking on an external dependency, but the codebase already reimplements this idiom 8+ times with drifting quality — the "no dependency" trade-off has already been paid for in duplication cost more than once; a single internal helper captures the same "no external dependency" benefit without the repeated cost.
- The slot-props vs. context+children split is not inherently wrong (different primitives genuinely have different composition needs — `Menu`'s children are heterogeneous items with shared keyboard state, `Button`'s aren't), but the absence of a stated rule for *when* each is appropriate means the choice currently looks arbitrary per-component rather than deliberate.

## Recommendations

1. **Fix the two case-mismatched CSS imports immediately** (`badge/Badge.tsx:2`, `checkbox/Checkbox.tsx:2`) — trivial, high-value, likely already causing CI or platform-specific failures.
2. **Fix `.adge--outlined` → `.badge--outlined`** in `Badge.css:91`.
3. **Remove the `console.log` calls from `useMenuKeyboard.ts`** (7 call sites) — trivial cleanup, currently shipping to every menu interaction in production.
4. **Add an accessible-name mechanism to `Checkbox`** (spread `HTMLAttributes`/accept `aria-label`) and give its current consumer (`Task.tsx:37`) one.
5. **Add ARIA to `Tabs` and `Caret`** — `role="tablist"`/`role="tab"`/`aria-selected` plus arrow-key navigation for `Tabs`; `aria-expanded`/`aria-label` for `Caret`'s interactive mode.
6. **Introduce one shared class-composition helper** and migrate the 8+ duplicated implementations to it — the single highest-leverage structural cleanup available in this layer.
7. **Resolve the `button--muted` gap** — either add `'muted'` as a real `variant` (if the visual treatment is intentional and durable) or replace the raw-`className` usage in `DailyNotesShortcuts.tsx:57` with a properly-typed variant, closing the "bypassed the component API" pattern.
8. **Write down the composition-idiom rule** (slot-props vs. context+children — when each applies) as a short comment or convention note, so future primitives have guidance.

## Confidence Level

- **Verified**: all per-primitive API surfaces, the two casing bugs, the `.adge--outlined` typo, the `console.log` statements, the `button--muted` unreachable-class finding, ARIA presence/absence per primitive (via direct source read).
- **Strong Evidence**: the ~40%-Figma-handoff-gap hypothesis connecting the `Badge` typo to an unverified design-to-code QA process (inference, not confirmed via any process documentation).
- **Unknown**: whether the case-mismatched imports have already caused an observed CI failure (no CI logs were available in this environment to check); whether `Entry`/tree components are wrapped in memoization or virtualization at the feature layer (not traced in this pass).

## Next Investigation Areas

1. **Confirm the CSS-import-casing bugs against actual CI/build logs** — the highest-priority follow-up from this entire investigation; if CI is green despite these mismatches, that itself is worth understanding (e.g., a case-insensitive build runner, or a resolution fallback this audit didn't find).
2. **Feature-layer consumers of `Entry`** (`Note`, `Folder`, plus `Task`/`Tag` per report 02) — worth a dedicated pass checking whether the near-identical `leading`/`actions` slot pattern (icon + overflow-menu button) repeats across all four, which would justify extracting a shared "collection entry" primitive rather than continued per-feature duplication (see Hidden Coupling).
3. **Large-list rendering performance** for `Entry`/`FolderTree` — whether virtualization or memoization exists at the feature layer; this report's primitive-layer read found no evidence either way, and it's a natural question for whoever investigates the sidebar/tree feature code.
4. **`Caret.css`** was not read in full in this pass (only referenced via `Caret.tsx`) — worth a follow-up read to fully confirm the rotate-based variant strategy described under Hidden Coupling, and to check whether `Caret.css` has any token-coverage issues symmetrical to what report 01 found in `editor.css`.
5. **Whether `docs/architecture-compliance-checklist.md` or any other governance document mentions the UI/component layer at all** — this report treated the primitive layer as effectively ungoverned by the app's existing architecture rules (which focus on data/persistence/application layers); worth confirming that's actually true rather than assumed, since if some UI governance exists elsewhere it should supersede several of this report's "no documented convention" findings.
