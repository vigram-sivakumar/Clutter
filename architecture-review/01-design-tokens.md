# 01 — Design Tokens Audit

Scope: `apps/app/src/design-system/` (`tokens.css`, `theme.css`, `styles/base.css`, `styles/editor.css`, `useTheme.ts`, `TagColors.ts`) plus every CSS custom-property definition/usage in the app (`apps/app/src/**/*.css`, 42 files, 314 `var(--...)` usages at time of audit).

## Summary

Clutter has a real, mostly-disciplined two-tier token system: primitives in `tokens.css` (`--neutral-*`, `--space-*`, `--text-*`, etc.) and theme-dependent semantic aliases in `theme.css` (`--surface-*`, `--text-primary`, `--tag-*-bg`, etc.), switched by a `[data-theme]` attribute. Token discipline in `apps/app/src/components/` is very good — zero hardcoded hex colors were found in any component stylesheet. But the system has no naming convention document, no lint/CI enforcement, several dead or unreachable tokens, at least one active theme-file bug (a self-overriding double-`var()` declaration), and one CSS file (`editor.css`) that references **six tokens that are defined nowhere in the codebase**, meaning those styles silently resolve to browser defaults today.

## Current Architecture

- **Primitives** (`tokens.css:1-129`): theme-independent raw values — neutral color ramp (`--neutral-0`…`--neutral-950`), two accent colors, opacity scale, two motion-duration/easing pairs, a spacing scale (`--space-0` … `--space-128`), radius/height/icon-size/button-gap scales derived from spacing, a z-index token, and a full typography scale (font family, size, line-height, letter-spacing, weight).
- **Semantic/alias layer** (`theme.css:1-263`): duplicated in full under `[data-theme='dark']` (`theme.css:20-138`) and `[data-theme='light']` (`theme.css:142-263`) blocks — surface, text, icon, border, shadow, interactive-state, per-component (secondary button, tabs, calendar, checkbox), tag-palette (9 palettes × 3 tokens), feedback, and editor-selection tokens. No primitive-level color token is theme-switched directly; every themed color is redefined as an independent semantic token per theme, not derived via a shared alias formula.
- **Theme switching** (`useTheme.ts:1-49`): a `data-theme` attribute on `document.documentElement`, driven by a `ThemePreference` of `'light' | 'dark' | 'system'` persisted to `localStorage` under `clutter-theme` (`useTheme.ts:6,24-25,38`), with a `matchMedia` listener when the preference is `'system'` (`useTheme.ts:29-35`). A `theme-transitioning` class is toggled for 200 ms around explicit switches to enable CSS transitions defined in `theme.css:1-16`, and is not applied on first paint.
- **Consumption**: `apps/app/src/app/main.tsx:9-11` imports `tokens.css`, `theme.css`, and `styles/base.css` in that order as global side-effect imports; every other CSS file in the app assumes these are already loaded and references custom properties without importing them.
- **Component-local tokens**: individual components declare their own scoped custom properties consumed via inline `style` from React — e.g. `--tree-level` (`Entry.tsx:65`, consumed at `Entry.css:11`), `--app-icon-size` (`AppIcon.tsx:23`, consumed at `AppIcon.css:9-10`) — a legitimate, narrow pattern for per-instance values that don't belong in the global theme.
- **Tag colors**: `TagColors.ts` exposes `tagColorsFromPalette(palette)` returning `{ background: 'var(--tag-{palette}-bg)', border: 'var(--border-strong)' }` (`TagColors.ts:17-22`). In practice, no component consumes `TagColors.ts` at all — the only consumer of `TagPaletteId` is `Badge.tsx:3,8`, and `Badge.css` reads the `--tag-*-bg`/`--tag-*-text` tokens directly via class names (`Badge.css:46-89`), bypassing `tagColorsFromPalette` entirely.

## Evidence

- **Primitive scale**: `tokens.css:34-53` (spacing), `tokens.css:56-60` (radius, all aliased to spacing tokens), `tokens.css:62-70` (height, ditto), `tokens.css:88-125` (typography).
- **Theme duplication, not derivation**: `theme.css:24-30` (dark surfaces) vs. `theme.css:146-152` (light surfaces) — independently authored values, not a shared formula parameterized by theme.
- **Bug — self-overriding declaration**: `theme.css:73` declares `--tab-active: var(var(--state-active));` (double-wrapped `var()`, invalid CSS custom-property reference) inside the dark block, then `theme.css:79` redeclares `--tab-active: var(--state-active);` two lines later in the same block — the second, correct declaration wins per CSS cascade-within-a-rule, but the first is dead/wrong code. The identical pattern repeats in light mode: `theme.css:198` (`var(var(--surface-primary))`, broken) immediately followed by the correct override at `theme.css:204`. **Verified.**
- **Dead tokens — never defined anywhere**: `editor.css` (imported nowhere in `main.tsx`'s CSS import list — see "Hidden Coupling" below) references `--lh-body-medium` (`editor.css:15`), `--node-bullet` (`editor.css:85`), `--interactive-disabled` (`editor.css:107`), `--node-collapse-ring` (`editor.css:120`), `--node-halo-border` (`editor.css:152`), and `--margin-24px` (`editor.css:174`) — none of these six custom properties are defined in `tokens.css`, `theme.css`, or any other CSS file in the repository (confirmed via exhaustive grep across all 42 `.css` files). **Verified.**
- **Unreferenced/never-imported stylesheet**: `apps/app/src/design-system/styles/editor.css` is not imported by `main.tsx` (`main.tsx:9-11` imports only `tokens.css`, `theme.css`, `styles/base.css`) and no other `import '...editor.css'` was found anywhere in `apps/app/src`. Either this file is dead entirely, or it's loaded through a path this audit didn't find (e.g., dynamically, or bundled by the editor package outside `apps/app/src`) — **Unknown**, flagged for follow-up (see Next Investigation Areas).
- **Tag border token defined but never consumed**: `theme.css` defines a `--tag-{palette}-border` token per palette (e.g. `theme.css:98,101,104...`), but the only code path that could plausibly use it, `TagColors.ts:20`, hardcodes `border: 'var(--border-strong)'` instead of `var(--tag-${palette}-border)` — and `TagColors.ts` isn't consumed by any component regardless (`Badge.css` doesn't reference border tokens for tag palettes at all, only background/text). Net effect: 9 palettes × 1 border token = 9 defined, styled-for tokens with zero live consumers. **Verified.**
- **Fallback-only token**: `Badge.css:39-40` reads `var(--dot-md, 8px)`; `--dot-md` is not defined anywhere, so the badge dot's size is permanently the CSS fallback, never the token. Either the token was planned and never added, or the fallback is intentionally the only value — the file gives no indication either way. **Verified (undefined) / Hypothesis (intent).**
- **Component-scoped custom properties correctly threaded through JS**: `Entry.tsx:65` (`'--tree-level': level`) and `AppIcon.tsx:23` (`'--app-icon-size': ...`) are the only two legitimate per-instance custom-property injections found; both are consumed by exactly one stylesheet each (`Entry.css:11`, `AppIcon.css:9-10`).
- **Zero hardcoded colors in components**: `grep -rlnE '#[0-9a-fA-F]{3,8}\b' apps/app/src/components/**/*.css` returns no matches. All 314 `var(--...)` usages across 42 CSS files were checked; the handful of hardcoded pixel values that exist outside `var()`/`calc()` are component-local geometry (`Overlay.css:38,47` `--overlay-y/x: 4px` — themselves *are* local tokens; `DateLabel.css:26` `border-radius: 999px` — a "pill" idiom, arguably should be a token but is a single, harmless outlier; `TauriDragStrip.css:6` `height: 48px` — a fixed OS-chrome-matching height, arguably legitimately non-tokenized).

## Strengths

1. **Real primitive/alias separation.** Unlike many ad hoc token systems, Clutter cleanly separates raw scale values (`tokens.css`) from theme-dependent meaning (`theme.css`), and the alias layer is comprehensive: surface, text, icon, border, shadow, state, and several component-family token groups (checkbox, tabs, calendar, tags, feedback) all exist and are theme-aware.
2. **No hardcoded colors in the primitive component layer.** Every stylesheet under `components/` sources color exclusively from custom properties — a genuinely strong invariant for a system with 314 token usages across 42 files.
3. **Derived scales reduce redundant authoring.** Radius, height, icon-size, and button-gap tokens are all defined as `var(--space-N)` aliases rather than independent literals (`tokens.css:56-83`), so the spacing scale is the actual single source of truth it claims to be (`tokens.css:34` comment).
4. **Theme-transition politeness.** The `theme-transitioning` class pattern (`theme.css:1-16`, `useTheme.ts:16-21`) deliberately avoids transitioning color on first paint (only on explicit user-triggered switches), which is the correct behavior for avoiding a flash-of-transition on load.
5. **`system` preference done properly.** `useTheme.ts` correctly re-derives from `matchMedia` on OS-level changes only while the preference is `'system'` (`useTheme.ts:29-35`), and persists the *preference*, not the resolved theme, to `localStorage` — so switching OS theme doesn't silently overwrite an explicit user choice.

## Weaknesses

1. **No enforcement mechanism.** Nothing in the repo (no stylelint config, no CI check) prevents a new hardcoded hex/px value from being introduced, or a new undefined `var(--...)` reference from shipping. The current cleanliness is apparently a product of discipline, not tooling — which is fragile at scale (compare to `ARCHITECTURE_RULES.md`'s general philosophy of enforced-not-aspirational rules; tokens have no equivalent).
2. **Dead/broken declarations shipped in the theme file itself** — the double-`var()` self-overriding lines (`theme.css:73,198`) are evidence that even the token *authors* aren't reviewing this file closely; it's the kind of thing a linter (`stylelint-no-unknown-animations`/custom-property validators exist) would catch immediately.
3. **`editor.css` is either dead code or a silent styling gap.** If it's imported somewhere this audit didn't find, six custom properties resolve to invalid/unset values in production, meaning the editor's node bullets, chevron ring, block-selection halo, and node-children indentation may be rendering with browser-default (i.e., wrong) values today. If it's genuinely unimported, it's ~190 lines of dead CSS. Either outcome needs resolving — see Next Investigation Areas.
4. **No token-usage linting means orphaned tokens accumulate invisibly.** `--dot-md` (fallback-only), the 9 `--tag-*-border` tokens (defined, unconsumed), and `TagColors.ts`'s `tagColorsFromPalette` (unconsumed function) are all silent dead weight — each looks live to a reader of `theme.css` alone.
5. **Motion tokens are underspecified as a system.** Only two named duration/easing pairs exist (`--duration-interaction`/`--easing-interaction` and `--duration-tab-slide`/`--easing-tab-slide`, `tokens.css:26-32`), but at least 8 other distinct hardcoded transition timings exist across component CSS (e.g., `Button.css:8-11` `160ms`, `Entry.css:18-20` `120ms`, `editor.css:48` `120ms`, `editor.css:57` `160ms cubic-bezier(...)`, `editor.css:87` `150ms cubic-bezier(...)`) that don't reference either motion token. There is no consistent "which duration for which kind of interaction" rule — the two named tokens exist but are barely used relative to how many transitions the app has.
6. **No elevation token beyond box-shadow presets.** `--shadow-sm/md/lg/xl` exist (`theme.css:60-66`, `182-191`) but there's no explicit z-index scale beyond a single `--z-overlay: 1000` (`tokens.css:86`) — every other stacking context in the app (if any exist) has no token to reach for, which is a coverage gap for a design system that will need more overlay/layer types as the app grows (dropdowns, tooltips, modals, toasts).
7. **No documented naming convention.** There's no README or comment block explaining, e.g., when to add a new semantic alias vs. reuse `--text-tertiary`, or the rule for when a component gets its own token family (`--checkbox-*`, `--tab-*`) vs. reusing generic `--state-*`/`--surface-*` tokens. The pattern is inferable from examples but not written down, which the codebase's own `ARCHITECTURE_RULES.md` philosophy (state the rule, don't rely on inference) would flag as a gap if tokens were in scope of that document.

## Hidden Assumptions

- **Global CSS load order is assumed, never enforced.** Every component CSS file assumes `tokens.css` + `theme.css` + `base.css` are already loaded via `main.tsx`'s side-effect imports. There is no per-file `@import` or build-time dependency check; a new entry point (e.g., a Storybook config, a second Tauri window) that doesn't replicate `main.tsx:9-11`'s import order would silently render with unstyled/undefined tokens. **Likely** risk, not verified against a second entry point (none was found in this audit, but the app is a Tauri app and could gain additional windows).
- **`--tab-active` assumes single redefinition wins.** The double-`var()` bug (above) only "works" because CSS custom properties resolve last-declaration-wins within a rule — a fragile mechanism to rely on even accidentally; a future refactor that removes the (seemingly redundant) duplicate line would silently break tab active-state styling.
- **Theme resolution assumes `matchMedia` is always available.** `getSystemTheme()` (`useTheme.ts:8-10`) calls `window.matchMedia` unconditionally; fine in a browser/Tauri webview context but would throw in an SSR or test context that doesn't polyfill it — no guard exists.

## Hidden Coupling

- **`TagColors.ts` and `theme.css`'s `--tag-*` tokens are coupled by string convention only** (`` `var(--tag-${palette}-bg)` ``, `TagColors.ts:19`), with the `TagPaletteId` union (`TagColors.ts:1-10`) as the only mechanism keeping them in sync — adding a palette requires updating three unconnected places (`TagColors.ts`'s union, `theme.css`'s dark block, `theme.css`'s light block) with no compiler or lint check that all three stay consistent. A palette added to the type but not to one theme's CSS block would silently fall back to `unset` in that theme only.
- **`Badge.css`'s palette classes (`badge--blue`, etc.) are coupled to `TagPaletteId` by naming convention, not by type**, since `badgeColor` (`Badge.tsx:8`) is `TagPaletteId | 'outlined'` but the CSS class list (`Badge.css:46-89`) was hand-authored separately and doesn't reference the TypeScript union at all — a palette renamed in one place and not the other fails silently at runtime (unstyled badge), not at compile time.
- **Component-scoped tokens (`--tree-level`, `--app-icon-size`) are invisible to anyone reading only the CSS** — you must find the `.tsx` file setting them via inline `style` to know they're runtime-computed, not part of the static theme. This is a reasonable pattern but undocumented as a convention, so a new contributor adding a similar per-instance token has no written guidance to follow the existing shape.

## Behavior Analysis

- Theme switching is synchronous and imperative (`applyTheme` directly mutates `document.documentElement`, `useTheme.ts:16-21`) rather than being derived purely from React state/CSS — meaning any consumer that doesn't call `useTheme()` still sees the correct theme (because it's a DOM attribute, not React context), but nothing in React re-renders in response to a theme change except components that separately call `useTheme()` for `resolvedTheme`. This is a deliberate, reasonable choice for a CSS-variable-driven theme system (no need to re-render on theme change since CSS custom properties cascade automatically) but is worth naming explicitly since it means `resolvedTheme` in React state can theoretically be one tick stale relative to the DOM attribute during the `system`-preference `matchMedia` listener's async callback.
- The `--tab-active` bug has zero *current* runtime effect (the correct override always follows immediately in source order), but it is a latent trap for the next edit to that block.

## UX Analysis

- Dark and light theme token sets are visually well-considered (distinct shadow opacities calibrated per theme, e.g. `theme.css:60-66` vs `182-191`; distinct checkbox hover/border treatment) — this isn't a mechanical inversion, someone tuned both themes independently, which is generally the right approach for perceptual correctness (a naive `invert()` filter approach would have been worse).
- If `editor.css`'s undefined tokens are in fact live (see Weaknesses #3), the practical UX impact would be: no line-height (defaults to `normal`) on editor nodes, invisible node bullets (`background: var(--node-bullet)` → initial/transparent), full opacity on trailing empty-node dots (missing dimming), no collapse-ring visual, no block-selection halo border color, and no indentation for nested children (`margin-inline-start: var(--margin-24px)` → `0`) — a meaningfully broken outline/tree UI if true. This needs to be resolved as a priority follow-up, not treated as cosmetic.

## Product Analysis

- The tag-color system (9 palettes, full bg/border/text per theme) is more built-out than its only consumer (`Badge`) currently exercises — `Badge` doesn't expose per-palette borders at all (`Badge.css` has no `border-color` overrides per palette; the base `.badge` rule sets `border: 1px solid transparent`, `Badge.css:9`). This suggests either the tag system was built for a broader tagging feature that hasn't shipped yet (consistent with `features/tags/` existing in the codebase — see Next Investigation Areas) or the palette's border tokens are simply unused scope creep.
- The design system currently serves a fairly small, cohesive interaction vocabulary (Notion/Workflowy/Tana-style tree editor + sidebar). The token set's shape (surface/text/icon/border/state, spacing/radius/height scales) is proportionate to that scope and not over-engineered for a much larger product surface — a reasonable maturity level for the app's apparent current stage.

## Performance Analysis

- CSS custom properties recalculating on theme switch is inherently cheap (native browser cascade, no JS re-render required for pure-CSS consumers) — no performance concern here.
- The 200 ms `theme-transitioning` class window (`useTheme.ts:20`) applies `transition` to `*`-selected descendants of `[data-themeable]` (`theme.css:3-10`), which could be a measurable layout/paint cost on a very large DOM (e.g., a long document with thousands of editor nodes) since the selector list includes `*`, `*::before`, `*::after` recursively under any `[data-themeable]` ancestor — every element and pseudo-element gets a transition rule applied for 200 ms around every theme toggle. This is a plausible, not measured, performance concern (**Hypothesis**) worth a follow-up profiling pass if theme-switching feels janky on large documents.

## Scalability Analysis

- The primitive/alias split will scale reasonably to more themes (e.g., a future high-contrast theme) since the pattern is already "one full alias block per `[data-theme='X']` value" — adding a third theme means adding a third full block, which is verbose (every token redeclared) but mechanically simple and low-risk.
- The *lack* of enforcement tooling is the main scalability risk: as more contributors touch CSS, the currently-clean "zero hardcoded colors in components" invariant has no mechanical guarantee of holding, and the dead-token/broken-declaration issues found in this single audit pass suggest the review process alone hasn't been catching these.
- Motion and elevation token coverage (Weaknesses #5, #6) will become a bigger gap as the app adds more overlay-style surfaces (tooltips, toasts, command palette) that need distinct z-index tiers and consistent animation curves — right now every new overlay-like component would need to invent its own timing/z-index rather than pull from a scale.

## Alternative Designs

- **Stylelint with `declaration-property-value-no-unknown` / a custom `var()`-existence rule**, run in CI, would have caught both the `editor.css` undefined-token issue and the `--dot-md` fallback-only issue mechanically, consistent with the codebase's own stated philosophy elsewhere ("enforced, not aspirational" — `ARCHITECTURE_RULES.md:3`) that currently isn't applied to the design-system layer at all.
- **A single-source token generator** (e.g., a JSON/TS token definition compiled to both `tokens.css`/`theme.css` and a typed TS object) would eliminate the `TagColors.ts` / `theme.css` string-convention coupling and make "does this palette exist in both themes" a build-time guarantee instead of a manual convention. This is a heavier investment not obviously justified at the current single-theme-pair, ~180-token scale, but worth naming as the standard fix once a third theme or many more component-family token groups are added.
- **Deriving light/light-adjacent theme values from the dark values via a formula** (e.g., a shared "surface elevation" function) instead of fully independent redeclaration per theme would reduce the ~240 lines of duplicated-shape token blocks, at the cost of losing the current, apparently-intentional per-theme perceptual tuning (see UX Analysis) — likely not worth it given the deliberate divergence already present.

## Trade-offs

- The current "no enforcement, but currently clean" state is a reasonable trade-off for a young design system with a small number of contributors and a small component surface, but the two verified defects found in a single manual audit pass (the double-`var()` bug, the undefined `editor.css` tokens) are exactly the class of error automated tooling exists to prevent — the trade-off will get worse, not better, as the surface area grows without that tooling.
- Full per-theme token redeclaration (vs. a derivation formula) trades verbosity for correctness/tunability — a defensible choice given the visible care taken in calibrating each theme's shadow/checkbox/border values independently.

## Recommendations

1. **Resolve the `editor.css` import-status question immediately** (see Next Investigation Areas) — this is the single highest-impact unresolved question from this audit, since it determines whether ~190 lines of editor styling are silently broken in production or entirely dead.
2. **Fix the two double-`var()` declarations** in `theme.css:73` and `theme.css:198` — delete the broken first declaration in each pair (`--tab-active` in both dark and light blocks), keeping only the correct one that already exists two-to-five lines later.
3. **Either wire up or delete** `TagColors.ts`'s `tagColorsFromPalette` (currently unconsumed) and the 9 unused `--tag-*-border` tokens — per `ARCHITECTURE_RULES.md`'s spirit (rule 8, "derived data is disposable," and the implementation rulebook's rule 13 against unconsumed speculative machinery), this is exactly the shape of dead scaffolding that rule exists to catch, applied to the design-token layer.
4. **Fix `badge/badge.css` and `checkbox/checkbox.css` import casing** — see report 03 for the full finding; this belongs to both audits since it's a token-consuming stylesheet that may not even load on case-sensitive filesystems.
5. **Add a stylelint pass (even a minimal one) to CI** checking for undefined `var()` references and disallowing raw hex/rgb literals outside `design-system/`, to make the current clean state durable rather than incidental.
6. **Name and consolidate the motion-token story** — either expand the two existing duration/easing pairs into a small documented scale (e.g., `--duration-fast/--duration-medium/--duration-slow`) that the ~8 currently-hardcoded transition timings can adopt, or explicitly document that per-component custom timing is intentional and the two global tokens are reserved for specific named use cases only.
7. **Document the token-authoring convention** (primitive vs. semantic vs. component-scoped, when to add a new component-family token group) in a short README colocated with `tokens.css`/`theme.css`, so the pattern currently only inferable from examples becomes a written rule new contributors can follow — consistent with this codebase's general philosophy of writing rules down rather than relying on tribal knowledge.

## Confidence Level

- **Verified**: token file contents and structure, the double-`var()` bug, the six undefined `editor.css` tokens, the `--dot-md` fallback-only status, zero hardcoded component colors, `TagColors.ts` non-consumption.
- **Strong Evidence**: `editor.css`'s import status being genuinely absent from the traced import graph (only `main.tsx`'s three imports were found; a wider search for `editor.css` imports across the whole repo, not just `apps/app/src`, was not exhaustively completed).
- **Hypothesis**: the perceived performance cost of the `theme-transitioning` wildcard-selector transition on large documents (not profiled); the product intent behind the unused tag-border tokens (whether they're for an unshipped feature or pure scope creep).
